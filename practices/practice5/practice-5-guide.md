# Практика №5: "Базовый workflow: линтер, статический анализ, блокировка merge"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Самостоятельная командная работа по письменной инструкции + межкомандное ревью workflow + общий круг по пункту ретроспективы модуля 2  
**Роль преподавателя:** Модератор ревью и общего круга, фиксация прогресса

## Цели практики

К концу занятия каждая команда должна:

1. **Оценить** выполнение пункта «Что меняем» из issue «Ретроспектива модуля 2»: в issue есть комментарий «выполнено / не выполнено» с наблюдаемым фактом из вашей же формулировки «Как проверим на практике №5»
2. **Добавить** ruff 0.17.1 и mypy 2.4.0 в dev-зависимости так, чтобы lock-файл вошёл в тот же коммит (`uv sync --locked` или `poetry check --lock` проходит), и **предсказать** по локальному запуску, какие шаги джоба `lint` упадут в CI: предсказание записано в описании PR до первого прогона
3. **Адаптировать** шаблон курса в `.github/workflows/ci.yml` по «Решению» ADR 004: джобы `lint` и `secrets` с именами шаблона, триггеры по вашей стратегии (GitFlow — `main` и `develop`), сканер по ADR 003, полная история — по п. 4 «Решения»; `git grep -n "АДАПТИРОВАТЬ"` по файлу находит только шапку и закомментированный джоб `test`, во вкладке **Checks** PR видны обе проверки
4. **Продемонстрировать** отказ в merge: после первого прогона владелец репозитория включает в `protect-main` (GitFlow — и в `protect-develop`) обязательные проверки `lint` и `secrets`; при красном `lint` merge недоступен, текст блокировки процитирован в комментарии PR
5. **Диагностировать** красный джоб по логу Actions: шаг, файл и строка, код или сообщение ошибки записаны в PR до push исправления; исправления — отдельными коммитами по типу ошибки, следующий прогон на голове PR зелёный
6. **Довести** ADR 004 до статуса «Принято»: время джобов — «(измерено)» из прогона, отклонения от «Решения» записаны с причиной; раздел «Защита ветки» в `CONTRIBUTING.md` и правило о защите веток в ADR 001 совпадают с ruleset — `git grep -n "TODO" CONTRIBUTING.md` находит только TODO в разделе о тестах
7. **Проверить** workflow другой команды по чек-листу шага 6.1 (шесть пунктов, у каждого — строка файла или ссылка на прогон) и оставить в её PR комментарий по формуле «где → что не так → чем грозит → что предлагаете» или доказанное «замечаний нет»; на каждое замечание к своему PR — ответ

### Права доступа

Ограничения практики №2 действуют: прямой push в защищённые ветки отклоняется, автор PR не может одобрить свой PR. Правило ruleset **Require status checks to pass** и настройки Actions меняет только **владелец репозитория** (личный репозиторий) или участник с ролью Admin (репозиторий организации). У преподавателя в ваших репозиториях роль Write — включить проверки за вас он не может.

**Право `workflow` у токена.** GitHub отклоняет push файлов из `.github/workflows/`, если токен, которым git входит в GitHub, не имеет права `workflow`. Вход через браузер (Git Credential Manager — по умолчанию в Git для Windows) это право обычно даёт; личный токен (PAT) или GitHub CLI — не всегда. Проверьте до занятия командой из «Проверки перед стартом» и «Если не работает → Push и права».

Для ревью чужого workflow нужен только доступ на чтение: репозитории публичные.

### Проверка перед стартом

```bash
git --version
uv --version                  # или: poetry --version
git fetch --prune origin
git branch -r                 # видна ветка ADR 004
git remote get-url origin     # как git входит в GitHub: адрес
git config --get-regexp "credential.*helper"    # и чем хранится вход
gh auth status                # только если git входит в GitHub через GitHub CLI
```

**Как git входит в GitHub** — по выводу двух команд перед `gh auth status`:

| Вывод | Вход | Что проверить |
|---|---|---|
| Адрес начинается с `git@github.com:` | SSH | Ничего: право `workflow` для SSH не нужно |
| Адрес `https://...`, в строках helper есть `gh auth git-credential` (даже если есть и `manager`) | GitHub CLI | `gh auth status` |
| Адрес `https://...`, helper — `manager`, `manager-core` или путь к `git-credential-manager` (даже если выше есть `osxkeychain` — так на macOS с установленным GCM) | Git Credential Manager: через браузер или PAT, смотря как входили на практике №1 | Входили через браузер — обычно ничего; вставляли токен — права PAT, ниже |
| Адрес `https://...`, helper — только `osxkeychain`, `store`, `cache` или строк нет | Личный токен (PAT) | Права PAT, ниже |

**Что должно получиться:** команды отвечают без ошибок; в списке удалённых веток есть ветка ADR 004 (кроме ситуации C). У `gh auth status` в строке `Token scopes` есть `'workflow'`; нет — `gh auth refresh -s workflow` до занятия. Git входит по личному токену (PAT) — на GitHub **Settings → Developer settings → Personal access tokens**: у классического токена отмечен `workflow`, у fine-grained — право **Workflows: Read and write**; нет — «Если не работает → Push и права» до занятия.

### Этап 1: ruff и mypy в dev-зависимостях, предсказание (20 мин)

Джоб `lint` запускает ruff и mypy из dev-зависимостей проекта: на раннере `uv sync --locked` (Poetry — `poetry install`) ставит ровно то, что записано в lock-файле. Поэтому линтеры добавляются в проект и lock-файл до того, как появится workflow. Версии закреплены курсом: у всех команд одни и те же правила на одном и том же коде.

#### Шаг 1.1: Добавить ruff и mypy (6 мин)

**Если uv:**

```bash
uv add --dev ruff==0.17.1 mypy==2.4.0
```

**Ожидаемый вывод** заканчивается списком установленных пакетов, среди них `+ mypy==2.4.0` и `+ ruff==0.17.1`. В `pyproject.toml` появился раздел:

```toml
[dependency-groups]
dev = [
    "mypy==2.4.0",
    "ruff==0.17.1",
]
```

**Если Poetry:**

```bash
poetry add --group dev ruff==0.17.1 mypy==2.4.0
```

**Ожидаемый вывод:** строки `Installing mypy (2.4.0)`, `Installing ruff (0.17.1)` и в конце `Writing lock file`. Poetry 2.x записывает группу в тот же раздел `[dependency-groups]`, версии — в виде `"ruff (==0.17.1)"`. `poetry export` повторять не нужно: dev-группа в `requirements.txt` не попадает, образ не меняется (проверено: после экспорта те же версии пакетов).

**Как проверить, что сработало:** `git status --short` показывает изменённые `pyproject.toml` и `uv.lock` (Poetry — `poetry.lock`) и ничего больше. ruff и mypy оказались в `dependencies` (основных зависимостях), а не в `[dependency-groups]`, — вы забыли `--dev` / `--group dev`: «Если не работает → Зависимости и lock-файл».

**Если на ноутбуке есть Docker** — проверьте синтаксис workflow программой [actionlint](https://github.com/rhysd/actionlint) из образа (первый запуск скачивает образ):

Прогона ещё нет — так и должно быть: триггер `push` только для `main` (GitFlow — и `develop`). Вкладка **Actions** пока показывает страницу «Get started with GitHub Actions» — так и должно быть: workflow `CI` появится там с первым прогоном на шаге 2.5.

#### Шаг 2.5: Открыть Pull Request (6 мин)

PR открывает автор PR по таблице ролей из своего аккаунта. Базовая ветка — `main` (GitFlow — `develop`). Заголовок — по Conventional Commits, например `chore: add CI pipeline with lint and secrets checks` (у Trunk-Based он станет сообщением squash-коммита). Заполните шаблон PR как обычно. Обязательно:

- **«Тип изменения»** — `chore` (зависимости, workflow), `docs` (ADR 004 и правки шага 5)
- **«Связанные задачи»** — `Refs #<номер issue «Ручные проверки перед merge»>`; issue нет — номер допишете на шаге 4.4, когда его создадите
- Раздел **`## Предсказание до первого прогона`** — таблица с шага 1.2
- Раздел **`## Кто что делал`** — таблица с шага 0.2

**Reviewers** — сокомандник. Старый PR с ADR 004, если он есть (в ситуации C его нет), закройте **Close pull request** с комментарием `Вошло в #<номер>` и удалите его ветку (**Delete branch**): после включения обязательных проверок он ждал бы их без конца — в его ветке нет workflow.

**Что должно получиться:** в **Files changed** — `.github/workflows/ci.yml`, `pyproject.toml`, lock-файл, ADR 004 (кроме ситуации C); нет `.pre-commit-config.yaml`. Внизу вкладки **Conversation** и во вкладке **Checks** — две проверки `CI / lint (pull_request)` и `CI / secrets (pull_request)` в состоянии ожидания или выполнения; без очереди раннеров прогон занимает 10–20 секунд. **Точка синхронизации 60.**

Проверок нет совсем — «Если не работает → Workflow не запускается».

#### Шаг 3.2: Включить обязательные проверки (8 мин)

Только после первого прогона: до него поиск ruleset предлагает лишь строку «Add lint · Any source», а строка `lint` с источником **GitHub Actions** появляется, когда проверка хотя бы раз выполнилась в репозитории. Включает **владелец репозитория** из своего аккаунта (ситуация F — сообщением ему сейчас).

**Settings** → **Rules** → **Rulesets** → `protect-main` → правило **Require status checks to pass** (в части интерфейсов — **Require status checks to pass before merging**) → **Add checks** → в поиске наберите `lint` и выберите строку `lint` с подписью **GitHub Actions** (список подгружается 1–3 секунды); затем так же `secrets`. **Require branches to be up to date before merging** не включайте: практика №2 его не требует. **Save changes**.

**GitFlow** — то же в `protect-develop`. Без этого PR в `develop`, куда идут все фичи, мержится и с красным `lint`.

**Что должно получиться:** в правиле ruleset две проверки — `lint` и `secrets`; в PR у обеих проверок пометка **Required**. Сделайте скриншот правила — он нужен для комментария на шаге 3.3. Почему обязательной делают каждую стадию, а не только последнюю, — [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), раздел **Handling skipped but required checks** (5 мин): пропущенный из-за `needs` или `if` джоб считается успешным.

Владелец недоступен (ситуация F) — шаги 3.2–3.3 переходят в ДЗ 1; в комментарии к PR напишите «обязательные проверки — ДЗ 1, владелец недоступен» и переходите к этапу 4.

**Перед тем как открыть блок merge, ответьте командой:** `lint` красный, `secrets` зелёный, approval пока нет. Что именно GitHub назовёт причиной, по которой merge недоступен?

Откройте вкладку **Conversation** PR и прокрутите к блоку merge внизу. В нём две части: состояние проверок (заголовок и строки `CI / lint (pull_request)`, `CI / secrets (pull_request)` с пометками) и **Merging is blocked** с причиной под ним. Скопируйте обе дословно и опубликуйте комментарий:

```markdown

Совпало с ответом команды: да / нет — [что GitHub назвал причиной]
Обязательные проверки: lint, secrets — [скриншот правила ruleset]
```

Кнопка merge недоступна и для владельца: Bypass list ruleset пуст (практика №2). **Точка синхронизации 80.**

**Первый прогон был зелёным — проба** (около 5 минут из буфера). Добавьте в блок импортов `main.py` строку `import os` по алфавиту — обычно сразу после `import logging`:

```bash
git add main.py
git commit -m "chore: probe required lint check with unused import"
git push
```

**Ожидаемый вывод** в логе `lint` на шаге `ruff check`: ``F401 [*] `os` imported but unused``, `--> main.py:2:8`, `Found 1 error.` (если `import os` стоит не по алфавиту, к нему добавится `I001 Import block is un-sorted or un-formatted` — тоже красный). Процитируйте блок merge по образцу выше. Затем верните код:


`git revert` возвращает `main.py` ровно к предыдущей версии; сообщение задаёте сами, потому что стандартное `Revert "..."` не соответствует типам Conventional Commits из вашего `CONTRIBUTING.md`.

#### Шаг 4.1: Формат кода (5 мин)

**Ожидаемый вывод:** `1 file reformatted, N files left unchanged`; `git diff --stat` — только файлы, которые назвал `ruff format --check` (обычно `settings.py`). Посмотрите `git diff`: меняются пробелы и пустые строки, логика — нет.

Push запускает второй прогон. Пока он идёт, делайте шаг 4.2 — не ждите. **Первый прогон был зелёным** (путь пробы) — `ruff format .` ничего не меняет, коммит и push этого шага пропустите.

**Ожидаемый результат второго прогона:** в `lint` шаг `ruff format --check` зелёный. У команд с `pydantic-settings` шаг `mypy` красный, в логе — та же ошибка `settings.py:...: error: Missing named argument "database_url" for "Settings"  [call-arg]`, что на шаге 1.2 (номер строки может сдвинуться на 1: `ruff format` добавляет пустые строки). До push шага 4.3 проверяющий публикует в PR комментарий: `Второй прогон: [ссылка] — lint: шаг mypy, файл:строка, [код или сообщение]`. У механизмов A, C1, C2 второй прогон зелёный целиком.

**Code owners:** коммит меняет `*.py` — PR будет ждать approval владельца этого пути (шаг 7.1).

#### Шаг 4.2: Проверка типов (5 мин)

**Если `pydantic-settings`** — перед правкой ответьте командой: кто заполняет поле `database_url`, когда выполняется `Settings()` без аргументов? Почему mypy считает этот вызов ошибкой? Что плагин меняет в проверке: [Pydantic: Mypy plugin](https://pydantic.dev/docs/validation/latest/integrations/dev-tools/mypy/), раздел **Generate a `__init__` signature for Pydantic models**, говорит, что обязательные поля становятся обязательными аргументами `__init__`. Почему тогда с плагином `Settings()` проходит? Посмотрите, от какого класса наследуется `Settings`, и найдите поиском по странице `is_settings` в исходнике плагина [pydantic/mypy.py](https://github.com/pydantic/pydantic/blob/main/pydantic/mypy.py): ответ — в строке, где это значение передаётся в `force_optional` (метод `get_field_arguments`) (3 мин). Затем допишите в конец `pyproject.toml`:

```toml
[tool.mypy]
plugins = ["pydantic.mypy"]
```

```bash
uv run mypy .                  # Poetry: poetry run mypy .
uv sync --locked               # Poetry: poetry check --lock
```

**Ожидаемый вывод:** `Success: no issues found in N source files`; вторая команда — без ошибки: раздел `[tool.mypy]` lock-файл не меняет.

```bash
git add pyproject.toml
git commit -m "chore: enable pydantic plugin for mypy"
```

Настройки ruff и mypy курс не расширяет: умолчания ruff и mypy без строгих флагов, единственная обязательная настройка — этот плагин. Строгие правила — бонусная задача 2.

**Механизм A, C1, C2** — mypy зелёный уже на шаге 1.2, шаг пропустите. **mypy нашёл другие ошибки** (код MVP) — исправьте их в коде отдельным коммитом `fix: ...` по сообщению mypy; не получается к 102-й минуте — «Если не работает → ruff и mypy».

#### Шаг 4.3: Зелёный прогон (7 мин)

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy .
# Poetry: poetry run ruff check . && poetry run ruff format --check . && poetry run mypy .
git push
```


**Ожидаемый вывод** локально: `All checks passed!`, `N files already formatted`, `Success: no issues found ...` (mypy ругается только на `venv/` — «Если не работает → ruff и mypy», CI это не касается). Через несколько минут в PR — новый прогон на голове ветки. Механизмы A, C1, C2 (после шага 4.1 новых коммитов нет): `git push` выводит `Everything up-to-date` — зелёный прогон уже есть, это второй прогон шага 4.1.

**Как проверить, что сработало:** во вкладке **Checks** у `lint` и `secrets` зелёные значки для **последнего** коммита PR (обязательная проверка засчитывается только для него). В блоке merge вместо «Some checks were not successful» — «All checks have passed»; **Merging is blocked** остаётся, пока нет approval (ситуация F — то же, только у проверок нет пометки **Required**). **Точка синхронизации 102.**

#### Шаг 4.4: Время CI в issue «Ручные проверки» (5 мин)

Откройте зелёный прогон: вкладка **Checks** → **Summary** (или вкладка **Actions** → прогон). У каждого джоба указано время, у прогона — общее время. Время отдельных шагов — в логе джоба справа от каждого шага.

Автор документов добавляет в issue «Ручные проверки перед merge» комментарий:

```markdown
CI на PR #<номер>, прогон [ссылка]: lint — N с (из них ruff check N с, ruff format --check N с, mypy N с), secrets — N с; от push до результата — около N мин.
Ручные проверки из таблицы этого issue, которые теперь запускает CI: [названия] — вместе N мин (измерено).
```

Особые случаи:

- Ручная проверка в issue измерена вместе с другими (например, одна строка `pre-commit run --all-files` — gitleaks и базовые хуки), а CI заменяет только часть — число не делите: строка входит в сумму «вместе» целиком, пометка — рядом с суммой: «вместе N мин (измерено; в том числе [что], отдельно не измерено)». На этапе 8 так и говорите: ручное время — верхняя граница
- Время в issue — оценка, а не замер: так и пишите — «(оценка)»; замер — ДЗ 1
- Issue нет — создайте его, первая строка комментария — в описание issue, вторая — в ДЗ 1 вместе с таблицей ручных проверок; номер issue допишите в описание PR (`Refs #<номер>`, шаг 2.5)

#### Шаг 5.2: `CONTRIBUTING.md` и ADR 001 совпадают с ruleset (5 мин)

### Этап 6: Межкомандное ревью workflow (25 мин)

Вы проверяете, сделала ли другая команда то, что записала в ADR 004, и работает ли блок merge. Ревью идёт по PR и прогонам на GitHub: клонировать чужой репозиторий не нужно.

**Как это оценивается.** Зачёт / незачёт этапа, баллы не начисляются. Зачёт команда получает, если:

1. Опубликован комментарий ревью в PR назначенной команды по шаблону шага 6.1: шесть пунктов чек-листа с доказательством и итог
2. На каждое замечание к вашему PR есть ответ — правкой или аргументом (шаг 6.2)

#### Шаг 6.1: Проверить чужой workflow (12 мин)

Работают рецензенты по таблице шага 0.2. Откройте PR назначенной команды:

- **Files changed** — `ci.yml`, ADR 004, ADR 001 и ADR 003 открываются в основной ветке репозитория
- **Commits** — у каждого коммита значок результата прогона: красный крестик у ранних коммитов — тот самый красный прогон
- **Checks** — проверки последнего коммита и пометка **Required**

| № | Что сверяете | Где смотреть |
|---|---|---|
| 1 | Триггеры покрывают ветки стратегии: GitHub Flow, Trunk-Based — `main`; GitFlow — `main` и `develop`, в `pull_request` и `push` | `ci.yml`, `on:`; стратегия — ADR 001 |
| 2 | Джобы называются `lint` и `secrets`; в `lint` — `ruff check`, `ruff format --check`, `mypy`, зависимости ставятся с lock-файлом: у uv — `--locked`, у Poetry — `poetry install` при закоммиченном `poetry.lock` (устаревший lock он отвергает сам) | `ci.yml`; `poetry.lock` в **Files changed** |
| 3 | Сканер в `secrets` — тот, что в ADR 003: gitleaks из образа `zricethezav/gitleaks:v8.28.0` или detect-secrets 1.5.0 с `--baseline` | `ci.yml`; ADR 003, «Решение» |
| 4 | Полная история — как записано в п. 4 «Решения» ADR 004: есть `fetch-depth: 0` и шаг `gitleaks (history)` или их нет | `ci.yml`; ADR 004 |
| 5 | Обязательные проверки работают: в PR был красный прогон, у `lint` и `secrets` пометка **Required**, в PR процитирован блок merge | **Commits**, **Checks**, комментарии PR; ADR 004, п. 3 |
| 6 | `test`, `build`, `publish` закомментированы; `.pre-commit-config.yaml` в PR не менялся | `ci.yml`; **Files changed** |

Публикует один из рецензентов из своего аккаунта: **Files changed** → **Review changes** → **Comment**. Замечание к конкретной строке `ci.yml` — комментарием к строке. В поле резюме:

```markdown
Ревью workflow: команда [название]
Рецензенты: [имена, логины GitHub]
Ветка и коммит: [ветка], [первые 7 символов SHA последнего коммита]

| № | Пункт | Результат | Доказательство (строка файла или ссылка на прогон) |
|---|---|---|---|
| 1 | Триггеры ↔ стратегия | выполнено / не выполнено / спорно | `ci.yml:28` ... |
| 2 | Имена джобов и проверки `lint` | | |
| 3 | Сканер ↔ ADR 003 | | |
| 4 | Полная история ↔ ADR 004, п. 4 | | |
| 5 | Обязательные проверки, красный прогон, блок merge | | [ссылка на красный прогон] |
| 6 | Джобы практики №6 закомментированы, pre-commit не менялся | | |

Замечания (где → что не так → чем грозит → что предлагаете):
1. [файл:строка или раздел] → [что не так] → [чем грозит] → [что предлагаете]

Итог: замечаний нет / N замечаний
```

«Замечаний нет» — нормальный результат, если у каждого из шести пунктов есть доказательство. Команда в ситуации F (обязательные проверки не включены, в PR комментарий о переносе): п. 5 — «перенесено в ДЗ 1», это не замечание; красный прогон всё равно найдите в **Commits** и дайте на него ссылку. Пример замечания: «`ci.yml:28`, `pull_request: branches: [main]` → команда на GitFlow, PR фич идут в `develop` → неиспользуемый импорт пройдёт в `develop` без проверки и всплывёт на релизе → добавить `develop` в оба триггера и обязательные проверки в `protect-develop`».

Approve в чужом PR не ставьте: вы не коллаборатор, защита ветки его не засчитает. Комментарий опубликуйте **к 130-й минуте**: после неё у команды-автора остаётся время на ответы и merge. **Точка синхронизации 130.**

| В поиске **Add checks** ruleset только «Add lint · Any source», строки `lint` с **GitHub Actions** нет | Проверка ещё ни разу не выполнялась в репозитории (или последний прогон старше недели) | «Any source» не выбирать: дождаться первого прогона на шаге 2.5, затем шаг 3.2 |
| В **Annotations** прогона notice `The ubuntu-latest label will migrate to Ubuntu 26 ...` | Предупреждение GitHub о смене образа раннера | Не ошибка: на результат проверок не влияет, ничего не менять |
| Джоб `skipped` (серый), а merge разрешён | Пропущенный из-за `if` или `needs` джоб считается успешным | Так задумано GitHub; поэтому обязательной делают каждую стадию. На практике №5 `needs` в `lint` и `secrets` нет |
| Merge доступен при красном `lint` | Обязательные проверки не включены, ruleset `Disabled`, или GitFlow: PR в `develop`, а проверки только в `protect-main` | Шаг 3.2 — правило в нужном ruleset, `Active`, Bypass list пуст |
| Прогон долго `Queued` или `Waiting for a runner` | Очередь раннеров GitHub, все команды пушат одновременно | Ждать, это буфер; повторно не перезапускать |
| `Unable to resolve action astral-sh/setup-uv@v10` | У `setup-uv` нет тегов major-версий | Полная версия, как в шаблоне: `@v10.3.0` |
| Poetry: `setup-python` падает с `Unable to locate executable file: poetry` | `setup-python` с `cache: poetry` стоит до установки Poetry | Порядок шагов — как в шаблоне: сначала `Install Poetry` |
| Workflow не запускается совсем, в **Actions** — сообщение о политике или о выключенных Actions | Actions выключены в настройках репозитория или организации | Ситуация E: владелец (организации) разрешает Actions. Владелец недоступен — прогоны, проверки и merge переходят в ДЗ 1 (ситуация E, «E вместе с F») |

### Секреты в CI

| Симптом | Причина | Что сделать |
|---|---|---|
| `secrets` красный: `WRN leaks found`, `File:` — файл, который есть в ветке, а в `.gitleaksignore` для него отпечаток вида `<коммит>:<файл>:<правило>:<строка>` | Находка истории практики №4 в файле, который всё ещё лежит в ветке. Отпечаток режима `git` содержит коммит, а режим `dir` даёт `<файл>:<правило>:<строка>` — без коммита (проверено) | Секрет уже ротирован — добавить в `.gitleaksignore` строку с отпечатком из вывода `dir` и комментарием над ней; реальное значение в файле — заменить ссылкой на переменную и ротировать. Если файла с находкой в ветке нет (например, `.env`), `dir` его не видит — проверка зелёная |
| `secrets` красный на новой находке в файле этой практики | Строка похожа на секрет | Значение настоящее — убрать из файла, ротировать. Заглушка — отпечаток в `.gitleaksignore` с комментарием |
| `gitleaks (history)` красный на старой находке | Находка истории не записана в `.gitleaksignore` | Как на шаге 3.4 практики №4: отпечаток из вывода с комментарием «ротирован ГГГГ-ММ-ДД» |
| detect-secrets в CI: `Potential secrets about to be committed` на `ci.yml` | Удалена пометка `# pragma: allowlist secret` | Вернуть строку `run: >-  # pragma: allowlist secret` из шаблона |
| detect-secrets в CI красный на другом файле | `.secrets.baseline` устарел | Проверить находку; заглушка — `detect-secrets scan --baseline .secrets.baseline` (как на практике №4: uvx / pipx), коммит baseline |
| Локально `gitleaks dir .` находит `.env` | `dir` не учитывает `.gitignore` | Не ошибка CI: на раннере `.env` нет. Локально — только по свежему клону (бонусная задача 4) |

### Push и права

| Симптом | Причина | Что сделать |
|---|---|---|
| Push отклонён: `refusing to allow ... to create or update workflow ... without workflow scope` | Токен, которым git входит в GitHub, без права `workflow` | **GitHub CLI** — `gh auth refresh -s workflow`, затем `git push`. **Вход через браузер или PAT** — сначала удалите сохранённый токен, иначе git снова отправит его: в терминале macOS / Linux / Git Bash (на Windows — именно Git Bash: в PowerShell 5.1 ввод команды может испортиться) `printf "protocol=https\nhost=github.com\n\n" \| git credential reject`. Затем `git push`: откроется вход через браузер (Git Credential Manager) или git спросит пароль — вставьте новый PAT с `workflow` (fine-grained — **Workflows: Read and write**). Не загружать файл через веб-интерфейс |
| То же, а новый токен получить быстро нельзя | — | Push по SSH, если SSH-ключ в GitHub уже добавлен: `git push git@github.com:<владелец>/<репозиторий>.git HEAD` — так же каждый следующий push, который меняет `ci.yml`. Иначе — с ноутбука сокомандника, где push workflow проходит. Коммит шага 2.4 есть только у водителя — перенесите файл: `ci.yml` — в чат команды; у сокомандника `git fetch origin`, `git checkout feature/ci-pipeline`, файл — в `.github/workflows/ci.yml`; если в этом клоне не выполнен `pre-commit install` (практика №4, ДЗ 3) — выполните сейчас, иначе коммит пройдёт без проверок; коммит шага 2.4 с `--author` водителя, `git push`. На ноутбуке водителя затем `git fetch origin` и `git reset --hard origin/feature/ci-pipeline` — локальный коммит заменится запушенным. Дальше можно работать на любом из двух ноутбуков, но коммиты, которые меняют `ci.yml` (в том числе правки после ревью на этапе 6), пушите с ноутбука сокомандника |
| Нет вкладки **Settings** или правила ruleset не редактируются | Вы не владелец репозитория | Включает владелец (шаг 3.2, ситуация F) |
| Блок merge называет причиной review от Code Owners | Включён `Require review from Code Owners` | Раздел «Code owners» ниже |

### Code owners

PR меняет `.github/` и `*.py`; ждёт approval владельцев этих путей из `.github/CODEOWNERS`.

- **Владелец пути пришёл, но он автор PR** — он не может одобрить свой PR: автором PR сделайте другого участника (шаг 0.2). Если PR уже открыт — его закрывают и открывают заново из аккаунта другого участника на ту же ветку
- **Владелец пути не пришёл, владелец репозитория на месте** — удалённый approval владельца пути (ссылка ему в чат); нет к 150-й минуте — временное снятие `Require review from Code Owners` владельцем репозитория **только с разрешения преподавателя**, merge, правило сразу вернуть; записать в комментарий-итог; в ДЗ 1 — второй владелец пути в `CODEOWNERS`
- **Единственный владелец `.github/` — он же владелец репозитория — не пришёл, но на связи** — всё удалённо, как в ситуации F: он включает проверки (шаг 3.2) и ставит approval после последнего коммита (шаг 7.1; ссылку на PR пришлите ему в чат к 150-й минуте). Снимать правило не нужно
- **Тот же владелец недоступен** — снять правило некому: на занятии PR с красным и зелёным прогоном и ревью, включение проверок и merge — ДЗ 1 (ситуация F); незачётом это не считается

### Windows

| Симптом | Причина | Что сделать |
|---|---|---|
| PowerShell: `curl` выводит таблицу | `curl` — псевдоним `Invoke-WebRequest` | `curl.exe` |
| PowerShell 5.1: `The token '&&' is not a valid statement separator` | `&&` появился только в PowerShell 7 | Команды по очереди через `;` (шаг 4.3) |

## Чек-лист для преподавателя

Роль преподавателя в репозиториях команд — **Write**: ruleset и настройки Actions видит и меняет только владелец, поэтому включение проверок подтверждается по PR (пометка **Required**, цитата блока merge, скриншот).

|---|---|---|
| Зависимости | `pyproject.toml`, lock-файл в коммите шага 1.3 | ruff и mypy закреплены в `[dependency-groups]`, lock-файл в том же коммите |
| Workflow | `ci.yml` в PR | Имена `lint`, `secrets`; триггеры по стратегии; сканер по ADR 003; история по ADR 004; джобы практики №6 закомментированы |
| Предсказание и диагноз | Описание и комментарии PR | Предсказание до первого прогона; диагноз — шаг, файл:строка, сообщение — до push коммита исправления: время комментария раньше запуска прогона на этом коммите (вкладка **Checks**) |
| Блок merge | **Checks**, комментарий шага 3.3 | Пометка **Required** у обеих проверок; цитата блока; GitFlow — оба rulesets |
| Красный → зелёный | Вкладка **Commits** PR | Ранний коммит с красным `lint` (или проба), последний — зелёный; исправления отдельными коммитами |

| Ревью | PR проверяемой команды | Шесть пунктов с доказательством, замечания по формуле или доказанное «замечаний нет» |
| Ответы на ревью | Собственный PR команды | На каждое замечание — правка или аргумент |
| PR-процесс | Смерженный PR | Approval после последнего коммита, Code owners, «Кто что делал», `--author` |
| Ретроспектива | Issue «Ретроспектива модуля 2» | Факт на этапе 0, вердикт на этапе 8 |

### 1. Закрыть незавершённое

Довести до merge PR практики, если не успели; ответить на замечания ревью. **Ситуация F:** PR практики на занятии не мержился (шаг 7.1). Владелец включает обязательные проверки по шагу 3.2, команда делает в том же PR пп. 1 и 3 шага 5.2 и п. 4 шага 5.1 (в п. 3 «Решения» ADR 004 — факт включения вместо «включаются в ДЗ 1»), показывает блок merge пробой по шагу 3.3 (последний прогон PR уже зелёный) и цитирует его; затем approval после последнего коммита и merge. **Ситуации E и F вместе, Actions были выключены:** владелец включает Actions (**Settings → Actions → General**) и пишет в PR практики комментарий о выбранном варианте. Первый прогон запускает push в ветку PR, например пустого коммита: `git commit --allow-empty -m "chore: trigger CI"`, затем `git push`. Дальше — шаги 3.1–4.4 по порядку (блок merge показывает красный прогон, проба шага 3.3 не нужна), затем пп. 1 и 3 шага 5.2, п. 4 шага 5.1, approval после последнего коммита и merge. **Снималось `Require review from Code Owners`:** правило возвращено, PR в `CODEOWNERS` со вторым владельцем пути. **Ситуация C:** ADR 004 по [материалам воркшопа №5](../../workshops/workshop5/workshop5-materials.md), разделы 5.1–5.5: сравнение вариантов, приложения А–Г, ревью команды, которую назовёт преподаватель (комментарием в PR, перенос в файл коммитом с `--author` рецензента), ответы; «Принято» — отдельным PR после ревью. **Пункты 5–6 шага 5.1**, если не вошли в PR практики, — отдельным PR со строкой в «Истории изменений» ADR 004. **Нет issue «Ручные проверки»** — таблица ручных проверок с измеренным временем.

**Критерий успеха:**

- [ ] PR практики смержен, обсуждения закрыты, прогон на `push` в основную ветку зелёный
- [ ] Обязательные `lint` и `secrets` включены во всех rulesets стратегии, блок merge процитирован в PR
- [ ] ADR 004 в основной ветке со статусом «Принято», п. 3 «Решения» называет включённые проверки; `CONTRIBUTING.md` и ADR 001 совпадают с ruleset
- [ ] Правило Code Owners, если снималось, возвращено

**Дедлайн:** 3 дня после практики.

### 2. GitFlow: релиз `develop` → `main`

Только GitFlow. Релиз — как на практиках №3–4 (ДЗ 2), версия поднимается в источнике из ADR 003. PR из `develop` (или `release/*`) в `main` проходит обязательные проверки `protect-main`: workflow из `develop` запускается на этот PR, потому что `main` есть в `on.pull_request.branches`. Релиз практики №4 не сделан — критерии ДЗ 2 практики №4 (issue «Оптимизация образа приложения» закрыт `Closes #`, `GET /version` = номер релиза) входят в этот же PR.

**Критерий успеха:**

- [ ] В PR релиза `lint` и `secrets` зелёные и помечены **Required**
- [ ] После merge в `main` — прогон на `push` в `main` зелёный
- [ ] В `main` есть `.github/workflows/ci.yml`, `settings.py`, `.pre-commit-config.yaml`

### 3. Линтеры у каждого участника

Каждый участник в своём клоне:

```bash
git checkout main          # GitFlow: develop
git pull
uv sync                    # Poetry: poetry install
uv run ruff check .        # Poetry: poetry run ...
uv run ruff format --check .
uv run mypy .
```

Ожидаемый вывод — как в CI: `All checks passed!`, `N files already formatted`, `Success: no issues found ...`. Иначе — что-то в вашем клоне отличается от основной ветки (`git status`), или раздел «Как запустить линтеры локально» в `CONTRIBUTING.md` неполон: исправьте его через PR.

**Критерий успеха:**

- [ ] Каждый участник оставил в смерженном PR практики комментарий из своего аккаунта: ОС и вывод трёх команд (`ruff check`, `ruff format --check`, `mypy`)
- [ ] Всё, что пришлось делать сверх `CONTRIBUTING.md`, внесено в него через PR
