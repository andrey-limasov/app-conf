# Практика №2: "Branch protection, PR-процесс и приёмка ADR"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Самостоятельная командная работа по письменной инструкции + межкомандное ревью  
**Роль преподавателя:** Модератор межкомандного ревью, фиксация прогресса

---

## Цели практики

К концу занятия каждая команда должна:

1. **Настроить** защиту основной ветки репозитория так, чтобы прямой `push` в неё отклонялся сервером, а merge был возможен только через Pull Request с минимум 1 approval
2. **Проверить** работоспособность защиты экспериментом «на отказ»: зафиксировать текст ошибки, которую возвращает GitHub при попытке прямого push и при попытке force-push
3. **Создать** шаблон Pull Request (`.github/pull_request_template.md`), который воспроизводит чек-лист ревью команды и применяется ко всем новым PR автоматически
4. **Переработать** `CONTRIBUTING.md` под выбранную стратегию ветвления так, чтобы правила именования веток, регламент code review и критерии approval были сформулированы проверяемо
5. **Оценить** ADR другой команды по чек-листу межкомандного ревью и сформулировать не менее трёх замечаний с указанием конкретного раздела документа
6. **Довести** `docs/adr/001-branching-strategy.md` до статуса «Принято» через Pull Request, прошедший межкомандное ревью и цикл «Request changes → правки → повторное ревью → merge»
7. **Применить** свой регламент к изменению кода: эндпоинт `GET /version` попадает в основную ветку разработки через PR, в котором шаблон подставился автоматически, а ревью провела другая команда

| **C.** Файл у отсутствующего участника | Заполнить заново по [шаблону](../../workshops/workshop2/adr-template.md): решение принято на воркшопе, переголосовывать не нужно. ### Права доступа

**В личном репозитории администратор один — владелец.** У коллабораторов один уровень доступа — запись; Settings, включая правила защиты веток, меняет только владелец ([GitHub Docs: Permission levels for a personal account repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)).

1. **Этапы 2–3 выполняет владелец.** Если его не будет — «Если не работает → Владелец отсутствует»
2. **На этапах 4–6 ограничения нет:** ветки, PR, approval и merge доступны любому коллаборатору
3. **Единственный владелец — риск**, строку о нём вы внесёте в ADR на шаге 5.1

**Автор PR не может поставить approval собственному PR** — на каждом PR нужны двое: автор и ревьюер.

### Этап 1: Синхронизация, доступы, роли, кольцо ревью (13 мин)

#### Шаг 1.1: Обновить локальные копии и проверить доступы (7 мин)

Каждый участник на своём ноутбуке. Если `git status` показывает изменённые файлы (`M`), сначала уберите их: `git stash push -m "leftovers from practice 1"`. Как вернуть их после занятия — «Если не работает → Изменения, убранные в stash».

```bash
git checkout main
git pull origin main
git config user.name
git config user.email
git push --dry-run origin main
```

**Ожидаемый вывод:** `Already up to date` или список обновлённых файлов; ваше имя и email; `Everything up-to-date`. Пусто вместо имени — `git config --global user.name "Имя Фамилия"` и то же для `user.email`. Запрос пароля или `Authentication failed` на последней команде — вход не настроен: [практика №1, шаг 1.3](../practice1/practice-1-guide.md).

**Владелец проверяет коллабораторов:** Settings → Collaborators — все участники и `andrey-limasov`, без «Pending». Кого нет — **Add people**. Приглашённый принимает по ссылке из письма или на `https://github.com/<владелец>/<репозиторий>/invitations`.

**Неотслеживаемые `pyproject.toml`, `poetry.lock` или `uv.lock`** (Poetry или uv с практики №1 вне git) — один участник отправляет их отдельным PR, он мержится на этапе 4:

```bash
git checkout -b chore/dependency-files
git add pyproject.toml poetry.lock    # uv: pyproject.toml uv.lock (и .python-version, если есть)
git commit -m "chore: add dependency manager files"
git push -u origin HEAD
git checkout main
```

После `git checkout main` эти файлы пропадут из папки — так и должно быть: они вернутся после merge PR и `git pull origin main`. Заново их не создавайте. У остальных участников такие же неотслеживаемые файлы удалите перед первым `git pull` после этого merge. Приложение запускается и без них: зависимости стоят в `venv/`.

Файл ADR в ситуации A (`?? docs/adr/...`) не трогайте.

#### Шаг 1.2: Распределить роли (3 мин)

Имена — в чат команды; на шаге 5.1 автор ADR перенесёт их в описание PR с ADR строкой «Роли на практике №2: …» (след вклада для оценки сокомандников). Один ноутбук на команду — врезка в начале этапа 4; состав из 2 или 5 человек и совмещение ролей — «Если не работает → Состав команды и один ноутбук».

**Команда из 4 человек**

| Участник | Этапы 2–3 | Этап 4 | Этапы 5–6 |

| 1 (владелец) | Защита ветки, проверка | Approval и merge PR этапа 4; список правил для «Защиты ветки» | Approval PR с ADR и PR с кодом своей команды |
| 2 | Черновик шаблона PR | Автор `docs/pr-template` (push к 65-й); с 75-й — ревью чужого ADR (5.2) | Второй круг ревью чужого ADR; ревью PR с кодом той же чужой команды (6.3) |
| 3 | Черновик `CONTRIBUTING.md` | Автор `docs/contributing-rules` | Автор PR на кодовой задаче (с 93-й) |
| 4 | ADR до целевого состояния 5.1 | PR с ADR к 75-й (5.1) | Правки ADR, «Принято» (5.3) |

**Команда из 3 человек**

| Участник | Этапы 2–3 | Этап 4 | Этапы 5–6 |
|---|---|---|---|
| 1 (владелец) | Защита ветки, проверка | Автор `docs/pr-template` (push к 65-й); approval PR `docs/contributing-rules`; с 75-й — ревью чужого ADR (5.2) | Второй круг ревью чужого ADR; ревью PR с кодом той же чужой команды (6.3); approval PR с ADR своей команды |

Нельзя совмещать автора PR и того, кто ставит ему approval.

#### Шаг 1.3: Записать назначение на межкомандное ревью (3 мин)

Преподаватель объявляет **кольцо ревью**: каждая команда ревьюит одну и получает ревью от одной (А→Б→В→А; две команды — взаимно; отсутствующую команду преподаватель замыкает на себя). Одна и та же пара ревьюит и ADR (этап 5), и PR с кодом (этап 6).

**Что должно получиться:** записаны ссылка на репозиторий, который вы ревьюите; логин вашего участника, который идёт к этой команде ревьюером (передайте его ей); логин ревьюера другой команды, который придёт к вам.

### Этап 2: Branch protection на основной ветке (27 мин)

Работает **владелец**. Остальные пишут черновики для этапа 4 — в редакторе или общем документе, **не в git**. Интерфейс GitHub меняется: ориентируйтесь на «Что должно получиться», не нашли пункт — ищите по названию правила.

#### Шаг 2.1: Открыть настройки правил (4 мин)

**Settings** репозитория → **Rules** → **Rulesets** (в части интерфейсов — **Code and automation → Rules**) → **New ruleset** → **New branch ruleset**.

**Что должно получиться:** форма с полями `Ruleset name`, `Enforcement status`, `Bypass list`, `Target branches` и списком правил.

Вкладки Settings нет — вы не владелец. Правила помечены как платные — репозиторий приватный: Settings → General → `Danger Zone` → `Change visibility` → Public. На бесплатном плане защита работает только в публичных репозиториях; публичность требует и [DoD, раздел 1](../../definition-of-done.md).

#### Шаг 2.2: Настроить ruleset для основной ветки (13 мин)

| Поле | Значение | Зачем |
|---|---|---|
| Ruleset name | `protect-main` | По имени искать |
| Enforcement status | **Active** | `Disabled` ничего не запрещает |
| Bypass list | **пусто** | Иначе владелец обойдёт защиту |
| Target branches | **Add target → Include default branch** | Привязка к `main` |

**Правила:**

- [x] **Restrict deletions**
- [x] **Block force pushes**
- [x] **Require a pull request before merging**, внутри: `Required approvals` → **1**; [x] `Dismiss stale pull request approvals when new commits are pushed`; [x] `Require conversation resolution before merging`
- [ ] **Require status checks to pass** — выключено: CI появится на практике №5
- [ ] **Require linear history** — только для Trunk-Based (шаг 2.3)

**Create**.

**Что должно получиться:** в Rulesets строка `protect-main`, `Active`, целевых веток `1`; на странице веток (**View all branches**) у `main` значок защиты. **Выпишите в чат список включённых правил** — для «Защиты ветки» в `CONTRIBUTING.md` и для ADR.

Прямой push в `main` закрыт для всех, включая владельца, до конца семестра ([DoD, раздел 1](../../definition-of-done.md)). Временное отключение (`Enforcement status` → `Disabled` и сразу обратно) записывается в `CONTRIBUTING.md`: кто, когда, зачем.

Автор `CONTRIBUTING.md` вставит в «Защиту ветки» задел под CI:

```markdown
> TODO (модуль 3, практика №5): после появления CI-пайплайна включить в ruleset `protect-main`
> правило «Require status checks to pass» и добавить в список обязательных проверок джобы
> линтера и тестов. До этого момента зелёный пайплайн не является условием merge.
```

#### Шаг 2.3: Учесть стратегию ветвления (10 мин)

**Все стратегии:** Settings → General → Pull Requests → **Automatically delete head branches**.

**GitHub Flow** — достаточно `protect-main`.

**Trunk-Based** — в `protect-main` включить **Require linear history**; в Settings → General → Pull Requests оставить только **Allow squash merging** (или в правиле PR: `Allowed merge methods` → Squash). **Что должно получиться:** на странице PR единственная кнопка — `Squash and merge`.

**GitFlow** — защищаются `main` и `develop`.

1. Есть ли `develop` на GitHub:

   ```bash
   git ls-remote --heads origin develop
   ```

   Есть строка `refs/heads/develop` — `git fetch origin`, `git checkout develop`. Пусто — создайте от свежего `main`:

   ```bash
   git checkout main
   git pull origin main
   git checkout -b develop
   git push -u origin develop
   ```

   **Ожидаемый вывод:** `* [new branch]      develop -> develop`. В обоих случаях вернитесь: `git checkout main`.

2. Ruleset `protect-develop`: **Include by pattern** → `develop`; правила — те же, что в `protect-main` (шаг 2.2): в ADR и `CONTRIBUTING.md` тогда один набор правил для обеих веток

**Что должно получиться (GitFlow):** `protect-main` и `protect-develop` в статусе `Active`.

#### Шаг 2.4 (альтернатива, не входит в тайминг): классический Branch protection rule

Только если rulesets недоступны: «Если не работает → Классическая защита».

### Этап 3: Проверка защиты «на отказ» (13 мин)

Правило может выглядеть включённым, но не применяться. Проверяет любой участник с правом записи.

#### Шаг 3.1: Попытка прямого push в защищённую ветку (5 мин)

```bash
git checkout main
git pull origin main
git commit --allow-empty -m "chore: verify branch protection"
git push origin main
```

**Ожидаемый вывод — rulesets:**

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: Review all repository rules at https://github.com/<владелец>/<репозиторий>/rules?ref=refs%2Fheads%2Fmain
remote:
remote: - Changes must be made through a pull request.
remote:
To https://github.com/<владелец>/<репозиторий>.git
 ! [remote rejected] main -> main (push declined due to repository rule violations)
error: failed to push some refs to 'https://github.com/<владелец>/<репозиторий>.git'
```

**Ожидаемый вывод — классическая защита:**

```
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: At least 1 approving review is required by reviewers with write access.
 ! [remote rejected] main -> main (protected branch hook declined)
```

Признак успеха — `GH013` или `GH006` и `[remote rejected]`. Push прошёл — «Если не работает → Push в защищённую ветку прошёл». **Текст отказа — в чат команды.**

**GitFlow:** `protect-develop` проверяется одним экспериментом — удалением `develop` на шаге 3.2: отказ доказывает, что правило активно и нацелено на `develop`. Отдельный push в `develop` не нужен.

#### Шаг 3.2: Проверка запрета force-push и удаления ветки (6 мин)

Перепишите верхний коммит, который уже есть на сервере (`--allow-empty` — на случай, если он пустой):

```bash
git reset --hard origin/main
git commit --amend --no-edit --allow-empty
git push --force origin main
```

**Ожидаемый вывод — rulesets:**

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote:
remote: - Cannot force-push to this branch
remote: - Changes must be made through a pull request.
```

**Классическая защита:** `GH006: Protected branch update failed …` и `Cannot force-push to this protected branch`.

Нужна строка про force-push: её даёт только `Block force pushes`. Формулировка может отличаться — ориентируйтесь на смысл; строки нет — вернитесь к шагу 2.2. Строку — в чат. Сразу верните историю:

```bash
git fetch origin
git reset --hard origin/main
```

**Удаление ветки.**

- **GitFlow:**

  ```bash
  git push origin --delete develop
  git ls-remote --heads origin develop
  ```

  **Ожидаемый вывод:** `GH013 … Cannot delete this branch` (или `GH006 … Cannot delete this protected branch`), затем строка `refs/heads/develop`. Текст — в чат. Строки `refs/heads/develop` нет — «Если не работает → Ветка `develop` удалена»
- **GitHub Flow и Trunk-Based:** не выполняйте. Default-ветку GitHub не даёт удалить при любых правилах, поэтому `Restrict deletions` здесь не проверить. В «Защите ветки» запишите: «`Restrict deletions` включено; на default-ветке экспериментом не проверяется»

**Что должно получиться:** `git status` — чистое дерево (в ситуации A допустима строка `?? docs/`); `git log --oneline -1` — тот же SHA, что у `main` на GitHub; пустого коммита `chore: verify branch protection` в истории нет (исключение — «Если не работает → Push прошёл»).

#### Шаг 3.3: Зафиксировать доказательство (2 мин)

**Обязательно:** тексты отказов (push, force-push; GitFlow — удаление `develop`) в чате — автор `docs/contributing-rules` вставит их в «Защиту ветки». **По желанию:** скриншот терминала в чат; автор сохранит его в своей ветке как `docs/branch-protection-check.png`.

```markdown
2. п.[N] чек-листа — [что не так] — [что сделать]
3. п.[N] чек-листа — [что не так] — [что сделать]

Открытые вопросы (не блокируют merge):
- [вопрос]
```

**Второй круг** (около 110-й минуты): по каждому замечанию ответ в обсуждении — «исправлено, принимаю» или уточнение (Resolve нажимает автор PR, регламент шага 4.2), затем **Approve** или повторный **Request changes**.

#### Регламент: что делать, если ревьюер и автор не согласны

1. Автор отвечает на каждый комментарий; незакрытое обсуждение блокирует merge (`Require conversation resolution`)
2. Разногласие пережило два круга — автор записывает его в «Риски и митигация»: риск, позиция ревьюера, что команда сделает, если риск реализуется. Ревьюер ставит Approve
3. Ревьюер считает, что решение противоречит DoD, — зовите преподавателя: по 2 минуты на позицию, его решение, итог — в «Историю изменений» ADR

Нельзя: закрывать обсуждение внешнего ревьюера до его ответа или Approve, менять вердикт «по дружбе», одобрять неоткрытый документ.

#### Шаг 5.3: Внести правки и довести ADR до статуса «Принято» (30 мин)

С 93-й минуты — правки; около 110-й — повторное ревью; к 123-й — merge. Пока замечаний нет, автор дописывает разделы, перечисленные в описании PR.

1. Перейти в ветку ADR — к 93-й минуте у вас может быть открыта `main` или другая ветка:

   ```bash
   git checkout docs/adr-001-branching-strategy
   git pull
   ```

   **Ожидаемый вывод:** `Switched to branch 'docs/adr-001-branching-strategy'`, затем `Already up to date` или список изменений, если ветку правили с другого ноутбука или в браузере

2. Ответить на каждый комментарий, внести правки, **Статус** → `Принято`, строка в «Историю изменений»:

   ```markdown
   | ГГГГ-ММ-ДД | Принято | Учтены замечания команды [название] по пп. 1, 4, 5 чек-листа ревью | [имя] |
   ```

3. Закоммитить и запушить:

   ```bash
   git add docs/adr/001-branching-strategy.md
   git commit -m "docs: address review comments on ADR 001"
   # на общем ноутбуке: git commit --author="Имя Фамилия <email-из-GitHub>" -m "..."
   git push
   ```

4. **Re-request review** (у внешнего ревьюера кнопки может не быть — напишите ему)
5. После ответа ревьюера и его Approve автор закрывает его обсуждения (**Resolve conversation**); сокомандник ставит **Approve** заново, если он сброшен
6. **Merge pull request**. Ситуация E — удалите ветку черновика: `git push origin --delete feature/adr-001`

**Что должно получиться:** в PR история Request changes → правки → Approve → merged, обсуждения закрыты. Проверка:


- `fatal: pathspec '...' did not match any files` — файла нет (например, скриншота); добавляйте только существующие

- `error: The following untracked working tree files would be overwritten by merge: pyproject.toml ...` при `git pull` — у вас неотслеживаемые копии файлов, которые пришли с PR `chore/dependency-files`. Удалите их (`rm pyproject.toml poetry.lock`; PowerShell: `Remove-Item pyproject.toml, poetry.lock`) и повторите `git pull`

- Ветка шага 6.1 создана не от той базы (например, без `git fetch origin` командами `git checkout develop` и `git pull origin develop`, которые влили `develop` в открытую ветку) — `git checkout main`, `git branch -D feature/version-endpoint` и повторите шаг 6.1 как написано
- `warning: ... LF will be replaced by CRLF` в Windows — предупреждение о концах строк, на результат не влияет

### Изменения, убранные в stash

`git stash pop` после занятия может дать конфликт: за практику файлы в `main` изменились. Безопасный порядок (bash и PowerShell одинаково):

```bash
git checkout main
git pull origin main
git stash list
git stash show -p
```

- **Изменения не нужны** (в том числе если diff меняет все строки файла — это только концы строк Windows): `git stash drop`. `pop` не выполняйте
- **Нужны:** `git stash pop`. Конфликт (`CONFLICT (content)`, в `git status` строки `UU`) — stash при этом сохраняется. Либо разрешите вручную: уберите маркеры `<<<<<<<`, `=======`, `>>>>>>>`, `git add <файл>`, затем `git stash drop`. Либо откажитесь от возврата: `git reset --hard HEAD` — **стирает все незакоммиченные изменения в отслеживаемых файлах**, зато возвращает дерево к `main`; stash остаётся, удалите его `git stash drop`, если он не нужен
- Изменения нужны и относятся к проекту — переносите их отдельной веткой и PR, а не коммитом в `main`

### 1. Закрыть незавершённое

Довести до merge всё, что не успели: цикл PR на кодовой задаче, незакрытые обсуждения, пункты чек-листа самопроверки, названные преподавателем. Если владелец не был на занятии — этапы 2–3. Незачёт за межкомандное ревью закрывается здесь же, в тот же срок: после правок ревьюер другой команды проводит повторное ревью в течение 24 часов.

**Критерий успеха:**

- [ ] В репозитории нет открытых PR, созданных на практике
- [ ] Все обсуждения в PR закрыты
- [ ] Чек-лист самопроверки закрыт полностью

### 2. Цикл PR каждым участником

Участники, которые на практике не были авторами PR, создают собственный PR с небольшим осмысленным изменением и проводят его через ревью и merge. Не годится: правка пробелов, коммит «fix», изменение одной буквы ради галочки.

**Критерий успеха:**

- [ ] У каждого участника команды есть минимум 1 смерженный PR после практики №2
- [ ] Каждый PR заполнен по шаблону и получил approval от другого участника
- [ ] Имена всех веток соответствуют шаблону из `CONTRIBUTING.md`

### 3. Отзыв команде-ревьюеру

Отзыв (5–7 предложений) команде, которая ревьюила ваш ADR, комментарием в вашем PR с ADR: какие замечания оказались полезными и что вы по ним изменили, какие были формальными и почему, что вы изменили в своём подходе к ревью, побывав в обеих ролях.

**Критерий успеха:**

- [ ] Отзыв опубликован комментарием в PR, а не в личном чате
- [ ] Названы конкретные замечания, а не «спасибо, всё было полезно»
- [ ] Отзыв подписан названием команды

### 4. Согласовать три источника правды

Правила работы с ветками должны совпадать в трёх местах: `docs/adr/001-branching-strategy.md` (раздел «Решение»), `CONTRIBUTING.md` («Git-стратегия», «Ветвление», «Критерии approval», «Защита ветки») и настройки репозитория (владелец — Settings → Rules → Rulesets; остальные — страница `https://github.com/<владелец>/<репозиторий>/rules`). Расхождения устраните отдельным PR с сообщением `docs: align branching rules across ADR, CONTRIBUTING and repo settings`. Расхождений нет — PR не нужен, напишите это комментарием в PR с ADR.

**Критерий успеха:**

- [ ] Число обязательных approval одинаково во всех трёх источниках
- [ ] Список защищаемых веток одинаков в ADR и настройках
- [ ] Шаблон имён веток из `CONTRIBUTING.md` совпадает с именами реально созданных веток

### 5. Подготовиться к воркшопу №3

Прочитать [материалы воркшопа №3](../../workshops/workshop3/workshop3-materials.md) и установить Docker: Docker Desktop на Windows и macOS, Docker Engine на Linux. Проверить:

```bash
docker --version
docker compose version
docker run --rm hello-world
```

**Ожидаемый вывод** последней команды содержит `Hello from Docker!`. На самом воркшопе Docker не нужен, но проверка в его материалах и вся практика №3 без Docker невозможны. Проблемы установки (виртуализация в BIOS, WSL2 на Windows, группа `docker` на Linux) решаются до практики №3.

**Критерий успеха:**

- [ ] `docker run --rm hello-world` отрабатывает на машине каждого участника
- [ ] Материалы воркшопа №3 прочитаны всеми участниками
- [ ] В `main` лежат: `.gitignore`, `README.md`, `CONTRIBUTING.md`, `.github/pull_request_template.md`, `docs/adr/001-branching-strategy.md` со статусом «Принято», приложение с `GET /` и `GET /health`; `GET /version` — в `main`, у GitFlow — в `develop` (в `main` он попадёт с релизом GitFlow на практике №3 или в её домашнем задании 1)
