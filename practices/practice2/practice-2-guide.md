# Практика №2: "Branch protection, PR-процесс и приёмка ADR"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Самостоятельная командная работа по письменной инструкции + межкомандное ревью  
**Роль преподавателя:** Модератор межкомандного ревью, фиксация прогресса

---

## Цели практики

К концу занятия каждая команда должна:

1. **Настроить** защиту основной ветки репозитория так, чтобы прямой `push` в неё отклонялся сервером, а merge был возможен только через Pull Request с минимум 1 approval
2. **Проверить** работоспособность защиты экспериментом «на отказ»: зафиксировать текст ошибки, которую возвращает GitHub при попытке прямого push и при попытке force-push
3. **Создать** шаблон Pull Request (`.github/pull_request_template.md`), который воспроизводит чек-лист ревью команды и применяется ко всем новым PR автоматически
4. **Переработать** `CONTRIBUTING.md` под выбранную стратегию ветвления так, чтобы правила именования веток, регламент code review и критерии approval были сформулированы проверяемо
5. **Оценить** ADR другой команды по чек-листу межкомандного ревью и сформулировать не менее трёх замечаний с указанием конкретного раздела документа
6. **Довести** `docs/adr/001-branching-strategy.md` до статуса «Принято» через Pull Request, прошедший межкомандное ревью и цикл «Request changes → правки → повторное ревью → merge»

### Где сейчас ваш ADR: четыре ситуации

От этого зависит, как вы начнёте этап 5. Определитесь **до занятия**.

| Ситуация | Что это значит | Что делать |
|---|---|---|
| **A. ADR только локально, у кого-то из присутствующих** | Обычный случай | Ничего. Работаете по шагу 5.1 как написано |
| **B. ADR уже закоммичен в `main`** | Команда закоммитила файл сразу после воркшопа. PR на этапе 5 получится пустым — мержить нечего | Не удаляйте файл. На шаге 5.1 создаёте ветку и **дорабатываете** ADR: дописываете незаполненные разделы, меняете статус на «Принято». Именно эта доработка и станет содержимым PR. Если ADR уже полностью заполнен — всё равно остаётся смена статуса «Предложено» → «Принято» плюс правки по итогам ревью |
| **C. ADR на ноутбуке участника, которого сегодня нет** | Файла нет ни у кого из присутствующих | Не ждите и не восстанавливайте по памяти. Берите [шаблон ADR](../../workshops/workshop2/adr-template.md) из репозитория курса, заполняйте заново по своей сравнительной таблице (решение команда уже приняла на воркшопе — переголосовывать не нужно). Ориентир по оформлению — [заполненный пример](../../workshops/workshop2/adr-example.md). Закладывайте на это буфер |
| **D. ADR не начинали** | На воркшопе не успели | Как в ситуации C. Предупредите преподавателя в начале занятия |

Ситуации B и C — не повод сдвигать тайминг: на шаге 5.1 вы в любом случае открываете PR с тем, что есть на 15-й минуте этапа, а дозаполняете уже по ходу ревью.

### Права доступа

**Обязательно:** в команде должно быть **минимум два участника с ролью Admin** на репозитории. Причины две:

- Настройку защиты веток (Settings → Rules) видит только Admin. Если единственный Admin не пришёл на занятие, этапы 2 и 3 команда выполнить не сможет
- На этапах 4–6 роли Admin и автора PR должны быть у разных людей, иначе один человек становится узким местом

Как выдать: Settings → Collaborators → Add people → у добавленного участника выбрать роль **Admin**. Если репозиторий создан в организации (GitHub Organization), роль Admin на репозиторий выдаёт владелец организации.

**Важное ограничение GitHub:** автор Pull Request не может поставить approval собственному PR — кнопка Approve для него недоступна. Поэтому в каждой команде approval всегда ставит кто-то другой, и на каждом этапе вам нужны как минимум два человека: автор и ревьюер. Это не настройка, которую можно отключить.

### ПО и доступы

- Git, настроенный аккаунт GitHub у **каждого** участника (понадобится для ревью чужих PR)
- Доступ к репозиториям команд, которые вы будете ревьюить (репозитории публичные — достаточно ссылки)
- Python 3.11+ и рабочее окружение из практики №1

### Проверка перед стартом

```bash
git --version
git remote -v          # должен показать origin с URL вашего репозитория
git status             # должно быть "nothing to commit, working tree clean"
git log --oneline -5   # должны быть видны коммиты практики №1
```

Преподаватель проверяет их вслух. Команда, отставшая от точки более чем на 10 минут, сообщает об этом сразу, а не в конце занятия.

### Этап 1: Синхронизация, роли, кольцо ревью (15 мин)

#### Шаг 1.1: Обновить локальные копии (5 мин)

**Что сделать.** Каждый участник команды выполняет:

```bash
git checkout main
git pull origin main
git status
```

**Что должно получиться:** `git status` выводит `Your branch is up to date with 'origin/main'` и `nothing to commit, working tree clean`.

**Если есть незакоммиченные изменения с практики №1** — уберите их до начала работы:

```bash
git stash push -m "leftovers from practice 1"
```

Вернуть их потом: `git stash pop`. Не начинайте практику с грязного рабочего дерева — на этапе 3 вы будете разбирать ошибки push, и лишние изменения помешают понять причину.

#### Шаг 1.2: Распределить роли в команде (5 мин)

Роли меняются по ходу занятия. Возьмите раскладку по размеру своей команды и запишите имена в чат команды.

**Команда из 4 человек**

| Участник | Этапы 2–3 | Этап 4 | Этапы 5–6 |
|---|---|---|---|
| 1 (Admin) | Настройка защиты | Ревью PR сокомандников | Approval PR с ADR |
| 2 | Черновик PR-шаблона | Автор PR `docs/pr-template` | Внешний ревьюер чужого ADR |
| 3 | Черновик разделов `CONTRIBUTING.md` | Автор PR `docs/contributing-rules` | Автор PR на кодовой задаче |
| 4 | Работа с ADR (сверка с таблицей воркшопа) | Автор ADR: шаг 5.1 идёт параллельно | Автор ADR: правки, статус «Принято» |

**Команда из 3 человек**

| Участник | Этапы 2–3 | Этап 4 | Этапы 5–6 |
|---|---|---|---|
| 1 (Admin) | Настройка защиты | Автор PR `docs/contributing-rules` | Approval PR с ADR, автор PR на кодовой задаче |
| 2 | Черновик PR-шаблона | Автор PR `docs/pr-template` | Внешний ревьюер чужого ADR |
| 3 | Работа с ADR | Автор ADR: шаг 5.1 идёт параллельно | Автор ADR: правки, статус «Принято» |

В команде из 3 человек **допустимо совмещать роли «Автор ADR» и «Внешний ревьюер»** — свой ADR вы в это время уже отдали на ревью, а чужой читаете, пока ждёте замечаний. Если оба потока приходятся на одного человека одновременно, приоритет у внешнего ревью: другая команда ждёт вас, а ваш PR — нет.

Нельзя совмещать в любой команде: автор PR и тот, кто ставит ему approval. Это запрещено самим GitHub (см. «Права доступа»).

#### Шаг 1.3: Получить назначение на межкомандное ревью (5 мин)

Преподаватель объявляет **кольцо ревью**. Базовая схема для трёх команд:

```
Команда А  ──ревьюит──>  Команда Б  ──ревьюит──>  Команда В  ──ревьюит──>  Команда А
```

Правила построения кольца:

- Каждая команда ревьюит ровно одну команду и получает ревью ровно от одной — нагрузка одинаковая
- Команд больше трёх — кольцо просто длиннее: А→Б→В→Г→А
- Команд две — взаимное ревью: А↔Б
- Команда отсутствует целиком — преподаватель замыкает кольцо через себя и сам выступает ревьюером

**Что записать** (понадобится на этапах 5 и 6):

- Название команды, которую вы ревьюите, и ссылка на её репозиторий
- Название команды, которая ревьюит вас, и GitHub-логины её ревьюеров
- Логины ваших ревьюеров, переданные «своей» команде

**Что должно получиться:** у каждой команды записаны две ссылки и минимум два чужих логина. Если чего-то не хватает — спросите преподавателя сейчас, а не на этапе 5.

### Этап 2: Branch protection на основной ветке (30 мин)

Работает **Admin**. Остальные в это время готовят черновики текстов для этапа 4 — в любом редакторе, **не в git**: веток для них ещё нет, и создавать их сейчас не нужно.

> **Интерфейс GitHub меняется.** Названия пунктов и их расположение могут отличаться от описанных ниже. Поэтому к каждому шагу указано **что должно получиться** — ориентируйтесь на результат, а не на путь кликов. Если не нашли пункт по описанному пути — ищите по названию правила через поиск в настройках репозитория.

#### Шаг 2.1: Открыть настройки правил (5 мин)

**Что сделать:**

1. Открыть репозиторий на GitHub
2. **Settings** (верхняя панель репозитория, не настройки аккаунта)
3. В левом меню — **Rules** → **Rulesets**
4. **New ruleset** → **New branch ruleset**

**Что должно получиться:** открыта форма создания правила с полями `Ruleset Name`, `Enforcement status`, секциями `Bypass list`, `Target branches` и списком `Rules` с чекбоксами.

**Если раздела `Rules` нет или правила недоступны:**

| Причина | Признак | Что делать |
|---|---|---|
| Нет роли Admin | Раздела Settings нет вообще либо в нём нет Rules | Работает другой Admin команды (см. «Права доступа») |
| Репозиторий приватный на бесплатном тарифе | Пункты правил показаны, но помечены как требующие платного плана | **Сделать репозиторий публичным.** Settings → General → внизу `Danger Zone` → `Change repository visibility` → `Make public`. Защита веток на бесплатном тарифе работает только для публичных репозиториев — это касается и rulesets, и классического механизма из шага 2.4, так что «переключиться на классический» проблему не решает. Публичность репозитория и так требуется [DoD, раздел 1](../../definition-of-done.md) |

#### Шаг 2.2: Настроить ruleset для основной ветки (15 мин)

**Что заполнить:**

| Поле | Значение | Зачем |
|---|---|---|
| Ruleset Name | `protect-main` | Понятное имя, по нему потом искать |
| Enforcement status | **Active** | В статусе `Disabled` или `Evaluate` правило ничего не запрещает |
| Bypass list | **оставить пустым** | Иначе администратор сможет обойти защиту, и проверка на этапе 3 не сработает |
| Target branches | **Add target → Include default branch** | Привязка к `main` (или к той ветке, которая у вас default) |

**Какие правила включить:**

- [x] **Restrict deletions** — ветку нельзя удалить
- [x] **Block force pushes** — `git push --force` отклоняется
- [x] **Require a pull request before merging** — прямой push запрещён, только через PR. Внутри этого правила:
  - `Required approvals` → **1**
  - [x] `Dismiss stale pull request approvals when new commits are pushed` — approval сбрасывается, если автор дослал коммиты после одобрения
  - [x] `Require conversation resolution before merging` — нельзя смержить, пока есть неотвеченные комментарии ревью
- [ ] **Require status checks to pass** — **оставить выключенным**. Проверок CI ещё нет, включённое правило с пустым списком либо не имеет смысла, либо заблокирует merge. Задел под CI фиксируется текстом (см. ниже), само правило включается в модуле 3 (практика №5)
- [ ] **Require linear history** — опционально, включайте только если в `CONTRIBUTING.md` вы договорились мержить через squash или rebase

**Сохранить:** кнопка **Create** внизу формы.

**Что должно получиться:** в списке Settings → Rules → Rulesets появилась строка `protect-main` со статусом `Active` и количеством целевых веток `1`. На главной странице репозитория рядом с именем ветки `main` появляется значок защиты.

> **Это надолго.** С пустым bypass list прямой push в основную ветку закрыт **для всех, включая владельца репозитория**, и останется закрытым до конца семестра. Так и задумано: это требование [DoD, раздел 1](../../definition-of-done.md). Все изменения с этого момента идут только через PR — включая правку одной строки в README.
>
> **Как временно снять правило, если это действительно нужно** (например, репозиторий нужно срочно перестроить):
>
> 1. Settings → Rules → Rulesets → открыть `protect-main` → `Enforcement status` → **Disabled** → Save
> 2. Сделать то, ради чего снимали
> 3. Немедленно вернуть **Active**
>
> Отключение правила — событие, а не рутина. Зафиксируйте в `CONTRIBUTING.md` или в issue: кто, когда, зачем отключал и когда вернул. Если отключение потребовалось больше одного раза за семестр — это повод пересмотреть процесс, а не правило.

**Задел под required status checks.** Добавьте в `CONTRIBUTING.md` (это делает автор PR `docs/contributing-rules` на шаге 4.2) строку:

```markdown
> TODO (модуль 3, практика №5): после появления CI-пайплайна включить в ruleset `protect-main`
> правило «Require status checks to pass» и добавить в список обязательных проверок джобы
> линтера и тестов. До этого момента зелёный пайплайн не является условием merge.
```

#### Шаг 2.3: Учесть вашу стратегию ветвления (10 мин)

Настройки зависят от того, что вы выбрали на воркшопе №2.

**Общее для всех стратегий**

- Settings → General → Pull Requests → включить **Automatically delete head branches**. Ветки будут удаляться после merge, список веток не зарастёт
- Правила защиты, которые вы включили, должны совпасть с тем, что написано в ADR 001 в разделе «Решение». Если в ADR написано «минимум 1 approval», а в ruleset стоит 2 — это расхождение, его увидит команда-ревьюер на этапе 5. Приведите документ и настройку в соответствие сейчас

**GitHub Flow** (ветки `feature/*` от `main`, других долгоживущих веток нет)

Достаточно одного ruleset `protect-main` из шага 2.2. Дополнительных действий нет.

**GitFlow** (есть долгоживущая `develop`, ветки `release/*` и `hotfix/*`)

Защищать нужно **две** ветки — `main` и `develop`, но по-разному.

1. Убедитесь, что ветка `develop` существует и запушена:

```bash
git checkout -b develop
git push -u origin develop
```

2. Создайте второй ruleset `protect-develop`:
   - Target branches → **Add target** → **Include by pattern** → ввести `develop`
   - Правила: `Require a pull request before merging` (Required approvals: **1**), `Block force pushes`, **`Restrict deletions`**
   - `Require conversation resolution` — на ваше усмотрение, `develop` интеграционная и обновляется чаще
3. Запомните: `develop` — **не** default-ветка, поэтому именно на ней вы сможете по-настоящему проверить правило `Restrict deletions` (шаг 3.2). Командам на других стратегиях эта проверка недоступна

**Что должно получиться:** два активных ruleset'а, `git push origin develop` из локальной `develop` отклоняется так же, как push в `main`.

**Trunk-Based Development** (короткоживущие ветки, частые merge в `main`)

К ruleset `protect-main` из шага 2.2 добавьте:

- [x] **Require linear history** — история остаётся плоской, что и является смыслом trunk-based
- В Settings → General → Pull Requests оставьте включённым только **Allow squash merging**, снимите `Allow merge commits` и `Allow rebase merging`

**Что должно получиться:** на странице PR доступна единственная кнопка merge — `Squash and merge`.

#### Шаг 2.4 (альтернатива, не входит в тайминг): классический Branch protection rule

Выполняется **вместо** шагов 2.1–2.2, если Rulesets недоступны или вы не нашли нужные пункты. Если ruleset уже создан — этот шаг пропускается.

1. **Settings** → **Branches** → **Add branch protection rule** (или **Add rule**)
2. `Branch name pattern`: `main`
3. Отметить:
   - [x] `Require a pull request before merging` → `Require approvals` → **1**
   - [x] `Dismiss stale pull request approvals when new commits are pushed`
   - [x] `Require conversation resolution before merging`
   - [x] **`Do not allow bypassing the above settings`** — без этой галочки администратор репозитория продолжит пушить в `main` напрямую, и проверка на этапе 3 провалится
4. Не отмечать `Allow force pushes` и `Allow deletions` — по умолчанию они выключены, то есть force-push и удаление уже запрещены
5. **Create** (потребуется подтвердить пароль или 2FA)

**Что должно получиться:** в Settings → Branches видна строка `main` с перечнем включённых правил.

Классический механизм имеет **то же ограничение по тарифу**, что и rulesets: на бесплатном плане он работает только в публичных репозиториях. Если причина была в приватности репозитория — возвращайтесь к таблице в шаге 2.1.

Классический механизм и rulesets работают параллельно; если случайно настроили оба — это не ошибка, применяется более строгое ограничение. Для чистоты оставьте один.

### Этап 3: Проверка защиты «на отказ» (12 мин)

**Этот этап обязателен.** Настройка, которая не проверена экспериментом, не считается выполненной: в интерфейсе правило может выглядеть включённым, но не применяться из-за bypass list, неактивного статуса или несовпадения имени ветки.

#### Шаг 3.1: Попытка прямого push в защищённую ветку (7 мин)

**Что сделать.** Любой участник команды (не обязательно Admin):

```bash
git checkout main
git pull origin main
git commit --allow-empty -m "chore: verify branch protection"
git push origin main
```

Пустой коммит (`--allow-empty`) используется намеренно: не нужно создавать файлы, команда одинаково работает в PowerShell, cmd, bash и zsh, и откатывать потом нечего, кроме самого коммита.

**Ожидаемый вывод — вариант для rulesets:**

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote:
remote: - Changes must be made through a pull request.
remote:
To https://github.com/<team>/<repo>.git
 ! [remote rejected] main -> main (push declined due to repository rule violations)
error: failed to push some refs to 'https://github.com/<team>/<repo>.git'
```

**Ожидаемый вывод — вариант для классического branch protection:**

```
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.
To https://github.com/<team>/<repo>.git
 ! [remote rejected] main -> main (protected branch hook declined)
error: failed to push some refs to 'https://github.com/<team>/<repo>.git'
```

**Если push прошёл успешно** — защита не работает. Диагностика по порядку:

| Симптом | Причина | Что сделать |
|---|---|---|
| Push прошёл у всех | Ruleset в статусе `Disabled` или `Evaluate` | Settings → Rules → Rulesets → открыть → `Enforcement status` → `Active` |
| Push прошёл только у владельца репозитория | Владелец в Bypass list / нет галочки `Do not allow bypassing` | Очистить Bypass list либо поставить галочку |
| Push прошёл, правило видно как активное | Правило нацелено не на ту ветку | Проверить `Target branches`: default-ветка у вас может называться `master` |
| Ошибка про отсутствие прав, а не про PR | Вы не контрибьютор репозитория | Принять приглашение в Settings → Collaborators |

Исправьте и повторите push, пока не получите отказ. **Коммит пока не откатывайте** — он нужен на шаге 3.2.

**Что должно получиться:** push отклонён сервером, локально есть один лишний пустой коммит поверх `origin/main`.

#### Шаг 3.2: Проверка запрета force-push и удаления ветки (3 мин)

**Проверка force-push.** Амендим тот же пустой коммит, чтобы изменился его SHA, и пробуем переписать историю:

```bash
git commit --amend --no-edit
git push --force origin main
```

Без `--amend` эта проверка бессмысленна: SHA не изменился бы, и git ответил бы `Everything up-to-date`, не обратившись к правилам сервера вообще.

**Ожидаемый вывод:** отказ, в котором перечислены **все** нарушенные правила. Для rulesets список выглядит так:

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote:
remote: - Cannot force-push to this branch
remote: - Changes must be made through a pull request.
```

Доказательством правила `Block force pushes` является именно строка `Cannot force-push to this branch`: обычный push отклоняется правилом про PR, а эта строка появляется только из-за запрета force-push.

**Про удаление ветки — важное ограничение проверки.** Команда

```bash
git push origin --delete main
```

**не является проверкой правила `Restrict deletions`.** GitHub запрещает удалять default-ветку репозитория сам по себе, независимо от того, включены ли у вас какие-либо правила. Отказ придёт и при полностью выключенном ruleset, выглядит он примерно так:

```
 ! [remote rejected] main (refusing to delete the current branch: refs/heads/main)
```

Что с этим делать:

- **GitFlow:** у вас есть вторая защищённая ветка, которая не является default. Проверьте правило на ней: `git push origin --delete develop`. Вот этот отказ (`GH013 … Cannot delete this branch` либо `GH006 … Cannot delete this protected branch`) действительно доказывает, что `Restrict deletions` работает. После проверки убедитесь, что ветка на месте: `git ls-remote --heads origin develop`
- **GitHub Flow и Trunk-Based:** правило `Restrict deletions` у вас включено, но экспериментом на этой практике не проверяется — защищённая ветка одна и она же default. Так и запишите в чек-листе: «включено, проверке на default-ветке не поддаётся». Проверить получится в модуле 2, когда появится вторая долгоживущая ветка

**Откат локальной истории — после обеих проверок:**

```bash
git reset --hard origin/main
git status
git log --oneline -1
```

**Что должно получиться:** force-push отклонён; `git status` показывает чистое дерево; `git log --oneline -1` показывает тот же коммит, что и на GitHub, — пустого коммита `chore: verify branch protection` в истории нет.

#### Шаг 3.3: Зафиксировать доказательство (2 мин)

Сделайте скриншот терминала с текстом отказа (достаточно одного — с результатом шага 3.1). Он понадобится:

- команде-ревьюеру на этапе 5 (проверка, что защита действительно включена)
- преподавателю при фиксации прогресса на этапе 7
- вам самим при защите проекта как доказательство пункта DoD «все изменения в `main` только через PR»

Сохраните скриншот в рабочую копию как `docs/branch-protection-check.png` — он войдёт в PR на шаге 4.3. Альтернатива, если со скриншотами возни больше, чем пользы: вставьте текст отказа блоком кода в `CONTRIBUTING.md`, в раздел «Защита ветки».

### Этап 4: Шаблон PR и регламент ревью в `CONTRIBUTING.md` (35 мин)

Здесь вы проходите **первые циклы PR при уже включённой защите**. Работа идёт в **двух независимых ветках и двух независимых PR** — они меняют разные файлы и друг другу не мешают:

| Ветка | Файл | Кто |
|---|---|---|
| `docs/pr-template` | `.github/pull_request_template.md` | Автор PR-шаблона |
| `docs/contributing-rules` | `CONTRIBUTING.md`, `docs/branch-protection-check.png` | Автор регламента |

Обе ветки создаются от свежего `main`. Совместная работа двух человек в одной ветке на этой практике не нужна и только создаст проблемы с синхронизацией.

Этап 4 идёт **после** этапа 3, а не параллельно ему: в `CONTRIBUTING.md` записывается фактический текст отказа и фактический состав правил, полученные на этапах 2–3.

Параллельно с этим этапом «Автор ADR» выполняет шаг 5.1 — см. «Точки синхронизации».

#### Шаг 4.1: Создать `.github/pull_request_template.md` (12 мин)

```bash
git checkout main
git pull origin main
git checkout -b docs/pr-template      # имя — по вашим правилам из ADR
mkdir -p .github
```

Создать файл `.github/pull_request_template.md`. Ниже заготовка — **перепишите её под свою команду**, шаблон должен отражать ваш чек-лист ревью, а не этот текст:

````markdown
## Тип изменения

- [ ] feat — новая функциональность
- [ ] fix — исправление бага
- [ ] docs — документация

- [ ] chore — инфраструктура, зависимости, конфигурация

## Связанные задачи

Closes #

## Как проверить

<!-- Команды, которые ревьюер выполнит, чтобы убедиться, что изменение работает. -->

```bash

```

Ожидаемый результат:

- [ ] Ветка названа по правилам из `CONTRIBUTING.md`
- [ ] Сообщения коммитов — Conventional Commits

- [ ] Документация обновлена, если менялось поведение
- [ ] Приложение запускается локально, `GET /health` отвечает `200`

## Чек-лист ревьюера

- [ ] Изменение соответствует описанию в PR
- [ ] Нет закомментированного и отладочного кода
- [ ] Имена понятны, магические числа вынесены
- [ ] Изменение не ломает существующие эндпоинты
- [ ] Замечания оформлены как комментарии к конкретным строкам
````

**Что должно получиться:** файл лежит по пути `.github/pull_request_template.md` (именно в папке `.github`, имя в нижнем регистре). Проверка пути:

```bash
ls -la .github/pull_request_template.md
```

**Важная особенность.** GitHub берёт шаблон PR **из базовой ветки**, то есть из `main`. Поэтому к самому этому PR шаблон ещё не применится — он заработает начиная со следующего PR, созданного после merge. Это ожидаемо, не считайте ошибкой.

#### Шаг 4.2: Обновить `CONTRIBUTING.md` (15 мин)

```bash
git checkout main
git pull origin main
git checkout -b docs/contributing-rules
```

**Что сделать.** Довести `CONTRIBUTING.md` до состояния, в котором по нему может работать человек, не участвовавший в вашем обсуждении.

**Правило правки:** разделы, созданные на практике №1 («Встречи команды», «Разрешение конфликтов», «Контакты»), **не удалять**. Их содержимое можно уточнять, но сами разделы остаются: они входят в требования [DoD, раздел 7](../../definition-of-done.md), и их исчезновение засчитывается как регресс.

Обязательные разделы и критерий «сформулировано проверяемо»:

| № | Раздел | Что должно быть | Проверяемо, если… |
|---|---|---|---|
| 1 | Стратегия ветвления | Название стратегии + ASCII-схема веток из ADR 001 | По схеме видно, от какой ветки создаётся фича и куда она вливается |
| 2 | Правила именования веток | Шаблон имени и 3–4 примера | По шаблону можно однозначно назвать ветку для задачи «добавить эндпоинт /version» |
| 3 | Правила коммитов | Список типов Conventional Commits + 2 примера из вашего репозитория | Пример можно найти в `git log` |
| 4 | Регламент code review | Кто назначается ревьюером, срок ответа в часах, что делает автор с комментариями | Названы конкретные сроки, а не «оперативно» |
| 5 | Критерии approval | Список условий, при которых ревьюер ставит Approve | Каждое условие проверяется по PR без обсуждения с автором |
| 6 | Разрешение конфликтов в коде | Порядок действий при конфликте PR с `main` (см. врезку ниже) | По тексту можно выполнить последовательность команд, не спрашивая автора |
| 7 | Защита ветки | Какие правила включены, текст отказа из шага 3.1, TODO по CI из шага 2.2 | Совпадает с фактическими настройками из этапа 2 |
| 8 | Контакты команды | Имя, роль и способ связи каждого участника; канал команды; время ответа | Стороннему человеку понятно, кому писать по какому вопросу |

Разделы 1–6 и 8 можно писать сразу. Разделы 7 заполняется данными, полученными на этапах 2–3: фактический список включённых правил и скопированный текст отказа.

Формулировки «ревьюер проверяет качество кода» и «мержим, когда всё хорошо» не проходят критерий проверяемости. Рабочие формулировки выглядят так:

```markdown
### Критерии approval

Ревьюер ставит Approve, только если выполнено всё:

1. Чек-лист автора в PR заполнен полностью
2. Ветка названа по шаблону из раздела «Именование веток»
3. Все коммиты в PR начинаются с типа Conventional Commits
4. В diff нет `.env`, ключей, паролей, токенов
5. Локальный запуск по инструкции из раздела «Как проверить» даёт описанный результат
6. Все комментарии предыдущих кругов ревью отвечены и закрыты

Если хотя бы один пункт не выполнен — Request changes с указанием номера пункта.

### Регламент code review

- Ревьюер назначается автором PR при создании, из числа участников команды
- Автор PR не может одобрить собственный PR — approval всегда ставит другой участник
- Срок первого ответа ревьюера: 24 часа с момента создания PR
- Автор отвечает на каждый комментарий: правкой либо аргументом, почему правка не нужна
- Комментарий закрывает (Resolve) тот, кто его оставил, а не автор PR
- Два круга «Request changes» без сближения позиций — вопрос выносится на встречу команды
```

**Что должно получиться:** `CONTRIBUTING.md` содержит все восемь разделов, разделы практики №1 на месте, и в нём нет ни одного правила, которое нельзя проверить, открыв PR.

> **Если PR конфликтует с `main`.** Пока вы работали в своей ветке, в `main` мог попасть чужой PR. GitHub покажет `This branch has conflicts that must be resolved`. Порядок действий:
>
> ```bash
> git checkout docs/contributing-rules
> git fetch origin
> git merge origin/main
> # git сообщит, в каких файлах конфликт
> ```
>
> Открыть конфликтующий файл, найти блоки `<<<<<<<`, `=======`, `>>>>>>>`, оставить нужный вариант (часто — оба фрагмента подряд, если правки не пересекаются по смыслу), удалить сами маркеры. Затем:
>
> ```bash
> git add <файл>
> git commit -m "merge: resolve conflict with main"
> git push
> ```
>
> **После этого approval сбрасывается** — у вас включено `Dismiss stale pull request approvals when new commits are pushed`, а разрешение конфликта это новый коммит. Нужно запросить ревью заново (кнопка **Re-request review**). Это не сбой, а смысл правила: ревьюер одобрял не тот код, который получился после merge.
>
> Не решайте конфликт через `git push --force`: force-push в ветку PR правилами не запрещён, но он ломает ссылки на комментарии ревью, и ревьюер теряет контекст обсуждения.

#### Шаг 4.3: Провести оба PR через ревью и merge (8 мин)

**PR №1 — шаблон PR:**

```bash
git checkout docs/pr-template
git add .github/pull_request_template.md
git commit -m "docs: add pull request template"
git push -u origin docs/pr-template
```

**PR №2 — регламент:**

```bash
git checkout docs/contributing-rules
git add CONTRIBUTING.md docs/branch-protection-check.png
git commit -m "docs: add branching and code review rules to CONTRIBUTING"
git push -u origin docs/contributing-rules
```

Если скриншот вы не делали и текст отказа вставили прямо в `CONTRIBUTING.md` — из `git add` уберите `docs/branch-protection-check.png`, иначе git ответит `pathspec ... did not match any files`.

Дальше на GitHub, для каждого PR:

1. Баннер **Compare & pull request** → **Create pull request**
2. Заголовок — то же сообщение, что у коммита
3. В описании — что меняется и почему (шаблона здесь ещё нет, см. примечание в шаге 4.1)

6. **Merge pull request**

Сначала мержится PR со шаблоном — тогда второй PR, если понадобится его переоткрыть, уже подхватит шаблон.

**Что должно получиться:**

- До approval кнопка merge серая, GitHub пишет `Review required` — это работает защита из этапа 2
- После merge оба файла видны в `main`
- Открытие любого нового PR автоматически подставляет ваш шаблон в поле описания (проверите на этапе 5)

```bash
git checkout main
git pull origin main
ls .github/pull_request_template.md
grep -c "^#\{2,3\} " CONTRIBUTING.md   # должно быть не меньше 8 — по числу разделов
```

### Этап 5: Межкомандное ревью ADR 001 и приёмка (45 мин)

Два потока работы идут одновременно: **Автор ADR** готовит и правит свой документ, **Внешний ревьюер** разбирает ADR другой команды. Не ждите друг друга.

**Как это оценивается.** Межкомандное ревью на этой практике оценивается по схеме **зачёт / незачёт**, баллы за него не начисляются. Зачёт ставится, если выполнены все три условия:

1. Вы оставили ревью ADR назначенной команды: минимум три содержательных замечания, привязанных к строкам, со ссылкой на пункты чек-листа
2. Вы вынесли вердикт (Request changes, затем после правок — Approve), а не ограничились комментариями
3. Ваш собственный ADR смержен со статусом «Принято» и с учтёнными замечаниями

Незачёт закрывается доработкой до следующего занятия. Балльная оценка peer review появляется в конце курса, на защите проектов, по [системе 360°](../../assessment.md) — этот этап тренирует навык, который там оценивается, но в итоговую формулу сам по себе не входит.

#### Шаг 5.1: Довести ADR и открыть PR (15 мин, идёт параллельно с этапом 4)

```bash
git checkout main
git pull origin main
git checkout -b docs/adr-001-branching-strategy
mkdir -p docs/adr
```

**Что сделать.** Привести `docs/adr/001-branching-strategy.md` в состояние, пригодное для ревью. Действия зависят от вашей ситуации из раздела «Где сейчас ваш ADR»:

- **A** — перенести локальный файл в репозиторий и дозаполнить
- **B** — файл уже в `main`, вы его дорабатываете; содержимым PR станет именно доработка
- **C, D** — заполняете с нуля по [шаблону](../../workshops/workshop2/adr-template.md), ориентир — [пример](../../workshops/workshop2/adr-example.md)

Целевое состояние: заполнены все разделы шаблона — Статус, Дата, Участники, Контекст, Рассмотренные варианты (все три), Решение со схемой и правилами, Обоснование, Последствия (положительные и отрицательные), Риски и митигация, Источники, История изменений.

Статус на этом шаге — **«Предложено»**. На «Принято» вы его поменяете на шаге 5.4, после ревью, и это изменение войдёт в тот же PR.

> **Открывайте PR вовремя, даже если ADR неполон.** К 75-й минуте PR должен быть открыт — это точка синхронизации, от неё зависит работа команды-ревьюера, которая без вашего PR просто простаивает. Если к этому моменту часть разделов пуста, откройте PR с тем, что есть, и в описании PR перечислите, какие разделы вы дописываете прямо сейчас. Ревьюер начнёт с готовых разделов, а незаполненные станут его первыми замечаниями — это нормальный ход ревью, а не провал. Опоздание с открытием PR хуже неполного PR.

```bash
git add docs/adr/001-branching-strategy.md
git commit -m "docs: complete ADR 001 on branching strategy"
git push -u origin docs/adr-001-branching-strategy
```

Создать PR. **Проверка:** поле описания PR должно автоматически заполниться вашим шаблоном из этапа 4 — если этого не произошло, проверьте, смержен ли PR №1, и путь с именем файла в шаге 4.1.

Заполнить шаблон, затем назначить ревьюеров:

- **Reviewers** → сокомандник (его approval засчитывается в branch protection; себя назначить нельзя)
- **Reviewers** → ревьюер из команды-ревьюера. Если GitHub не даёт его выбрать — просто пришлите ссылку на PR; на публичном репозитории любой пользователь GitHub может оставить ревью и комментарии
- Ссылку на PR отправить команде-ревьюеру и преподавателю

> **Про approvals из другой команды.** В защите ветки засчитываются approval'ы от пользователей с правом записи в репозиторий. Ревью от стороннего пользователя видно в PR и учитывается вами содержательно, но кнопку merge разблокирует approval сокомандника. Если хотите, чтобы approval внешнего ревьюера тоже засчитывался, добавьте его в Settings → Collaborators с ролью **Write** — и обсудите это решение в команде: вы даёте другой команде право записи в свой репозиторий.

#### Шаг 5.2: Провести ревью чужого ADR (15 мин)

**Что сделать.** Открыть PR команды, которую вы ревьюите, вкладка **Files changed**. Пройти по чек-листу ниже, оставляя комментарии **к конкретным строкам** (наведение на строку → синий плюс → комментарий → `Start a review`).

**Чек-лист межкомандного ревью ADR 001**

| № | Что проверяем | Признак выполнения |
|---|---|---|
| 1 | Контекст | Названы размер команды, опыт участников с Git, частота релизов, требования к стабильности основной ветки. Не общие слова, а цифры и факты |
| 2 | Полнота вариантов | Разобраны все три стратегии: GitFlow, GitHub Flow, Trunk-Based. У каждой минимум по 2 плюса и 2 минуса |
| 3 | Честность минусов | У выбранной стратегии перечислены её реальные минусы, а не «минусов нет» |
| 4 | Схема ветвления | Есть схема, по которой видно, от какой ветки создаётся фича и куда вливается. Схема соответствует названной стратегии |
| 5 | Правила работы | Минимум 5 правил. Каждое сформулировано так, что по нему можно проверить конкретный PR |
| 6 | Именование веток | Задан шаблон имени с примерами. По шаблону можно однозначно назвать новую ветку |
| 7 | Связь обоснования с контекстом | Каждый аргумент в «Обосновании» опирается на факт из «Контекста», а не на общие свойства стратегии |
| 8 | Отрицательные последствия | Раздел заполнен, содержит минимум 2 пункта |
| 9 | Риски и митигация | Таблица, минимум 3 строки, в колонке «Митигация» — действие, а не намерение |
| 10 | Соответствие DoD, раздел 1 | Из правил ADR следует: merge в основную ветку только через PR, минимум 1 approval, применяется стратегия ветвления |
| 11 | Согласованность с настройками | Правила ADR совпадают с фактическим ruleset репозитория и с `CONTRIBUTING.md`. Откройте их и сверьте |
| 12 | Оформление | Заполнены Статус, Дата, Участники, История изменений. Ссылки в «Источниках» открываются |

**Обязательный минимум:** не менее **трёх** содержательных замечаний с указанием номера пункта чек-листа. «Всё хорошо» ревью не является: в ADR, написанном за 10 минут воркшопа, всегда есть что уточнить.

**Вердикт.** Первый круг ревью на этой практике **всегда** завершается **Request changes** — это тренировка цикла доработки, а не оценка качества документа. Оформление: **Review changes** → выбрать `Request changes` → в поле резюме написать, что именно должно измениться, чтобы вы поставили Approve → **Submit review**.

**Шаблон резюме ревью:**

```markdown
Ревьюер: команда [название]

Что хорошо:
- [1-2 пункта]

Что нужно исправить до Approve:
1. п.[N] чек-листа — [что не так] — [что сделать]
2. п.[N] чек-листа — [что не так] — [что сделать]
3. п.[N] чек-листа — [что не так] — [что сделать]

Открытые вопросы (не блокируют merge):
- [вопрос]
```

#### Регламент: что делать, если ревьюер и автор не согласны

Разногласие — нормальная часть ревью, отдельного времени в тайминге на него не заложено. Порядок разрешения:

1. **Автор отвечает на каждый комментарий** — правкой либо аргументом, почему правка не нужна. Молча проигнорированный комментарий блокирует merge: у вас включено `Require conversation resolution`
2. **Второй круг.** Ревьюер либо соглашается и ставит Approve, либо повторяет Request changes с уточнённой формулировкой
3. **Разногласие пережило два круга** — оно не решается перепиской. Автор дописывает его в раздел «Риски и митигация» ADR отдельной строкой: риск, позиция ревьюера, что команда будет делать, если риск реализуется. Ревьюер после этого ставит Approve: зафиксированное разногласие полезнее заблокированного PR
4. **Принципиальное расхождение** (ревьюер считает, что решение противоречит DoD) — зовите преподавателя. Формат разбора: по 2 минуты на позицию каждой стороны, решение преподавателя, запись итога в «Историю изменений» ADR с указанием обеих позиций

Чего делать нельзя: закрывать чужие комментарии без ответа, менять вердикт ревью «по дружбе», ставить Approve документу, который вы не открывали.

#### Шаг 5.4: Внести правки и довести ADR до статуса «Принято» (15 мин)

1. Разобрать замечания команды-ревьюера, ответить на каждый комментарий в PR
2. Внести правки в ADR
3. Изменить **Статус** на `Принято`
4. Дописать строку в «Историю изменений»:

```markdown
| 2026-XX-XX | Принято | Учтены замечания команды [название] по пп. 1, 5, 9 чек-листа ревью | [имя] |
```

5. Закоммитить и запушить:

```bash
git add docs/adr/001-branching-strategy.md
git commit -m "docs: address review comments on ADR 001"
git push
```

6. Запросить повторное ревью: кнопка **Re-request review** рядом с именем ревьюера
7. Ревьюер проверяет правки → **Approve**
8. Сокомандник ставит **Approve** (если его approval был сброшен новыми коммитами — из-за `Dismiss stale approvals` — поставить заново)
9. **Merge pull request**

**Что должно получиться:**

- В `main` лежит `docs/adr/001-branching-strategy.md` со статусом «Принято»
- В PR видна история: Request changes → коммит с правками → Approve → merged
- Все комментарии ревью закрыты (`Resolve conversation`)
- Ветка `docs/adr-001-branching-strategy` удалена после merge

```bash
git checkout main
git pull origin main
grep -i -m 2 "Принято" docs/adr/001-branching-strategy.md
```

### Этап 6: Полный цикл PR на кодовой задаче (28 мин)

ADR — документ. Теперь тот же процесс проходится на изменении кода, в том темпе, в котором вы будете работать весь семестр.

#### Шаг 6.1: Взять задачу и создать ветку (5 мин)

**Задача по умолчанию:** добавить эндпоинт `GET /version`, возвращающий версию приложения и имя команды. Если у вас уже есть своя задача по проекту — берите её, эта нужна только чтобы не тратить время на выдумывание.

```bash
git checkout main
git pull origin main
git checkout -b feature/version-endpoint   # имя — строго по вашим правилам именования
```

**Что должно получиться:** имя ветки соответствует шаблону из `CONTRIBUTING.md`. Если не соответствует — либо переименуйте ветку, либо признайте, что шаблон нерабочий, и поправьте `CONTRIBUTING.md` (второе — нормальный результат практики, зафиксируйте это отдельным коммитом в той же ветке).

Для GitFlow: ветка создаётся от `develop`, а не от `main`, и PR открывается в `develop`.

#### Шаг 6.2: Изменение, локальная проверка, коммиты (5 мин)

В `main.py` версия приложения уже задана — в конструкторе `FastAPI(..., version="0.1.0")`. Второй константы заводить не нужно: FastAPI отдаёт это значение как `app.version`, и оно же попадает в OpenAPI-схему на `/docs`. Две копии версии неизбежно разъедутся.

Поднять версию в конструкторе и добавить эндпоинт:

```python
app = FastAPI(
    title="Project Name",
    description="Project description",
    version="0.2.0",          # было 0.1.0
)

TEAM_NAME = "название-вашей-команды"


@app.get("/version")
async def version():
    """Версия приложения и команда-владелец."""
    return {"version": app.version, "team": TEAM_NAME}
```

**Локальная проверка.** Сервер занимает терминал, поэтому нужны два окна:

- **Окно 1** — активировать виртуальное окружение и запустить сервер:

```bash
# Windows PowerShell
venv\Scripts\Activate.ps1
# macOS / Linux
source venv/bin/activate

uvicorn main:app --reload
```

- **Окно 2** — проверить эндпоинт. Либо просто открыть в браузере `http://localhost:8000/version`, либо из терминала:

```bash
# macOS / Linux
curl http://localhost:8000/version

# Windows PowerShell: curl — это алиас Invoke-WebRequest с другим синтаксисом,
# поэтому вызываем настоящий curl явно
curl.exe http://localhost:8000/version
```

**Ожидаемый вывод:**

```json
{"version":"0.2.0","team":"название-вашей-команды"}
```

Заодно откройте `http://localhost:8000/docs` — версия `0.2.0` должна быть видна в заголовке схемы. Это и есть проверка, что версия действительно одна.

**Обновить `README.md`.** Ваш же чек-лист автора в PR требует обновлять документацию при изменении поведения. Новый эндпоинт — изменение поведения: допишите `GET /version` в раздел README с описанием API (если раздела нет — заведите его, это требование [DoD, раздел 7](../../definition-of-done.md)).

```bash
git add main.py README.md
git commit -m "feat: add version endpoint"
git push -u origin feature/version-endpoint
```

**Что должно получиться:** `git log --oneline -1` показывает сообщение, начинающееся с типа Conventional Commits.

#### Шаг 6.3: PR, ревью другой командой, merge (18 мин)

1. Создать PR. Шаблон подставляется автоматически — заполнить **все** его разделы, включая «Как проверить» с рабочей командой запуска
2. Назначить ревьюером сокомандника и отправить ссылку команде-ревьюеру
3. Команда-ревьюер проверяет по чек-листу ревьюера из вашего PR-шаблона и по разделу «Критерии approval» вашего `CONTRIBUTING.md` — то есть по **вашим** правилам, а не по своим. Это проверка того, что ваш регламент вообще пригоден для использования посторонним. Отдельно ревьюер проверяет пункт про документацию: обновлён ли README
4. Автор отвечает на комментарии, при необходимости дорабатывает
5. Approve от сокомандника → **Merge pull request** → удалить ветку

**Что должно получиться:**

```bash
git checkout main
git pull origin main
grep -n "version" main.py
grep -n "/version" README.md
```

Эндпоинт и его описание в README попали в `main` только через PR, в PR видна цепочка «ревью → ответы автора → approval → merge».

#### Если время кончается

Этап 6 — единственный, который можно перенести в домашнее задание без потерь: branch protection, PR-шаблон, регламент и принятый ADR к этому моменту уже готовы. Сообщите преподавателю на этапе 7, что цикл на кодовой задаче доделываете дома, и доведите его до merge **до следующего занятия**.

#### Если вы закончили раньше (бонусные задачи)

Берите по порядку, каждая — отдельный PR:

1. **`CODEOWNERS`.** Создать файл `.github/CODEOWNERS` со строками вида `docs/ @login1 @login2` и `*.py @login3`. В ruleset включить `Require review from Code Owners`.
   **Обязательное условие:** каждый логин в файле должен иметь право записи (роль Write или выше) на репозиторий. Логин без write-доступа GitHub просто игнорирует — правило при этом не срабатывает и **не выдаёт ошибки**, вы об этом не узнаете. Проверьте Settings → Collaborators перед тем, как вписывать логины.
   **Проверка:** PR, меняющий файл в `docs/`, автоматически запрашивает ревью у указанных логинов; в блоке Reviewers появляется пометка Code Owner.
   **Как откатить, если правило заблокировало работу:** Settings → Rules → Rulesets → `protect-main` → снять `Require review from Code Owners` → Save. Сам файл `.github/CODEOWNERS` при этом можно оставить — без правила он работает как подсказка о том, кого звать на ревью.
2. **Шаблоны issue.** Создать `.github/ISSUE_TEMPLATE/bug_report.md` и `.github/ISSUE_TEMPLATE/feature_request.md` с полями «Шаги воспроизведения», «Ожидаемое поведение», «Фактическое поведение». **Проверка:** кнопка New issue предлагает выбор из двух шаблонов
3. **Auto-merge.** Settings → General → Pull Requests → включить `Allow auto-merge`. На PR нажать `Enable auto-merge`. **Проверка:** PR мержится сам сразу после получения недостающего approval
4. **Метки и связь PR с issue.** Завести метки `type:feat`, `type:fix`, `type:docs`, создать issue на следующую задачу проекта, в PR написать `Closes #N`. **Проверка:** issue закрывается автоматически при merge PR
5. **Защита тегов.** Отдельный ruleset с типом `Tag`, запрет удаления и перезаписи тегов — задел под семантическое версионирование релизов

### Этап 7: Самопроверка и фиксация у преподавателя (10 мин)

1. Команда проходит чек-лист самопроверки ниже и отмечает пункты
2. Преподаватель обходит команды и фиксирует: название команды, стратегию ветвления, ссылку на репозиторий, ссылку на смерженный PR с ADR, кого ревьюили и кто ревьюил, статус по чек-листу
3. Незакрытые пункты чек-листа называются вслух и попадают в домашнее задание

## Чек-лист для преподавателя

Роль преподавателя в репозиториях команд — **Write** (выдана на практике №1). Раздел Settings → Rules при этой роли недоступен, поэтому проверки ниже построены на том, что видно с правом записи.

| Что проверяем | Как проверяем | Признак выполнения |
|---|---|---|
| Защита ветки включена | Открыть в браузере `https://api.github.com/repos/<owner>/<repo>/rules/branches/main` — публичный REST-эндпоинт, аутентификация для публичного репозитория не нужна | Возвращается непустой массив правил; среди `type` есть `pull_request`, `non_fast_forward`, `deletion` |
| Число обязательных approval | Тот же ответ API, объект с `"type": "pull_request"` | В `parameters` поле `required_approving_review_count` равно 1 (или тому, что записано в ADR) |
| Защита реально работает | Попробовать самому: `git push origin main` пустым коммитом в клоне репозитория команды | Push отклонён с `GH013`/`GH006`. Дополнительно — скриншот команды из шага 3.3 |
| Требование approval | Открыть любой смерженный PR команды | В PR есть блок Reviewers с как минимум одним Approve до merge, и approve поставил не автор PR |
| Прямых push нет | `git log --first-parent --oneline --since=<дата практики №2> main` | Все коммиты после даты практики — merge-коммиты PR либо squash-коммиты с номером PR. Коммиты практики №1 не учитываются: защиты тогда ещё не было |
| Шаблон PR применяется | Открыть последний созданный PR команды | Описание PR содержит структуру шаблона, разделы заполнены, а не пусты |
| Шаблон PR не скопирован вслепую | Сравнить `.github/pull_request_template.md` с образцом из инструкции | Есть минимум 2 пункта, отражающие специфику проекта команды |
| `CONTRIBUTING.md` обновлён | Открыть файл в `main` | Есть все 8 разделов, включая «Контакты команды»; разделы практики №1 не удалены; сроки ревью указаны в часах |
| Согласованность документов | Сверить правила ADR 001, `CONTRIBUTING.md` и ответ API про ruleset | Число approvals, имена веток и защищаемые ветки совпадают во всех трёх источниках |
| ADR принят | `docs/adr/001-branching-strategy.md` в `main` | Статус «Принято», заполнены риски и отрицательные последствия |
| ADR прошёл межкомандное ревью | Открыть PR с ADR, вкладка Conversation | Есть ревью от участника другой команды, минимум 3 комментария, вердикт Request changes на первом круге |
| Отклонённый PR отработан | Тот же PR, история событий | Виден порядок: Request changes → новый коммит → Approve → merged |
| Качество ревью команды | Открыть PR команды, которую они ревьюили | Комментарии привязаны к строкам, ссылаются на пункты чек-листа, содержат предложение исправления |
| Разногласия разрешены по регламенту | Комментарии в PR и раздел «Риски» ADR | Либо все комментарии закрыты с ответами, либо разногласие вынесено в «Риски» с позицией обеих сторон |
| Цикл на кодовой задаче пройден | `main.py` и `README.md` в `main`; PR, которым они пришли | В `main.py` есть `@app.get("/version")` и `version="0.2.0"` в конструкторе, отдельной константы версии нет; в `README.md` описан `GET /version`; изменение пришло через PR с ревью |

### 1. Закрыть незавершённое

Довести до merge всё, что не успели на занятии: цикл PR на кодовой задаче, незакрытые комментарии ревью, пункты чек-листа самопроверки, отмеченные преподавателем.

**Критерий успеха:**

- [ ] В репозитории нет открытых PR, созданных на практике
- [ ] Все комментарии ревью закрыты
- [ ] Чек-лист самопроверки закрыт полностью

**Дедлайн:** 3 дня после практики.

### 2. Цикл PR каждым участником

Участники, которые на практике не были авторами PR, создают собственный PR с небольшим осмысленным изменением и проводят его через ревью и merge. Не годится: правка пробелов, коммит «fix», изменение одной буквы ради галочки.

**Критерий успеха:**

- [ ] У каждого участника команды есть минимум 1 смерженный PR
- [ ] Каждый PR заполнен по шаблону и получил approval от другого участника
- [ ] Имена всех веток соответствуют шаблону из `CONTRIBUTING.md`

**Дедлайн:** к началу воркшопа №3.

### 3. Отзыв команде-ревьюеру

Написать команде, которая ревьюила ваш ADR, отзыв (5–7 предложений) комментарием в вашем PR с ADR: какие замечания оказались полезными и что вы по ним изменили, какие были формальными и почему, что вы сами изменили в своём подходе к ревью, побывав в обеих ролях.

**Критерий успеха:**

- [ ] Отзыв опубликован комментарием в PR, а не отправлен в личный чат
- [ ] Названы конкретные замечания, а не «спасибо, всё было полезно»
- [ ] Отзыв подписан названием команды

**Дедлайн:** 3 дня после практики.

### 4. Согласовать три источника правды

Проверить, что правила работы с ветками записаны одинаково в трёх местах: `docs/adr/001-branching-strategy.md` (раздел «Решение»), `CONTRIBUTING.md` (разделы 1, 2, 5) и настройки репозитория (Settings → Rules → Rulesets). Расхождения устранить отдельным PR с сообщением `docs: align branching rules across ADR, CONTRIBUTING and repo settings`.

**Критерий успеха:**

- [ ] Число обязательных approval одинаково во всех трёх источниках
- [ ] Список защищаемых веток одинаков в ADR и настройках
- [ ] Шаблон имён веток из `CONTRIBUTING.md` совпадает с именами реально созданных веток

**Дедлайн:** к началу воркшопа №3.

### 5. Подготовиться к воркшопу №3

Изучить разосланные материалы по контейнеризации и установить Docker: Docker Desktop на Windows и macOS, Docker Engine на Linux. Проверить:

```bash
docker --version
docker compose version
docker run --rm hello-world
```

Ожидаемый вывод последней команды содержит `Hello from Docker!`. Проблемы установки (виртуализация в BIOS, WSL2 на Windows, группа `docker` на Linux) решаются до воркшопа — на занятии времени на установку не будет.

**Критерий успеха:**

- [ ] `docker run --rm hello-world` отрабатывает на машине каждого участника
- [ ] Материалы по контейнеризации прочитаны всеми участниками
- [ ] В `main` лежат: `.gitignore`, `README.md`, `CONTRIBUTING.md`, `.github/pull_request_template.md`, `docs/adr/001-branching-strategy.md` со статусом «Принято», приложение с `GET /`, `GET /health`, `GET /version`

**Дедлайн:** к началу воркшопа №3.
