# Практика №6: "Тесты, миграции, публикация образа в реестр, «Сломать и починить»"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Самостоятельная командная работа по письменной инструкции + «Сломать и починить» с проверкой диагноза другой командой + ретроспектива модуля 3  
**Роль преподавателя:** Модератор проверки диагнозов и ретроспективы, фиксация прогресса

---

## Цели практики

К концу занятия каждая команда должна:

1. **Добавить** зависимости тестов и миграций — `pytest`, `pytest-cov`, `httpx2` в dev-зависимости, `sqlalchemy` и `alembic` в основные — так, чтобы lock-файл вошёл в тот же коммит: `uv sync --locked` или `poetry check --lock` проходит; у Poetry `git grep -n alembic -- requirements.txt` находит строку
2. **Настроить** Alembic с минимальной таблицей основной сущности проекта: `alembic upgrade head --sql` без базы печатает `CREATE TABLE <ваша таблица>`; `ruff check`, `ruff format --check`, `mypy` и сканер секретов по ADR 003 на новых файлах чистые
3. **Реализовать** тесты по приложению А ADR 005 — минимум каждый эндпоинт, `/health` с `200` и `503`, «Миграции применились»: в логе джоба `test` шаги `Migrations` и `pytest` зелёные, строка `TOTAL` отчёта покрытия процитирована в PR
4. **Заменить** закомментированные `test`, `build`, `publish` текстом джобов курса по «Решению» ADR 005 и **включить** обязательные `test` и `build` после первого прогона (GitFlow — в обоих rulesets): в `ci.yml` нет строк `# test:` и «раскомментируете», во вкладке **Checks** PR у `test` и `build` пометка **Required**
5. **Опубликовать** образ: после merge в `main` в прогоне на `push` джоб `publish` зелёный, в **Packages** репозитория — тег `sha-<40 символов>`, равный SHA коммита в `main`. GitFlow — зелёный `build` на PR в `develop`, публикация — домашнее задание 2
6. **Диагностировать** две поломки по логу — хост базы в `env` джоба `test` и код, который читает столбец без миграции: в каждом PR-поломке до коммита починки есть предсказание, диагноз «джоб → шаг → строка лога → причина → починка» и цитата блока merge; после починки прогон зелёный
7. **Проверить** диагноз другой команды по логу её PR-поломки и оставить комментарий по формуле «где → что не так → чем грозит → что предлагаете» или доказанное «диагноз подтверждён: шаг и строка лога совпадают»; на каждое замечание к своим PR — ответ
8. **Довести** ADR 005 до статуса «Принято» (время `test` и `build` и процент покрытия — «(измерено)», отклонения от «Решения» с причиной), написать раздел «Как запустить тесты локально» в `CONTRIBUTING.md` (bash и PowerShell, на Windows — `127.0.0.1`) и строку «Уточнён ADR 005» в «Истории изменений» ADR 004; привести «Защиту ветки» `CONTRIBUTING.md` и ADR 001 к ruleset с `test` и `build`: `git grep -n "TODO" -- CONTRIBUTING.md` и `git grep -n "практике №6" -- CONTRIBUTING.md docs/adr/001*` выводят пустоту
9. **Оценить** модуль 3 на ретроспективе: issue «Ретроспектива модуля 3» с одним пунктом «Что меняем» и строкой «Как проверим на практике №7» — наблюдаемый факт, а не намерение

### Права доступа

Ограничения практик №2 и №5 действуют: прямой push в защищённые ветки отклоняется, автор PR не может одобрить свой PR, merge блокируют красные обязательные проверки. Добавить `test` и `build` в ruleset может только **владелец репозитория** (личный репозиторий) или участник с ролью Admin (репозиторий организации). У преподавателя в ваших репозиториях роль Write.

**Право `workflow` у токена** нужно и на этом занятии: PR меняет `.github/workflows/ci.yml` (шаг 4.3, шаг 8.1). На практике №5 push прошёл — значит, право есть. Сменили ноутбук водителя — проверьте по «Проверке перед стартом» практики №5.

**Публикация в реестр** идёт под токеном `GITHUB_TOKEN` прогона, отдельный токен или секрет не нужен: право записи даёт строка `packages: write` джоба `publish`. Репозиторий организации — публикацию packages разрешает владелец организации (ДЗ 4 воркшопа №6).

Для проверки чужого диагноза на этапе 9 нужен только доступ на чтение: репозитории публичные.

**Как читать таблицу.** Этапы 0–7 идут на одном ноутбуке. Каждый push в ветку PR запускает прогон на раннере GitHub: на PR — около 2 минут (`lint`, `test` и `build` идут друг за другом), на `push` в `main` с публикацией — около 3. Это цифры демо курса на uv; у Poetry прогон дольше: `lint` и `test` каждый ставят Poetry и зависимости, ориентир — время `lint` в вашем ADR 004. В начале занятия, когда пушат все команды, раннер может ждать в очереди. Пока идёт прогон, водитель не ждёт: штурман читает следующий шаг, автор документов пишет текст. Минуты этапов рассчитаны на то, что **автор документов работает параллельно с водителем**: с этапа 1 готовит описание PR с предсказанием (шаг 4.3), с этапа 3 — правки ADR 005, `CONTRIBUTING.md`, ADR 001 и ADR 004 (этап 6). Буфер разделён на две части. Первые 10 минут (110–120) — на отставание этапов 0–7: очередь раннеров, долгие прогоны у Poetry, ситуации C, E, F, G, Code owners, повторный approval, долгая первая сборка образа. Этап 8 начинается **не позже 120-й минуты** — от него зависит команда-рецензент. Последние 8 минут (157–165) — на хвосты этапов 8–9. **Ретроспектива начинается на 165-й минуте при любом состоянии PR.**

**Что обязательно на занятии, а что можно перенести.**

#### Шаг 0.3: Рабочая ветка и ветка ADR 005 (4 мин)

Имя рабочей ветки в инструкции — `feature/tests-and-build`. Если ваш `CONTRIBUTING.md` требует другое — по своим правилам.

**GitHub Flow и Trunk-Based** — ветка от `main`:

```bash
git checkout main
git pull origin main
git checkout -b feature/tests-and-build      # имя — по вашим правилам
```

**GitFlow** — ветка от `develop`, PR на шаге 4.3 открывается в `develop`:

```bash
git checkout develop
git pull origin develop
git checkout -b feature/tests-and-build
```

**Влить ветку ADR 005** (все ситуации, кроме C). Имя ветки — из списка `git branch -r` «Проверки перед стартом»:

```bash
git merge --no-edit -m "docs: include ADR 005 draft" origin/docs/adr-005-testing-and-build    # имя — как в списке
```

**Отправить рабочую ветку** (все ситуации, в том числе C):

```bash
git push -u origin HEAD
```

**Что должно получиться:** `git merge` выводит `Merge made by the 'ort' strategy.` или `Fast-forward` — при перемотке коммит не создаётся, это не ошибка; `git ls-files docs/adr` показывает файл ADR 005 (кроме ситуации C); вывод `git push` заканчивается строкой `branch 'feature/tests-and-build' set up to track 'origin/feature/tests-and-build'.` **Точка синхронизации 10.**

### Этап 1: Зависимости тестов и миграций (9 мин)

Джоб `test` ставит зависимости из lock-файла (`uv sync --locked`, Poetry — `poetry install`), поэтому pytest и Alembic попадают в проект и lock-файл до того, как появятся джобы. `pytest`, `pytest-cov` и `httpx2` нужны только для тестов — dev-зависимости. `sqlalchemy` и `alembic` — основные: миграции выполняются и в контейнере приложения (ДЗ 2), а dev-зависимостей в образе нет.

`httpx2` вместо `httpx` из [FastAPI: Testing](https://fastapi.tiangolo.com/tutorial/testing/): `TestClient` из Starlette 1.7 (она в lock-файлах ваших проектов) с `httpx` пишет в лог каждого прогона `StarletteDeprecationWarning` и сам советует `httpx2`; с `httpx2` тесты работают без предупреждения.

#### Шаг 1.1: Добавить зависимости (4 мин)

**Если uv:**

```bash
uv add --dev pytest pytest-cov httpx2
uv add sqlalchemy alembic
```

**Ожидаемый вывод** каждой команды заканчивается списком установленных пакетов: у первой среди них `+ httpx2==...`, `+ pytest==...`, `+ pytest-cov==...`, у второй — `+ alembic==...`, `+ sqlalchemy==...` (при подготовке инструкции: pytest 9.2.0, pytest-cov 7.1.0, httpx2 2.16.0, SQLAlchemy 2.1.8, Alembic 1.20.1; у вас версии могут быть новее). В `pyproject.toml` `sqlalchemy` и `alembic` появились в `dependencies`, три других пакета — в `[dependency-groups] dev` рядом с ruff и mypy.

**Если Poetry:**

```bash
poetry add --group dev pytest pytest-cov httpx2
poetry add sqlalchemy alembic
poetry export -f requirements.txt --output requirements.txt
```

**Ожидаемый вывод:** у каждой `poetry add` в конце `Writing lock file`; `poetry export` — без вывода. Экспорт обязателен: `Dockerfile` ставит зависимости образа из `requirements.txt`, и без него Alembic в образе не будет. Dev-группа в `requirements.txt` не попадает.

**Как проверить, что сработало:** `git status --short` показывает изменённые `pyproject.toml` и `uv.lock` (Poetry — `poetry.lock` и `requirements.txt`) и ничего больше. Poetry — `git grep -n -E "^(alembic|sqlalchemy)==" -- requirements.txt` находит две строки. pytest оказался в `dependencies` — вы забыли `--dev` / `--group dev`: «Если не работает → Зависимости и lock-файл».

#### Шаг 1.2: Настройки pytest и покрытия (2 мин)

Допишите в конец `pyproject.toml`:

```toml
[tool.pytest.ini_options]
pythonpath = ["."]

[tool.coverage.run]
source = ["."]
omit = ["tests/*", "migrations/*", "venv/*", ".venv/*"]
```

`pythonpath` нужен, чтобы тесты из папки `tests/` импортировали `main` из корня: без него pytest падает при сборе с `ModuleNotFoundError: No module named 'main'`. `[tool.coverage.run]` — то, что вы записали в п. 3 «Решения» ADR 005: кодом считаются модули приложения, тесты и миграции — нет. Записали в ADR другое (например, код в пакете `app/`) — `source` и `omit` по своему ADR. Что делают `source` и `omit` — [coverage.py: Specifying source files](https://coverage.readthedocs.io/en/latest/source.html), раздел **Execution** (3 мин).

Порог покрытия (`--cov-fail-under`) не ставьте: в CI — только отчёт, порог 60 % проверяется к защите (чек-лист перед защитой в [DoD](../../definition-of-done.md)).

#### Шаг 2.2: Адрес базы и пометки для сканера (6 мин)

Правит водитель, штурман сверяет с текстом ниже. Три файла.

**1. `alembic.ini`.** Найдите строку `sqlalchemy.url = driver://user:pass@localhost/dbname` (у Alembic 1.20 — строка 89) и замените её комментарием:

```ini
# sqlalchemy.url задаётся в migrations/env.py из DATABASE_URL
```

Адрес базы Alembic получит из модуля настроек (п. 2 ниже), строка в `alembic.ini` не используется. С ней detect-secrets не пропускает коммит: `driver://user:pass@...` для него — пароль в адресе.

**2. `migrations/env.py`** — две правки. В блок импортов, сразу после строки `from alembic import context`, добавьте:

```python
from sqlalchemy.engine import make_url

from settings import settings
```

Сразу после строки `config = context.config` — адрес базы из модуля настроек:

```python
config.set_main_option(
    "sqlalchemy.url",
    make_url(settings.database_url)
    .set(drivername="postgresql+psycopg")
    .render_as_string(hide_password=False)
    .replace("%", "%%"),
)
```

**python-dotenv** (`settings.py` без класса `Settings`, в коде `settings.DATABASE_URL`): в импортах вместо `from settings import settings` — `import settings`, в правке — `make_url(settings.DATABASE_URL)`. Имя поля другое — по своему `settings.py`.

`DATABASE_URL` остаётся в форме `postgresql://...`: в таком виде его принимает `psycopg.connect` в `/health`. Драйвер psycopg 3 для Alembic `make_url(...).set(drivername="postgresql+psycopg")` подставляет явно — так `env.py` не зависит от версии SQLAlchemy, и так, как вы записали в «Последствиях» ADR 005 (раздел 5.4 [материалов воркшопа №6](../../workshops/workshop6/workshop6-materials.md)). `.env.example`, `compose.yaml` и `env` джоба `test` не меняются.

**3. `migrations/script.py.mako`** — шаблон, из которого Alembic создаёт каждый файл миграции. Допишите пометку в конец двух строк:

```text
revision: str = ${repr(up_revision)}  # pragma: allowlist secret
down_revision: Union[str, Sequence[str], None] = ${repr(down_revision)}  # pragma: allowlist secret
```

detect-secrets принимает номер миграции вида `"48de1a805c45"` за секрет (`Hex High Entropy String`). Пометка в шаблоне попадает в каждую следующую миграцию, в том числе в ту, что вы создадите на этапе 8. Пометки нужны всем командам, и с gitleaks тоже: файлы останутся проходимыми, если команда сменит сканер.

**Что должно получиться:** `git grep --untracked -n "pragma" -- migrations/script.py.mako` — две строки; `git grep --untracked -n "driver://" -- alembic.ini` — пусто.

#### Шаг 2.3: Первая миграция (5 мин)

```bash
uv run alembic revision -m "create items table"      # Poetry: poetry run alembic ...; items — ваша таблица
```

**Ожидаемый вывод:** `Generating ...migrations/versions/<номер>_create_items_table.py ...  done`. Базы и `DATABASE_URL` для этой команды не нужно.

В созданном файле замените `pass` в функциях `upgrade()` и `downgrade()`. Имя таблицы и второго поля — ваши; второе поле — то, без которого сущность не имеет смысла (название, заголовок):

```python
def upgrade() -> None:
    """Upgrade schema."""
    op.create_table(
        "items",
        sa.Column("id", sa.Integer, primary_key=True),
        sa.Column("name", sa.String(100), nullable=False),
    )


def downgrade() -> None:
    """Downgrade schema."""
    op.drop_table("items")
```

Как устроены `op.create_table` и `sa.Column` — [Alembic: Tutorial](https://alembic.sqlalchemy.org/en/latest/tutorial.html), раздел **Create a Migration Script**. У команды уже есть модели SQLAlchemy (CRUD сделан раньше) — таблица миграции повторяет таблицу модели, автогенерацию на этом занятии не используйте.

**Как проверить, что сработало:** в начале файла строки `revision: str = '<номер>'  # pragma: allowlist secret` (двойные кавычки появятся после `ruff format` на шаге 2.4) и `down_revision: ... = None  # pragma: allowlist secret`. Пометок нет — шаблон поправлен после `alembic revision`: допишите их в файл миграции так же, как в шаге 2.2, п. 3.

#### Шаг 2.4: Линтеры, офлайн-проверка, коммит (4 мин)

Файлы, которые создаёт Alembic, не проходят ruff 0.17.1 (`I001`, `UP035`, `UP007` — порядок импортов и старый синтаксис типов). Исправления механические:

```yaml
      contents: read
      packages: write                   # только здесь: запись в реестр

        with:
          name: image
          path: ${{ runner.temp }}

          registry: ghcr.io

          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,format=long

      - name: Tag and push
        env:

        run: |
          for tag in $TAGS; do
            docker tag "app:${{ github.sha }}" "$tag"
            docker push "$tag"
          done
```

### Этап 5: Первый прогон, обязательные `test` и `build` (14 мин)

#### Шаг 5.1: Прочитать лог (8 мин)

PR → вкладка **Checks** → прогон `CI`. Граф прогона показывает порядок: `test` ждёт `lint` (если `needs: lint`), `build` — все три, `publish` пропущен. Как найти упавший шаг — [Using workflow run logs](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs), раздел **Viewing logs to diagnose failures**.

**Ожидаемый результат** зелёного прогона:

- `test`: в шаге `Initialize containers` поднимается сервис `postgres`; шаг `Migrations` — строка `Running upgrade  -> <номер>, create items table`; шаг `pytest` — таблица покрытия, строка `TOTAL` и `N passed`
- `build`: шаг `Build image` собирает образ по вашему `Dockerfile`; шаг `Upload image` пропущен — на PR образ не выгружается
- `publish` — пропущен (серый значок): он запускается только на `push` в `main`

На прогонах демо курса (uv) `test` шёл 21–26 секунд, `build` — 13–24, без учёта очереди; ваш образ может собираться дольше. У Poetry `test` дольше: установка Poetry и зависимостей добавит к нему примерно столько же, сколько идёт ваш `lint` (время — в ADR 004).

**Пока идёт прогон,** проверяющий закрывает старый PR с ADR 005 (в ситуации C его нет): **Close pull request** с комментарием `Вошло в #<номер нового PR>`, затем **Delete branch**. После включения обязательных `test` и `build` он ждал бы их без конца — в его ветке этих джобов нет.

Проверяющий публикует комментарий в PR:

```markdown

| Джоб | Результат | Время | Упавший шаг и строка лога (если красный) |
|---|---|---|---|
| lint | | | |
| secrets | | | |
| test | | | |
| build | | | |
| publish | пропущен | — | — |

Покрытие (строка TOTAL из лога pytest): `TOTAL ...`
Совпало с предсказанием: да / нет — [что не совпало и почему]
```

**Первый прогон красный** — комментарий публикуется **до правки**, в нём шаг и строка лога дословно; затем исправление отдельным коммитом и push. Частые причины — «Если не работает»: `Install dependencies` (lock-файл), `Migrations` (`env.py`, адрес базы), `pytest` (ожидаемое значение в тесте), `build` (ситуация E — action не разрешён). Ситуация E вместе с F — запишите в комментарии «`build` красный: actions `docker/*` не разрешены, исправление — ДЗ 1» и переходите к этапу 6.

#### Шаг 5.2: Добавить `test` и `build` в обязательные проверки (4 мин)

Только после первого прогона: до него поиск ruleset предлагает лишь строку «Add test · Any source», строка с источником **GitHub Actions** появляется, когда проверка хотя бы раз выполнилась в репозитории. Добавляет **владелец репозитория** из своего аккаунта (ситуация F — не сейчас: просьба войдёт в одно сообщение шага 6.3).

`publish` не добавляйте: на PR он пропущен по `if`, а пропущенный по условию джоб GitHub считает успешным — такая проверка ничего не проверяет. `build` и `test` обязательны оба: `build`, пропущенный из-за упавшего `test`, может не заблокировать merge сам — блокирует красный `test` ([Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), раздел **Handling skipped but required checks**, 5 мин).

**Что должно получиться:** в правиле ruleset четыре проверки — `lint`, `secrets`, `test`, `build`; в PR у `test` и `build` пометка **Required**. Сделайте скриншот правила.

**Ситуация F** — в комментарии к PR напишите «обязательные `test` и `build` — сообщением владельцу после шага 6.3» (владелец на связи) или «обязательные `test` и `build` — ДЗ 1, владелец недоступен» и переходите к шагу 5.3.

Обязательная проверка засчитывается только для **последнего** коммита PR. Во вкладке **Checks** у `lint`, `secrets`, `test`, `build` зелёные значки для последнего коммита; был красный прогон — его исправление запушено, новый прогон зелёный.

Опубликуйте комментарий:

```markdown

Прогон на голове PR: [ссылка] — зелёный
```

Ситуация F — в первой строке текст шага 5.2 вместо скриншота.

**Что должно получиться:** в блоке merge «All checks have passed»; **Merging is blocked** остаётся, пока нет approval. **Точка синхронизации 84.**


`items` и `item` замените всюду, а не только в SQL: путь, имя функции, запрос, тест (таблица `tickets` — `/tickets/statuses`, `ticket_statuses`, `FROM tickets`, `test_ticket_statuses`). Имена адреса базы и таймаута — как в вашем `/health` (python-dotenv — `settings.DATABASE_URL` и `settings.DB_CONNECT_TIMEOUT`); таймаута в модуле настроек нет — уберите аргумент `connect_timeout`, иначе mypy сделает красным `lint`. Перед эндпоинтом в `main.py` и перед тестом в `tests/test_main.py` — по две пустые строки.

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy .
# PowerShell 5.1: вместо && — по очереди через ; (как в шаге 3.4). Poetry: poetry run вместо uv run
git add main.py tests/test_main.py
git commit -m "feat: add item statuses endpoint"      # item — ваша сущность
git push -u origin HEAD
```

Линтеры должны быть чистыми: поломка — в схеме базы, а не в стиле; красный `lint` скроет ту ошибку, ради которой PR открыт. `ruff format --check` называет файл — `uv run ruff format .` и снова линтеры. mypy называет файлы в `venv/` — как на шаге 2.4.

Автор PR-поломок открывает два PR в основную ветку разработки, заголовки — `Сломать и починить: Д1 — хост базы` и `Сломать и починить: С1 — столбец без миграции`, в описании первой строкой — «Учебная поломка практики №6, не мержить».

**Что должно получиться:** два PR открыты, в каждом идёт прогон.

#### Шаг 8.2: Предсказание (2 мин)

Диагност своего PR — **до того, как открыть вкладку Checks** — публикует в PR комментарий:

```markdown
Предсказание (до лога):
- Упадёт джоб: [...], шаг: [...]
- Сообщение в логе будет про: [...]
- build: выполнится / пропущен — почему
- Merge: доступен / заблокирован — чем
```

#### Шаг 8.3: Диагноз по логу (6 мин)

Откройте упавший джоб и шаг. Диагност публикует комментарий **до коммита починки**; автор PR-поломок добавляет к нему цитату блока merge (вкладка **Conversation**, внизу):

```markdown
Диагноз: [ссылка на красный прогон]

- Джоб → шаг: [...]
- Строка лога (дословно): `...`
- Причина: [почему эта строка появилась — одной-двумя фразами]
- Починка: [что меняем и почему это устраняет причину]
- Блок merge: «[заголовок блока проверок и строка упавшей проверки дословно]»; «Merging is blocked: [причина дословно]»
- Совпало с предсказанием: да / нет — [что не совпало]
```

**`test` и `build` ещё не обязательные** (ситуация F): шаблон тот же, цитируйте то, что на экране. Упавшая проверка без пометки **Required** merge не блокирует, блокирует отсутствие approval — так и запишите в строке «Блок merge». Блокировку обязательной проверкой команда покажет пробой в ДЗ 1.

Причина — то, что объясняет строку лога, а не пересказ строки. Пример на другом сбое: «`password authentication failed`» — симптом; «пароль в `DATABASE_URL` джоба не совпадает с `POSTGRES_PASSWORD` сервиса» — причина: она отвечает на «почему». Как джоб на раннере обращается к сервис-контейнеру — материал 3 к воркшопу №6: [Creating PostgreSQL service containers](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers), раздел **Running jobs directly on the runner machine**.

**Точка синхронизации 145** — диагнозы в обоих PR. Ссылки на оба PR отправьте команде-рецензенту и преподавателю сразу после диагноза, не дожидаясь починки.

#### Шаг 8.4: Починка, зелёный прогон, итог (8 мин)

Починка устраняет причину из диагноза. Не считается починкой: удалить тест, поставить `continue-on-error`, убрать `test` из обязательных проверок.

**Д1:**

```bash
git checkout break/service-host      # ваше имя ветки
git revert --no-commit HEAD
git commit -m "chore: restore localhost for the test database service"
git push
```

**С1** — миграция для столбца. Сгенерированный файл получит пометки `pragma` из шаблона (шаг 2.2):

```bash
git checkout break/column-without-migration      # ваше имя ветки
uv run alembic revision -m "add status to items"      # items — ваша таблица
```

В созданном файле:

```python
def upgrade() -> None:
    """Upgrade schema."""
    op.add_column(
        "items",
        sa.Column("status", sa.String(20), nullable=False, server_default="new"),
    )


def downgrade() -> None:
    """Downgrade schema."""
    op.drop_column("items", "status")
```

`server_default` нужен, чтобы столбец `NOT NULL` добавился и в таблицу, где уже есть строки. Пример второй миграции — [Alembic: Tutorial](https://alembic.sqlalchemy.org/en/latest/tutorial.html), раздел **Running our Second Migration**.

```bash
uv run ruff check --fix . && uv run ruff format .
DATABASE_URL=postgresql://localhost/offline uv run alembic upgrade head --sql    # PowerShell — как в шаге 2.4
git add migrations
git commit -m "feat: add status column to items"
git push
# PowerShell 5.1: вместо && — по очереди через ; (как в шаге 3.4). Poetry: poetry run вместо uv run
```

**Ожидаемый вывод** офлайн-проверки: после первой миграции — `Running upgrade <номер> -> <номер>, add status to items` и `ALTER TABLE items ADD COLUMN status VARCHAR(20) DEFAULT 'new' NOT NULL;`.

**Итог в PR.** Пока идёт прогон, диагност дописывает в свой PR (SHA — из `git log -1 --format=%h`):

```markdown
Починка: <SHA коммита>
Починка устранила причину, а не симптом: [почему]
```

Ссылку на прогон, когда он завершится, добавляет в оба PR автор PR-поломок — отдельным комментарием `Прогон починки: [ссылка] — зелёный.`: диагност к этому времени уже на шаге 9.1.

**Что должно получиться:** в обоих PR новый прогон на голове ветки зелёный, блок merge — «All checks have passed»; в каждом PR — итог починки. PR не мержите и не закрывайте до конца этапа 9: команда-рецензент читает их сейчас.

### Этап 9: Проверка диагноза другой командой (12 мин)

Вы проверяете **диагноз**: совпадает ли он с логом и объясняет ли причину; одним пунктом — базовые тесты команды. Работа идёт по PR и логам на GitHub, клонировать чужой репозиторий не нужно.

**Как это оценивается.** Зачёт / незачёт этапа, баллы не начисляются. Зачёт команда получает, если:

1. Опубликован комментарий проверки в PR-поломке назначенной команды по шаблону шага 9.1: шесть пунктов с доказательством и итог
2. На каждое замечание к вашим PR-поломкам есть ответ — правкой или аргументом (шаг 9.2)

#### Шаг 9.1: Проверить чужой диагноз (6 мин)

Работают проверяющие по таблице шага 0.2: каждый берёт один PR-поломку назначенной команды (вдвоём — оба PR; один проверяющий — один PR на выбор). Откройте PR:

- **Conversation** — предсказание, диагноз, починка и время каждого комментария
- **Commits** — коммит поломки с красным крестиком, коммит починки с зелёной галочкой и время коммитов
- **Checks** → красный прогон → упавший шаг — лог, который вы сверяете с диагнозом

| № | Что сверяете | Где смотреть |
|---|---|---|
| 1 | Предсказание опубликовано раньше диагноза, диагноз — раньше коммита починки | Время комментариев в **Conversation** и коммитов в **Commits** |
| 2 | Джоб и шаг в диагнозе — те, что красные в прогоне | **Checks** |
| 3 | Строка лога процитирована дословно и есть в логе этого шага | Лог упавшего шага |
| 4 | Причина объясняет эту строку, а не повторяет её | Диагноз; `ci.yml` или код в **Files changed** |
| 5 | Починка устраняет причину, а не симптом (тест не удалён, проверка не ослаблена); прогон после неё зелёный | **Files changed** коммита починки, **Checks** |
| 6 | Базовые тесты: есть тест на каждый эндпоинт, `/health` с `200` и `503`, «Миграции применились» (около минуты) | Файл `tests/test_main.py` целиком в ветке PR-поломки: вкладка **Code**, переключатель веток — ветка PR |

Публикует проверяющий из своего аккаунта комментарием в PR:

```markdown
Проверка диагноза: команда [название], PR [Д1 / С1]
Проверяющий: [имя, логин GitHub]

| № | Пункт | Результат | Доказательство |
|---|---|---|---|
| 1 | Предсказание → диагноз → починка по времени | выполнено / не выполнено / спорно | [время комментариев и коммита] |
| 2 | Джоб и шаг | | |
| 3 | Строка лога дословно | | [ссылка на строку лога] |
| 4 | Причина объясняет строку | | |
| 5 | Починка — причина, не симптом; зелёный прогон | | |
| 6 | Базовые тесты: эндпоинты, `/health` 200 и 503, миграции | | [имена тестов] |

Замечания (где → что не так → чем грозит → что предлагаете):
1. ...

Итог: диагноз подтверждён: шаг и строка лога совпадают / N замечаний
```

«Диагноз подтверждён» — нормальный результат, если у каждого из пунктов 1–5 есть доказательство; п. 6 оценивает тесты и на итог по диагнозу не влияет. Пример замечания: «Диагноз, „Строка лога“ → процитированной строки нет в логе шага, который назван красным, — она из другого шага → рецензент и преподаватель не смогут проверить диагноз по логу → процитировать строку из лога названного шага или исправить шаг».

П. 6 заполняйте после пп. 1–5. Не успели его к 151-й — опубликуйте комментарий с пп. 1–5, а п. 6 допишите отдельным комментарием до 157-й. Approve в чужом PR не ставьте. Комментарий опубликуйте **к 151-й минуте**. **Точка синхронизации 151.**

#### Шаг 9.2: Ответить и закрыть PR-поломки (6 мин)

1. На каждое замечание к вашему диагнозу — ответ в PR: исправленный текст диагноза новым комментарием (старый не удаляйте) или аргумент со ссылкой на строку лога
2. После ответов автор PR-поломок закрывает оба PR **Close pull request** с комментарием «Учебная поломка, закрыто без merge» и удаляет ветки (**Delete branch**). Миграция С1 в основную ветку не идёт: столбец появится вместе с CRUD, когда он понадобится

**Точка синхронизации 157.**

Берите по порядку:

4. **Колонка `Missing`.** По отчёту покрытия выберите непокрытую строку приложения и напишите тест из приложения А (например, отказ старта при недопустимом `APP_ENV`). **Проверка:** строка исчезла из `Missing` в логе `test`

## Если не работает

Сначала найдите сообщение об ошибке: в выводе команды, в логе джоба (вкладка **Checks**) или во вкладке **Actions**. Ищите его в таблице.

### Зависимости и lock-файл

| Симптом | Причина | Что сделать |
|---|---|---|
| В CI шаг `Install dependencies`: `The lockfile at uv.lock needs to be updated, but --locked was provided` | `pyproject.toml` изменён, а `uv.lock` не обновлён или не закоммичен | `uv lock`, `git add uv.lock`, коммит, push |
| Poetry в CI: `pyproject.toml changed significantly since poetry.lock was last generated` | `poetry.lock` не закоммичен или устарел | `poetry lock`, коммит; проверка — `poetry check --lock` → `All set!` |
| pytest или Alembic оказались не в той группе (`pytest` в `dependencies`, `alembic` в dev) | `uv add` с `--dev` или без него не там | `uv remove <пакет>` (`--dev` для dev-группы), затем команда шага 1.1 |
| Красный `Install dependencies` с сетевой ошибкой (`tls handshake eof`, `Connection reset`, `Read timed out`), код зависимостей не менялся | Сбой сети между раннером и PyPI | **Re-run failed jobs** на странице прогона. В диагноз этапа 8 такой прогон не включайте: диагноз пишется по прогону, где упал ваш шаг |
| Poetry: команды `export` нет | Не установлен плагин `poetry-plugin-export` | `poetry self add poetry-plugin-export`, затем `poetry export` шага 1.1 |
| Poetry: `git grep alembic -- requirements.txt` пусто | `poetry export` не выполнен после `poetry add` | `poetry export -f requirements.txt --output requirements.txt`, коммит вместе с `poetry.lock` |
| В логе `pytest`: ``StarletteDeprecationWarning: Using `httpx` with `starlette.testclient` is deprecated; install `httpx2` instead.`` | Установлен `httpx`, а не `httpx2` | `uv remove --dev httpx`, `uv add --dev httpx2` (Poetry — `poetry remove --group dev httpx`, `poetry add --group dev httpx2`) |

### Alembic и миграции

| Симптом | Причина | Что сделать |
|---|---|---|
| `alembic` не найден: `Failed to spawn: alembic` или `command not found` | Alembic не установлен или команда без `uv run` / `poetry run` | Шаг 1.1; команды — через `uv run alembic ...` |

| `ModuleNotFoundError: No module named 'settings'` при запуске `alembic` | Команда запущена не из корня репозитория | `cd` в корень, где лежат `alembic.ini` и `settings.py` |
| ruff: `I001`, `UP035`, `UP007` в `migrations/` | Файлы, созданные Alembic, написаны в старом стиле | `ruff check --fix .` и `ruff format .` (шаг 2.4) |
| ruff: `I001` в `tests/test_main.py` | python-dotenv: `import settings` стоит ниже `from main import app` | Перенести `import settings` выше или `ruff check --fix .` (шаг 3.1) |
| ruff: `F821 Undefined name 'op'` или `'sa'` в файле миграции | `ruff check --fix` запущен до того, как заполнено тело миграции: он удалил `pass` и неиспользуемые импорты | Вернуть в начало файла `import sqlalchemy as sa` и `from alembic import op`; порядок — сначала тело (шаг 2.3), потом ruff (шаг 2.4) |
| Коммит падает: `end-of-file-fixer`, `Fixing migrations/README`, `files were modified by this hook` | Alembic создаёт `migrations/README` без перевода строки в конце, хук его дописал | `git add migrations`, повторить `git commit` (шаг 2.4) |
| detect-secrets: `Basic Auth Credentials`, `Location: alembic.ini:89` | Строка `sqlalchemy.url = driver://user:pass@...` осталась | Шаг 2.2, п. 1 |
| detect-secrets: `Hex High Entropy String` в файле миграции | Нет `# pragma: allowlist secret` у `revision` / `down_revision` | Пометка в файл миграции и в `script.py.mako` (шаг 2.2, п. 3) |
| detect-secrets: `Basic Auth Credentials`, `Location: CONTRIBUTING.md:...` или `docs/adr/005...` | В адресе базы в «Как запустить тесты локально» или в п. 6 ADR 005 пароль, в том числе одноразовый `postgres` | Пароль заменить заглушкой `<пароль>` (шаги 6.1, 6.2), `git add` файла, коммит |
| Локально `alembic upgrade head` висит, ничего не выводя | Windows: `localhost` ждёт IPv6; или порт в `DATABASE_URL` никто не слушает, тогда висит и с `127.0.0.1`: у подключения нет таймаута | `Ctrl+C`: через несколько секунд команда прервётся с traceback и `KeyboardInterrupt`, это не ошибка проекта. Адрес `127.0.0.1`; порт — как в колонке `PORTS` в `docker ps` |
| `createdb: error: connection to server on socket ... failed: No such file or directory` | `docker compose up -d db` вернулся раньше, чем база на новом томе запустилась | `docker compose up -d --wait db`, повторить `createdb`; `--wait` — в п. 6 ADR 005 (шаг 3.3) |
| `FATAL: database "..." does not exist`; pytest — `2 failed` | `createdb` не выполнен или упал, тестовой базы нет | Повторить `createdb` по п. 6 ADR 005, затем `alembic upgrade head` и `pytest` |
| `connection refused` или `the database system is starting up` сразу после запуска базы | База ещё стартует: шаг ожидания пропущен | Строка ожидания шага 3.3 или `--wait`, затем повторить команду |
| Ожидание шага 3.3 повторяется без конца, в выводе `is not running` | `docker run` не запустил контейнер, например порт занят | `Ctrl+C`; прочитайте ошибку `docker run`; `docker rm -fv p6-test-db`, другой порт в `docker run` и `DATABASE_URL` |
| `docker run`: `Conflict. The container name "/p6-test-db" is already in use` | Прошлый запуск прерван до `docker rm -fv` | `docker rm -fv p6-test-db`, повторить блок |
| `Multiple head revisions are present` | Две миграции ссылаются на одну и ту же предыдущую (`down_revision`) — например, две ветки добавили миграции | В одной из них `down_revision` = номер другой; или `alembic merge heads`. На этом занятии не встречается: миграция С1 не мержится |

### Тесты и покрытие

| Симптом | Причина | Что сделать |
|---|---|---|
| `ModuleNotFoundError: No module named 'main'` при сборе тестов | Нет `pythonpath = ["."]` | Шаг 1.2 |
| `ERROR collecting` с `ValidationError` или `INTERNALERROR> SystemExit` | `DATABASE_URL` не задан — fail fast модуля настроек | Ожидаемо без переменной (шаг 3.2). В CI — проверьте `env` джоба `test` |
| Тест `503` красный: пришёл `200` | Подмена адреса не сработала: другое имя поля, или код читает адрес не через модуль настроек | Имя поля в `monkeypatch.setattr` — как в `settings.py`; в python-dotenv — `import settings`, а не `from settings import DATABASE_URL` |
| В CI `test_migrations_applied` красный: таблицы нет в множестве | В тесте имя таблицы не совпадает с миграцией | Имя — как в `op.create_table` |
| В таблице покрытия есть `tests/test_main.py` или `migrations/` | Нет `[tool.coverage.run]` или `pytest` запущен с `--cov=.` | Шаг 1.2; в `ci.yml` — `--cov` без аргумента |
| На Windows тест `503` длится около 3 секунд | Подключение к закрытому порту ждёт `connect_timeout` | Не ошибка; на раннере Linux — мгновенно |

### Джобы и workflow

| Симптом | Причина | Что сделать |
|---|---|---|
| В PR есть `lint` и `secrets`, а `test` и `build` нет | Ошибка отступа при вставке: джобы оказались вне `jobs:` или внутри `secrets` | Отступ `test:` — два пробела, как у `lint:`; во вкладке **Actions** — `Invalid workflow file` с номером строки |
| `test` красный на `Initialize containers` | Неверный образ сервиса (опечатка в `postgres:16`) | Образ — как в `compose.yaml` |
| `test` красный на `Migrations` или `pytest`: `password authentication failed` | Пароль в `DATABASE_URL` не совпадает с `POSTGRES_PASSWORD` сервиса | Оба — `postgres`, как в тексте джобов |
| `build` красный с сообщением, что action `docker/...` не разрешён | Actions permissions без `docker/*` (ситуация E) | Владелец добавляет `docker/*` (шаг 0.1); недоступен — ДЗ 1 |
| `build` красный на `Build image` с ошибкой шага `Dockerfile` | Образ не собирается и локально | `docker build .` локально, если Docker есть; ошибка `requirements.txt` у Poetry — `poetry export` (шаг 1.1) |
| `build` пропущен (`skipped`) | Упал `lint`, `secrets` или `test`: `needs: [lint, secrets, test]` | Чинить упавший джоб; merge блокирует он |
| `publish` пропущен на PR | `if` — только `push` в `main` | Так задумано |
| Проверки `test` или `build` висят с `Expected — Waiting for status to be reported` | Обязательная проверка, а workflow на этот PR не запустился: старый PR без этих джобов (PR ADR 005) или ветка вне фильтра `branches` | Старый PR ADR 005 закрыть (шаг 5.1); базовая ветка PR — в `on.pull_request.branches` |
| В поиске **Add checks** только «Add test · Any source» | Проверка ещё ни разу не выполнялась | Не выбирать «Any source»: дождаться прогона на шаге 5.1 |
| В **Annotations** notice `The ubuntu-latest label will migrate to Ubuntu 26 ...` | Предупреждение GitHub о смене образа раннера | Не ошибка |

### Публикация

| Симптом | Причина | Что сделать |
|---|---|---|
| `publish` красный на `Download image`: артефакт `image` не найден | В `build` шаг `Upload image` не выполнился: изменено его `if` или имя артефакта | `if` у `Upload image` и у `publish` — одинаковые, `name: image` в обоих шагах |
| `publish` красный на `Tag and push`: `repository name must be lowercase` | Имя образа взято не из `meta`, а напрямую из `github.repository` с заглавными буквами | Теги — только из `steps.meta.outputs.tags`, как в тексте джобов |
| `publish` красный на `Tag and push`: `denied` или `403` | Репозиторий организации: публикация packages запрещена политикой; или пакет с таким именем уже есть и не связан с репозиторием | Владелец организации разрешает packages; страница пакета → **Package settings** → **Manage Actions access** → **Add repository** ([Configuring a package's access control and visibility](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility), раздел **Ensuring workflow access to your package**, 3 мин) |
| Пакета нет в **Packages** после зелёного прогона | Смотрите прогон на PR или на `push` в `develop`: там `publish` пропущен | Прогон с событием `push` в `main` |
| GitFlow: `publish` не запускается после merge | PR в `develop`, а `publish` — только для `main` | Ожидаемо: публикация через релиз, ДЗ 2 |

### Code owners

PR меняет `*.py`, `.github/` и `docs/`; ждёт approval владельцев этих путей из `.github/CODEOWNERS`.

- **Владелец пути — автор PR** — он не может одобрить свой PR: автором PR сделайте другого участника (шаг 0.2). PR уже открыт — его закрывают и открывают заново из аккаунта другого участника на ту же ветку
- **Владелец пути не пришёл, владелец репозитория на месте** — удалённый approval владельца пути (ссылка ему в чат); нет к 100-й минуте — временное снятие `Require review from Code Owners` владельцем репозитория **только с разрешения преподавателя**, merge, правило сразу вернуть; записать в комментарий-итог; в ДЗ 1 — второй владелец пути в `CODEOWNERS`
- **Единственный владелец `.github/` — он же владелец репозитория — не пришёл, но на связи** — всё удалённо, одним сообщением после push шага 6.3: `test` и `build` в ruleset и approval на последний коммит
- **Тот же владелец недоступен** — на занятии PR с прогоном, PR-поломки и проверка диагноза; обязательные проверки и merge — ДЗ 1 (ситуация F)

## Чек-лист для преподавателя

Роль преподавателя в репозиториях команд — **Write**: ruleset видит и меняет только владелец, поэтому обязательные `test` и `build` подтверждаются по PR (пометка **Required**, скриншот правила).

| Что проверяем | Как проверяем | Признак выполнения |
|---|---|---|
| Зависимости | Коммит шага 1.3 | Группы верные, lock-файл в том же коммите; Poetry — `requirements.txt` с `alembic` |
| Миграции | `migrations/`, `alembic.ini` в PR | Таблица основной сущности, `env.py` с `make_url`, pragma в шаблоне, нет `driver://` |
| Тесты и покрытие | `tests/`, лог `test` | Строки приложения А для эндпоинтов, `200`/`503`, миграций; `TOTAL` в PR; в отчёте нет `tests/` |
| Workflow | `ci.yml` в PR | Текст джобов курса, адаптация по ADR 005, старой заготовки нет |
| Обязательные проверки | **Checks**, комментарий шага 5.3 | `test` и `build` **Required**; GitFlow — оба rulesets |
| Публикация | **Packages**, комментарий шага 7.2 | Тег `sha-` = SHA коммита в `main`; GitFlow — ДЗ 2 |
| Документы | Файлы после merge | ADR 005 «Принято», время и покрытие измерены; `CONTRIBUTING.md` без TODO; «Защита ветки» и ADR 001 называют `test` и `build`; строки истории в ADR 001 и ADR 004 |
| «Сломать и починить» | Два PR-поломки | Предсказание → диагноз → починка по времени; строка лога дословно; причина, а не симптом; блок merge процитирован |
| Проверка диагноза | PR-поломка другой команды | Шесть пунктов с доказательством (п. 6 — базовые тесты), замечания по формуле или доказанное «диагноз подтверждён» |

### 2. Миграции при старте стека; GitFlow — релиз и публикация

По п. 2 «Решения» ADR 005 — один из двух способов: команда контейнера `app` (`alembic upgrade head && uvicorn ...`) или отдельный сервис `migrate` в `compose.yaml`, от которого `app` зависит через `depends_on` с `condition: service_completed_successfully`. Миграции не вызываются из кода приложения. Отдельный PR; в нём — вывод `docker compose up --build` на чистом томе (`docker compose down -v` перед запуском — только если данные тома не нужны).

**GitFlow:** релиз `develop` → `main` — как на практиках №3–5 (ДЗ 2), версия по ADR 003; PR релиза проходит обязательные `lint`, `secrets`, `test`, `build` в `protect-main`. После merge — прогон на `push` в `main` с `publish` и тег `sha-` в **Packages**. Релиз практики №5 не сделан — его критерии входят в этот же PR.

**Критерий успеха:**

- [ ] `docker compose up --build` на чистом томе поднимает стек с первого раза, в логе — `Running upgrade  -> <номер>, create <таблица> table`, `GET /health` — `200`
- [ ] Повторный `docker compose up` не падает: миграции уже применены
- [ ] Строка в «Последствиях» ADR 005 — какой способ выбран и что проверено
- [ ] GitFlow: в **Packages** тег `sha-` с SHA коммита в `main`

### 3. Тест-план целиком и покрытие

Покрытие по строке `TOTAL` лога `test` — не меньше 60 %; меньше — issue «Покрытие до 60 %» с перечнем строк из колонки `Missing` и планом. Порог в CI не добавляйте.
