# Практика №3: "Dockerfile, менеджер зависимостей и стек одной командой"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Самостоятельная командная работа по письменной инструкции + межкомандная проверка воспроизводимости  
**Роль преподавателя:** Модератор межкомандной проверки, фиксация прогресса

---

## Цели практики

К концу занятия каждая команда должна:

1. **Перевести** проект на менеджер зависимостей из ADR 002 (uv или Poetry) так, чтобы в репозитории были `pyproject.toml` и lock-файл, проверка lock-файла (`uv sync --locked` или `poetry check --lock`) проходила без ошибок, а приложение запускалось из нового окружения
2. **Доработать** `GET /health` так, чтобы он проверял соединение с базой данных: при доступной базе — `200` и `{"status": "healthy", "database": "ok"}`, при недоступной — `503`
3. **Написать** `Dockerfile` и `.dockerignore` так, чтобы повторная сборка после правки кода показывала `CACHED` на шаге установки зависимостей, а `venv/`, `.venv/`, `.env` и `.git` не попадали в образ
4. **Собрать** `compose.yaml` по своей схеме окружения — хост базы в `DATABASE_URL`, путь тома и условие `depends_on` команда определяет по схеме сама — так, чтобы `docker compose up --build` после `docker compose down -v` поднимал стек с первого раза, `db` был в состоянии `healthy`, `/health` отвечал `200`, а пароль базы брался только из `.env` (в репозитории — `.env.example`)
5. **Проверить** воспроизводимость стека другой команды по её README без устных вопросов и оставить в её PR ревью по шаблону: команды, результат `/health`, число вопросов авторам, замечания по формуле
6. **Обосновать** решение ADR 002 фактами сборки: заменить гипотезу «команда для Dockerfile» проверенной командой и довести ADR до статуса «Принято» в составе PR со стеком

### Права доступа

Ограничения практики №2 действуют (у команд без практики №2 — с первых 10 минут занятия, блок «Практика №2 не закрыта»): прямой push в защищённые ветки отклоняется, автор PR не может одобрить свой PR. Других прав на этой практике не нужно — остальные настройки репозитория вы не меняете. Исключение — запасной путь для `Require review from Code Owners` («Если не работает → Code owners»): правило снимается только с разрешения преподавателя и возвращается сразу после merge.

Для межкомандной проверки нужен только доступ на чтение к чужому репозиторию: он публичный, клонировать его может любой.

### Проверка перед стартом

Окружение `venv/` не должно быть активно: если строка приглашения начинается с `(venv)` — выполните `deactivate`. Исключение — **Poetry установлен в `venv/` проекта**: сначала активируйте `venv/` (`source venv/bin/activate`; Git Bash на Windows — `source venv/Scripts/activate`; Windows PowerShell — `venv\Scripts\Activate.ps1`) и оставьте активным до конца занятия — подробнее в начале этапа 2.

```bash
git --version
docker --version
docker compose version     # Docker Compose version v2.x или новее
docker info --format "{{.ServerVersion}}"   # версия сервера — значит, Docker запущен
uv --version               # или: poetry --version
docker image ls python
docker image ls postgres
```

**Что должно получиться:** все команды отвечают без ошибок; в списке образов есть `python` с тегом версии Python вашего проекта (например, `3.12-slim`) и `postgres` с тегом из вашей схемы (например, `16`). `uv: command not found` (PowerShell: `The term 'uv' is not recognized`) при неактивном `venv/` — uv стоит только в `venv/`: поставьте его установщиком из «ПО и доступы» сейчас (1–2 минуты из буфера), откройте новое окно терминала и повторите `uv --version`.

Образы и синхронизация `develop` (GitFlow) — требования раздела «Что должно быть готово»: буфера занятия на оба сразу не хватит. Если образов всё же нет — запустите скачивание сейчас в отдельном окне терминала и не ждите его (теги — ваши):

```bash
docker pull python:3.12-slim
docker pull postgres:16
```

По таблице этап 8 заканчивается на 160-й минуте, но точка синхронизации для merge стоит на 170-й: 10 из 12 минут буфера к этому моменту обычно уже потрачены на скачивание образов, установку uv вне `venv/`, синхронизацию `develop` на занятии (GitFlow, шаг 1.1), ситуации C, D, E из раздела «Подготовка» или ожидание проверяющей команды. Если буфер не понадобился — берите бонусные задачи из этапа 8.

**Что обязательно на занятии, а что можно перенести.** Работа идёт на одном ноутбуке: перерасход времени уходит в буфер, недоделанное — в домашнее задание 1 (3 дня после практики).

- **На занятии обязательно:** PR со стеком открыт к 125-й минуте (шаг 6.3) и ревью чужого стека опубликовано к 150-й (шаг 7.3) — от этого зависит другая команда, это условия зачёта 1–2 этапа 7; ответы на замечания к своему PR (шаг 7.4) и merge PR со стеком в основную ветку разработки — `main`, у GitFlow `develop` (шаг 8.1). Merge не успели к 170-й (ждали проверяющих или повторный approval) — назовите это в комментарии-итоге и смержите в срок домашнего задания 1: незачётом это не считается. Так же — если совпали ситуации C или E с D, а на занятии двое: тогда на занятии обязательны открытый PR и ревью чужого стека
- **Можно перенести в домашнее задание 1:** повторную проверку стека после «незачёта» (условие зачёта 3); у GitFlow — релиз в `main` (шаг 8.2 целиком); в ситуации D — раздел «Риски и митигация» ADR 002; в ситуации E — полную схему и её ревью другой командой; бонусные задачи

Перенесённое назовите в комментарии-итоге на этапе 9. Сделанное в срок домашнего задания 1 незачётом не считается.

С 150-й до 170-й минуты за ноутбуком по порядку: ответы на ревью своего PR (шаг 7.4) → approval сокомандника заново, если правки его сбросили, и merge (шаг 8.1) → чистый старт из основной ветки. Ответы в обсуждениях чужого PR — с телефона.

### Точки синхронизации

Преподаватель проверяет их вслух. Команда, отставшая от точки более чем на 10 минут, сообщает об этом сразу, а не в конце занятия.

| Минута | Что должно быть сделано у всех команд |
|---|---|
| **32** | Lock-файл закоммичен, рабочая ветка запушена |
| **70** | Образ собран, контейнер отвечает на `GET /`, кэш слоёв проверен |
| **103** | Стек поднят через `docker compose`, `/health` отвечает `200` |
| **125** | PR **открыт**, ссылка отправлена проверяющей команде |
| **150** | Ревью воспроизводимости от другой команды получено |
| **170** | PR смержен, ADR 002 — «Принято» |

### Этап 1: Синхронизация, роли, входная развилка (12 мин)

#### Шаг 1.1: Обновить репозиторий и создать рабочую ветку (5 мин)

Имя рабочей ветки в инструкции — `feature/containerize`. Если ваш `CONTRIBUTING.md` требует другое (например, Trunk-Based с типами Conventional Commits — `feat/containerize`), назовите ветку по своим правилам: дальше в инструкции ни одна команда не зависит от этого имени. Если правила различают `feature/` и `chore/`, подходит любой из двух: работа и инфраструктурная, и меняет поведение `/health` — не тратьте время на спор.

**GitHub Flow и Trunk-Based** — ветка от `main`:

```bash
git checkout main
git pull origin main
git checkout -b feature/containerize      # имя — по вашим правилам из CONTRIBUTING.md
```

**GitFlow** — первый блок не выполняйте: ветка создаётся от `develop`, PR на этапе 6 открывается в `develop`. Сначала проверьте, что в `develop` есть всё, что практика №2 смержила в `main` (строка «Только GitFlow» в разделе «Подготовка»):

```bash
git checkout develop
git pull origin develop
git fetch origin
git log --oneline --no-merges origin/develop..origin/main
```

**Ожидаемый вывод:** пустой — в `main` нет коммитов, которых не было бы в `develop`; создайте рабочую ветку от `develop`:

```bash
git checkout -b feature/containerize      # имя — по вашим правилам из CONTRIBUTING.md
```

Если команда вывела коммиты (например, `docs: add pull request template`), в `develop` нет актуальных `CONTRIBUTING.md` и ADR 001, а у Poetry и uv — ещё и `pyproject.toml` с lock-файлом (практика №2 мержила их только в `main`): ревью на шаге 8.1 пойдёт по старому `CONTRIBUTING.md`, а этап 2 начнётся без ваших файлов зависимостей. Шаблон PR GitHub берёт из `main`, он подставится в любом случае. Подтяните `main` в `develop` через отдельную ветку — тип `docs/`, потому что переносятся документы практики №2 (если ваши правила требуют другой тип — по `CONTRIBUTING.md`):

```bash
git checkout -b docs/sync-main-into-develop
git merge --no-edit -m "docs: sync develop with main" origin/main
# если git сообщит о конфликтах: исправить файлы, затем git add <файлы> и git commit --no-edit
git push -u origin docs/sync-main-into-develop
git checkout -b feature/containerize      # рабочая ветка — от ветки синхронизации
```

`-m` задаёт сообщение коммита слияния по Conventional Commits, `--no-edit` не даёт git открыть редактор (на macOS и Linux это vim). Если git ответил `Fast-forward` — коммита слияния нет, это тоже правильно.

Рабочая ветка создана от ветки синхронизации, то есть от `develop` вместе с тем, что в неё сейчас вольётся: файлы зависимостей и документы практики №2 у вас уже есть, вливать `develop` повторно не нужно. Откройте PR ветки синхронизации в `develop`. Его approval и merge (**Create a merge commit**, не squash: иначе `main` и `develop` снова разойдутся по истории) делает не водитель, пока водитель ведёт этап 2, — ждать merge не нужно. Он должен быть смержен до шага 6.3: иначе в PR со стеком попадут и файлы синхронизации.

**Влить ветки ADR 002 и схемы** (ситуации A и C из раздела «Подготовка»; все стратегии). Найдите имя ветки в списке удалённых веток:

```bash
git fetch --prune origin      # --prune убирает из списка ветки, уже удалённые на GitHub
git branch -r
git merge --no-edit -m "docs: include ADR 002 draft" origin/docs/adr-002-dependency-manager    # имя — как в списке
```

В ситуации C влейте так же ветку схемы: `git merge --no-edit -m "docs: include environment schema" origin/<ветка схемы>`.

Сообщение `-m` нужно, чтобы коммит слияния тоже начинался с типа Conventional Commits: критерий approval «все коммиты PR — по Conventional Commits» из вашего `CONTRIBUTING.md` касается и его.

**Что должно получиться:** `git merge` выводит `Merge made by the 'ort' strategy.` или `Fast-forward`; `git status` показывает `On branch <ваша рабочая ветка>` и чистое дерево; в списке файлов есть `docs/adr/002-dependency-manager.md` (кроме ситуации D) и `docs/environment-schema.md` (кроме ситуации E).

```bash
git status
git ls-files docs
```

Старые PR с ADR 002 и схемой не закрывайте сейчас: на шаге 6.3 вы закроете их со ссылкой на новый PR — история их ревью останется доступной.

#### Шаг 1.2: Распределить роли (3 мин)

Работа идёт на **одном ноутбуке** — том, где работают Docker и выбранный менеджер зависимостей. Роли меняются по этапам, чтобы вклад был у каждого. Как на практиках №1–2, водитель не на своём ноутбуке коммитит от своего имени: `git commit --author="Имя Фамилия <email-из-GitHub>" -m "..."` (email — тот, что привязан к GitHub, например адрес вида `ID+логин@users.noreply.github.com` из **Settings → Emails**).

Сейчас запишите: **чей это ноутбук** и для каждого, кто будет водителем на чужом ноутбуке, — его готовую строку `--author="..."` с настоящими именем и email. В каждом коммите инструкции дан комментарий `# не свой ноутбук: ...` — проверяющий перед коммитом сверяет, кто водитель, и водитель добавляет `--author` со своей строкой. Push идёт под входом владельца ноутбука — так и должно быть.

**Аккаунты на общем ноутбуке.** В браузере ноутбука открыт аккаунт владельца. PR открывает автор PR по таблице ролей из своего аккаунта; ревью в чужом PR (шаг 7.3) и approval (шаг 8.1) — тоже каждый из своего аккаунта: с телефона или в окне инкогнито. Approval от аккаунта, который открыл PR, GitHub не примет.

| Роль | Что делает |
|---|---|
| **Водитель** | Набирает команды и код, делает коммиты |
| **Штурман** | Читает инструкцию вслух на шаг вперёд, сверяет `compose.yaml` со схемой окружения |
| **Проверяющий** | Сверяет вывод команд с «Что должно получиться», ведёт таблицу «Кто что делал» для описания PR |
| **Автор документов** | Со своего ноутбука, с телефона или на бумаге готовит текст README (шаг 6.1) и правки ADR 002 (шаг 6.2) по ходу этапов 2–5. В ситуации D пишет ADR 002 целиком |

**Команда из 4 человек**

| Участник | Этапы 1–3 | Этап 4 | Этап 5 | Этап 6 | Этапы 7–8 |
|---|---|---|---|---|---|
| 1 | Водитель | Штурман | Проверяющий | Штурман | Approval своего PR |
| 2 | Штурман | Водитель | Штурман | Проверяющий | Внешний проверяющий чужого стека |
| 3 | Проверяющий | Проверяющий | Водитель | Проверяющий | Внешний проверяющий чужого стека |
| 4 | Автор документов | Автор документов | Автор документов | Водитель: коммит README и ADR 002, автор PR | Ответы на ревью своего PR |

**Команда из 3 человек**

| Участник | Этапы 1–3 | Этап 4 | Этап 5 | Этап 6 | Этапы 7–8 |
|---|---|---|---|---|---|
| 1 | Водитель | Штурман | Проверяющий | Водитель, автор PR | Ответы на ревью своего PR |
| 2 | Штурман | Водитель | Штурман | Проверяющий | Внешний проверяющий чужого стека |
| 3 | Проверяющий, автор документов | Проверяющий, автор документов | Водитель | Штурман | Второй внешний проверяющий, затем approval своего PR |

Участник 1 в обеих таблицах — владелец ноутбука, `--author` нужен остальным. Автор документов закреплён: в команде из 4 — участник 4 (этапы 2–5), из 3 — участник 3 (этапы 2–4, в паузах проверки: установка пакетов, сборка образа). **В ситуации D** в команде из 3 участник 3 пишет ADR 002 целиком, а README — участник 2 на этапе 5. **В ситуации E** минимум схемы к этапу 5 готовит участник 3 в команде из 4 и участник 2 (штурман этапов 1–3) в команде из 3. Команда из 5 и двое на занятии — «Если не работает → Состав команды и несколько ситуаций сразу».

Нельзя совмещать: автор PR и тот, кто ставит ему approval.

**Таблица «Кто что делал»** — то же, что строка «Роли» на практике №2, но таблицей. Проверяющий ведёт её с первой минуты, она войдёт в описание PR на шаге 6.3 и понадобится вам в конце курса для оценки сокомандников:

```markdown
| Участник | Роли | Что конкретно сделал |
|---|---|---|
| [Имя] | Водитель этапов 1–3 | Перевод на uv, `/health` с проверкой базы |
```

#### Шаг 1.3: Назвать ситуацию, получить назначение, проверить Docker (4 мин)

2. **Ситуация D:** выберите uv или Poetry сейчас, за 5 минут — 4 из них берутся из буфера. Решение команда принимает по своей таблице сравнения, а не по совету соседей. Запишите одной строкой, почему выбрали, — это основа раздела «Обоснование» на шаге 6.2. Назовите, кто пишет ADR 002 (шаг 1.2). ### Этап 2: Переход на uv или Poetry (20 мин)

Цель этапа — заменить `requirements.txt` из `pip freeze` (или старую настройку Poetry) на `pyproject.toml` с прямыми зависимостями и lock-файл со всеми версиями. Заодно добавляется драйвер PostgreSQL `psycopg[binary]` — он нужен на этапе 3.

Перед началом деактивируйте старое окружение, если оно активно: `deactivate`. Папку `venv/` не удаляйте — она в `.gitignore` и никому не мешает. С этой практики окружение uv-проекта — `.venv/`, которое создаёт сам uv: `--active` из практик №1–2 больше не нужен, а появившаяся папка `.venv/` — норма, а не ошибка. Poetry создаёт окружение в своей служебной папке, `.venv/` у него может не появиться — это тоже нормально.

**Исключение — Poetry установлен в `venv/` проекта** (практика №1, `pip install poetry`) и ADR 002 выбрал Poetry. Тогда `venv/`, наоборот, активируйте (`source venv/bin/activate`; Git Bash на Windows — `source venv/Scripts/activate`; Windows PowerShell — `venv\Scripts\Activate.ps1`) и оставьте активным до конца занятия: без него команды `poetry` нет. Плагин экспорта встанет в этот же `venv/`, и зависимости проекта Poetry тоже поставит в него. Для uv такого исключения нет: uv должен работать при неактивном `venv/` (раздел «ПО и доступы»).

#### Шаг 2.1: Создать `pyproject.toml` и lock-файл (14 мин)

**Найдите прямые зависимости.** Это пакеты, которые команда ставила сама: с практики №1 — `fastapi` и `uvicorn[standard]`, плюс всё, что вы добавляли позже. Остальные строки `requirements.txt` — транзитивные зависимости: их подтянет инструмент. Переносить весь вывод `pip freeze` нельзя: каждая транзитивная зависимость станет прямой с жёсткой версией, и обновлять их придётся вручную.

**Если ваш ADR выбрал uv.**

*Если `pyproject.toml` уже есть.* С `pyproject.toml` команда `uv init` завершится ошибкой `Project is already initialized`. Два случая:

- **Проект на Poetry с практики №1.** Выпишите из `pyproject.toml` прямые зависимости (раздел `dependencies` или `[tool.poetry.dependencies]`) и уберите файлы Poetry — дальше выполните команды основного пути как написано; если среди выписанных есть пакеты сверх `fastapi` и `uvicorn[standard]`, добавьте их в `uv add`:

  ```bash
  git rm -f --ignore-unmatch pyproject.toml poetry.lock
  ```

  `--ignore-unmatch` нужен, если файлы Poetry с практики №1 не были закоммичены: `git rm` уберёт закоммиченные, а незакоммиченные останутся на диске. Удалите их:

  ```bash
  # macOS / Linux / Git Bash
  rm -f pyproject.toml poetry.lock

  # Windows PowerShell
  Remove-Item pyproject.toml, poetry.lock -ErrorAction SilentlyContinue
  ```

  **Ожидаемый вывод:** `git status --short` показывает `D  pyproject.toml` и `D  poetry.lock` для закоммиченных файлов и ничего — для незакоммиченных; файлов `pyproject.toml` и `poetry.lock` в папке нет.

- **Проект уже на uv** (практика №1: `pyproject.toml` и `uv.lock` есть): `uv init` пропустите, выполните `uv python pin 3.12` (ваша версия Python проекта) и `uv add "psycopg[binary]"`. Ошибка `is incompatible with the project requires-python` — «Если не работает», строка про `requires-python`.

*Основной путь* — проект на `requirements.txt` (или после `git rm` выше):

```bash
uv init --bare --python ">=3.11"
uv python pin 3.12          # версия Python вашего проекта из README
uv add fastapi "uvicorn[standard]" "psycopg[binary]"
```

- `uv init --bare` создаёт только `pyproject.toml` и не трогает ваши `main.py` и `README.md`. Без `--bare` uv создаст лишние файлы. `--python ">=3.11"` — то же требование, что в практике №1: проект допускает любой Python от 3.11, и сокомандник со старой версией не сломает окружение
- `uv python pin` создаёт `.python-version` — версию, на которой работает проект и собирается образ (шаг 4.2). Без него uv возьмёт первую подходящую под `requires-python` версию Python на ноутбуке, и локальное окружение разойдётся с образом
- Кавычки вокруг пакетов с квадратными скобками обязательны в zsh (macOS) и безопасны в остальных оболочках

**Ожидаемый вывод** `uv add` заканчивается списком установленных пакетов, среди них:

```
 + fastapi==...
 + psycopg==...
 + psycopg-binary==...
 + uvicorn==...
```

Появились файлы `pyproject.toml`, `uv.lock`, `.python-version` и папка `.venv/`. В `pyproject.toml` в списке `dependencies` ровно три строки:

```toml
dependencies = [
    "fastapi>=...",
    "psycopg[binary]>=...",
    "uvicorn[standard]>=...",
]
```

`uv init` записывает в `pyproject.toml` `name` по имени папки и `version = "0.1.0"`: на запуск приложения это не влияет. Версии пакетов в `uv.lock` могут оказаться новее, чем были в `requirements.txt`, — uv берёт последние подходящие; это нормально, запишите факт в «Последствия» ADR 002 на шаге 6.2.

Старый `requirements.txt`, если он есть, удалите: источником правды о зависимостях теперь будет `pyproject.toml` и `uv.lock`, а второй список неизбежно разойдётся с ними.

```bash
git rm -f --ignore-unmatch requirements.txt
```

Если `requirements.txt` не был закоммичен, `git rm` его не тронет — удалите файл с диска:

```bash
# macOS / Linux / Git Bash
rm -f requirements.txt

# Windows PowerShell
Remove-Item requirements.txt -ErrorAction SilentlyContinue
```

**Ожидаемый вывод:** в `git status --short` строка `D  requirements.txt`, если файл был закоммичен; если не был — строки с `requirements.txt` нет (строки `?? pyproject.toml`, `?? uv.lock` и другие новые файлы остаются). Файла `requirements.txt` в папке нет.

**Если ваш ADR выбрал Poetry:**

1. Плагин экспорта. В Poetry 2.x команды `poetry export` без него нет, а она понадобится для образа на этапе 4:

   ```bash
   poetry self add poetry-plugin-export
   ```

   **Ожидаемый вывод** заканчивается строкой `Writing lock file` (это lock-файл самого Poetry, не вашего проекта).

2. `pyproject.toml`. Если он уже есть с практики №1 (Poetry или uv) — переходите к пункту 3; у uv-проекта сначала уберите его lock-файл, иначе в репозитории останутся два:

   ```bash
   git rm -f --ignore-unmatch uv.lock
   rm -f uv.lock               # если uv.lock не был закоммичен
   # Windows PowerShell: Remove-Item uv.lock -ErrorAction SilentlyContinue
   ```

   Если проект на `requirements.txt`:

   ```bash
   poetry init --no-interaction --python ">=3.11"
   ```

   `--python ">=3.11"` — как в практике №1: проект допускает любой Python от 3.11. Версию, на которой собирается образ, задаёт тег на шаге 4.2

3. Отключите режим пакета: ваш проект — приложение, а не библиотека для публикации, и без этой настройки `poetry install` завершится ошибкой. Допишите в конец `pyproject.toml`:

   ```toml
   [tool.poetry]
   package-mode = false
   ```

   Если таблица `[tool.poetry]` в файле уже есть (так бывает у `pyproject.toml` с практики №1) — добавьте строку `package-mode = false` в неё, а не создавайте вторую: две одинаковые таблицы — ошибка формата TOML.

4. Зависимости. Выполните **одну** из двух команд; вывод заканчивается строкой `Writing lock file`.

   Проект на `requirements.txt` — все три:

   ```bash
   poetry add fastapi "uvicorn[standard]" "psycopg[binary]"
   ```

   `pyproject.toml` с практики №1 (Poetry или uv) и `fastapi`, `uvicorn` в нём уже есть — только драйвер:

   ```bash
   poetry add "psycopg[binary]"
   ```

5. Проверка lock-файла и установка:

   ```bash
   poetry check --lock
   poetry install
   ```

   **Ожидаемый вывод** `poetry check --lock`: `All set!`. Если вместо этого `pyproject.toml changed significantly since poetry.lock was last generated` — выполните `poetry lock` и повторите.

6. Файл зависимостей для образа. Poetry в образ не ставится: образ получит `requirements.txt`, сгенерированный из `poetry.lock`:

   ```bash
   poetry export -f requirements.txt --output requirements.txt
   ```

   Старый `requirements.txt` из `pip freeze` при этом перезаписывается. Новый содержит точные версии и хеши из `poetry.lock`: строки вида `fastapi==... ; python_version >= "3.11"` и под ними `--hash=sha256:...`. Этот файл коммитится. **Правило на весь семестр:** после каждого `poetry add`, `poetry remove` или `poetry lock` экспорт повторяется, иначе образ соберётся со старыми зависимостями. Это правило вы запишете в ADR 002 на шаге 6.2.

### Этап 3: `GET /health` с проверкой базы (13 мин)

#### Шаг 3.1: Переписать обработчик (9 мин)

Сейчас `/health` отвечает `{"status": "healthy"}`, даже если база недоступна, — то есть врёт. По [DoD, раздел 6](../../definition-of-done.md) health-check проверяет подключение к базе данных.

Адрес базы приложение берёт из переменной окружения `DATABASE_URL` — её имя записано в вашей схеме окружения. Значение задаст `compose.yaml` на этапе 5, в коде его нет.

Что меняется в `main.py`:

1. Импорты — в начало файла, вместо строки `from fastapi import FastAPI`
2. Строка `logger = ...` — после `app = FastAPI(...)` (и `TEAM_NAME`, если он есть), до первого обработчика
3. Старый обработчик `/health` — декоратор `@app.get("/health")` и функцию `async def health_check()` под ним — **удалите целиком** и на его место вставьте новый. Если оставить оба, FastAPI отвечает первым зарегистрированным — старым: `/health` вернёт `200` `{"status":"healthy"}` без проверки базы, и перезапуск сервера не поможет

Остальной код (`/` и `/version`, если он есть) не трогайте. Если `/version` у вас ещё нет (долг домашнего задания практики №2) — на этом занятии его не делайте:

```python
import logging
import os

import psycopg
from fastapi import FastAPI
from fastapi.responses import JSONResponse

app = FastAPI(...)                         # без изменений
logger = logging.getLogger("uvicorn.error")

# ... GET / и другие эндпоинты без изменений ...


@app.get("/health")                        # вместо старого обработчика
def health_check():
    """Приложение работает и база данных отвечает на запрос."""
    database_url = os.environ.get("DATABASE_URL")
    if not database_url:
        return JSONResponse(
            status_code=503,
            content={"status": "unhealthy", "database": "DATABASE_URL is not set"},
        )
    try:
        with psycopg.connect(database_url, connect_timeout=3) as conn:
            conn.execute("SELECT 1")
    except psycopg.Error as exc:
        logger.warning("Health check: database is unavailable: %s", exc)
        return JSONResponse(
            status_code=503,
            content={"status": "unhealthy", "database": "unavailable"},
        )
    return {"status": "healthy", "database": "ok"}
```

Два вопроса команде — ответьте вслух, прежде чем идти дальше; проверяющий записывает ответы по одной строке, преподаватель может спросить их на обходе. Ответы ищите по ссылкам раздела «Сводка полезных ссылок» → «Приложение»:

1. Почему обработчик объявлен через `def`, а не `async def`, если `psycopg.connect` ждёт ответа базы до трёх секунд? Что случилось бы с другими запросами к приложению за это время при `async def`?
2. Почему при недоступной базе ответ — `503`, а не `200` с текстом ошибки в теле? Кто будет читать этот ответ, кроме человека с `curl`?

Ещё две детали кода:

- **Причина сбоя — в лог, а не в ответ.** Ответ видит любой, кто откроет `/health`; лог видите вы через `docker compose logs app` (`app` — имя сервиса приложения в вашем `compose.yaml`). Это пригодится при диагностике на этапе 5
- **Строка подключения `postgresql://...` из схемы подходит как есть** — `psycopg` 3 принимает её без изменений

### Этап 4: `Dockerfile` и `.dockerignore` (25 мин)

#### Шаг 4.1: Создать `.dockerignore` (2 мин)

При сборке Docker отправляет в сборщик всю папку проекта — это **контекст сборки**. `.dockerignore` исключает из него то, чему не место в образе. Без него инструкция `COPY . .` на шаге 4.2 положит в образ ваш локальный `.venv/` поверх окружения, собранного внутри образа (с бинарниками Windows или macOS и путями вашего ноутбука), а также `.env` с паролем и всю историю `.git`.

Создайте в корне репозитория, рядом с будущим `Dockerfile`, файл `.dockerignore`:

```
.git
.venv
venv
env
.env
**/__pycache__
**/*.pyc
.idea
.vscode
```

Шаблоны отсчитываются от корня проекта: `**/` нужен, чтобы исключить `__pycache__` и во вложенных папках (например, `app/`).

Если ваше окружение называется иначе (например, `.env-dev/` или `myenv/`) — добавьте его имя.

#### Шаг 4.2: Написать `Dockerfile` (7 мин)

Порядок инструкций в образце выбран не случайно — почему, вы выясните на шаге 4.4.

**Если uv.** Создайте `Dockerfile`:

```dockerfile
FROM python:3.12-slim

# uv берётся из официального образа; версия — та, которой создан ваш uv.lock
COPY --from=ghcr.io/astral-sh/uv:0.12.7 /uv /bin/uv

WORKDIR /app

# Зависимости
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev --no-install-project

# Код
COPY . .

ENV PATH="/app/.venv/bin:$PATH"

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

В теге `ghcr.io/astral-sh/uv:0.12.7` замените `0.12.7` на версию из `uv --version` на ноутбуке водителя: образ с более старой версией uv может не прочитать lock-файл, созданный более новой. Тег `python:3.12-slim` — версия Python проекта из `.python-version`.

- `--locked` — ошибка, если `uv.lock` не соответствует `pyproject.toml`: образ не соберётся из устаревшего lock-файла
- `--no-dev` — без dev-зависимостей (тесты, линтеры)
- `--no-install-project` — ставить только зависимости, без самого проекта

**Если Poetry.** Создайте `Dockerfile`:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

# Зависимости: requirements.txt получен командой poetry export (шаг 2.1)
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# Код
COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Тег `python:3.12-slim` — версия Python проекта из README. Хеши в `requirements.txt` включают у `pip` проверку: пакет, содержимое которого не совпадает с `poetry.lock`, не установится.

**Для обоих вариантов:**

- **`--host 0.0.0.0` обязателен.** По умолчанию uvicorn слушает `127.0.0.1` — это `localhost` внутри контейнера, и запросы с вашего ноутбука до приложения не дойдут
- `CMD` записан в форме списка (exec-форма): uvicorn запускается напрямую, без оболочки, и корректно останавливается по `docker stop`
- Если код в `app/main.py` — в `CMD` замените `main:app` на `app.main:app`. `COPY . .` скопирует папку `app/` целиком

#### Шаг 5.1: Создать `.env` и `.env.example` (4 мин)

Здесь `.env` нужен только для пароля базы, который читает Compose; конфигурацию самого приложения через переменные окружения вы разберёте на воркшопе №4.

Пароль базы не пишется в `compose.yaml`: файл коммитится, и пароль навсегда останется в истории git. Compose сам читает файл `.env` из папки проекта и подставляет значения в `${...}`.

Создайте `.env.example` — он коммитится и показывает, какие переменные нужны:

```
# Скопируйте в .env и задайте свой пароль: только латинские буквы и цифры
POSTGRES_PASSWORD=changeme
# Порт приложения на вашем компьютере; если 8000 занят — поставьте, например, 8001
APP_PORT=8000
```

Создайте свой `.env` из примера:

```bash
# macOS / Linux / Git Bash
cp .env.example .env

# Windows PowerShell
Copy-Item .env.example .env
```

Откройте `.env` в редакторе и замените `changeme` на свой пароль. Со значением `changeme` стек тоже поднимется, но это пароль из публичного репозитория. Пароль — только латинские буквы и цифры: он войдёт в строку подключения `postgresql://...`, где символы `@`, `:`, `/`, `#` имеют особый смысл.

**Как проверить, что `.env` не попадёт в git:**

```bash
git check-ignore -v .env
```

**Ожидаемый вывод:** строка вида `.gitignore:N:.env	.env`, где `N` — номер строки в вашем `.gitignore`, — `.env` игнорируется (он есть в `.gitignore` с практики №1). Если вывод пустой — добавьте строку `.env` в `.gitignore` до любого `git add`; `.gitignore` войдёт в коммит шага 5.5.

**Если `.env` уже был закоммичен раньше:**

```bash
git rm --cached .env
git commit -m "chore: stop tracking .env"
```

Файл останется у вас локально, но уйдёт из следующих коммитов. Из истории он не исчезнет — переписывать её нельзя (force push запрещён правилами репозитория), поэтому пароль из того коммита считается скомпрометированным: задайте в `.env` новый и выполните `docker compose down -v` перед шагом 5.3.

#### Шаг 5.2: Написать `compose.yaml` (12 мин)

Каркас ниже соответствует типичной схеме воркшопа №3: сервисы `app` и `db`, база `app`, пользователь `postgres`, именованный том, проверка готовности базы. В нём три места не заполнены — `<ХОСТ>`, `<ПУТЬ_ТОМА>` и `<УСЛОВИЕ>`. Это критерии 3–5 проверки схемы на воркшопе №3: ответ на каждое — в вашей схеме окружения (в ситуации E — по ссылкам), вопросы к ним — в таблице под каркасом. Остальное **подставьте из своей схемы** — имена сервисов, базы, тома, пользователя, тег образа.

**Имена сервисов.** Во всех командах инструкции сервис приложения называется `app`, базы — `db`: `docker compose logs app`, `docker compose run ... app`, `docker compose build app`. Если в вашей схеме и `compose.yaml` имена другие (например, `api`) — подставляйте свои. Список имён выводит `docker compose config --services`. Будьте внимательны с `docker compose logs`: с несуществующим именем сервиса он ничего не выводит и не сообщает об ошибке — пустой вывод легко принять за пустой лог.

```yaml
services:
  app:
    build: .
    ports:
      - "${APP_PORT:-8000}:8000"
    environment:
      DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}@<ХОСТ>:5432/app   # место 1
    depends_on:
      db:
        condition: <УСЛОВИЕ>   # место 3

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}
      POSTGRES_DB: app
    volumes:
      - pgdata:<ПУТЬ_ТОМА>   # место 2
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h localhost -U postgres -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s

volumes:
  pgdata:
```

Как колонки схемы ложатся в файл:

| Колонка схемы | Ключ в `compose.yaml` | Что заполнить или проверить |
|---|---|---|
| Образ или сборка | `build: .` у приложения, `image: postgres:16` у базы | Тег образа базы — как в схеме, не `latest` |
| Порты `хост:контейнер` | `ports` | **Порт базы `5432` решает схема.** Записано, кто подключается к базе с хоста и зачем (например, клиент базы данных в IDE), — публикуйте `5432:5432` и добавьте 5432 в строку «Нужно» README. Причины нет — не публикуйте, как в каркасе (приложение ходит к базе по сети Compose), а `5432:5432` из схемы уберите (шаг 5.5). Порт приложения — `"${APP_PORT:-8000}:8000"` у всех, как в каркасе: у кого 8000 занят, меняет `APP_PORT` в своём `.env` (шаг 5.1). В схеме запишите так же (шаг 5.5) |
| Переменные окружения | `environment` | **Место 1.** Код приложения выполняется в контейнере `app`. По какому имени из этого контейнера видна база? Сверьте с ответом на вопрос 1 раздела 3 вашей схемы. Если в схеме у приложения записана ещё и `POSTGRES_PASSWORD` — отдельно её не передавайте: пароль уже внутри `DATABASE_URL`, а код читает только `DATABASE_URL`. Исправьте схему (шаг 5.5) |
| Тома | `volumes` у сервиса и в корне файла | **Место 2.** Какой тег `postgres` в вашей схеме? Куда образ этой версии пишет данные? Ответ — в разделе PGDATA [описания образа](https://github.com/docker-library/docs/blob/master/postgres/README.md); для версий до 17 и с 18 он разный |
| Зависит от (условие) | `depends_on` с `condition` | **Место 3.** Допустимые значения — в [Control startup order](https://docs.docker.com/compose/how-tos/startup-order/). При каком из них Compose дождётся, пока `healthcheck` базы пройдёт, а не только пока её контейнер запустится? |
| Healthcheck | `healthcheck` у базы | Возьмите из каркаса целиком, пользователя и имя базы — из схемы. Если в схеме проверка записана иначе (без `-h localhost`, меньше попыток) — оставьте каркас и исправьте схему (шаг 5.5): `-h localhost` в `pg_isready` — проверка по сети, а не через сокет; `retries: 10` и `start_period: 30s` — запас на первую инициализацию базы: на Docker Desktop она идёт до полутора минут |

`${POSTGRES_PASSWORD:?...}` — подстановка с проверкой: если переменной нет в `.env` или она пустая, Compose остановится с понятной ошибкой вместо того, чтобы поднять базу без пароля.

Пользователь `postgres` — `POSTGRES_USER` не нужен, из схемы его уберите (шаг 5.5). Если в вашей схеме пользователь не `postgres` — добавьте у `db` переменную `POSTGRES_USER` и поменяйте пользователя в `DATABASE_URL` и в `pg_isready -U`.

Проверьте синтаксис и подстановку:

```bash
docker compose config --quiet
```

**Ожидаемый вывод:** пустой — ошибок нет. Без `--quiet` команда выведет итоговую конфигурацию **с подставленным паролем** — не копируйте этот вывод в PR и чаты.

**Как проверить, что все три места заполнены:** `config --quiet` ловит только место 3 (`condition value must be one of ...`). Поиск по файлу ловит все три:

```bash
# macOS / Linux / Git Bash
grep -n "<" compose.yaml

# Windows PowerShell
Select-String -Pattern "<" -Path compose.yaml
```

**Ожидаемый вывод:** пустой. Если строка нашлась — место не заполнено.

#### Шаг 5.3: Поднять стек и проверить (6 мин)

```bash
docker compose up --build -d
docker compose ps
```

**Ожидаемый вывод** `up`: строки `Container ...-db-1 Waiting` → `Healthy` → `Container ...-app-1 Started`: приложение стартует только после того, как база готова. Если строк `Waiting` и `Healthy` нет, а `app` стартует сразу за `db` — вернитесь к месту 3.

**Ожидаемый вывод** `ps`:

```
NAME                  IMAGE                 ...  SERVICE   STATUS                    PORTS
<папка>-app-1         <папка>-app           ...  app       Up 3 seconds              0.0.0.0:8000->8000/tcp, [::]:8000->8000/tcp
<папка>-db-1          postgres:16           ...  db        Up 10 seconds (healthy)   5432/tcp
```

Вместо `app` и `db` — имена сервисов из вашего `compose.yaml`; у базы в колонке `PORTS` будет `0.0.0.0:5432->5432/tcp`, если по схеме порт базы опубликован.

Проверка:

```bash
# macOS / Linux
curl -i http://localhost:8000/health

# Windows PowerShell
curl.exe -i http://localhost:8000/health
```

**Ожидаемый вывод:**

```
HTTP/1.1 200 OK
...
{"status":"healthy","database":"ok"}
```

Если сразу после `up` `curl` пишет `Connection refused` или `Empty reply from server` — приложение ещё стартует, повторите через 2–3 секунды. Если `503` — смотрите лог приложения:

```bash
docker compose logs app          # app — имя сервиса приложения в вашем compose.yaml
```

Пустой вывод почти всегда означает, что имя сервиса указано неверно (см. «Имена сервисов» в шаге 5.2), а не что лог пуст.

Строка `Health check: database is unavailable: ...` назовёт причину; что с ней делать — в разделе «Если не работает». Вывод логов может содержать пароль базы: в PR и чаты копируйте только строку ошибки, заменив пароль на `***`. **Точка синхронизации 103.**

#### Шаг 5.4: Проверка «на отказ» и чистый старт (6 мин)

**Перед тем как остановить базу, ответьте командой:** база остановлена, затем снова запущена командой `docker compose start db`, а контейнер `app` никто не перезапускал. Что вернёт `/health` через 10 секунд после запуска базы? Почему? Запишите ответ, затем проверьте.

```bash
docker compose stop db
curl -i http://localhost:8000/health      # PowerShell: curl.exe -i ...
curl -i http://localhost:8000/
docker compose start db
# подождите 10 секунд
curl -i http://localhost:8000/health
```

**Ожидаемый вывод:** при остановленной базе `/health` — `503` и `"database":"unavailable"`, `/` — `200`; после `start db` через несколько секунд `/health` снова `200`. Контейнер приложения всё это время работает. Сравните с предсказанием и объясните, какая строка обработчика из шага 3.1 делает это возможным.

**Чистый старт — то, что сделает проверяющая команда.** `down -v` удаляет контейнеры и том с данными базы, затем стек поднимается командой из [DoD, раздел 3](../../definition-of-done.md):

```bash
docker compose down -v
docker compose up --build
```

Здесь `up` без `-d`: логи идут в этот терминал. Во втором окне проверьте `/health` — `200`. После `down -v` база инициализируется заново, от `up` до первого ответа — до 1,5–2 минут на Docker Desktop (Windows, macOS), на Linux быстрее: пока в логах нет строки `Application startup complete.` от приложения, `curl` не получит ответа — повторите через несколько секунд. Затем остановите стек в первом окне: `Ctrl+C`.

**Как проверить, что сработало:** стек поднялся с первой попытки, без ручных действий между `down -v` и `up`.

### Этап 7: Межкомандная проверка воспроизводимости (25 мин)

Вы проверяете то, что в конце курса другие команды будут оценивать по [системе 360°](../../assessment.md) в критерии «Воспроизводимость»: стек поднимается командой `docker compose up --build` с первого раза **без дополнительных вопросов**. Проверяется ветка открытого PR — до merge, чтобы авторы успели исправить найденное.

**Как это оценивается.** Как на практике №2: **зачёт / незачёт**, баллы не начисляются. Зачёт команда получает, если выполнены все три условия:

1. Вы опубликовали ревью в PR назначенной команды по шаблону шага 7.3: команды, результат `/health`, число вопросов авторам, замечания по формуле
2. Ваш PR получил ревью от проверяющей команды, и на каждое замечание есть ответ — правкой или аргументом
3. Проверяющие поставили вашему стеку «зачёт» — сразу или после ваших правок, до дедлайна домашнего задания

#### Шаг 7.1: Подготовить место (3 мин)

Кого вы проверяете, записано на шаге 1.3; ссылку на их PR они прислали на шаге 6.3. Если ссылки нет — найдите PR в списке **Pull requests** их репозитория. PR ещё не открыт — сообщите преподавателю: он скажет, проверять ли их запушенную рабочую ветку без PR.

Остальные остаются на своём PR: отвечают на ревью, как только оно придёт. **Если ноутбук один** — сначала проверка чужого стека (шаг 7.2), затем ответы на ревью своего PR (шаг 7.4): замечания к вашему PR к этому времени уже придут.

#### Шаг 7.3: Оставить ревью в чужом PR (5 мин)

Ревью публикует один из проверяющих из своего аккаунта (телефон или окно инкогнито, шаг 1.2). В PR проверяемой команды: **Files changed** → **Review changes**. Если замечание относится к конкретной строке (`compose.yaml`, `Dockerfile`, README) — оставьте его комментарием к этой строке. Итог — в поле резюме по шаблону:

```markdown

1. `...`
2. `...`

Результат:
- Стек поднялся с первой попытки: да / нет
- `docker compose ps`: db — healthy / [другой статус]
- `GET /health`: [код] [тело ответа]
- Время от клонирования до `200`: [мин]
- Вопросов авторам: [число]
- `.env` в репозитории и истории: нет / есть

Замечания (где → что не так → чем грозит → что предлагаете):
1. README, раздел запуска: не сказано, что `.env` создаётся из `.env.example`. Без него `docker compose up` останавливается с ошибкой `required variable POSTGRES_PASSWORD is missing a value`. Предлагаем добавить первым шагом команду копирования
2.

Рекомендация или вопрос:
-

Воспроизводимость: зачёт / незачёт
```

**Вердикт:** «зачёт» — стек поднялся по README с первой попытки, `/health` — `200`, вопросов авторам не было, `.env` нет в истории. Иначе «незачёт» и **Request changes**; при зачёте — **Comment**. Approval в чужом PR не ставьте: DoD требует approval участника команды, а ваш approval защита ветки не засчитает — вы не коллаборатор их репозитория. Он только создаст впечатление, что код одобрен.

Если замечаний нет — так и напишите, но в разделе «Результат» каждая строка должна быть заполнена фактом. **Точка синхронизации 150** — ревью должно быть у каждой команды.

Когда авторы ответят на ваши замечания (шаг 7.4), сразу после своего шага 7.4 и не позже 157-й минуты вернитесь в их PR (с телефона) и ответьте в каждом обсуждении: «исправлено, принимаю» или что ещё не так. Resolve нажимает автор PR — у вас этой кнопки нет.

#### Шаг 7.4: Ответить на ревью своего PR (5 мин)

1. На каждое замечание — ответ в PR: правка (коммит + ссылка на него в ответе) или аргумент, почему правка не нужна
2. Правки README и `compose.yaml` коммитите в ту же ветку и пушите (`git push`) — PR обновится сам
3. Обсуждения проверяющей команды закрывает автор PR (**Resolve conversation**) после их ответа в обсуждении — регламент ревью практики №2: у проверяющих без права записи кнопки Resolve нет. Обсуждения сокомандников закрывает тот, кто их открыл. Нет ответа проверяющих к 158-й минуте — замечание, **исправленное коммитом**, закройте сами с комментарием «Исправлено в <SHA>, подтверждение проверяющих — в их домашнем задании 1». 5. Если вы не согласны с вердиктом — ответьте в PR аргументом и не спорьте дальше в комментариях: спор о вердикте решает преподаватель на этапе 9

### Этап 8: Merge; для GitFlow — релиз в `main` (10 мин)

#### Шаг 8.1: Approval и merge (5 мин)

1. Сокомандник ревьюит PR по чек-листу ревьюера и критериям approval из вашего `CONTRIBUTING.md` (нет его — по пунктам шага 6.3) и ставит **Approve** из своего аккаунта (шаг 1.2). Если после approval были коммиты с правками — approval сбросился (`Dismiss stale approvals`), его нужно поставить заново
2. Все обсуждения закрыты по шагу 7.4 — иначе merge заблокирует `Require conversation resolution`. Обсуждения, закрытые по исключению шага 7.4, approval сокомандника не блокируют
3. **Code owners включены:** approval должен поставить владелец изменённых файлов (`main.py`, `docs/`, файлы в корне по `.github/CODEOWNERS`), и это не может быть автор PR. Владельца нет на занятии — «Если не работает → Code owners»
4. **Merge pull request** нажимает автор PR после approval. **Trunk-Based:** кнопка `Squash and merge`, сообщение — по Conventional Commits, например `chore: containerize app with compose stack`; номер PR `(#N)` GitHub допишет в конец сам

```bash
git checkout main          # GitFlow: develop
git pull
git ls-files compose.yaml Dockerfile .env.example
```

**Что должно получиться:** `git ls-files` выводит все три имени — файлы на месте в основной ветке разработки; в `docs/adr/002-dependency-manager.md` статус «Принято». Финальная проверка — тот же чистый старт, что на шаге 5.4, уже из основной ветки:

```bash
docker compose down -v
docker compose up --build -d
curl -i http://localhost:8000/health      # PowerShell: curl.exe -i ...
```

**Точка синхронизации 170.**

**GitHub Flow и Trunk-Based:** `Restrict deletions` экспериментом не проверяется — защищённая ветка одна, и она же default. Запись в разделе «Защита ветки» `CONTRIBUTING.md` с практики №2 («включено; на default-ветке экспериментом не проверяется») остаётся окончательной. Такой записи нет (практика №2 до исправления 2026-10-10 её не требовала) — допишите её в домашнем задании 1.

#### Шаг 8.2: GitFlow — релиз `develop` → `main` и проверка `Restrict deletions` (5 мин)

Только для GitFlow. Стек и принятый ADR 002 должны попасть в `main`: [DoD, раздел 1](../../definition-of-done.md) говорит о `main`, и именно `main` оценивается на защите проекта.

Релиз с двумя PR и проверками занимает 12–15 минут, поэтому обычно это домашнее задание 1 — незачётом это не считается (на занятии обязателен только merge фичи в `develop`, шаг 8.1). Начинайте на занятии, только если шаг 8.1 закрыт к 165-й минуте. Конец этапа застал вас на любом пункте — открытые PR оставьте открытыми, пункт, на котором остановились, назовите в комментарии-итоге (этап 9).

Как устроен релиз, решает ваш `CONTRIBUTING.md`:

| Ваш `CONTRIBUTING.md` | Источник релиза | Версия в `main.py` | Обратное вливание в `develop` |
|---|---|---|---|
| В `main` мержатся только `release/*` и `hotfix/*` (обычное правило GitFlow) | Ветка `release/<версия>` от `develop` | Поднимается в релизной ветке | Да — пункт 7 |
| PR из `develop` в `main` разрешён напрямую | `develop` | Не меняется | Не нужно: коммит слияния подтянет следующая синхронизация по шагу 1.1 |

1. **Только для `release/*`.** Номер релиза — следующая версия после той, что в `main.py` (`version="0.2.0"` с практики №2 → `0.3.0`): после релиза `GET /version` в `main` отвечает номером релиза. Поэтому единственный коммит релизной ветки — подъём версии в `main.py` (комментарий вида `# было 0.1.0` обновите или удалите) и, если README показывает ответ `GET /version`, — номера там. Поле `version` в `pyproject.toml` на приложение не влияет, его не трогайте:

   ```bash
   git checkout develop
   git pull origin develop
   git checkout -b release/0.3.0
   # в main.py: version="0.2.0" → version="0.3.0"; в README — номер в ответе /version, если он там есть
   git add main.py README.md
   git commit -m "chore: bump version to 0.3.0"
   git push -u origin HEAD
   ```

   **Ожидаемый вывод** последней команды заканчивается строкой `branch 'release/0.3.0' set up to track 'origin/release/0.3.0'.`
2. На GitHub: **New pull request**, base — `main`, compare — `release/0.3.0` (или `develop`). Заголовок — `chore: release 0.3.0 with containerized stack` (из `develop` — `chore: release containerized stack`). Если в шаблоне PR есть раздел «В какую ветку» — отметьте `main`
3. `Can't automatically merge` — в `main` есть коммиты, которых нет в `develop`: синхронизации по шагу 1.1 не было. Шаг 8.2 целиком — в домашнее задание 1: сначала синхронизация, затем этот шаг
4. Approval сокомандника, **Create a merge commit** (не squash: иначе `main` и `develop` снова разойдутся по истории)
5. `develop` пережила merge? `Automatically delete head branches` удаляет ветку-источник (`release/0.3.0` исчезнет — так и должно быть), но защищённую ветку — нет:

   ```bash
   git ls-remote --heads origin develop
   ```

   **Ожидаемый вывод:** строка с SHA и `refs/heads/develop`. Пусто — защита не сработала: на странице PR **Restore branch** и проверьте ruleset `protect-develop`

6. Повторная проверка `Restrict deletions` после реального релиза — та же попытка удаления, что на практике №2:

   ```bash
   git push origin --delete develop
   ```

   **Ожидаемый вывод:** отказ сервера — `GH013: Repository rule violations found ... Cannot delete this branch` (rulesets) либо `GH006: Protected branch update failed ... Cannot delete this protected branch` (классическая защита); `git ls-remote --heads origin develop` — ветка на месте. Если отказа на удаление `develop` в «Защите ветки» `CONTRIBUTING.md` нет (практика №2 до исправления 2026-10-10 его не требовала) — запишите его, если текст отличается — обновите: в PR обратного вливания, отдельным PR или в домашнем задании 1

7. **Только для `release/*`: обратное вливание в `develop`.** Коммит подъёма версии есть только в `main`; без обратного вливания следующая ветка от `develop` снова получит `0.2.0`. `release/0.3.0` уже удалена, её содержимое — в `main`, поэтому PR открывается из `main`: base — `develop`, compare — `main`, заголовок `chore: merge release 0.3.0 back into develop` (в разделе «В какую ветку» — `develop`). Approval сокомандника, **Create a merge commit**; защищённая `main` после merge не удалится. Проверка:

   ```bash
   git fetch --prune origin
   git log --oneline --no-merges origin/develop..origin/main
   ```

   **Ожидаемый вывод:** до merge этого PR — строка `chore: bump version to 0.3.0`; после — пустой вывод

#### Если время кончается

Что обязательно на занятии, а что переносится в домашнее задание 1, — список под таблицей тайминга («Что обязательно на занятии, а что можно перенести»). Перенесённое назовите в комментарии-итоге на этапе 9.

#### Если вы закончили раньше (бонусные задачи)

Берите по порядку, каждая — отдельный PR:

1. **Healthcheck приложения.** Добавьте сервису `app` в `compose.yaml` свой `healthcheck`, который обращается к `/health`. В образе `python:3.12-slim` нет `curl` — проверку можно написать на Python: `["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]`. **Проверка:** `docker compose ps` показывает `(healthy)` и у `app`; после `docker compose stop db` статус `app` через несколько интервалов меняется на `(unhealthy)`
2. **Политика перезапуска.** `restart: unless-stopped` для обоих сервисов. **Проверка:** `docker compose exec -T app sh -c "kill 1"` — процесс приложения завершается изнутри, как при падении. Через несколько секунд `docker compose ps -a` снова показывает `app` в статусе `Up`, а `docker inspect <имя контейнера app из ps> --format "{{.RestartCount}}"` выводит `1`. `docker compose kill` и `docker compose stop` для такой проверки не годятся: Docker считает их ручной остановкой, и `unless-stopped` после них контейнер не поднимает. Запишите в README, зачем нужна политика перезапуска, — пригодится в модуле 3 при деплое
3. **Dev-зависимость.** Добавьте `pytest` как dev-зависимость (`uv add --dev pytest` или `poetry add --group dev pytest`, для Poetry затем `poetry export`). **Проверка:** пересоберите образ `docker compose build app` — без пересборки проверка пройдёт на старом образе и ничего не докажет; затем `docker compose run --rm app python -c "import pytest"` завершается `ModuleNotFoundError`
4. **Шаблон PR.** Добавьте в чек-лист автора `.github/pull_request_template.md` пункты «lock-файл обновлён вместе с `pyproject.toml`» и «`docker compose up --build` после `down -v` поднимает стек»; для Poetry — «после изменения зависимостей выполнен `poetry export`» (митигация из ADR 002, шаг 6.2)

### Состав команды и несколько ситуаций сразу

- **Команда из 5:** раскладка на 4; пятый — второй автор документов (README) на этапах 2–5, на этапе 7 — третий проверяющий чужого стека
- **На занятии двое** (один или двое отсутствуют). Роль проверяющего берёт штурман, автора документов — тот, кто не водитель, в паузах сборки. Участник 1 — владелец ноутбука, `--author` нужен участнику 2 на этапе 4. На этапе 7 участник 2 проверяет чужой стек на этом же ноутбуке, пока участник 1 ждёт ревью своего PR. Параллельной работы над схемой (C, E) и ADR 002 (D) почти не будет — это время из буфера, минимум ADR — в шаге 6.2, остальное — домашнее задание 1.   | Участник | Этапы 1–3 | Этап 4 | Этап 5 | Этап 6 | Этапы 7–8 |
  |---|---|---|---|---|---|
  | 1 | Водитель | Штурман, исправления схемы / ADR 002 | Водитель | Водитель, автор PR | Ответы на ревью своего PR |
  | 2 | Штурман и проверяющий | Водитель | Штурман и проверяющий | Проверяющий | Внешний проверяющий чужого стека, затем approval своего PR |

- **C и D (или E и D) одновременно.** Выполняйте обе строки таблицы ситуаций: схему исправляет (в E — готовит минимум) один участник-не водитель, ADR 002 пишет другой. ### Code owners

Включено `Require review from Code Owners`, а единственный владелец пути отсутствует или сам автор PR. По порядку:

1. Попросите отсутствующего владельца посмотреть PR и поставить approval удалённо — со ссылкой на PR в чате команды. Это основной путь: правила не меняются
2. Если к 160-й минуте approval нет — попросите разрешения у преподавателя. Только получив его, участник с правами администратора (владелец репозитория на GitHub) временно снимает правило, как в бонусной задаче 1 практики №2: **Settings → Rules → Rulesets** → ruleset ветки, в которую открыт PR → снять `Require review from Code Owners` → **Save**. Approval сокомандника по-прежнему обязателен — снимается только требование владельца файлов
3. Merge, затем сразу вернуть галочку `Require review from Code Owners` и **Save**
4. В комментарии-итоге (этап 9) записать: правило снималось на время merge с разрешения преподавателя, кто его вернул. В домашнем задании 1 — PR в `CODEOWNERS`, после которого у каждого пути есть второй владелец (бонусная задача 1 практики №2: «у каждого участка — владелец, который в нём обычно не пишет»)

Ждать отсутствующего владельца до конца занятия не нужно.

Не нашли своего случая — покажите преподавателю **текст ошибки** и команду, которая её вызвала.

Роль преподавателя в репозиториях команд — **Write**. Все проверки ниже выполняются по PR и по клону репозитория.

| Что проверяем | Как проверяем | Признак выполнения |
|---|---|---|
| Lock-файл и прямые зависимости | PR, **Files changed**: `pyproject.toml`, `uv.lock` / `poetry.lock` | В `dependencies` — прямые зависимости с `psycopg[binary]`, без транзитивных пинов из `pip freeze`; lock-файл в PR |

### 1. Закрыть незавершённое

Довести до merge всё, что не успели на занятии: PR со стеком, ответы на замечания проверяющей команды, пункты чек-листа самопроверки, названные преподавателем. Если вердикт по воспроизводимости — «незачёт», после правок попросите проверяющую команду повторить холодный запуск. Повторный вердикт они оставляют комментарием в PR с правками (если исходный PR уже смержен — в новом PR), а вы добавляете ссылку на этот комментарий в исходный PR. Командам на GitFlow — синхронизация `develop` с `main` (шаг 1.1), если её не было, затем релиз в `main`, обратное вливание в `develop` и повторная проверка `Restrict deletions` (шаг 8.2), если не успели; текст отказа на удаление `develop` запишите в раздел «Защита ветки» `CONTRIBUTING.md`, если его там нет, или обновите, если он отличается. Ситуация D — дописать в ADR 002 «Риски и митигация» и дополнить остальные разделы шаблона. Ситуация E — полная схема отдельным PR: остальные колонки таблицы сервисов и разделы 1, 3 по работающему `compose.yaml`; раздел 4 — по ревью проверяющей команды в этом PR (вы переносите его в файл коммитом с `--author` рецензента), раздел 5 — вы. **Всем командам как проверяющим:** если команда, которую вы проверяли, в ситуации E — в её PR со схемой оставьте ревью по чек-листу раздела 4 бланка комментарием; в обсуждениях её PR со стеком, закрытых без вас по исключению шага 7.4, ответьте «подтверждаю» или «не исправлено» (тогда авторы снимают Resolve и исправляют). GitHub Flow и Trunk-Based без записи о `Restrict deletions` в «Защите ветки» — дописать её (шаг 8.1). Включённый `Require review from Code Owners`, если на шаге 8.1 правило снималось, — PR в `CODEOWNERS` со вторым владельцем для каждого пути.

**Критерий успеха:**

- [ ] PR со стеком смержен, все комментарии ревью закрыты
- [ ] В вашем PR есть вердикт «Воспроизводимость: зачёт» от проверяющей команды — первый или повторный
- [ ] ADR 002 в основной ветке: статус «Принято», все разделы шаблона заполнены
- [ ] GitFlow: стек в `main`, для `release/*` — релиз влит обратно в `develop`; текст отказа на удаление `develop` записан в «Защите ветки» `CONTRIBUTING.md`
- [ ] Ситуация E: схема с заполненными разделами 1–5 смержена через PR
- [ ] В обсуждениях, закрытых по исключению шага 7.4, есть ответ проверяющих

**Дедлайн:** 3 дня после практики. Долги практики №2 — свой срок (блок «Практика №2 не закрыта»).

### 3. Исходное состояние образа

На практике №4 образ будут оптимизировать — multi-stage build и non-root пользователь. Чтобы было с чем сравнить, зафиксируйте, каков он сейчас:

```bash
docker compose build app            # app — имя сервиса приложения в вашем compose.yaml
docker image ls
docker compose run --rm app whoami
```

`docker image ls` показывает размер образа приложения (имя вида `<папка>-app`); в зависимости от версии Docker колонка называется `SIZE` или `DISK USAGE` и `CONTENT SIZE` — запишите все. `whoami` покажет, от какого пользователя работает приложение в контейнере.

Создайте issue «Оптимизация образа приложения» и запишите в нём: базовый образ и его тег, размер образа, пользователя из `whoami`, версию Docker (`docker --version`).

**Критерий успеха:**

- [ ] Issue создан, в нём четыре значения: базовый образ, размер, пользователь, версия Docker
- [ ] Размер записан с единицами измерения и названием колонки, из которой он взят

**Дедлайн:** к началу воркшопа №4.

Файл `.env` на вашем ноутбуке не удаляйте: на воркшопе №4 вы продолжите работать с конфигурацией приложения, начиная с него.
