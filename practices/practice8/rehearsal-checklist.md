# Чек-лист репетиции защиты

**К занятию:** [практика №8](practice-8-guide.md), этапы 1–2; второй раз — за день до защиты (D − 1)  
**Кто заполняет:** части A и B — роль «Документация», часть C — «Презентация», часть D — «Демо», часть E — каждый участник, часть F — слушающая команда на репетиции

Как отмечать: ☐ → ☑ и в колонке «Доказательство» — ссылка (коммит, прогон, комментарий), вывод команды или строка файла. Пункт не выполнен — не ставьте ☑: пишите «не выполнено → кто, срок»; срок — не позже D − 1 (D — дата защиты). Таблица части A целиком уходит в описание PR финализации (шаг 1.2 инструкции).

Команды — в корне своего репозитория; где Windows PowerShell 5.1 и 7 отличается от bash — отдельной строкой. `<поддомен>` — имя вашего сервера, без угловых скобок.

После воркшопа №8, до 11.12, в чек-лист добавится раздел «Что чаще всего не проходило на воркшопе №8» — находки холодного запуска всех команд, без названий команд; о добавлении скажет строка «Истории изменений».

## Часть A. Чек-лист перед защитой

Одиннадцать пунктов — дословно «Чек-лист для самопроверки перед защитой» [Definition of Done](../../definition-of-done.md). За каждым стоят разделы DoD 1–7: «Все пункты обязательны» (примечание 1).

| № | Пункт DoD | Как проверить | Что должно получиться |
|---|---|---|---|
| 1 | `docker compose up --build` работает с первого раза | Комментарий холодного запуска сокомандника в PR документации (ДЗ 1 воркшопа №8). Раздел запуска README менялся после него — повторить: свежий клон в новую папку, только по README | `200` на `/health` без действий вне README; время — в доказательство |
| 2 | Все тесты проходят | **Actions** → последний прогон CI на `main` → лог джоба `test`; GitFlow — и последний прогон `develop`: его код придёт в `main` релизом на репетиции | Строка `N passed`, нет `failed` и `error` |
| 3 | Покрытие кода тестами — не меньше 60 % по отчёту джоба `test` | Тот же лог (GitFlow — оба): раскройте шаг `pytest` щелчком по названию, `TOTAL` — в конце его вывода (поле **Search logs** ищет только в раскрытых шагах) | Строка вида `TOTAL               57      3    95%`; последнее число не меньше `60%`. Что считается кодом — `[tool.coverage.run]` и ADR о тестировании |
| 4 | Пайплайн CI/CD зеленый | **Actions** → последний прогон на `main`; GitFlow — и на `develop` (там `publish` не запускается) | Все джобы зелёные, в том числе `publish` (и `deploy` у способа B) |
| 5 | Приложение доступно по публичному URL | `curl -sS -o /dev/null -w "%{http_code} %{ssl_verify_result}\n" https://<поддомен>/health`; Windows PowerShell 5.1 и 7: `` curl.exe -sS -o NUL -w "%{http_code} %{ssl_verify_result}`n" https://<поддомен>/health `` | `200 0` без `-k`. `000` и `curl: (60)` — сертификат не проходит проверку. Ситуация I — пункт остаётся ☐: публичного URL нет; в доказательстве — ссылка на согласование `DEPLOY.md` преподавателем в PR и «публичного URL нет, „Деплой“ на защите — частично» вместо «кто, срок» |
| 6 | `/health` возвращает `200 OK` | `curl -i https://<поддомен>/health` (PowerShell — `curl.exe -i`) | `HTTP/... 200` и тело, как в README. Ситуация 5 — `curl -k -i`: без `-k` будет `curl: (60)`, это уже записано в пункте 5; ситуация I — `curl -k -i https://localhost/health` |
| 7 | README содержит все необходимые разделы | Таблица аудита README (раздел 5.2 [материалов воркшопа №8](../../workshops/workshop8/workshop8-materials.md)). К 50-й — по README в ветке PR финализации; в буфере 1, после merge на репетиции, — по README в `main`. GitFlow — после merge релиза: `git fetch --prune origin`, затем `git diff --stat origin/main origin/develop -- README.md` | Шесть пунктов DoD 7 — «есть», ни одного «нет», «устарело», «ДЗ 1»; пример `/version` — как ответ сервера. GitFlow — `git diff` ничего не выводит или только `1 file changed, 1 insertion(+), 1 deletion(-)`: строка примера `/version`, поднятая в релизе, придёт в `develop` обратным merge после 145-й |
| 8 | Есть минимум 2 ADR | `git ls-files docs/adr`; статусы в файлах и в индексе ADR README | Не меньше двух ADR с разделами Контекст, Решение, Обоснование, Последствия; статусы совпадают. ADR 006 «Предложено» — строка «на защите — вопрос по критерию „Архитектура“». Не сделаны п. 5 и 7 ADR 006 «(измерено)», приложение Б или basic auth варианта (б) — здесь же «не выполнено → кто, срок» |
| 9 | Подготовлена презентация (7 минут) | К 50-й минуте — «после репетиции»; в буфере 1 — время из протокола репетиции (часть F) | 7:00 ± 0:30 |
| 10 | Подготовлен сценарий live-demo (5 минут) | К 50-й — «после репетиции»; в буфере 1 — «merge → `200`» из протокола | Время по часам; больше 5 минут — в части D сказано, что говорите, пока идёт прогон |
| 11 | Все участники команды готовы отвечать на вопросы | К 50-й — «после репетиции»; на шаге 5.1 инструкции — ☑, только если каждый уже ответил вслух на два вопроса части E по своим ролям (бонусная задача 2 буфера 1); иначе — «не выполнено → кто, к D − 1» | Кто не готов — строка «кто, к D − 1» |

## Часть C. Каркас презентации (7 минут)

Слайды не обязательны: годится любой формат, который можно показать с ноутбука или телефона. На защите после презентации — live-demo и вопросы, поэтому презентация не показывает код и не пересказывает ADR целиком.

| № | Часть | Время | Что сказать | Источник в репозитории | Кто говорит |
|---|---|---|---|---|---|
| 1 | Для кого и какая проблема | 1:00 | Кто пользователь, что он делает без вашего сервиса и что — с ним | README: название и краткое описание (DoD 7) |  |
| 2 | Архитектура | 1:30 | Что где работает: сервисы, прокси, база, CI, реестр, сервер | Приложение А ADR 006 (схема) |  |
| 3 | Два-три решения | 2:00 | Что выбрали, из каких вариантов и почему — по одному решению на ADR | ADR, «Обоснование» |  |
| 4 | Инцидент | 1:30 | Что сломалось за курс, как обнаружили (лог, проверка, CI), как починили, что изменили, чтобы не повторилось | Issue, PR, комментарии-итоги практик |  |
| 5 | Что дальше | 0:30 | Что не сделано и что сделали бы следующим | Комментарий-итог практики №8 |  |
| 6 | Переход к live-demo | 0:30 | Что сейчас покажете и чего ждать: «через N минут после merge — новая версия на сервере» | Время «merge → `200`» из протокола |  |
| | **Итого** | **7:00** | | | |

Части делите между всеми, кто будет на защите: на вопросы отвечает каждый.

## Часть D. Сценарий live-demo (5 минут)

PR и проверки готовы заранее; вживую — merge, деплой, `/health`. Команды деплоя по способу п. 4 ADR 006 — шаг 2.2 [инструкции](practice-8-guide.md).

| Минута | Что на экране | Что говорим | Кто |
|---|---|---|---|
| 0:00–0:30 | PR: описание, вкладка **Checks** — зелёные, approval | Что в PR и что проверено до merge |  |
| 0:30–0:45 | **Merge** (Trunk-Based — **Squash and merge**; GitFlow — релизный PR в `main`) | «Засекаем время» |  |
| 0:45–3:30 | **Actions**: прогон на `main` — `publish`, затем деплой по способу | Как новая версия попадёт на сервер (п. 4 ADR 006); что будет, если деплой не пройдёт (п. 5); по желанию — строка лога с `request_id` и как её найти (п. 7) |  |
| 3:30–4:30 | `Стало: sha-<SHA>, /health через прокси: 200`; `curl -i https://<поддомен>/health` (временный сертификат — `curl -k -i`; ситуация I — `curl -k -i https://localhost/health`) | Новый тег — SHA коммита merge |  |
| 4:30–5:00 | Итог | «merge → `200` за N минут» |  |

**Время «merge → `200`»** — по часам, от нажатия **Merge** до строки `Стало: ...: 200` или первого `200` на новом теге. Больше 5 минут — сценарий заканчивается тем, что успели, и вы говорите, сколько это обычно занимает (комментарий-итог практики №7, строка «Новая версия на сервере»; протокол репетиции).

**Запасной план:**

| Что случилось | Что делаем |
|---|---|
| Нет сети или GitHub в аудитории | Раздача интернета с телефона на ноутбук |
| SSH на сервер не проходит (способ A) | Раздача с телефона; не помогло — показать вывод `deploy.sh` с репетиции и сказать, какую команду запустили бы |
| Прогон ждёт в очереди | Говорить по строке 0:45–3:30; показать прошлый зелёный прогон на `main` |
| Деплой красный | Откат по п. 5 ADR 006 (команда из строки `Откат:` или тег из строки `Было:`; способ C — сначала выключить расписание) — это тоже демонстрация |
| Способ C: `cron` не успевает за 5 минут | Ручной запуск с тем же замком и журналом — «Способ C вручную», шаг 2.2 инструкции |
| Ситуация I | Деплой в клоне-«сервере» на ноутбуке, `curl -k -i https://localhost/health`; macOS и `sed -i` без `.bak` в `deploy.sh` — с GNU sed («Ситуация I на macOS», шаг 2.2 инструкции) |

## Часть E. Банк вопросов

Вопросы — по семи критериям преподавателя ([система оценивания](../../assessment.md), раздел 1) и по инциденту. Ответов здесь нет: ответ — ваш проект и ваши ADR. На репетиции слушатели выбирают два вопроса; к D − 1 каждый участник должен ответить вслух на два вопроса по своим ролям за курс.

| Критерий | Вопросы |
|---|---|
| Архитектура | Какой ADR вы бы сейчас пересмотрели и почему? Какой вариант вы отвергли в ADR 006 и чем он обошёлся бы? Где у вас граница между кодом приложения и конфигурацией сервера? |
| Конфигурация | Где хранится пароль базы на сервере, кто его знает и как его сменить? Чем `dev` отличается от `prod` — какие переменные? Что будет, если в `prod` не задать обязательную переменную? |
| Контейнеризация | Под каким пользователем работает приложение в контейнере и почему? Что пересобирается, если изменился только код? Как база получает схему на новом сервере? |
| CI/CD | Что блокирует merge в основную ветку? Каким тегом помечен образ на сервере и как по тегу найти коммит? Что будет, если тест упадёт после merge? |
| Деплой | Как новая версия попадает на сервер и кто это запускает? Как откатиться и сколько это занимает? Что видит пользователь во время обновления? |
| Документация | По каким шагам новый участник развернёт проект на чистом сервере? Где описаны ошибки API? Откуда берётся каждое значение `deploy/.env`? |
| Защита | Кто пользователь вашего сервиса и что он получает? Как найти в логах все строки одного запроса? Что проверяет `/health`, кроме того, что процесс жив? |
| Инцидент | Что сломалось, как вы это обнаружили, сколько заняла починка, что изменили, чтобы не повторилось? |

## Часть F. Протокол репетиции (заполняет слушающая команда)

Протоколист публикует его комментарием в PR финализации докладчиков (GitFlow — в релизном PR) со своего аккаунта, до 95-й минуты практики.

```markdown
## Протокол репетиции защиты

**Слушающая команда:** [название]; хронометрист — [имя]; протоколист — [имя]
**Докладчики:** команда [название], раунд 1 / 2

| Что | Значение | Цель |
|---|---|---|
| Презентация | __ мин __ с | 7:00 ± 0:30 |
| Остановлена на 8:00 | да, не закончили часть __ / нет | нет |
| Merge (по часам) | ЧЧ:ММ:СС | — |
| `200` на новом теге (по часам) | ЧЧ:ММ:СС / не дошло, откат | — |
| Merge → `200` | __ мин __ с | в пределах 5 минут live-demo |

Способ деплоя (п. 4 ADR 006): A / B / C; ситуация I: да / нет
Что показали в конце: [код `/health`, тег]

**Вопросы** (из части E чек-листа)

| № | Вопрос | Кто отвечал | Ответ: аргументирован / частично / нет |
|---|---|---|---|
| 1 |  |  |  |
| 2 |  |  |  |

**Замечания** (не больше двух; где → что не так → чем грозит → что предлагаете) или «Замечаний нет»:
1.
2.
```

«Аргументирован» — ответ ссылается на решение и его причину (ADR, вывод, цифру), а не на «так принято». Замечание — о том, что можно исправить до защиты: время, порядок, непонятное место, ответ без довода.
