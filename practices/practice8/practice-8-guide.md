# Практика №8: "Финализация документации, репетиция защиты, межкомандная оценка, ретроспектива модуля 4"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Командная работа по письменной инструкции + репетиция защиты парами команд + межкомандная оценка по кольцу с баллами  
**Роль преподавателя:** Модератор: точки синхронизации, кольцо и пары, проверка доказательности оценок, фиксация

Итоговая защита — отдельное занятие недели 16. На этой практике вы доводите проект до «Чек-листа для самопроверки перед защитой» [Definition of Done](../../definition-of-done.md), один раз проживаете защиту без баллов и ставите баллы назначенной команде по трём критериям [системы оценивания](../../assessment.md), раздел 2. Лекции и демо преподавателя нет. Ниже **D** — дата защиты, «D − 2» — за два дня до неё, до 23:59 этого дня; даты преподаватель пришлёт в рассылке.

## Цели практики

К концу занятия каждая команда должна:

1. **Довести** проект до «Чек-листа перед защитой» DoD: в описании PR финализации — часть A [чек-листа репетиции](rehearsal-checklist.md), у пунктов 1–8 доказательство (ссылка, вывод команды, строка `TOTAL` джоба `test` не ниже 60 %) или строка «не выполнено → кто, срок не позже D − 1», у пунктов 9–11 к 50-й минуте — «после репетиции», после неё — время из протокола и ответ по пункту 11 (буфер 1, шаг 5.1); PR зелёный, с approval, к 50-й минуте (GitFlow — релизный PR к началу своего live-demo)
2. **Отрепетировать** защиту перед другой командой: протокол репетиции (часть F чек-листа) комментарием в PR финализации от слушающей команды — время презентации (цель 7:00 ± 0:30), время «merge → `200` на новом теге» по часам, два вопроса с оценкой ответа, не больше двух замечаний по формуле «где → что не так → чем грозит → что предлагаете»
3. **Оценить** проект назначенной команды по критериям «Воспроизводимость», «Документация», «Качество кода»: issue в её репозитории по шаблону шага 3.1 — SHA её `main`, баллы 1–10 по таблицам вычетов шага 3.3, у каждого вычета находка с командой и выводом или ссылкой на строку, время холодного запуска от `git clone` до `200`, общая рекомендация; опубликован к 137-й минуте (крайний срок — D − 2)
4. **Проверить** оценку своей команды: ответ в issue оценки по каждой находке, опубликованной к 145-й минуте, — «принято» или возражение по факту с доказательством (вывод, ссылка), без возражений по вкусу; на то, что опубликуют позже, — до D − 2
5. **Провести** ретроспективу модуля 4: вердикт по пункту, перенесённому из модуля 3 (если был); issue «Ретроспектива модуля 4» по шаблону шага 4.1 — один пункт «Что меняем» со строкой «Как проверим на защите» и строка «Курс целиком» от каждого участника
6. **Спланировать** работу до защиты: комментарий-итог в PR финализации — невыполненное из частей A–E чек-листа с владельцем и сроком; кто готовит PR для live-demo защиты (открыт к D − 1, не смержен)

### Права доступа

Ограничения прошлых практик действуют: прямой push в защищённые ветки отклоняется, автор PR не может одобрить свой PR, merge блокируют красные обязательные проверки.

**Чужой репозиторий.** Issue оценки вы открываете в публичном репозитории другой команды со своего аккаунта, без роли в нём. По документации GitHub issue в публичном репозитории открывает любой вошедший пользователь, пока владелец не выключил Issues и не ограничил их создание участниками — настройка **Creation allowed by: Collaborators only** ([changelog GitHub от 29.06.2026](https://github.blog/changelog/2026-06-29-restrict-issue-creation-to-collaborators-only/), 1 мин; для репозиториев организаций то же — строка **Open issues** у роли Read в [Repository roles for an organization](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization); проверено по документации 24.11.2026). Поэтому строка про Issues в таблице выше. Не получается — «Если не работает → Оценка». Описание issue оценки правит только тот участник, который его открыл (шаг 3.1); остальные, в том числе оцениваемая команда, пишут комментарии. Логи прогонов Actions публичного репозитория видны любому, кто вошёл в GitHub ([Using workflow run logs](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs), проверено 24.11.2026). Approve в чужом репозитории не ставьте, файлы за другую команду не правьте.

### Проверка перед стартом

На ноутбуке команды, в корне своего репозитория:

```bash
git fetch --prune origin
git status
docker compose version
curl -sS -o /dev/null -w "%{http_code} %{ssl_verify_result}\n" https://<поддомен>/health
```

```powershell
# Windows PowerShell 5.1 и 7 — последняя команда
curl.exe -sS -o NUL -w "%{http_code} %{ssl_verify_result}`n" https://<поддомен>/health
```

**Что должно получиться:** `git status` — `nothing to commit, working tree clean`; `Docker Compose version v2...` или новее; последняя команда — `200 0`. Код `200` без `-k` значит, что сертификат прошёл проверку; в Windows второе число всегда `0`, решает код. `000` и строка `curl: (60)` — сертификат не проходит проверку (ситуация 5). Ситуация I — стек на ноутбуке, вместо последней команды:

```bash
curl -k -sS -o /dev/null -w "%{http_code}\n" https://localhost/health
```

```powershell
# Windows PowerShell 5.1 и 7
curl.exe -k -sS -o NUL -w "%{http_code}`n" https://localhost/health
```

**Ожидаемый вывод:** `200`. Второе число `%{ssl_verify_result}` с `-k` не нужно: проверка сертификата выключена.

## Пошаговая инструкция

Общий тайминг: **180 минут**.

| Этап | Название | Минут |
|---|---|---|
| 0 | Вход: кольцо, пара, ситуация, роли | 10 |
| 1 | Финализация и подготовка защиты по ролям | 40 |
| 2 | Репетиция защиты парами команд | 35 |
| — | Буфер 1: поздний merge и деплой, заморозка `main` | 10 |
| 3 | Межкомандная оценка по кольцу | 50 |
| — | Буфер 2: поздняя публикация, уборка | 10 |
| 4 | Ретроспектива модуля 4 | 15 |
| 5 | Итог и план до защиты | 10 |
| | **Итого** | **180** |

**Как читать таблицу.** Минуты этапов — время работы команды, а не ожидания. Прогон на PR — около 2 минут, на merge в `main` с `publish` — около 3 (цифры курса на uv). Poetry дольше: он ставится заново в каждом джобе — по прогону курса без GitHub оценка около 5,5–7 минут на PR и 3,5–4 на merge с `publish`; на GitHub не измерено, репетиция измерит. GitFlow + Poetry проходит три прогона до live-demo — релизный PR откройте сразу после merge в `develop`. В начале этапа 2 раннеры могут ждать в очереди: в одну и ту же минуту мержат все команды. Холодный запуск чужого проекта со сборкой — минуты; скачивание базовых образов по сети аудитории может занять больше получаса, поэтому образы скачивают заранее. Два буфера стоят там, где копится отставание: первый — после merge и деплоя на репетиции, второй — после оценки. **На 95-й минуте `main` замораживается** до 145-й: оценивающая команда проверяет один коммит, и все её роли видят один и тот же код. **Этап 4 начинается на 155-й минуте при любом состоянии оценки.**

**Один ноутбук на команду.** Этап 1 — на ноутбуке только водитель; «Презентация» и «Демо» работают с телефона или второго устройства. Этап 2 — ноутбук нужен докладчикам; слушателям он не нужен. Этап 3 — ноутбук у «Запуска» под холодный запуск чужого проекта (перед этим — `docker compose down` своего стека: порты). «Документация» и «Код» работают с телефона, а команды `git grep` и `curl` выполняют во втором окне терминала того же ноутбука, только пока идёт `docker compose up --build` и после `200`: в эти минуты клавиатура «Запуску» не нужна. «Запуск» их не ждёт, таймер идёт по его шагам. Есть второй ноутбук — эти команды с него. **Команда из двоих:** «Демо» — сам водитель, часть D он пишет на ноутбуке, пока идут **Checks** (шаг 1.3); время «merge → новая версия» и отката для неё выписывает второй участник вместе с частью A. Точка 50 может сдвинуться на 2–3 минуты.

**Что обязательно на занятии, а что можно перенести.**

- **На занятии обязательно:** PR финализации с таблицей части A, зелёный и с approval (этап 1); репетиция и протокол в PR (этап 2); issue оценки — хотя бы «Документация» и «Качество кода»: им сборка не нужна (этап 3); ответ на то, что опубликовано в оценке вашей команды к 145-й (шаг 3.4); issue «Ретроспектива модуля 4» (этап 4); комментарий-итог (этап 5)
- **Можно перенести до D − 2:** «Воспроизводимость», если холодный запуск упёрся в сеть аудитории (сборка без кэша, скачивание образов): оценку дописываете в том же issue по тому же SHA. Это запасной путь, а не правило: оценка, не опубликованная целиком к D − 2, — штраф 0,8 к баллам вашей команды от других команд ([система оценивания](../../assessment.md), раздел 2)
- **Можно перенести до D − 1:** merge PR финализации, если на репетиции деплой не прошёл (шаг 2.2), и всё «не выполнено» части A

### Точки синхронизации

Преподаватель проверяет их вслух. Команда, отставшая от точки больше чем на 10 минут, сообщает об этом сразу.

| Минута | Что должно быть сделано у всех команд |
|---|---|
| **10** | Записаны: кого оцениваете, кто оценивает вас, пара репетиции; ситуация названа; ветка `docs/finalize-defense` создана (ситуация 2 — ветка PR документации, обновлена `git pull`) |
| **30** | PR финализации открыт, **Checks** идут (GitFlow — PR в `develop`) |

| **67** | Раунд 1: у первых докладчиков записаны время презентации и «merge → `200`» |

| **137** | Issue оценки опубликован |

| **170** | Начинается этап 5 |

**PR к 50-й не готов** (красная проверка, нет approval). Вы докладчики раунда 1 — договоритесь с парой поменяться раундами: если её PR готов, она начинает. К началу вашего live-demo PR всё ещё не готов — live-demo по запасному плану части D: прошлый зелёный прогон на `main` и что произошло бы после merge; в протоколе — «merge не сделан». Merge и деплой — в буфере 1 (до 95-й) или до D − 1.

### Этап 1: Финализация и подготовка защиты по ролям (40 мин)

Водитель и «Документация» доводят проект до части A, «Презентация» и «Демо» одновременно готовят части C и D на своих устройствах. В PR финализации — только мелочи: правки README и ADR, тест для покрытия, хвосты ДЗ практики №7, которые укладываются в этап. Новых функций нет. Остальное — строкой «не выполнено → кто, срок».

#### Шаг 1.1: Части A и B чек-листа репетиции (12 мин)

«Документация» идёт по [чек-листу репетиции](rehearsal-checklist.md), часть A — 11 пунктов «Чек-листа перед защитой» DoD, у каждого команда проверки и ожидаемый вывод. Затем часть B — документация глазами проверяющего: Т1–Т3 и О1–О3 по своему README. Водитель тем временем выполняет команды проверок, которые нужны с ноутбука.

**Что должно получиться:** у каждого пункта части A — доказательство или «не выполнено → кто, срок»; список правок для PR — в чате команды.

#### Шаг 1.2: Правки, коммиты, PR (18 мин)

Водитель вносит правки по списку. Коммит — после каждой правки; если текст писал другой участник, автор коммита — он:

```bash
git add README.md docs/adr
git commit -m "docs: update README status for defense"
# не свой ноутбук: git commit --author="Имя Фамилия <email-из-GitHub>" -m "docs: update README status for defense"
git push -u origin HEAD
```

Пути и сообщение — свои: сообщение называет то, что изменено в этом коммите (`docs: add ADR index to README`, `docs: fix /version example in README`). Покрытие (ситуация 8) — отдельным коммитом `test: ...` с тестом. Poetry — менялись зависимости: `requirements.txt` из `poetry export` в том же коммите. Даже если всё готово, PR финализации нужен: он и есть live-demo репетиции. Тогда в нём — хотя бы одна правка, например строка «Статус» README.

PR: **Pull requests → New pull request**, ваша ветка → `main` (GitFlow — `develop`), заголовок `docs: finalize project for defense`. GitHub подставит в описание шаблон PR вашего репозитория (`.github/pull_request_template.md`, практика №2): блок ниже вставьте в начало описания, разделы шаблона заполните как обычно. Ситуация 2 — новый PR не открывайте: в PR документации замените заголовок на `docs: finalize project for defense` (при **Squash and merge** заголовок станет сообщением коммита в `main`) и допишите блок в начало его описания, ответы на ревью не удаляйте.

```markdown
## Финализация к защите

Часть A чек-листа репетиции:
[таблица части A — копия из чек-листа с заполненными колонками]

Не мержить до репетиции (этап 2): merge этого PR — live-demo.
[GitFlow — вместо строки выше: «Merge в develop — на этапе 1; live-demo — релизный PR в main».]

[таблица «Кто что делал»]
```

**Что должно получиться:** PR открыт, во вкладке **Checks** идут обязательные проверки. **Точка синхронизации 30.**

#### Шаг 1.3: Проверки, approval, без merge (10 мин)

1. Красная проверка — исправление новым коммитом в той же ветке; лог джоба — вкладка **Checks**. Джоб упал не из-за кода — `The job has exceeded the maximum execution time` или сетевая ошибка при установке зависимостей — в прогоне **Re-run jobs → Re-run failed jobs**, без нового коммита: прогон идёт на том же коммите, approval не снимается ([Re-running workflows and jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs), раздел **Re-running failed jobs in a workflow**, 2 мин)
2. Approval — участник, который не автор PR. Approval после последнего коммита
3. **GitHub Flow и Trunk-Based:** PR **не мержите**. Его merge — live-demo на шаге 2.2
4. **GitFlow:** PR в `develop` мержите сейчас, затем релиз — ветка `release/<версия>` от `develop`, версию в коде поднимите, если так записано в ADR 003 или `CONTRIBUTING.md`; пример `/version` в README — версия этого релиза:

```bash
git switch develop
git pull
git switch -c release/<версия>
# версию в коде подняли (ADR 003 или CONTRIBUTING.md) — закоммитьте её:
git commit -am "chore: bump version to <версия>"
git push -u origin HEAD
```

Релизный PR `release/<версия>` → `main`: проверки зелёные, approval, **не мержите** — его merge и есть live-demo. GitHub пишет в PR `This branch has conflicts that must be resolved` — обратного merge прошлого релиза не было: «Если не работает → Деплой на репетиции».

**Что должно получиться:** PR зелёный, с approval, не смержен; GitFlow — релизный PR открыт, **Checks** идут, зелёный и с approval — к началу вашего live-demo. **Точка синхронизации 50.**

#### Шаг 1.4: Каркас презентации (параллельно шагам 1.1–1.3)

«Презентация» заполняет часть C чек-листа: шесть частей на 7 минут, кто говорит, источник каждой части в репозитории. Инструмент любой — заметка или слайды; требование одно: показать с ноутбука или телефона на репетиции. Схема архитектуры — приложение А ADR 006, её не перерисовывайте. Инцидент — один случай курса, когда у вас что-то сломалось: что сломалось, как нашли, как починили.

**Что должно получиться:** у каждой части — тезисы, время и докладчик; сумма — 7:00.

#### Шаг 1.5: Сценарий live-demo (параллельно шагам 1.1–1.3)

«Демо» заполняет часть D: что на экране и что говорим по минутам, команды деплоя по вашему способу (шаг 2.2), запасной план. Время «merge → новая версия» — из комментария-итога практики №7, строка «Новая версия на сервере» («через N мин после merge»). Комментарий-итог или протокол практики №7 называет сбой раннера или установки зависимостей и повтор прогона — это число раздуто сбоем, не берите его: возьмите время без сбоя из README или ADR 006; его нет — считайте, что больше 4 минут (ниже), число даст протокол репетиции (пункт 10 части A, буфер 1). В README («Развёртывание на сервере» или `DEPLOY.md`) или ADR 006 записано другое время **от merge** — в сценарии берите большее, а запись с меньшим числом поправьте в PR финализации на большее и укажите, откуда оно (ссылка на комментарий-итог). Время от другой точки отсчёта — например, у способа C в ADR 006 «до 2 мин после `publish`» — не расхождение, его не правьте. Больше 4 минут (у Poetry — почти всегда, см. «Как читать таблицу») — в сценарии то, что вы говорите, пока идёт прогон. Время отката для запасного плана — п. 5 ADR 006 «(измерено)»; пометки «(измерено)» нет — в запасном плане откат без числа («командой из строки `Откат:`, время не измеряли»), а в пункте 8 части A — «не выполнено → кто, срок».

**Что должно получиться:** сценарий на 5 минут с запасным планом; «Демо» знает, где в **Actions** прогон после merge и какая строка значит успех.

### Этап 2: Репетиция защиты парами команд (35 мин)

Две команды по очереди выступают друг перед другом так, как на защите: презентация 7 минут, live-demo 5 минут, вопросы, отзыв. Баллов нет; результат — протокол в PR докладчиков. Пара — из рассылки; при нечётном числе команд одна команда выступает перед преподавателем в раунде 1. Тогда до 67-й минуты он занят: с вопросом по деплою сначала откройте «Если не работает → Деплой на репетиции», к преподавателю — после 67-й.

| Минуты раунда | Что происходит |
|---|---|
| 0–7 | Презентация докладчиков |
| 7–12 | Live-demo: merge → деплой → `/health` |
| 12–15 | Два вопроса слушателей из банка части E |
| 15–17 | Отзыв слушателей: время, ответы, до двух замечаний |

**На 8:00 хронометрист останавливает презентацию**, даже если она не закончена: в протоколе — «остановлена на 8:00, не закончили часть N», и сразу live-demo. Раунд удлиняется не больше чем на минуту, из буфера 1; на защите на презентацию тоже 7 минут (`syllabus.md`, раздел 10).

**Слушатели:** хронометрист засекает презентацию (от первой фразы до «переходим к демо») и время по часам — нажатие **Merge** и первый `200` на новом теге; двое задают по одному вопросу из части E (вопрос выбирают сами, не по порядку); протоколист заполняет бланк части F и публикует его комментарием в PR финализации докладчиков (GitFlow — в релизном PR) **до 95-й минуты**. Ноутбук слушателям не нужен.

#### Шаг 2.1: Раунд 1 (17 мин)

Докладчики — команда, которой в рассылке назначен раунд 1. Ход раунда — таблица выше, live-demo — шаг 2.2.

**Что должно получиться:** у хронометриста записаны время презентации и «merge → `200`». **Точка синхронизации 67.**

#### Шаг 2.2: Live-demo на репетиции (параллельно раундам)

Pull request и проверки готовы заранее (этап 1). Вживую — только merge и то, что за ним следует. «Демо» за ноутбуком:

1. Показывает PR: что в нём, проверки зелёные, approval
2. **Merge** (Trunk-Based — **Squash and merge**; GitFlow — merge релизного PR в `main`). Хронометрист записывает время
3. Деплой по п. 4 ADR 006 — как на шаге 7.1 [практики №7](../practice7/practice-7-guide.md) и в разделе «Развёртывание на сервере» вашего README:

| Способ | Что сделать после merge | Признак успеха |
|---|---|---|
| **A** | Дождаться зелёного `publish` (**Actions**, прогон на `main`), затем на сервере в папке `deploy`: `git fetch --prune origin`, `git checkout -B main origin/main`, `sh deploy.sh sha-<SHA коммита в main>` | `Стало: sha-<SHA>, /health через прокси: 200`, код выхода `0` |
| **B** | Ничего: после `publish` джоб `deploy` запустится сам — откройте его лог в **Actions** | В логе джоба `deploy` — строка `Стало: sha-<SHA>, /health через прокси: 200` |

#### Шаг 3.4: Ответ на оценку своей команды (8 мин)

Откройте issue оценки в своём репозитории. Ответ — комментарием в нём, по каждой опубликованной находке с вычетом; описание issue не правьте — его правит только автор из оценивающей команды. Оценка ещё не опубликована целиком (в шапке осталась строка «Статус» или нет баллов «Воспроизводимости») — отвечайте на то, что есть, остальное — задание 2 раздела «Домашнее задание», до D − 2. Свободное время — уборка `p8-cold` и строки комментария-итога.

```markdown

|---|---|---|
| В1 | принято | — |
```

| Симптом | Причина | Что сделать |
|---|---|---|
| `curl` в Windows PowerShell 5.1 спрашивает о разборе или выводит `StatusCode` | `curl` — псевдоним `Invoke-WebRequest` | `curl.exe` |
| `A parameter cannot be found that matches parameter name 'rf'` | В PowerShell `rm` — другая команда (`Remove-Item`) | `Remove-Item -Recurse -Force p8-cold` |
| `-w "%{http_code}\n"` выводит `\n` буквально | В PowerShell перевод строки — `` `n `` | Блоки PowerShell инструкции |
| `Remove-Item`: файл занят другим процессом | Стек ещё работает или терминал открыт в папке | `docker compose down -v` в папке, `cd ..`, повтор |

### Состав команды и особые случаи

- **Пара не пришла.** Вы выступаете в своём раунде перед преподавателем; протокол пишет он
- **Оцениваемая команда не пришла.** Оценка идёт: её проект на GitHub и сервер не нужны ей самой. Не пришла оценивающая вас — она всё равно оценивает вас до D − 2, по SHA `main` на 95-й минуте (его запишет преподаватель). Оценки нет и к D − 2 — преподаватель назначает другую команду (замену), в расчёт идёт её оценка ([система оценивания](../../assessment.md), раздел 2), и «Презентацию» на защите ставит тоже она; не сдавшая — штраф 0,8, «Презентацию» она этой команде не ставит. Замена публикует оценку до 12:00 D − 1; ответ оцениваемой команды — до 23:59 D − 1, к этому же сроку замена исправляет вычеты, а спор решает преподаватель
- **Владелец `.github/` не пришёл.** Approval удалённо до 50-й минуты; нет — PR финализации без изменений в его путях
- **На занятии двое** — таблица «Команда из 2 человек» шага 0.2

Не нашли своего случая — покажите преподавателю **текст ошибки** и шаг, который её вызвал.

## Чек-лист для преподавателя

Роль преподавателя в репозиториях команд — **Write**; баллы за команды он не ставит и оценки не правит: всё проверяется по PR, протоколам и issue.

| Что проверяем | Как проверяем | Признак выполнения |
|---|---|---|
| Финализация | PR финализации к 50-й | Таблица части A заполнена (9–11 — «после репетиции»); зелёный, approval, не смержен (GitFlow — релизный PR открыт, зелёный — к live-demo) |
| Ситуация I: согласование `DEPLOY.md` | Комментарий «Прошу согласовать `DEPLOY.md`» с вашим @логином в PR финализации | Ответ комментарием до 50-й: «согласован» или что поправить |
| Репетиция | Протокол в PR | Два времени; два вопроса с оценкой ответа; замечания по формуле |
| Live-demo | Протокол, комментарий-итог | Merge → `200` на новом теге или откат; время по часам |
| Заморозка | История `main` команд с 95-й по 145-ю | Merge нет |
| Межкомандная оценка | Issue в репозитории оцениваемой команды к 137-й | SHA; у каждого вычета — находка с доказательством и строка таблицы вычетов; рекомендация с причиной. Вычет без находки — вернуть рецензенту до D − 2 |
| Ответ на оценку | Комментарий в issue | По каждой находке; возражения — фактом |
| Ретроспектива модуля 4 | Issue | Вердикт с фактом; пункт с проверкой на защите; «Курс целиком» от каждого |
| План до защиты | Комментарий-итог | Невыполненное с владельцем и сроком; кто готовит PR live-demo |

**Что фиксировать по каждой команде:** ситуация · PR финализации смержен на занятии или перенос · время презентации · «merge → `200`» · кого оценивала / кто оценивал её · issue оценки к 137-й или к D − 2 · три полученных балла · спор · пункт «Что меняем» модуля 4.

## Связь с Definition of Done

Практика проверяет [Definition of Done](../../definition-of-done.md) целиком: часть A чек-листа репетиции — это «Чек-лист для самопроверки перед защитой», а за ним стоят разделы 1–7 («Все пункты обязательны», примечание 1).

| Раздел DoD | Чем проверяется на этой практике |
|---|---|
| 1. Репозиторий | PR финализации с approval; GitFlow — `develop` и `main` только через PR |
| 3. Контейнеризация: «`docker compose up --build` поднимает весь стек с первого раза» | Холодный запуск другой командой на её ноутбуке — «Воспроизводимость» |
| 4. CI/CD: «Минимум 60% покрытия»; «Все стадии … проходят успешно» | Строка `TOTAL` в логе `test` и зелёный прогон `main` — часть A и «Качество кода» |
| 5. Деплой: публичный URL, HTTPS, автоматический деплой | Live-demo репетиции (merge → `200`); `curl` без `-k` оценивающей командой. Ситуация I — `DEPLOY.md` по примечанию 2 |
| 6. Наблюдаемость: `GET /health` | `200` на новом теге в live-demo |
| 7. Документация: README, OpenAPI, ADR | Часть B; «Документация» другой команды: README, Т1–Т3, О1–О3, ADR |
| Примечание 4: «Если ваш проект невозможно развернуть по README, он не готов» | Холодный запуск только по README |
| Чек-лист перед защитой: презентация, сценарий live-demo, «все готовы отвечать» | Части C, D, E и репетиция |

**Остаётся до защиты:** всё «не выполнено» части A и принятые находки оценки — к D − 1; PR для live-demo защиты — к D − 1; «Презентация» и баллы преподавателя — на защите.

| № | Что | Критерий | Срок |
|---|---|---|---|

| 3 | Невыполненное из чек-листа репетиции | Строки таблицы комментария-итога закрыты ссылками на коммит, прогон или вывод | D − 1 |
| 4 | PR для live-demo защиты | Открыт, проверки зелёные, approval, **не смержен**; GitFlow — релизный PR; в описании — время «merge → `200`» с репетиции | D − 1 |
| 5 | Пункт «Что меняем» модуля 4 | Проверка — на защите, по строке «Как проверим на защите» issue | D |
| 6 | Балл «Презентация» команде, которую вы оценивали | Раздел «Презентация» того же issue оценки; правит автор issue, его нет на защите — другой участник комментарием «Презентация: N / 10» с причиной; критерий — [система оценивания](../../assessment.md), раздел 2; у снижения — что именно не так: время, часть презентации, ответ на вопрос. Ваша оценка не сдана к D − 2 и преподаватель назначил замену — «Презентацию» этой команде ставит замена, не вы | D, день защиты (позже — штраф 0,8 к баллам вашей команды от других команд) |
| 7 | Оценка сокомандников | По форме [системы оценивания](../../assessment.md), раздел 3: каждого сокомандника и себя (самооценка — для калибровки, в `K_вклада` не входит); ссылку на форму пришлёт преподаватель | После защиты, срок объявит преподаватель |

Сервер не выключайте до объявления итоговых баллов: спор о «Документации» по URL может решаться и после защиты.

**PR для live-demo защиты (задание 4).** На защите live-demo — то же, что на репетиции: PR и проверки готовы заранее, вживую — merge, деплой и `/health`. Изменение в PR — любое настоящее (правка из «не выполнено», строка README); merge — только на защите. GitFlow — релизный PR новой версии от `develop`, после обратного merge (буфер 2). Изменение в `main` после открытия PR — обновите ветку PR и дождитесь зелёных проверок до защиты.
