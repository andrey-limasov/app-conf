# Практика №4: "Конфигурация через `pydantic-settings`, окружения `dev` и `prod`, pre-commit и оптимизация `Dockerfile`"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Самостоятельная командная работа по письменной инструкции + приёмка работы другой командой как заказчиком + ретроспектива модуля 2  
**Роль преподавателя:** Модератор приёмки и ретроспективы, фиксация прогресса

## Цели практики

К концу занятия каждая команда должна:

1. **Реализовать** механизм конфигурации из «Решения» ADR 003 так, чтобы все параметры приложения были описаны в одном месте (`git grep -n -E "environ|getenv" -- "*.py"` находит только его), запуск без обязательной переменной завершался сообщением с её именем, а `/health` по-прежнему отвечал `200` при работающей базе и `503` при остановленной
2. **Различить** окружения `dev` и `prod` наблюдаемым поведением: `/docs` отвечает `200` в `dev` и `404` в `prod`; у секретных параметров нет значений по умолчанию; `APP_ENV` появляется в `compose.yaml` и `.env.example` в том же коммите, что и код, который его читает
3. **Настроить** pre-commit со сканером секретов из ADR 003 и базовыми проверками так, чтобы `pre-commit run --all-files` проходил, коммит файла с фиктивным ключом отклонялся, а находки из истории (если они есть) были ротированы и зафиксированы с комментарием: в `.gitleaksignore` (gitleaks) или в «Контексте» ADR 003 со словом «ротирован» (detect-secrets)
4. **Оптимизировать** `Dockerfile` — multi-stage, непривилегированный пользователь, `HEALTHCHECK` — так, чтобы `whoami` в контейнере выводил не `root`, слой зависимостей после правки кода оставался `CACHED`, а размер нового образа был записан в issue «Оптимизация образа приложения» рядом с исходным, в той же колонке `docker image ls`, с объяснением разницы одной фразой
5. **Довести** ADR 003 до статуса «Принято»: гипотезы в «Решении» заменены проверенными командами, выбран единственный источник версии приложения, ADR смержен в одном PR с реализацией и approval сокомандника; «Последствия» и приложение А уточнены на занятии или в ДЗ 1
6. **Принять** работу другой команды как заказчик: поднять её стек по README из `.env.example`, выполнить пять проверок по чек-листу шага 6.2 и оставить в её PR комментарий с командами, результатами и вердиктом «принято / не принято»
7. **Сформулировать** одно улучшение процесса команды по итогам модуля 2 в issue «Ретроспектива модуля 2»: что меняете, кто отвечает, как проверите на практике №5

### Права доступа

Ограничения практики №2 действуют: прямой push в защищённые ветки отклоняется, автор PR не может одобрить свой PR. Других прав не нужно. Для приёмки заказчиком нужен только доступ на чтение к чужому репозиторию: он публичный.

#### Шаг 1.2: Модуль настроек (10 мин)

Создайте рядом с `main.py` файл `settings.py`. Поля класса — это строки приложения А вашего ADR 003. Правила переноса:

- Строка, значение которой различается между окружениями, — поле класса. Имя поля — имя переменной в нижнем регистре: `DATABASE_URL` → `database_url`
- **Секрет** (в том числе `DATABASE_URL` — в нём пароль) — поле **без значения по умолчанию**
- Несекретный параметр — поле со значением по умолчанию, которое записано в приложении А
- Строки «не конфигурация, остаётся в коде» (`TEAM_NAME`, версия) — в класс не переносятся
- `POSTGRES_PASSWORD` и `APP_PORT` читает Compose, а не приложение, — это не поля класса

**Если приложение А расходится с образцом ниже** — не останавливайтесь, берите образец: поля `app_env`, `database_url`, `db_connect_timeout` есть у всех, на них опираются шаги 1.3–2.1. Строки `APP_ENV` нет в приложении А, таймаут назван иначе (`connect_timeout`) или помечен «остаётся в коде», модуль в «Решении» назван `config.py` — запишите расхождение, приложение А и п. 1 «Решения» поправит автор документов (шаг 5.1, пп. 2 и 7). Имя модуля — `settings.py` при любом механизме (B, A, C1, C2): на это имя опираются шаги 1.3–2.1 и проверки заказчика.

```python
"""Все параметры конфигурации приложения — в одном месте.

Значения берутся из переменных окружения, при локальном запуске — ещё и из файла .env.
Переменная окружения побеждает значение из .env.
"""
from typing import Literal

from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",   # при запуске без Docker; в контейнере .env нет (.dockerignore)
        extra="ignore",    # в .env лежат и переменные Compose: POSTGRES_PASSWORD, APP_PORT
        hide_input_in_errors=True,  # не выводить значения (в том числе пароли) в сообщение об ошибке
    )

    # Окружение: dev — ноутбук разработчика, prod — сервер
    app_env: Literal["dev", "prod"] = "dev"

    # Секрет: без значения по умолчанию, пустая строка не принимается
    database_url: str = Field(min_length=1)

    # Несекретные параметры — с умолчанием
    db_connect_timeout: int = 3


settings = Settings()
```

Три настройки в `model_config` — ответы на вопросы, которые иначе всплывут на шаге 1.4:

- `extra="ignore"` — по умолчанию `pydantic-settings` отвергает переменные из `.env`, для которых нет поля, ошибкой `Extra inputs are not permitted`. В вашем `.env` с практики №3 лежат `POSTGRES_PASSWORD` и `APP_PORT` для Compose: один `.env` служит и Compose, и приложению
- `Field(min_length=1)` — без него строка `DATABASE_URL=` в `.env` пройдёт проверку как значение
- `hide_input_in_errors=True` — без него сообщение об ошибке показывает введённые значения, в том числе начало и конец пароля из `.env`

Если ваш ADR 003 называет другие параметры (например, таймаут под другим именем или ключ внешнего API) — добавьте их по тем же правилам. Ключ внешнего API, без которого приложение не может работать, — секрет без умолчания; если без ключа отключается только одна функция, допустимо `str | None = None` с записью в «Последствиях» ADR.

**Вариант A — `os.environ`.** Тот же модуль без библиотеки; проверку при старте вы пишете сами:

```python
"""Все параметры конфигурации приложения — в одном месте."""
import os
import sys

REQUIRED = ("DATABASE_URL",)
missing = [name for name in REQUIRED if not os.environ.get(name)]
if missing:
    sys.exit(f"Не заданы обязательные переменные окружения: {', '.join(missing)}")

APP_ENV = os.environ.get("APP_ENV", "dev")
if APP_ENV not in ("dev", "prod"):
    sys.exit(f"APP_ENV должна быть dev или prod, получено: {APP_ENV}")

DATABASE_URL = os.environ["DATABASE_URL"]
DB_CONNECT_TIMEOUT = int(os.environ.get("DB_CONNECT_TIMEOUT", "3"))
```

В `main.py` дальше обращайтесь к `settings.DATABASE_URL` после `import settings`. Этот вариант не читает `.env`: при запуске без Docker переменные задаются в окружении терминала.

**Вариант C1 — python-dotenv.** Как вариант A, но `.env` читается до проверки: импорт — к остальным импортам, вызов `load_dotenv()` — сразу после них, перед строкой `REQUIRED`:

**Вариант C2 — environs.** Проверку обязательных environs делает сам:

```python

env.read_env()

APP_ENV = env.str("APP_ENV", "dev", validate=OneOf(["dev", "prod"]))
```

#### Шаг 1.3: `main.py` читает настройки (5 мин)

Что меняется в `main.py`:

1. Строку `import os` удалите, после импортов добавьте `from settings import settings`
2. В обработчике `/health` удалите блок с `os.environ.get("DATABASE_URL")` и ответом `"DATABASE_URL is not set"`: теперь без `DATABASE_URL` приложение не запустится. Проверка базы и ответ `503` при её недоступности остаются — их требует [DoD, раздел 6](../../definition-of-done.md)

```python
import logging

import psycopg
from fastapi import FastAPI
from fastapi.responses import JSONResponse

from settings import settings

app = FastAPI(...)                         # без изменений на этом шаге
logger = logging.getLogger("uvicorn.error")

# ... GET / и другие эндпоинты без изменений ...


@app.get("/health")
def health_check():
    """Приложение работает и база данных отвечает на запрос."""
    try:
        with psycopg.connect(
            settings.database_url, connect_timeout=settings.db_connect_timeout
        ) as conn:
            conn.execute("SELECT 1")
    except psycopg.Error as exc:
        logger.warning("Health check: database is unavailable: %s", exc)
        return JSONResponse(
            status_code=503,
            content={"status": "unhealthy", "database": "unavailable"},
        )
    return {"status": "healthy", "database": "ok"}
```

Строку со ссылкой `errors.pydantic.dev/...` можно не читать. Вариант A и C1 — `Не заданы обязательные переменные окружения: DATABASE_URL`, C2 — `EnvNotSetError`.

**Как проверить, что сработало:** в сообщении названа переменная, и строки `Application startup complete.` нет. Если в выводе `input_value={'postgres_password': ...}` — в `model_config` нет `hide_input_in_errors=True`. Если `Extra inputs are not permitted` — нет `extra="ignore"`. То же в контейнере вы проверите на шаге 4.2 — новым образом, так же, как проверит заказчик.

Стек целиком — `DATABASE_URL` задаёт `compose.yaml`:

```bash
docker compose up --build -d
curl -i http://localhost:8000/health        # Windows PowerShell: curl.exe -i ...
docker compose stop db
curl -i http://localhost:8000/health
docker compose start db
```

**Ожидаемый вывод:** сначала `HTTP/1.1 200 OK` и `{"status":"healthy","database":"ok"}`; при остановленной базе — `HTTP/1.1 503 Service Unavailable` и `"database":"unavailable"`; через несколько секунд после `start db` — снова `200`.

**`curl` сразу после `docker compose up`.** Приложение ещё стартует, и `curl` пишет `curl: (7) Failed to connect`, `curl: (52) Empty reply from server` или `curl: (56) Recv failure: Connection was reset` (Docker Desktop). #### Шаг 1.5: Закоммитить (2 мин)

**Правило для `.env.example`.** Вид строки зависит от того, кто читает переменную из `.env`:

| Кто читает из `.env` | Какие переменные | Строка в `.env.example` |
|---|---|---|
| Compose — подставляет в `compose.yaml` | `POSTGRES_PASSWORD`, `APP_PORT`, с шага 2.1 — `APP_ENV` | Активная: секрет — с заглушкой, остальные — со значением для `dev` |
| Только приложение, запущенное без Docker | `DB_CONNECT_TIMEOUT`, с шага 2.3 — `DATABASE_URL` с `localhost` | Закомментированная, с образцом значения |

Строка появляется в том же коммите, что и код, который читает переменную. Приложению в контейнере `.env` не виден (его исключает `.dockerignore`): значения ему задаёт `environment` в `compose.yaml`, в том числе `DATABASE_URL`, собранный из `POSTGRES_PASSWORD`. Поэтому `DATABASE_URL` — единственный параметр класса настроек, у которого строки в `.env.example` может не быть: если порт 5432 не опубликован (шаг 2.3).

Допишите новый параметр (имя и умолчание — как в вашем `settings.py`):

```
# Таймаут подключения к базе, секунд (необязательно, по умолчанию 3).
# Действует при запуске без Docker. В контейнере не задаётся: действует умолчание из settings.py
# DB_CONNECT_TIMEOUT=3
```

`compose.yaml` на этом шаге не меняется. Понадобится другое значение в контейнере — это строка `DB_CONNECT_TIMEOUT: ${DB_CONNECT_TIMEOUT:-3}` в `environment`, тогда строка в `.env.example` становится активной (её подставляет Compose); на занятии это не требуется.

```bash

git add settings.py main.py pyproject.toml uv.lock .env.example
# Poetry
git add settings.py main.py pyproject.toml poetry.lock requirements.txt .env.example

git commit -m "feat: load configuration from settings with fail fast"
# не свой ноутбук: git commit --author="Имя Фамилия <email-из-GitHub>" -m "..."
git push
```

**Что должно получиться:** `git status` чист, `.env` в коммите нет. **Точка синхронизации 40.**

### Этап 2: Окружения `dev` и `prod`, `.env.example`, README (15 мин)

Приложение узнаёт окружение из переменной `APP_ENV`. Сервер появится в модуле 4: значения `prod` из приложения А пока гипотеза, а режим `prod` вы запускаете локально.

#### Шаг 2.1: `APP_ENV` в коде, `compose.yaml` и `.env.example` (7 мин)

В `main.py` дополните `FastAPI(...)` тремя аргументами:

```python
app = FastAPI(
    title=...,                               # ваши значения без изменений
    version=...,                             # как сейчас: число или APP_VERSION (шаг 1.3)
```

Если у прежнего последнего аргумента (`version="0.1.0"`) нет запятой — допишите её. Варианты A, C1, C2: вместо `settings.app_env` — `settings.APP_ENV` (модуль `settings` импортирован командой `import settings`).

В `compose.yaml` у сервиса приложения — строка `APP_ENV` в `environment`:

```yaml

      APP_ENV: ${APP_ENV:-dev}
      DATABASE_URL: postgresql://...      # без изменений
```

В `.env.example` — строка для новой переменной. Её подставляет Compose, поэтому по правилу шага 1.5 строка активная:

```
# Окружение приложения: dev или prod (в prod отключена документация API /docs)
APP_ENV=dev
```

Ту же строку `APP_ENV=dev` добавьте в свой `.env`.

**Файлы на окружение** (ADR 003 выбрал `.env.dev` и `.env.prod`). Реализуйте путь выше: один `.env` и переменная `APP_ENV`. Причина: Compose по умолчанию читает только `.env`, и второй файл требует ключа `--env-file` в каждой команде, а значения `prod` по ADR живут на сервере, а не в папке проекта. На шаге 5.1 перенесите прежний вариант в «Рассмотренные варианты», в п. 2 «Решения» — `APP_ENV`, в «Последствиях» — причина замены.

Проверка в `dev`:


**Ожидаемый вывод:** `HTTP/1.1 200 OK`. `curl: (7)`, `(52)` или `(56)` — приложение ещё стартует: повторяйте, как на шаге 1.4.

**Перед переключением ответьте командой:** в `.env` записано `APP_ENV=dev`, а в терминале вы задаёте `APP_ENV=prod`. Какое значение получит контейнер? Проверьте:

### Этап 3: pre-commit — сканер секретов и базовые проверки (24 мин)

pre-commit запускает проверки перед каждым `git commit` и отменяет коммит, если проверка не прошла. В конфигурацию входят сканер секретов из ADR 003 и пять базовых проверок из [pre-commit-hooks](https://github.com/pre-commit/pre-commit-hooks). Линтеры кода (ruff и аналоги) сюда не входят — они появятся в пайплайне на практике №5.

#### Шаг 3.1: Проверить pre-commit (1 мин)

```bash
pre-commit --version
```

**Ожидаемый вывод:** `pre-commit 4.x.x`. Команды нет — установите по разделу «ПО и доступы» (uv — `uv tool install pre-commit`, Poetry — `pipx install pre-commit`) и откройте новое окно терминала.

#### Шаг 3.2: Конфигурация и первый коммит через проверки (10 мин)

Создайте в корне репозитория `.pre-commit-config.yaml`.

**Если gitleaks** — путь по умолчанию. Сканер запускается из того же образа `zricethezav/gitleaks:v8.28.0`, что на воркшопе №4:

```yaml
# Проверки перед каждым коммитом. Установка в клон: pre-commit install
minimum_pre_commit_version: "4.0.0"

repos:
  # Базовые проверки файлов
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: check-added-large-files   # файлы больше 500 КБ
      - id: check-merge-conflict      # забытые маркеры <<<<<<< и >>>>>>>
      - id: check-yaml                # синтаксис compose.yaml и других YAML
      - id: detect-private-key        # закрытые ключи SSH и TLS
      - id: end-of-file-fixer         # перевод строки в конце файла

  # Сканер секретов из ADR 003: проверяет то, что вы добавили в коммит
  - repo: local
    hooks:
      - id: gitleaks
        name: gitleaks (secrets)
        language: docker_image
        # -e ...: git в контейнере доверяет папке проекта при любой ОС и любом владельце файлов
        entry: -e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory -e GIT_CONFIG_VALUE_0=* zricethezav/gitleaks:v8.28.0 git --pre-commit --redact --staged --verbose --no-banner --no-color
        pass_filenames: false
```

`rev` и тег образа закрепляют версии: у всех участников и у заказчика проверки одинаковые. `--staged` — проверить только то, что добавлено в коммит; `--redact` — не выводить найденное значение. Три ключа `-e` не удаляйте: без них на части машин (Linux, macOS) git в контейнере не признаёт репозиторий, и gitleaks пишет `Passed`, ничего не проверив. Docker должен быть запущен при каждом коммите.

**gitleaks без Docker** (ситуация F; Linux, где Docker работает только через `sudo`). gitleaks ставится как программа той же версии в папку `~/.local/bin` — туда же uv и pipx поставили pre-commit, она уже в `PATH`. Архив сверяется с контрольной суммой из файла `gitleaks_8.28.0_checksums.txt` того же релиза: в bash и zsh программа ставится, только если суммы совпали. Выполните блок для своей ОС.

```bash
# Linux x64 (Linux ARM: в строке ниже linux_arm64 вместо linux_x64)
V=8.28.0; F=gitleaks_${V}_linux_x64.tar.gz
curl -fsSLO https://github.com/gitleaks/gitleaks/releases/download/v$V/$F
curl -fsSL https://github.com/gitleaks/gitleaks/releases/download/v$V/gitleaks_${V}_checksums.txt | grep "$F" | sha256sum -c && tar -xzf "$F" gitleaks && mkdir -p ~/.local/bin && mv gitleaks ~/.local/bin/ && rm "$F"
gitleaks version
```

```bash
# macOS на Apple M1 и новее (Intel: в строке ниже darwin_x64 вместо darwin_arm64)
V=8.28.0; F=gitleaks_${V}_darwin_arm64.tar.gz
curl -fsSLO https://github.com/gitleaks/gitleaks/releases/download/v$V/$F
curl -fsSL https://github.com/gitleaks/gitleaks/releases/download/v$V/gitleaks_${V}_checksums.txt | grep "$F" | shasum -a 256 -c && tar -xzf "$F" gitleaks && mkdir -p ~/.local/bin && mv gitleaks ~/.local/bin/ && rm "$F"
gitleaks version
```

**Ожидаемый вывод (Linux, macOS):** строка вида `gitleaks_8.28.0_linux_x64.tar.gz: OK`, затем `gitleaks version` — `8.28.0`. `FAILED` и `did NOT match` — архив повреждён, программа не поставлена: удалите архив (`rm "$F"`) и повторите блок.

В Windows PowerShell — два блока: сначала скачать и сверить, затем установить.

```powershell
# Windows PowerShell, блок 1: скачать и сверить
$ProgressPreference = "SilentlyContinue"
$Url = "https://github.com/gitleaks/gitleaks/releases/download/v8.28.0"
Invoke-WebRequest "$Url/gitleaks_8.28.0_windows_x64.zip" -OutFile "$env:TEMP\gitleaks.zip"
(Invoke-RestMethod "$Url/gitleaks_8.28.0_checksums.txt") -split "`n" | Select-String windows_x64
(Get-FileHash "$env:TEMP\gitleaks.zip").Hash.ToLower()
```

**Ожидаемый вывод:** строка с суммой и именем `gitleaks_8.28.0_windows_x64.zip`, под ней — та же сумма. Суммы различаются — блок 2 не выполняйте, повторите блок 1.

```powershell
# Windows PowerShell, блок 2: установить (только если суммы совпали)
Expand-Archive "$env:TEMP\gitleaks.zip" -DestinationPath "$env:TEMP\gitleaks-tmp" -Force
New-Item -ItemType Directory -Force "$HOME\.local\bin" | Out-Null
Move-Item -Force "$env:TEMP\gitleaks-tmp\gitleaks.exe" "$HOME\.local\bin\"
Remove-Item -Recurse "$env:TEMP\gitleaks.zip", "$env:TEMP\gitleaks-tmp"
gitleaks version
```

**Ожидаемый вывод:** `8.28.0`.

**Если `gitleaks version` не сработал** (любая ОС): `gitleaks: command not found` (bash, zsh) или `The term 'gitleaks' is not recognized` (PowerShell) — откройте новое окно терминала; не помогло — `uv tool update-shell` или `pipx ensurepath`. `exec format error` или `cannot execute binary file` — архив не для вашей ОС или процессора: `rm ~/.local/bin/gitleaks` и повторите блок со своим архивом.

Замените блок `repo: local` в `.pre-commit-config.yaml`:

```yaml
    hooks:
      - id: gitleaks
        name: gitleaks (secrets)
```

То же — строкой в «Последствия» ADR 003 (шаг 5.1). В ситуации F вернуть вариант с образом можно в ДЗ 1, когда появится Docker.

**Если detect-secrets.** Вместо блока `repo: local`:

Откройте `.secrets.baseline`: в блоке `"results"` перечислены находки в текущих файлах. Каждую проверьте — это должны быть заглушки, а не реальные значения (шаг 3.4).

Подключите проверки к репозиторию и сделайте первый коммит через них:

#### Шаг 3.4: Находки в истории и ротация (6 мин)

История не переписывается (воркшоп №4): секрет, попавший в любой коммит, считается скомпрометированным и заменяется. Хук не пропустит **новые** секреты, но старые находки останутся в полной проверке истории: если команда включит её в пайплайн (модуль 3), они её остановят. Поэтому каждую находку из «Контекста» ADR 003 вы фиксируете как известную, с комментарием.

**Ситуация E — пароль БД ещё не заменён.** Задайте в `.env` новый пароль (латинские буквы и цифры) и пересоздайте базу:

```bash
docker compose down -v
docker compose up -d
```

`down -v` удаляет том: база создаётся заново с новым паролем. Каждый участник меняет пароль в своём `.env` в ДЗ 3. Ключ внешнего сервиса — отозвать у провайдера сразу (ситуация E, этап 0).

**Если gitleaks.** Полная проверка истории — команда воркшопа №4 с ключом `-v`:

```bash
# macOS / Linux
docker run --rm -v "$(pwd):/repo:ro" zricethezav/gitleaks:v8.28.0 git /repo --redact --no-banner --no-color -v
# Git Bash на Windows
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd):/repo:ro" zricethezav/gitleaks:v8.28.0 git /repo --redact --no-banner --no-color -v
# Windows PowerShell
docker run --rm -v "${PWD}:/repo:ro" zricethezav/gitleaks:v8.28.0 git /repo --redact --no-banner --no-color -v
# gitleaks без Docker (шаг 3.2), любая ОС
gitleaks git . --redact --no-banner --no-color -v
```

**Ожидаемый вывод:** `INF no leaks found` — шаг закончен. Если `WRN leaks found: N` — у каждой находки есть строка `Fingerprint:` вида `<коммит>:<файл>:<правило>:<строка>`. Создайте в корне `.gitleaksignore`: над каждым отпечатком — строка комментария, что это и что сделано:

```
# Пароль БД в коммите a1b2c3d (chore: add .env). Скомпрометирован, ротирован ГГГГ-ММ-ДД. Историю не переписываем.
a1b2c3d4e5f6...:.env:generic-api-key:1
```

Повторите проверку: `INF no leaks found`. Отпечаток — это не сам секрет, его можно коммитить.

```bash
git add .gitleaksignore
git commit -m "chore: record rotated secrets in gitleaks ignore list"
```

**Если detect-secrets.** Историю он не смотрит — находки из «Контекста» ADR 003 остаются записанными только там, со словом «ротирован». В `.secrets.baseline` — находки в текущих файлах: для каждой убедитесь, что это заглушка (`changeme`, имя переменной), и запишите в ADR 003 в «Последствия» одну строку: файл, строка, почему не секрет. Реальное значение в текущем файле — замените его на ссылку на переменную, ротируйте и пересоздайте baseline.

**Запись в ADR 003** — одна строка в «Контексте», рядом с проверкой истории воркшопа №4; её вносит автор документов (шаг 5.1). gitleaks: «полная проверка истории ГГГГ-ММ-ДД: N находок, все ротированы и в `.gitleaksignore`» или «… 0 находок». detect-secrets историю не смотрит: «проверка текущих файлов detect-secrets ГГГГ-ММ-ДД: N находок, все — заглушки» и рядом прежние находки истории со словом «ротирован». Если в истории скомпрометированного не было (воркшоп №4 нашёл 0 или только заглушки) — «находок истории нет, ротировать нечего»: слово «ротирован» нужно только там, где было что менять.

### Этап 4: Multi-stage, непривилегированный пользователь, `HEALTHCHECK` (27 мин)

Сейчас в образе лежит то, что нужно только для сборки, а приложение работает от `root`: уязвимость в приложении даёт права администратора контейнера. Multi-stage build собирает окружение в первой стадии, а в финальный образ копирует только результат.

#### Шаг 4.1: Новый `Dockerfile` (8 мин)

**Перед тем как писать, ответьте командой:** что из нынешнего образа не попадёт в финальную стадию? Насколько, по-вашему, уменьшится образ — заметно или почти нет? Запишите ответ: сверите на шаге 4.2.

**Если uv.** Замените `Dockerfile`:

```dockerfile
# Версия Python проекта (README, .python-version) — одна на обе стадии
ARG PYTHON_VERSION=3.12

# ---------- Стадия 1: сборка окружения с зависимостями ----------
FROM python:${PYTHON_VERSION}-slim AS builder

# Версия uv — вывод uv --version на ноутбуке, где на шаге 1.1 обновлён uv.lock
COPY --from=ghcr.io/astral-sh/uv:0.12.7 /uv /bin/uv

WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev --no-install-project

# ---------- Стадия 2: финальный образ ----------
FROM python:${PYTHON_VERSION}-slim

# Непривилегированный пользователь, от которого работает приложение
RUN useradd --create-home appuser

WORKDIR /app

# Из стадии сборки берётся только готовое окружение
COPY --from=builder /app/.venv /app/.venv
COPY . .

ENV PATH="/app/.venv/bin:$PATH"

USER appuser

EXPOSE 8000

# Контейнер здоров, если /health отвечает 200 (приложение живо и база доступна)
HEALTHCHECK --interval=10s --timeout=5s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=4)"]

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`PYTHON_VERSION` — версия Python вашего проекта. `0.12.7` замените на вывод `uv --version` водителя — то же правило, что на практике №3; номер в вашем нынешнем `Dockerfile` может быть другим, берите `uv --version`: этим uv на шаге 1.1 пересоздан `uv.lock`.

**Если Poetry.** Замените `Dockerfile`:

```dockerfile
# Версия Python проекта из README — одна на обе стадии
ARG PYTHON_VERSION=3.12

# ---------- Стадия 1: сборка окружения с зависимостями ----------
FROM python:${PYTHON_VERSION}-slim AS builder

WORKDIR /app
# Отдельное окружение без pip; зависимости в него ставит pip из базового образа
RUN python -m venv --without-pip /app/.venv
# requirements.txt получен командой poetry export
COPY requirements.txt ./
RUN pip --python /app/.venv/bin/python install --no-cache-dir -r requirements.txt

# ---------- Стадия 2: финальный образ ----------
FROM python:${PYTHON_VERSION}-slim

# Непривилегированный пользователь, от которого работает приложение
RUN useradd --create-home appuser

WORKDIR /app

# Из стадии сборки берётся только готовое окружение
COPY --from=builder /app/.venv /app/.venv
COPY . .

ENV PATH="/app/.venv/bin:$PATH"

USER appuser

EXPOSE 8000

# Контейнер здоров, если /health отвечает 200 (приложение живо и база доступна)
HEALTHCHECK --interval=10s --timeout=5s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=4)"]

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`--python` стоит **до** слова `install`: это параметр самого pip.

**Для обоих вариантов:**

- `ARG` до первого `FROM` действует в обеих стадиях: окружение собрано тем же Python, что запускает приложение. Разные версии в стадиях — `.venv` не запустится
- `USER appuser` стоит после всех `COPY` и `RUN`: файлы принадлежат `root` и доступны пользователю только на чтение. Приложению на этой практике писать в `/app` не нужно
- В `python:*-slim` нет `curl`, поэтому `HEALTHCHECK` написан на Python: `urlopen` завершается ошибкой при ответе `503`, и контейнер становится `unhealthy`
- Код в `app/main.py` — в `CMD` `app.main:app`

На занятии обязательны пункты 1–5 и 8, а также строки «Последствий», которых требуют развилки (файлы на окружение, gitleaks без Docker, ключ внешнего API). Пункты 6–7 целиком — если автор документов подготовил их к 106-й минуте; иначе ДЗ 1, отдельным коммитом в ту же ветку или новым PR.

**Ситуация C (ADR 003 нет).** Автор документов на этапах 1–4 копирует [шаблон ADR](../../workshops/workshop2/adr-template.md) в `docs/adr/003-configuration.md` и пишет минимум по [материалам воркшопа №4](../../workshops/workshop4/workshop4-materials.md), раздел 5. Заголовок, удаление врезки-цитаты и названия подразделов «Решения» — по таблице раздела 5.1 материалов. «Контекст» — аудит из 8 пунктов (5.3) и проверка истории (шаг 3.4 этой инструкции); «Решение» — четыре пункта по этой инструкции (`pydantic-settings`, `APP_ENV`, значения `prod` на сервере вне git, сканер в pre-commit) и строка о версии; «Последствия» — строки, которых требуют развилки (например, gitleaks без Docker); «История изменений» — строка «Предложено». Остальные разделы шаблона не удаляйте, а оставьте с пометкой «ДЗ 1». Статус — «Предложено»: таблица сравнения вариантов, приложение А, ревью другой команды и «Принято» — ДЗ 1. Этот минимум входит в PR практики и merge не блокирует. **Двое на занятии:** аудит из 8 пунктов тоже переходит в ДЗ 1; в «Контексте» — только строка о проверке истории.

Базовая ветка — `main` (GitFlow — `develop`). Заголовок — по Conventional Commits, например `feat: add configuration settings, pre-commit and optimized image` (у Trunk-Based он же станет сообщением squash-коммита, шаг 7.1). ### Этап 6: Приёмка заказчиком (27 мин)

Вы — заказчик, который получает работу команды и решает, принять ли её. Проверяется ветка открытого PR, до merge, — авторы успеют исправить найденное. Отличие от ревью на практике №3: кроме холодного старта по README вы проверяете, что обещанное в ADR 003 действительно работает.

**Как это оценивается.** Зачёт / незачёт, баллы не начисляются. Зачёт команда получает, если выполнены три условия:

1. Вы опубликовали комментарий приёмки в PR назначенной команды по шаблону шага 6.3
2. На каждое замечание заказчика к вашему PR есть ответ — правкой или аргументом
3. Заказчик поставил вашей работе «принято» — сразу или после правок, до дедлайна ДЗ 1. После правок кода «принято» ставится только по повторному запуску проверки (шаг 6.3)

#### Шаг 6.1: Подготовить место (2 мин)

Приёмку ведут два участника на ноутбуке с Docker — по таблице шага 0.2. **Если ноутбук один** — сначала приёмка чужой работы, затем правки по замечаниям к своему PR (шаг 6.4): коммит проходит через проверки pre-commit, а им нужен этот ноутбук. **Ситуация F:** приёмку вы ведёте на ноутбуке преподавателя (он подготовлен заранее) с 119-й минуты, как все; комментарий — к 146-й. Преподаватель только запускает ноутбук, команды набираете вы. Остановите свой стек, чтобы освободить порты:

```bash
docker compose down
```

#### Шаг 6.2: Холодный старт и пять проверок (17 мин)

Клонируйте репозиторий рядом со своим, на ветке PR (видна в шапке PR):

```bash
cd ..
git clone -b <ветка-PR> <URL-репозитория> peer-check
cd peer-check
```

Записывайте каждую команду и её результат — они войдут в комментарий.

**Проверка 1. Холодный старт по README.** Работайте только по разделу запуска README авторов: каждое действие, которого в README нет, и каждый вопрос авторам — замечание. Ожидаемый путь:

```bash
cp .env.example .env           # Windows PowerShell: Copy-Item .env.example .env
# в .env заменить changeme на свой пароль, если README этого требует
docker compose up --build -d
docker compose ps
curl -i http://localhost:8000/health       # Windows PowerShell: curl.exe -i ...
```

Ожидается `200`, у приложения в `docker compose ps` — `(healthy)`. Первая сборка и инициализация новой базы занимают на Docker Desktop до 2–3 минут от `up`; ошибки `curl` до старта приложения — шаг 1.4. Если README авторов велит `docker compose up --build` без `-d` (на переднем плане), запустите так и проверяйте во втором окне терминала или добавьте `-d` — это не замечание: результат тот же.

**Проверка 2. Запуск без обязательных переменных.** Имя образа — из `docker compose images` (обычно `peer-check-app`):

```bash
docker run --rm peer-check-app
```

Ожидается: контейнер завершается сам, в конце вывода названа недостающая переменная (`database_url` над строкой `Field required`; у вариантов A и C1 — `Не заданы обязательные переменные окружения: DATABASE_URL`). Последняя строка у `pydantic-settings` — ссылка `errors.pydantic.dev`, имя переменной — выше неё. Приложение запустилось и пишет `Application startup complete.` — проверки при старте нет (`Ctrl+C`).

**Проверка 3. `dev` и `prod`.**

```bash
curl -sS -i http://localhost:8000/docs | head -1
APP_ENV=prod docker compose up -d       # Linux через sudo: sudo env APP_ENV=prod docker compose up -d
curl -sS -i http://localhost:8000/docs | head -1
```

```powershell
# Windows PowerShell
curl.exe -sS -i http://localhost:8000/docs | Select-Object -First 1
$env:APP_ENV = "prod"; docker compose up -d
curl.exe -sS -i http://localhost:8000/docs | Select-Object -First 1
Remove-Item Env:APP_ENV
```

Ожидается: `200` в `dev`, `404` в `prod`. `curl: (7)`, `(52)` или `(56)` сразу после `up` — приложение стартует, повторяйте `curl` каждые 5 секунд (шаг 1.4). Если авторы различают окружения иначе — проверьте то различие, которое названо в п. 2 «Решения» их ADR 003.

**Проверка 4. Образ.**

```bash
docker image ls peer-check-app
docker compose exec -T app whoami
```

Ожидается: пользователь — не `root`. Размер сравните с таблицей в issue авторов: у вас другой Docker и, возможно, другая колонка — запишите свою колонку и число. Размер на вердикт не влияет.

**Проверка 5. Проверка секретов при коммите.** pre-commit у вас установлен с этапа 3. Если он стоит в `venv/` вашего проекта (временный путь «ПО и доступы»), активируйте это окружение: `source ../<ваша-папка>/venv/bin/activate`, Windows PowerShell — `..\<ваша-папка>\venv\Scripts\Activate.ps1`.

```bash
pre-commit install
printf '%s\n' 'API_KEY = "Zq7Lm2Xv9Rt4Wp8Ks3Nb6Hd1Fg5Jc0Ye"' > leak_probe.py
# Windows PowerShell: Set-Content -Encoding ascii -Path leak_probe.py -Value 'API_KEY = "Zq7Lm2Xv9Rt4Wp8Ks3Nb6Hd1Fg5Jc0Ye"'
git add leak_probe.py
git commit -m "test: leak probe"
```

Ожидается: строка сканера `Failed`, коммит не создан. Если сканер у авторов другой, чем у вас, pre-commit сначала установит его окружение — это минута-две. Коммит прошёл — проверка не работает: это замечание, отмените коммит `git reset HEAD~1`. Push в чужой репозиторий в любом случае не пройдёт: вы не коллаборатор. Если в выводе ``Executable `gitleaks` not found`` — авторы выбрали вариант «gitleaks без Docker» (шаг 3.2): попросите их показать проверку 5 на своём ноутбуке и запишите это.

**Сверка с ADR 003.** Откройте «Решение» ADR авторов в PR: совпадает ли то, что вы увидели, с написанным (механизм, окружения, сканер)?

После проверки уберите за собой — контейнеры, том и собранный образ:

```bash
git restore --staged leak_probe.py
rm leak_probe.py              # Windows PowerShell: Remove-Item leak_probe.py
docker compose down -v --rmi local
cd ..
```

Папку `peer-check` не удаляйте до конца ДЗ 1: повторная проверка после правок авторов идёт в ней (шаг 6.3). Вернитесь в свой репозиторий.

**Ситуация F у авторов (без Docker):** проверки 1–4 — их первая сборка; при ошибке сборки запишите шаг и текст ошибки — это и есть результат.

#### Шаг 6.3: Комментарий приёмки (4 мин)

Публикует один из заказчиков из своего аккаунта: **Files changed** → **Review changes**. Замечания к конкретной строке (`settings.py`, `Dockerfile`, README) — комментарием к строке. В поле резюме:

```markdown
Приёмка заказчиком: команда [название]
Принимали: [имена, логины GitHub], ОС: [Windows / macOS / Linux], Docker: [версия]
Ветка и коммит: [ветка], [первые 7 символов SHA — `git log --oneline -1`]

| № | Проверка | Команды | Результат |
|---|---|---|---|
| 1 | Холодный старт по README | `...` | `/health`: [код, тело]; с первой попытки: да / нет; вопросов авторам: [N]; время до `200`: [мин] |
| 2 | Запуск без обязательных переменных | `docker run --rm ...` | [строка ошибки с именем переменной] / приложение запустилось |
| 3 | `dev` и `prod` | `...` | `/docs`: dev [код], prod [код] |
| 4 | Образ | `docker image ls ...`, `whoami` | [колонка и размер]; пользователь: [имя]; в issue авторов: [до → после] |
| 5 | Проверка секретов при коммите | `pre-commit install`, коммит `leak_probe.py` | коммит отклонён: [имя проверки] / прошёл |

Сверка с «Решением» ADR 003: совпадает / расходится: [что именно]

Замечания (где → что не так → чем грозит → что предлагаете):
1. [файл, строка или раздел] → [что не так] → [чем грозит] → [что предлагаете]
2.

Вердикт: принято / не принято
```

**Вердикт «принято»** — выполнены все пять: стек поднялся по README с первой попытки и без вопросов авторам, `/health` — `200`; запуск без переменных завершился сообщением с именем переменной; `/docs` различается в `dev` и `prod` (или различие из ADR наблюдается); пользователь в контейнере — не `root`; коммит фиктивного ключа отклонён. Иначе «не принято» и **Request changes**; при «принято» — **Comment**. Approval в чужом PR не ставьте: вы не коллаборатор, защита ветки его не засчитает. **Точка синхронизации 146.**

**Повторная проверка.** Когда авторы ответят на замечания, не позже 153-й минуты вернитесь в их PR и ответьте в каждом обсуждении: «исправлено, принимаю», «проверю запуском — на занятии / в ДЗ 1» или что ещё не так. Как подтверждать:

| Что исправили авторы | Как подтвердить | Когда |
|---|---|---|
| Текст: README, ADR | По диффу коммита в PR, можно с телефона | На занятии |
| Код, `Dockerfile`, `compose.yaml`, `.pre-commit-config.yaml` | Повторить ту проверку, которая не прошла: `docker compose down` в своём репозитории, затем в `peer-check` — `git pull` и команды проверки из шага 6.2; после — уборка, как в шаге 6.2 | На занятии, если ваш ноутбук свободен после шага 7.1; иначе ДЗ 1 |

Вердикт «принято» после правок кода без повторного запуска не ставьте. PR уже смержен и ветка удалена — в `peer-check` вместо `git pull`: `git checkout main` (GitFlow: `develop`), затем `git pull`. Итог повторной проверки — новым комментарием в PR: команды, результат, вердикт. **Ситуация F:** повторный запуск — на ноутбуке преподавателя, если он свободен после 146-й минуты; иначе в ДЗ 1 на любом ноутбуке с Docker, клон `peer-check` — заново по шагу 6.2.

#### Шаг 6.4: Ответить на приёмку своего PR (4 мин, по мере поступления замечаний)

Замечания вашего заказчика приходят к 146-й минуте, поэтому этот шаг фактически идёт в начале этапа 7 и в буфере — время на него там заложено.

1. На каждое замечание — ответ в PR: правка (коммит + ссылка в ответе) или аргумент. Ответ аргументом пишите сразу, с телефона
2. Правки коммитит водитель правок по таблице шага 0.2 на ноутбуке с Docker — после того как ваши заказчики закончили приёмку и убрали за собой стек `peer-check` (`docker compose down -v --rmi local`). Коммит в ту же ветку, затем push: правки проходят через ваши проверки pre-commit. Веб-редактор GitHub для правок не используйте — он коммитит в обход проверок
3. Обсуждения заказчика закрывает автор PR (**Resolve conversation**) после ответа заказчика. Нет ответа к 154-й минуте или ответ «проверю запуском» — замечание, **исправленное коммитом**, закройте сами с комментарием «Исправлено в <SHA>, подтверждение заказчика — в их ДЗ 1»; замечания, отклонённые аргументом, без ответа заказчика не закрывайте. Пока такое обсуждение открыто, при включённом `Require conversation resolution` merge недоступен — он переходит в ДЗ 1, это не незачёт
4. «Не принято» — после правок попросите заказчика повторить проверку по шагу 6.3, блок «Повторная проверка»: правки текста он подтверждает по диффу, правки кода — повторным запуском. Не успеваете — ДЗ 1
5. Не согласны с вердиктом — ответьте аргументом в PR; спор решает преподаватель на шаге 7.2

### Этап 7: Merge и самопроверка (9 мин)

#### Шаг 7.1: Approval и merge (4 мин)

1. Сокомандник ревьюит PR по чек-листу ревьюера из `CONTRIBUTING.md` и ставит **Approve** из своего аккаунта. После новых коммитов approval сбрасывается — поставьте заново
2. Все обсуждения закрыты по шагу 6.4
3. **Code owners включены:** approval владельца изменённых путей; владельца нет — «Если не работает → Code owners»
4. **Merge pull request** нажимает автор PR. **Trunk-Based:** `Squash and merge`, сообщение по Conventional Commits, например `feat: add configuration settings, pre-commit and optimized image`. **GitFlow:** PR в `develop`; релиз в `main` — ДЗ 2

```bash
git checkout main          # GitFlow: develop
git pull
```

**Что должно получиться:** на GitHub PR в состоянии **Merged**; в `docs/adr/003-configuration.md` основной ветки статус «Принято» (ситуация C — «Предложено»). Стек из основной ветки после merge каждый участник поднимает в ДЗ 3 — на занятии не перезапускайте его: стек этой ветки уже проверили вы (шаг 4.3) и заказчик (шаг 6.2). GitHub Flow и Trunk-Based: issue образа закрыт автоматически по `Closes #`. GitFlow: GitHub закрывает issue по `Closes #` только при merge PR в ветку по умолчанию (`main`), поэтому issue сейчас открыт — это нормально; в ДЗ 2 впишите `Closes #<номер>` в описание PR релиза. Ситуация F: issue открыт до ДЗ 1.

#### Шаг 7.2: Самопроверка и комментарий-итог (5 мин)

1. Команда проходит чек-лист самопроверки ниже
2. Оставьте в своём PR комментарий-итог одним списком: входная ситуация A–F; механизм, окружения, сканер, источник версии; размер образа до и после (колонка); кого принимали (ссылка на комментарий) и ваш вердикт; вердикт заказчика по вашей работе; статус ADR 003; что переносите в ДЗ 1
3. Преподаватель на обходе уточняет неясное; спор о вердикте решается здесь

**Точка синхронизации 165** — ретроспектива начинается при любом состоянии PR.

#### Если время кончается

Что обязательно на занятии, а что переносится в ДЗ 1, — список под таблицей тайминга. Ретроспективу не сокращайте и не переносите.

#### Если вы закончили раньше (бонусные задачи)

Берите по порядку, каждая — отдельный PR:

1. **Пароль не печатается.** Сделайте `database_url` типом `SecretStr` (`from pydantic import SecretStr`), в `/health` — `settings.database_url.get_secret_value()`. **Проверка:** `uv run python -c "from settings import settings; print(settings)"` при заданном `DATABASE_URL` выводит `database_url=SecretStr('**********')`
2. **`HEALTHCHECK` на отказ.** `docker compose stop db`, затем через 30–40 секунд `docker inspect --format "{{.State.Health.Status}}" <контейнер приложения из docker compose ps>`. **Проверка:** `unhealthy`; после `docker compose start db` — снова `healthy`, контейнер не перезапускался
3. **Слои образа в issue.** Перенесите в issue образа по три самых больших слоя `before` и `after` из шага 4.2 (размер, команда) и подпишите, что в каждом
4. **`.dockerignore`.** Сверьте, что в образ не попадают `.pre-commit-config.yaml`, `.gitleaksignore`, `.secrets.baseline`, `docs/` — нужны ли они приложению? **Проверка:** `docker run --rm team-app:after ls -a` после правки
5. **Ключи внешних сервисов** (команды, чьё приложение обращается к внешнему API): ключ — поле настроек без значения по умолчанию или с `None` и записью в ADR; в `environment` в `compose.yaml` — строка `ИМЯ_КЛЮЧА: ${ИМЯ_КЛЮЧА}`, в `.env.example` — активная строка с пустым значением и комментарием (правило шага 1.5)

### Буфер (10 мин)

### Этап 8: Ретроспектива модуля 2 (15 мин)

Модуль 2 закончен: практики №3–4, воркшопы №3–4. Ретроспектива — про процесс команды, а не про технологии и не про людей.

#### Шаг 8.1: В команде (7 мин)

1. **2 минуты молча:** каждый пишет для себя (телефон, бумага) один-два пункта «что помогло» и один-два «что мешало» за модуль — роли за одним ноутбуком, PR и ревью, ADR, домашние задания, подготовка к занятиям
2. **3 минуты:** зачитайте по кругу, без обсуждения; затем выберите **один** пункт «что мешало», который команда может изменить сама до практики №5
3. **2 минуты:** создайте issue «Ретроспектива модуля 2» по шаблону:

```markdown
## Ретроспектива модуля 2 (практики №3–4, воркшопы №3–4)

**Что помогло:**
-

**Что мешало:**
-

**Что меняем (один пункт):**
- Действие: [что конкретно делаем иначе]
- Кто отвечает: [@логин]
- Как проверим на практике №5: [наблюдаемый признак — например, «у каждого PR есть approval до начала следующего этапа»]
```

Пункт «Что меняем» проверяем: «больше общаться» — не пункт, «до занятия каждый поднимает стек у себя и пишет в чат команды „готово“» — пункт.

#### Шаг 8.2: Общий круг (8 мин)

Каждая команда за одну минуту называет свой пункт «Что меняем» и как его проверит. Остальные слушают: похожий пункт у другой команды можно добавить к себе в issue строкой «Также берём у команды …». Ссылку на issue — в комментарий-итог PR.

## Если не работает

Сначала найдите сообщение об ошибке: в выводе команды, в `docker compose logs app` или в выводе pre-commit. Ищите его в таблице.

### Настройки и запуск

| Симптом | Причина | Что сделать |
|---|---|---|
| `ValidationError` ... `postgres_password` / `app_port` `Extra inputs are not permitted [type=extra_forbidden]` | В `model_config` нет `extra="ignore"`, а в `.env` лежат переменные Compose | Шаг 1.2: `extra="ignore"` |
| В сообщении об ошибке видно `input_value={'postgres_password': 'Ab...9z', ...}` | Нет `hide_input_in_errors=True`: ошибка показывает введённые значения | Добавить в `model_config`. Если вывод уже попал в чат или PR — пароль скомпрометирован, сменить (шаг 3.4) |
| Приложение запустилось с `DATABASE_URL=` (пустая строка), `/health` — `503` | У поля нет `min_length=1` | `database_url: str = Field(min_length=1)` |
| `app_env  Input should be 'dev' or 'prod' [type=literal_error]` | В `APP_ENV` опечатка или другое значение (`production`) | В `.env` или окружении — ровно `dev` или `prod` |
| `db_connect_timeout  Input should be a valid integer` | В переменной не число | Исправить значение в `.env` |
| `uvicorn main:app --reload` после ошибки настроек не завершается | С `--reload` процесс-наблюдатель ждёт правки файлов | Это нормально: `Ctrl+C`. Для проверки шага 1.4 — без `--reload` |
| Локально `/health` → `503`, хотя стек поднят | В `.env` нет `DATABASE_URL` на `localhost` или порт базы не опубликован | Шаг 2.3. Порт не опубликован — проверяйте через `docker compose up` |
| Poetry: `The requested command export does not exist.` | Не установлен плагин экспорта (Poetry переустановлен, новый ноутбук) | `poetry self add poetry-plugin-export`, затем повторить `poetry export` (шаг 1.1). Poetry в `venv/` проекта или `poetry self add` ответил `already present ... Nothing to add` — `pip install poetry-plugin-export` при активном `venv/` |
| `curl` сразу после `docker compose up` выводит пустую строку, `curl: (7) Failed to connect`, `(52) Empty reply from server` или `(56) Recv failure: Connection was reset` | Приложение ещё стартует | Повторять `curl` каждые 5 секунд, на Docker Desktop — до 30 секунд; дольше — `docker compose logs app` (шаг 1.4) |
| `ModuleNotFoundError: No module named 'pydantic_settings'` в контейнере | Poetry: не выполнен `poetry export`; uv: образ собран из старого кэша без `--build` | Poetry — `poetry export ...` и пересборка; оба — `docker compose up --build` |
| `ModuleNotFoundError: No module named 'settings'` | Код в `app/`, а импорт `from settings import ...` | `from app.settings import settings` |
| `/docs` отвечает `200` и при `APP_ENV=prod` | Контейнер не пересоздан, `APP_ENV` не передан в `environment` или переменная стоит перед `sudo` (`sudo` её сбрасывает) | `docker compose exec -T app printenv APP_ENV`; пусто — строка `APP_ENV: ${APP_ENV:-dev}` в `compose.yaml`; `dev` при `sudo` — `sudo env APP_ENV=prod docker compose up -d` |
| PowerShell: `/docs` всё ещё `404` после возврата в `dev` | `$env:APP_ENV` остался в окне терминала | `Remove-Item Env:APP_ENV`, затем `docker compose up -d` |

### pre-commit

| Симптом | Причина | Что сделать |
|---|---|---|
| `pre-commit: command not found` / `The term 'pre-commit' is not recognized` | Не установлен или папка инструментов не в `PATH` | Раздел «ПО и доступы»; uv — `uv tool update-shell`, pipx — `pipx ensurepath`, затем новое окно терминала |

| Первый коммит или `run` долго висит на `Installing environment` | Первая установка окружений проверок | Ждать: это один раз на ноутбук и версию. Не прерывать |
| `fix end of files ... Failed`, `files were modified by this hook` | Проверка дописала перевод строки | Шаг 3.3: `git add -u` и повторить коммит |
| `[WARNING] Unstaged files detected` | В рабочей папке есть незакоммиченные правки | Не ошибка: pre-commit проверяет только добавленное и возвращает правки на место |
| gitleaks: `Cannot connect to the Docker daemon` / `error during connect` | Docker Desktop не запущен | Запустить Docker и повторить коммит. Docker на этом ноутбуке нет совсем — шаг 3.2, блок «gitleaks без Docker». `--no-verify` не использовать |
| Linux: `permission denied while trying to connect to the Docker daemon socket` при коммите | Docker только через `sudo` | Шаг 3.2, блок «gitleaks без Docker», или `sudo usermod -aG docker $USER` и перелогин (ДЗ) |
| ``Executable `gitleaks` not found`` | Вариант «gitleaks без Docker», программы нет на этом ноутбуке | Поставить gitleaks (шаг 3.2) |
| `gitleaks`: `exec format error` / `cannot execute binary file` | Поставлен архив не для вашей ОС или процессора | `rm ~/.local/bin/gitleaks`, повторить шаг 3.2 с нужным архивом |
| detect-secrets: `Detect secrets ... Failed` без пояснений сразу после создания baseline в PowerShell | `.secrets.baseline` записан в UTF-16 | Пересоздать: `... detect-secrets scan \| Out-File -Encoding ascii .secrets.baseline` |
| detect-secrets: `Your baseline file (.secrets.baseline) is unstaged` | Baseline изменён, но не добавлен в коммит | `git add .secrets.baseline` |
| Сканер находит заглушку (`changeme`) в текущем файле | Ложное срабатывание | gitleaks — отпечаток в `.gitleaksignore` с комментарием (шаг 3.4); detect-secrets — пересоздать baseline и записать в ADR |
| Проба фиктивным ключом прошла, хотя проверки установлены | Файл не добавлен в коммит (`git add` пропущен) или сканер другой версии | `git status` — файл в `Changes to be committed`? Сверить `rev` и тег с шагом 3.2 |
| Проба прошла, у gitleaks `Passed` | Файл не проверялся: в `entry` нет ключей `-e GIT_CONFIG_...`, и git в контейнере не признал репозиторий | `git reset HEAD~1`, `git add leak_probe.py`, затем `pre-commit run gitleaks --verbose`. В выводе `ERR [git] error: unknown option` и `staged` — сверить `entry` с образцом шага 3.2 построчно, повторить пробу |
| `InvalidManifestError` / `InvalidConfigError` | Ошибка отступов в `.pre-commit-config.yaml` | Отступы — пробелы, как в образце; `pre-commit validate-config` |

### Образ

| Симптом | Причина | Что сделать |
|---|---|---|
| `uv sync`: `The lockfile at uv.lock needs to be updated, but --locked was provided` | `pyproject.toml` изменён после `uv.lock` (например, версия поменяна руками) | `uv lock`, закоммитить `uv.lock`; версию менять командой `uv version` |
| Контейнер падает: `exec: "uvicorn": executable file not found` | `ENV PATH` не указывает на `/app/.venv/bin` или `.venv` не скопирован из `builder` | Сверить строки `COPY --from=builder` и `ENV PATH` с образцом |
| `.venv/bin/python: No such file or directory` / `bad interpreter` | `PYTHON_VERSION` в стадиях разный | Одна `ARG PYTHON_VERSION` до первого `FROM`, обе стадии `FROM python:${PYTHON_VERSION}-slim` |
| Poetry: `The --python option must be placed before the pip subcommand name` | `--python` записан после `install` | `pip --python /app/.venv/bin/python install ...` |
| `PermissionError: [Errno 13] Permission denied` в `/app` | Приложение пишет в файл в рабочей папке, а `appuser` может только читать | Писать во временную папку (`/tmp`); если папка нужна — `RUN mkdir /app/data && chown appuser /app/data` до `USER` и запись в ADR |
| Приложение в `docker compose ps` — `(unhealthy)`, а `/health` с ноутбука отвечает `200` | В `HEALTHCHECK` другой порт или путь | `docker inspect --format "{{json .State.Health}}" <контейнер>` — в `Output` текст ошибки; порт в `HEALTHCHECK` — порт внутри контейнера (`8000`) |
| Приложение `(unhealthy)` при остановленной базе | Так и задумано: `HEALTHCHECK` смотрит `/health`, а он проверяет базу | Не ошибка |
| `whoami: cannot find name for user ID ...` | `USER` с числом без `useradd` | `RUN useradd --create-home appuser` и `USER appuser` |
| Размеры «до» и «после» в разных колонках | Замеры на разных версиях Docker | Оба замера на одном ноутбуке (шаги 0.3 и 4.2) |
| `docker run --rm team-app:before ...`: `Unable to find image` | Образ `before` не собирался (шаг 0.3) или удалён | Сравнение — с числом из issue практики №3; запишите, что замеры с разных ноутбуков |

### Состав команды и особые случаи

- **Команда из 5:** раскладка на 4; пятый — второй автор документов (README и ADR 003 параллельно) на этапах 1–4, на этапе 6 — третий заказчик
- **На занятии двое.** Роли — таблица «Команда из 2 человек» шага 0.2. Ситуация C при двоих — минимум ADR 003: «Решение» из четырёх пунктов, строка о версии и строка о проверке истории в «Контексте» (шаг 5.1), остальное — ДЗ 1. Отсутствующим — ДЗ 3 и их доля в ДЗ 1
- **Приложение не стартует без ключа внешнего API.** Заказчик ключа не получает и стек не поднимет. Сделайте функцию, которой нужен ключ, отключаемой (`str | None = None`), и запишите это в «Последствия» ADR 003; иначе вердикт по проверке 1 — «не принято»

### Code owners

Включено `Require review from Code Owners`, а единственный владелец пути отсутствует или сам автор PR — порядок тот же, что на [практике №3](../practice3/practice-3-guide.md), раздел «Если не работает → Code owners»: удалённый approval владельца; к 158-й минуте — временное снятие правила администратором **только с разрешения преподавателя**, merge, сразу вернуть правило; записать в комментарий-итог; в ДЗ 1 — второй владелец в `CODEOWNERS`.

- [ ] В issue образа строки «до» и «после» в одной колонке и объяснение разницы

## Чек-лист для преподавателя

Роль преподавателя в репозиториях команд — **Write**. Проверки — по PR и по клону.

| Что проверяем | Как проверяем | Признак выполнения |
|---|---|---|
| Одно место параметров | `git grep -n -E "environ\|getenv" -- "*.py"` в клоне | Только модуль настроек; поля из приложения А ADR 003 |
| Проверка при старте | Выборочно: `docker run --rm <образ>` без переменных | Контейнер завершается, названа переменная, значений из `.env` в выводе нет |
| `/health` проверяет базу | `main.py` в PR | Подключение к базе и `503` при ошибке остались |
| `dev` / `prod` | `compose.yaml`, `.env.example`, `main.py` в одном коммите | `APP_ENV` во всех трёх; `/docs` выключается в `prod` |
| Секреты | `.gitignore`, `.pre-commit-config.yaml`, `.gitleaksignore` / `.secrets.baseline` | Правило `.env.*` с `!.env.example`; сканер из ADR с закреплённой версией; находки истории с комментарием (`.gitleaksignore` или «Контекст» ADR у detect-secrets); ротация отмечена в ADR |
| Образ | `Dockerfile` в PR | Две стадии, одна `PYTHON_VERSION`, `USER` не `root`, `HEALTHCHECK`, зависимости копируются до кода |
| Issue образа | Issue «Оптимизация образа приложения» | «До» и «после» в одной колонке, объяснение одной фразой |
| ADR 003 | Файл после merge | «Принято», факты вместо гипотез, источник версии, строка в «Истории изменений» |
| Приёмка содержательная | PR принимаемой команды | Пять проверок с командами и результатами, сверка с ADR, вердикт по условиям |
| Замечания отработаны | Собственный PR команды | На каждое замечание заказчика — ответ правкой или аргументом |
| PR-процесс | Смерженный PR | Approval сокомандника, «Кто что делал», коммиты с `--author` |
| Ретроспектива | Issue «Ретроспектива модуля 2» | Один пункт: действие, ответственный, проверка на практике №5 |

**Что фиксировать по каждой команде** (источник — комментарий-итог в PR, шаг 7.2): ссылка на PR · входная ситуация · механизм, сканер, источник версии · размер образа до / после · кого принимали / кто принимал · вердикт заказчика · зачёт этапа 6 · ADR 003 · merge на занятии / ДЗ 1 · пункт ретроспективы · перенесённое в ДЗ.

### 1. Закрыть незавершённое

Довести до merge PR практики, если не успели; ответить на замечания заказчика; после «не принято» — попросить заказчика повторить проверку (повторный вердикт — комментарием в PR). **Всем как заказчикам:** ответить в обсуждениях, закрытых авторами без вас по исключению шага 6.4; правки кода подтверждать повторным запуском в `peer-check` (шаг 6.3, «Повторная проверка»). **Ситуация C:** ADR 003 по [материалам воркшопа №4](../../workshops/workshop4/workshop4-materials.md), разделы 5.1–5.6: таблица сравнения, приложение А, ревью команды, которую назовёт преподаватель (комментарием в PR, перенос в файл коммитом с `--author` рецензента), ответы; статус «Принято» — отдельным PR после ревью. **Ситуация F:** собрать образ, заполнить «до» и «после» в issue (образ «до» — из основной ветки до merge практики или по числу из ДЗ 3 практики №3 с пометкой) и закрыть issue со ссылкой на PR практики. **Вариант A без проверки при старте:** дописать проверку (шаг 1.2) и перевести ADR 003 в «Принято». Правило `Require review from Code Owners` снималось — PR в `CODEOWNERS` со вторым владельцем. **Пункты 6–7 шага 5.1** («Последствия», приложение А), если не вошли в PR практики, — коммитом в ветку PR до merge или отдельным PR со строкой в «Истории изменений» ADR 003.

**Критерий успеха:**

- [ ] PR практики смержен, обсуждения закрыты
- [ ] В PR есть «принято» от заказчика — первое или повторное
- [ ] ADR 003 в основной ветке со статусом «Принято»
- [ ] В issue образа строки «до» и «после» в одной колонке

**Дедлайн:** 3 дня после практики.

### 2. GitFlow: релиз `develop` → `main`

Только GitFlow. Как на шаге 8.2 практики №3, но версия поднимается в источнике из ADR 003: версия в коде — в `main.py`; версия в `pyproject.toml` — `uv version <номер>` или `poetry version <номер>`, в коммит входят `pyproject.toml` (и `uv.lock`). После релиза `GET /version` в `main` отвечает номером релиза; для `release/*` — обратное вливание в `develop`.

**Критерий успеха:**

- [ ] Настройки, pre-commit и новый `Dockerfile` в `main`
- [ ] Issue «Оптимизация образа приложения» закрыт PR релиза (`Closes #` в его описании)
- [ ] `GET /version` в `main` = номер релиза; версия поднята только в одном месте

### 3. Проверки и стек у каждого участника

Каждый участник в своём клоне:

```bash
git checkout main          # GitFlow: develop
git pull
pre-commit install
# .env: строка APP_ENV=dev; пароль БД — новый, если менялся (шаг 3.4), затем docker compose down -v
docker compose up --build -d
curl -i http://localhost:8000/health      # Windows PowerShell: curl.exe -i ...
```

`/health` — `200` из основной ветки (ошибки `curl` до старта приложения — шаг 1.4; после `down -v` до ответа — до 2–3 минут, шаг 4.3). Затем — проба фиктивным ключом (шаг 3.5; коммит должен быть отклонён, файл удалите) и стек в `prod` (`APP_ENV=prod docker compose up -d`, `/docs` — `404`; Windows PowerShell: `$env:APP_ENV = "prod"; docker compose up -d`, после проверки `Remove-Item Env:APP_ENV`). Вариант «gitleaks без Docker» — сначала поставьте gitleaks по шагу 3.2. Linux с Docker только через `sudo` — `sudo usermod -aG docker $USER` и перелогин; до этого переменную передавайте после `sudo`: `sudo env APP_ENV=prod docker compose up -d`.

**Критерий успеха:**

- [ ] Каждый участник оставил в смерженном PR комментарий: ОС, `/health` из основной ветки — `200`, проверка отклонила фиктивный ключ (имя проверки), `docker compose exec -T app whoami` — вывод, `/docs` в `prod` — `404`
- [ ] Всё, что пришлось делать сверх README, внесено в README через PR
