# Практика №7: "Развёртывание на сервере, reverse-proxy и HTTPS, структурированные логи, health-check"

**Длительность:** 4 академических часа (180 минут)  
**Формат:** Командная работа по письменной инструкции на сервере команды + приёмка сервиса другой командой по публичному URL  
**Роль преподавателя:** Модератор приёмки, фиксация прогресса

---

## Цели практики

К концу занятия каждая команда должна:

1. **Развернуть** стек `app` + `db` + reverse-proxy на сервере команды из образа `sha-<40 символов>` в **Packages**, без сборки на сервере: `curl -i https://<поддомен>/health` с ноутбука выводит `200`; `docker compose ps` на сервере — `app` и `db` `(healthy)`, прокси `Up`
2. **Настроить** reverse-proxy и HTTPS по п. 1–2 «Решения» ADR 006: `http://<поддомен>` отвечает `301` или `308` с `Location: https://...`; сертификат Let's Encrypt проходит проверку `curl` без `-k`; в `docker compose ps` порты наружу есть только у прокси, запрос с ноутбука на порты `8000` и `5432` — таймаут
3. **Вынести** переменные `prod` на сервер по п. 3: `deploy/.env` на сервере с правами `600`, `git ls-files deploy` его не показывает; `/docs` отвечает по п. 8 (`404` в вариантах (а) и (б), `200` в варианте (в))
4. **Реализовать** структурированные логи (structlog или loguru по [шаблону логирования](logging-template.md)) с Request ID: запрос через публичный URL с заголовком `X-Request-ID: <значение>` возвращает тот же заголовок; `docker compose logs app` на сервере находит по значению строку JSON с временем, уровнем, `request_id`, методом и путём
5. **Автоматизировать** деплой способом из п. 4: после merge (GitFlow — релиза) на сервере работает тег `sha-<SHA коммита в main>` без ручной правки файлов на сервере; способ A — одна команда `sh deploy.sh <тег>`, которая проверяет `/health` через прокси; время «merge → новая версия» записано в комментарии-итоге
6. **Проверить** перезапуск по п. 6: `restart: unless-stopped` (или `always`, если так в п. 6) у трёх сервисов; после завершения процесса приложения в контейнере `RestartCount` `app` — `1`, `/health` снова `200`
7. **Довести** ADR 006 до статуса «Принято» в одном PR с кодом, который его реализует (ситуации C и B без ревью другой команды — «Предложено», «Принято» — ДЗ 1): адрес, сертификат и время запуска стека — «(измерено)», отклонения от «Решения» с причиной; строка «Истории изменений» ADR 003 (значения `prod` подтверждены, `/docs` — по п. 8); ADR 005 — строкой истории только при реальном поводе
8. **Принять** сервис другой команды по её публичному URL: комментарий в её PR с командами и выводом по трём проверкам (HTTPS и редирект; закрытые порты и `/docs`; `X-Request-ID`) по формуле «где → что не так → чем грозит → что предлагаете» или доказанное «принято»; на каждое замечание к своему сервису — ответ
9. **Проверить** пункт «Что меняем» issue «Ретроспектива модуля 3» по его строке «Как проверим на практике №7»: вердикт с наблюдаемым фактом комментарием в issue

В проекте ещё нет structlog или loguru, папки `deploy/`, джоба деплоя: всё это появляется на этом занятии. Сервер готовит курс: Docker с Compose, git, межсетевой экран ufw (открыты 22, 80, 443; порты `8000` и `5432` явно запрещены), DNS-запись поддомена, пользователь в группе `docker`. Команде `sudo` не нужен. Как это делается, если сервер свой, — «Сводка полезных ссылок → Сервер».

**До занятия решите в команде:** кто водитель и кто входит на сервер (ключ на сервере только у двух человек); роли по таблицам шага 0.2; у кого второй ноутбук (этапы 2 и 3 идут параллельно — абзац «Как читать таблицу»). Ключи SSH отправляйте с тех двух ноутбуков, которые будут на занятии: этап 2 ведётся только с ноутбука, чей ключ на сервере.

**Только способ B — до занятия (владелец, 10 мин).** Ключ деплоя создаётся на самом сервере: так не нужен ключ без фразы-пароля на ноутбуке (`-N ""` в Windows PowerShell 5.1 и 7 ведёт себя по-разному), и закрытый ключ деплоя не лежит на ноутбуках. Владелец входит на сервер (команда — «Проверка перед стартом») и выполняет:

```bash
ssh-keygen -t ed25519 -N "" -C github-deploy -f ~/.ssh/deploy_key
echo "restrict $(cat ~/.ssh/deploy_key.pub)" >> ~/.ssh/authorized_keys
cat ~/.ssh/deploy_key
echo "<поддомен> $(cut -d' ' -f1,2 /etc/ssh/ssh_host_ed25519_key.pub)"
```

`restrict` перед ключом деплоя запрещает по нему интерактивный терминал и пробросы: ключ годится только для команды джоба. Вывод третьей команды — от `-----BEGIN OPENSSH PRIVATE KEY-----` до `-----END OPENSSH PRIVATE KEY-----` включительно — значение секрета `DEPLOY_SSH_KEY`; последняя строка (`<поддомен> ssh-ed25519 AAAA...`) — `DEPLOY_KNOWN_HOSTS`; `DEPLOY_HOST` — поддомен, `DEPLOY_USER` — имя пользователя. Секреты — **Settings → Secrets and variables → Actions → New repository secret** ([Using secrets in GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets), раздел **Creating secrets for a repository**, 3 мин). Затем закрытый ключ с сервера удалите — он теперь только в секрете: `rm ~/.ssh/deploy_key`. Закрытый ключ не вставляйте в чат и файлы репозитория. Ограничение **Actions permissions** списком разрешённых издателей (практика №6) джобу `deploy` не мешает: сторонних actions в нём нет. Курсом этот блок на сервере не проверен; не получилось — «Если не работает → Деплой», до занятия.

### Права доступа

Ограничения прошлых практик действуют: прямой push в защищённые ветки отклоняется, автор PR не может одобрить свой PR, merge блокируют красные обязательные проверки. Секреты Actions и настройки пакета меняет только **владелец репозитория** (личный репозиторий) или участник с ролью Admin (репозиторий организации). У преподавателя в ваших репозиториях роль Write.

**Сервер.** Пользователь команды — в группе `docker`: он запускает контейнеры без `sudo`. Это права, равные root на этом сервере ([Docker Docs: Linux post-installation steps](https://docs.docker.com/engine/install/linux-postinstall/), раздел **Manage Docker as a non-root user**): не запускайте на сервере ничего, кроме команд инструкции и своего стека. `sudo`, ufw и DNS — у курса.

**Право `workflow` у токена** нужно, если PR меняет `.github/workflows/ci.yml` (способ B). На практике №6 push с `ci.yml` прошёл — значит, право есть.

Для приёмки на этапе 8 нужен только доступ на чтение и `curl`: репозитории публичные, сервис другой команды открыт по HTTPS.

### Ключ SSH — водитель и владелец

Ключи собирают после воркшопа №7, до 25.11. Отправили и вход работает — пропустите блок. Ключ ещё не отправлен — сделайте это сейчас и напишите преподавателю: курс добавит его на сервер до занятия.

На ноутбуке, который будет на занятии (macOS, Linux, Git Bash, Windows PowerShell 5.1 и 7 — команда одна):

```bash
ssh-keygen -t ed25519 -C "<логин GitHub>"
```

На вопрос о пути к файлу — `Enter` (путь по умолчанию: `~/.ssh/id_ed25519`, в Windows — `%USERPROFILE%\.ssh\id_ed25519`). Фраза-пароль: пустая — `Enter` дважды; с фразой `ssh` будет спрашивать её при каждом входе. `Overwrite (y/n)?` — ключ уже есть: ответьте `n` и отправьте существующий. **Ожидаемый вывод:** `Your public key has been saved in ...id_ed25519.pub`. Открытый ключ:

```bash
cat ~/.ssh/id_ed25519.pub                          # macOS / Linux / Git Bash
```

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub   # Windows PowerShell 5.1 и 7
```

Одна строка `ssh-ed25519 AAAA... <логин GitHub>` — её и отправьте преподавателю в чат курса с поддоменом или названием команды. Открытый ключ — не секрет. Файл без `.pub` (`id_ed25519`) — закрытый ключ: его никому не отправляйте. Подробнее для Windows — [Key-Based Authentication in OpenSSH for Windows](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement), раздел **User key generation** (5 мин).

### Проверка перед стартом

На ноутбуке водителя, в корне репозитория (`<пользователь>` и `<поддомен>` — из рассылки, без угловых скобок):

```bash
git --version
uv --version                  # или: poetry --version
git fetch --prune origin
git branch -r                 # видна ветка ADR 006
ssh <пользователь>@<поддомен> "docker compose version && git --version && groups"
```

**Что должно получиться:** команды отвечают без ошибок (`git fetch` без вывода — нового на GitHub нет); в списке удалённых веток есть ветка ADR 006 (кроме ситуации C); последняя команда при первом входе спрашивает `Are you sure you want to continue connecting (yes/no/[fingerprint])?` — ответьте `yes`, затем печатает `Docker Compose version v...`, `git version ...` и строку групп, в которой есть `docker`. В Windows PowerShell команды те же. Пароль запрошен, `Permission denied (publickey)` или `Connection timed out` — «Если не работает → SSH и сервер».

#### Шаг 2.3: Запуск (7 мин)

**Nginx — сначала сертификат** (порт 80 свободен, пока прокси не запущен; около минуты): команда `docker compose run ... certbot certonly ...` из раздела 2.2 шаблона, ожидаемый вывод — там же. **Нет строки `Successfully received certificate.`** — прокси не запускайте: без сертификата Nginx перезапускается по кругу (`cannot load certificate`). Найдите первую ошибку certbot в «Если не работает → HTTPS и прокси»; повторите выпуск не больше одного раза (лимит Let's Encrypt). Не выдан — сразу блок «Временный сертификат» раздела 2.2 шаблона, затем команды ниже; строка в «Рисках» — по шагу 2.4.

**Все прокси:**

```bash
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
```

**Ожидаемый вывод:** `config` — пусто; `pull` скачивает образ приложения, `postgres` и прокси без запроса входа в реестр (на сервере демо курса — около минуты); `up -d` — строки `Container ... Started` (с сервисом `migrate` — до минуты: Compose ждёт `Healthy` у `db` и завершения `migrate`); через 20–40 секунд `ps` показывает `app` и `db` `Up ... (healthy)`, `proxy` `Up` с `0.0.0.0:80->80/tcp` и `0.0.0.0:443->443/tcp` (если в Docker на сервере включён IPv6 — ещё те же с `[::]:`; у Caddy ещё `443/udp, 2019/tcp` без `0.0.0.0:` — порты образа, не опубликованы). В колонке `PORTS` у `app` — `8000/tcp`, у `db` — `5432/tcp`, без `0.0.0.0:`: наружу они не опубликованы. `app` в `(health: starting)` — подождите 30 секунд и повторите `ps`. `pull access denied` или `denied` — ситуация D; `required variable ... is missing a value` — опечатка в `.env`; `app` `unhealthy` или `Restarting` — `docker compose logs app` и «Если не работает → Compose на сервере».

**Ситуация G — миграции один раз вручную**, после того как `db` стала `healthy`:

```bash
docker compose run --rm app alembic upgrade head
```

**Ожидаемый вывод:** `Running upgrade  -> <номер>, create <таблица> table`. Без этого эндпоинты, которые читают таблицу, отвечают `500`; `/health` — `200`: он проверяет только подключение.

Время `pull` и первого `up -d` запишите — автор документов внесёт его в ADR 006 «(измерено)».

#### Шаг 2.4: Проверить с ноутбука (5 мин)

На ноутбуке (не в SSH-сессии), второй терминал. Выпуск сертификата идёт в первые секунды после запуска прокси (на сервере курса: Caddy и certbot — около 10 с, Traefik — около 20 с); `curl: (35)` в первую минуту — повторите через 30 секунд.

```bash
# macOS / Linux / Git Bash
curl -sS -i https://<поддомен>/health
curl -sS -I http://<поддомен>/health
curl -sS -o /dev/null -w "%{http_code}\n" https://<поддомен>/docs
curl -sS -m 5 http://<поддомен>:8000/health
curl -sS -m 5 http://<поддомен>:5432/
```

```powershell
# Windows PowerShell 5.1 и 7
curl.exe -sS -i https://<поддомен>/health
curl.exe -sS -I http://<поддомен>/health
curl.exe -sS -o NUL -w "%{http_code}`n" https://<поддомен>/docs
curl.exe -sS -m 5 http://<поддомен>:8000/health
curl.exe -sS -m 5 http://<поддомен>:5432/
```

**Ожидаемый вывод:**

| Команда | Что должно быть | Что это доказывает |
|---|---|---|
| 1 | `HTTP/1.1 200 OK` или `HTTP/2 200`, тело `/health` вашего кода | Сервис доступен по публичному URL; сертификат проходит проверку (без `-k`) |
| 2 | `HTTP/1.1 308 Permanent Redirect` (Caddy, Traefik) или `301 Moved Permanently` (Nginx), строка `Location: https://<поддомен>/health` | Порт 80 только перенаправляет на HTTPS |
| 3 | `404` — п. 8 варианты (а) и (б); вариант (в) — тоже `404`, пока на сервере образ без правки шага 3.3 (`200` — на этапе 7). Временный сертификат — без `-k` `curl: (60)`, с `-k` — код | `/docs` по п. 8 |
| 4, 5 | Через 5 секунд `curl: (28) Connection timed out after 500x milliseconds` (или `Failed to connect ... Timed out`); бывают и `curl: (7) Failed to connect ... Connection refused` или `curl: (52) Empty reply from server` (так отвечает сетевой шлюз перед сервером) — тоже не ответ приложения | Порты `app` и `db` закрыты |

Таймаут команд 4–5 сам по себе слабое доказательство: сеть аудитории может закрывать исходящие на нестандартные порты. Главное доказательство — колонка `PORTS` в `docker compose ps` шага 2.3: у `app` и `db` нет `0.0.0.0:`. Ответ на `:8000` (JSON вашего `/health`) — у `app` остался `ports:`: Docker открыл порт мимо запрета ufw ([Docker Docs: Packet filtering and firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/), раздел **Docker and ufw**). Уберите `ports:` из `deploy/compose.yaml` коммитом, на сервере `git pull` и `docker compose up -d`.

Издатель сертификата — на сервере:

```bash
echo | openssl s_client -connect 127.0.0.1:443 -servername <поддомен> 2>/dev/null | openssl x509 -noout -issuer -enddate
```

Подключение к `127.0.0.1` на самом сервере, имя — в `-servername`: так же проверяет прокси `deploy.sh`, результат не зависит от того, куда ведёт публичный адрес изнутри сети сервера.

**Ожидаемый вывод:** строка `issuer=` с `O = Let's Encrypt` (например, `issuer=C = US, O = Let's Encrypt, CN = YE1`; имя после `CN =` — промежуточный сертификат Let's Encrypt, оно бывает другим: на сервере курса у Caddy и Nginx — `YE1`, у Traefik — `YR1`) и `notAfter=...` — примерно через 90 дней. Временный сертификат (ниже) — другой издатель: Caddy `tls internal` — `Caddy Local Authority - ECC Intermediate`, 12 часов; Nginx — `issuer=CN = <поддомен>`, 7 дней; Traefik — `issuer=CN = TRAEFIK DEFAULT CERT`, 1 год. Издатель и дату — в ADR 006 «(измерено)».

**Let's Encrypt не выдал сертификат к 45-й минуте** (DNS, лимит неудачных проверок — «Если не работает → HTTPS и прокси») — временный сертификат: Caddy — `tls internal` (раздел 2.1 шаблона); Nginx — самоподписанный сертификат в томе (раздел 2.2 шаблона, блок «Временный сертификат»); Traefik уже отдаёт свой `TRAEFIK DEFAULT CERT`, ничего не меняйте.

**Caddy: строку `tls internal` — коммитом, не правкой на сервере.** Файлы клона на сервере руками не правят: конфигурация сервера равна git, а `git checkout` шага 7.1 (и джоба `deploy`, и `poll.sh`) на локальной правке может остановиться. На ноутбуке — строка `tls internal` в `deploy/Caddyfile` внутри блока сайта перед `reverse_proxy`, затем:

```bash
git add deploy/Caddyfile
git commit -m "chore: temporary internal certificate until Let's Encrypt"
git push      # отклонён (fetch first) — второй ноутбук уже запушил этап 3: git pull --rebase, затем git push
```

На сервере, в папке `deploy`:

```bash
git pull
docker compose up -d --force-recreate proxy
```

**Ожидаемый вывод:** `git pull` — `Fast-forward` с `deploy/Caddyfile`; `Container deploy-proxy-1 Started` (с сервисом `migrate` выше ещё строки `deploy-migrate-1` `Started` и `Exited`: Compose запускает зависимости прокси, миграции повторно ничего не меняют). Сертификат внутреннего удостоверяющего центра Caddy действует 12 часов и перевыпускается сам — так и запишите срок в ADR 006. Дальше, для всех прокси:

- `curl` с ноутбука по `https://` — с `-k` (PowerShell — `curl.exe -k`): здесь — команды 1 и 3, дальше — цикл шага 7.1 и запрос шага 7.2. Без `-k` — `curl: (60)` или `SEC_E_UNTRUSTED_ROOT`, а цикл 7.1 выводит одни `000`. Приёмщику на этапе 8 скажите о временном сертификате вместе с поддоменом
- в `deploy/.env` на сервере допишите строку `CURL_INSECURE=1` (в папке `deploy`: `echo CURL_INSECURE=1 >> .env`): иначе `deploy.sh` на шаге 4.3 не пройдёт проверку сертификата и выйдет с кодом `1`. Строку удалите вместе с переходом на Let's Encrypt (ДЗ 1; Caddy — строку `tls internal` удалить отдельным PR)
- строка в «Рисках» ADR 006 и в комментарии-итоге; пункт DoD «Настроен HTTPS (Let's Encrypt или аналог)» при этом **не закрыт** — его закрывает Let's Encrypt в ДЗ 1

**Что должно получиться:** команды 1–5 дали ожидаемое; факты — у автора документов. **Точка синхронизации 45.**

### Этап 3: Структурированные логи с Request ID (25 мин)

Код — [шаблон логирования](logging-template.md), библиотека — по п. 7 ADR 006. Этап идёт на ноутбуке, в рабочей ветке. До merge на сервере работает прежний образ: логи с `request_id` вы увидите на сервере на этапе 7.

#### Шаг 3.1: Зависимость (4 мин)

Раздел 1 шаблона логирования: `uv add structlog==26.1.0` или `uv add loguru==0.7.3`; Poetry — `poetry add ...` и `poetry export`. Poetry и loguru — `poetry add` с ключом `--python` из раздела 1: без него `version solving failed`.

**Как проверить:** `git status --short` — изменены `pyproject.toml` и lock-файл (Poetry — и `requirements.txt`); Poetry — `git grep -n -E "^(structlog|loguru)==" -- requirements.txt` находит строку.

#### Шаг 3.2: `LOG_LEVEL` в модуле настроек (3 мин)

Раздел 2 шаблона: поле `log_level` (`pydantic-settings`) или `LOG_LEVEL` с проверкой (python-dotenv). Умолчание `INFO` допустимо: это не секрет. На сервере значение приходит из `deploy/.env` через строку `LOG_LEVEL: ${LOG_LEVEL:-INFO}` в `deploy/compose.yaml`.

#### Шаг 3.3: Модуль логов, `main.py`, `Dockerfile` (8 мин)

1. `app_logging.py` в корне проекта — раздел 3 (structlog) или 4 (loguru) шаблона, текст без изменений; python-dotenv — две замены под блоком
2. `main.py` — четыре правки раздела 5: удалить `import logging` и `logger = ...`, импорт `from app_logging import log, request_context`, строка `app.middleware("http")(request_context)` после `app = FastAPI(...)`, новая строка в `/health`
3. `Dockerfile` — `"--no-access-log"` в `CMD` (раздел 6). Миграции командой `app`: в `command:` у `app` в `deploy/compose.yaml` `--no-access-log` уже есть (шаг 1.1, раздел 7 шаблона reverse-proxy); корневой `compose.yaml` не меняется — на ноутбуке access-строки не мешают
4. **П. 8, вариант (в):** в `FastAPI(...)` удалить строки `docs_url=`, `redoc_url=`, `openapi_url=` (раздел 5 шаблона)

«Наблюдаемость» сверяет поля с п. 7 ADR 006: время, уровень, `request_id`, метод, путь; пользователь — если есть авторизация.

**Как проверить:** `git grep -n "uvicorn.error" -- "*.py"` — пусто; `git grep -n --untracked "request_context" -- "*.py"` — три строки: определение в `app_logging.py`, импорт и регистрация в `main.py` (`--untracked`: `app_logging.py` ещё не добавлен в git).

#### Шаг 3.4: Проверить локально (5 мин)

Раздел 7 шаблона логирования: приложение без базы в первом окне, запрос с `X-Request-ID: local-1` во втором.

Запрос — после строки `Application startup complete.` в окне 1 (первый `uv run` на новом клоне сначала ставит зависимости); раньше — `curl: (7) Failed to connect`.

**Ожидаемый вывод:** `503` и `x-request-id: local-1` в ответе; в окне приложения две строки JSON с `"request_id": "local-1"` — `database unavailable` и `request finished`. Остановить — `Ctrl+C`. Строки текстом без `request_id` (`INFO:     Started server process`) — сам uvicorn, так и должно быть.

#### Шаг 3.5: Линтеры, тесты, коммит (5 мин)

**Тесты, которые читают вывод приложения.** Строки лога теперь идут в stdout. Тест, который запускает приложение в дочернем процессе и сравнивает его вывод (часто — проверка `/docs` при `APP_ENV=prod` из ДЗ 3 практики №6), получит лишнюю строку `request finished` и упадёт в джобе `test` с ошибкой вида `assert '{"status": 4...Z"}\n404' == '404'`. Проверка:

```bash
git grep -n -E "stdout|capsys|capfd" -- tests
```

Пусто — переходите к линтерам. Нашлось сравнение вывода — в окружение дочернего процесса этого теста добавьте `LOG_LEVEL="WARNING"` (например, `run_python(code, tmp_path, DATABASE_URL=..., APP_ENV="prod", LOG_LEVEL="WARNING")`): строки уровня `info` не пишутся, код приложения не меняется. Вывод читается в том же процессе (`capsys`, `capfd`) — сравнивайте последнюю строку: `.strip().splitlines()[-1]`. Файл теста — в `git add` ниже.

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy .
git add app_logging.py main.py settings.py Dockerfile pyproject.toml uv.lock
# изменён тест: git add tests
# Poetry: poetry run ... вместо uv run ...; git add ... poetry.lock requirements.txt вместо uv.lock
git commit -m "feat: structured JSON logs with request id"
# не свой ноутбук: --author водителя (шаг 0.2)
git push      # отклонён (fetch first) — в ветке уже есть чужой коммит (шаг 2.4 или ADR веб-редактором): git pull --rebase, затем git push
```

**Ожидаемый вывод:** `All checks passed!`, `N files already formatted`, `Success: no issues found in N source files`; коммит через pre-commit — `Passed`. `ruff format --check` нашёл файл — `uv run ruff format .`, затем `git add` снова. `I001 Import block is un-sorted or un-formatted` — импорт `app_logging` не по алфавиту (раздел 5 шаблона, правка 2): `uv run ruff check --fix .`, затем `git add` снова. loguru: `BLE001` — нет пометки `# noqa` из шаблона. Тесты практики №6, которые не читают вывод приложения, этот код не ломает (проверено на проекте курса); тесты пройдут в джобе `test` на этапе 6. **Точка синхронизации 70.**

#### Шаг 4.2: Обвязка по способу из п. 4 (6 мин)

| Способ | Что сделать на ноутбуке | Где текст |

#### Шаг 6.1: Прогон и approval (7 мин)

Прогон на PR — `lint`, `secrets`, `test`, `build`; `publish` и `deploy` (способ B) пропущены: они только для `push` в `main`. Красная проверка — диагноз по логу, как на практике №6, затем исправление отдельным коммитом. Частые причины: `lint` — `ruff format`, `I001` (порядок импортов, шаг 3.5), `BLE001` у loguru; `test` — тест сравнивает вывод приложения со строкой, а в выводе теперь строка JSON (шаг 3.5, `LOG_LEVEL="WARNING"` для этого теста). Сбой сети или таймаут при установке зависимостей (`No matching distribution`, `tls handshake`, `exceeded the maximum execution time`) — не код: **Re-run failed jobs**. Покрытие в отчёте `test` может снизиться на несколько процентов: ветка `except` middleware тестами не покрыта (бонус 3); порог практики №6 — 60 %. Poetry без `poetry export` прогон не ловит: `test` ставит зависимости из `poetry.lock` и зелёный, а образ из `requirements.txt` — без библиотеки логов, и `app` на сервере упадёт с `ModuleNotFoundError`; проверка — шаг 3.1.


**Что должно получиться:** PR в состоянии **Merged**; последняя команда выводит 40 символов — SHA коммита в основной ветке. Тег новой версии — `sha-` и этот SHA.

### Этап 7: Новая версия на сервере: логи и перезапуск (15 мин)

Команды на сервере — в `~/<репозиторий>/deploy`.

#### Шаг 7.1: Новая версия (5 мин)

**Перед тем как запускать деплой**, проверяющий включает на ноутбуке цикл запросов — увидеть, что получает пользователь во время обновления (остановить — `Ctrl+C`):

```bash
# macOS / Linux / Git Bash
while true; do printf '%s ' "$(date +%T)"; curl -s -m 2 -o /dev/null -w '%{http_code}\n' https://<поддомен>/health; sleep 0.2; done
```

```powershell
# Windows PowerShell 5.1 и 7
while ($true) { $t = Get-Date -Format "HH:mm:ss"; $c = curl.exe -s -m 2 -o NUL -w "%{http_code}" https://<поддомен>/health; "$t $c"; Start-Sleep -Milliseconds 200 }
```

**Временный сертификат** (шаг 2.4) — в цикле `curl -k` (PowerShell — `curl.exe -k`): без `-k` каждая строка — `000`, и окно не увидеть.

Цикл идёт дольше пары минут (способ B: ждёт `publish` и джоб `deploy`, 4–6 мин) — можно выводить только ответы, отличные от `200`: в bash в конце цикла `done | grep -v ' 200$'`, в PowerShell вместо `"$t $c"` — `if ($c -ne "200") { "$t $c" }`. Пока всё `200`, экран пустой; первая и последняя строки — границы окна.

По способу из п. 4:

| Способ | Что сделать | Что увидите |
|---|---|---|
| **A** | На сервере: `git checkout -B main origin/main` после `git fetch`, затем `sh deploy.sh sha-<SHA из шага 6.2>` | `Стало: sha-<SHA>, /health через прокси: 200`, код выхода `0` |
| **B** | Ничего: джоб `deploy` уже отработал (шаг 6.2); цикл запросов включён до merge (шаг 6.2). Секретов нет (ситуация E) или обвязка B перенесена в ДЗ 1 — как строка A | В логе джоба — строка `Стало: ...: 200`; на сервере `sed -n 's/^APP_TAG=//p' .env` — новый тег |
| **C** | На сервере — расписание командой раздела 6 шаблона; затем ждите до 2 минут или запустите сами `sh poll.sh` | `tail ~/poll.log` — время, тег и `Стало: ...: 200`. Кода выхода в журнале нет: `200` в строке `Стало:` — успешный деплой (код `0`), другой код — ошибка (код `1`) |

Команды способа A целиком:

```bash
git fetch --prune origin
git checkout -B main origin/main
sh deploy.sh sha-<40 символов>
```

**Ожидаемый вывод** цикла на ноутбуке: строки `200`, во время пересоздания `app` — строки `502` (Traefik — в основном `404`: он снимает маршрут, пока `app` не запущен или не `healthy`; бывают и `000` — ответ не уложился в `-m 2`), затем снова `200`. Образ скачивается до остановки старого контейнера — всё время скачивания идёт `200`. Длина окна зависит от прокси и миграций:

| Прокси и миграции | Окно | Почему |
|---|---|---|
| Caddy, Nginx; без сервиса `migrate` | несколько секунд (прогоны курса — 2 и 8 с) | Прокси ведёт запросы в `app`, как только тот слушает порт |
| Traefik; без сервиса `migrate` | до ~10 с (сервер курса — 6,6 с); на слабом или загруженном сервере — до 20–30 с (имитация сервера под нагрузкой — 21–28 с) | Traefik не ведёт запросы в новый `app`, пока тот не `healthy`: окно не короче времени до первой успешной проверки `HEALTHCHECK` из `Dockerfile`, плюс запуск приложения и `alembic upgrade head` в команде `app` |
| Любой прокси с сервисом `migrate` (раздел 7 шаблона reverse-proxy) | секунды, до ~10 с (сервер курса: Caddy — 5,7 с, Nginx — 5,4 с, Traefik — 9,7 с); на слабом или загруженном сервере — до 30–40 с (имитация — 33–34 с) | Compose пересоздаёт и `migrate` с новым образом, а новый `app` стартует только после миграций: к окну без `migrate` добавляется их время |

Окно у вас длиннее или короче строки таблицы — это не сбой: запишите окно как есть, сократить его — вопрос ДЗ 3. Признак новой версии — новый тег в `deploy/.env` на сервере и заголовок `X-Request-ID` в ответе (шаг 7.2); `/version` меняется, только если версию в коде поднимали (GitFlow — релиз).

Время первой и последней строки не `200` и их число запишите: разница во времени — окно простоя вашего способа обновления (п. 5 ADR 006). Шаг цикла на Windows бывает больше 0,2 с, поэтому окно считают по меткам времени, а не по числу строк. Строк не `200` нет, а тег не сменился — деплой не запустился: «Если не работает → Деплой».

#### Шаг 7.2: Request ID через публичный URL (4 мин)

На ноутбуке — запрос со своим идентификатором (`<команда>` — короткое имя латиницей):

```bash
# macOS / Linux / Git Bash
curl -sS -D - -o /dev/null -H "X-Request-ID: p7-<команда>-1" https://<поддомен>/health
```

```powershell
# Windows PowerShell 5.1 и 7
curl.exe -sS -D - -o NUL -H "X-Request-ID: p7-<команда>-1" https://<поддомен>/health
```

На сервере:

```bash
docker compose logs --no-log-prefix app | grep '"request_id": "p7-<команда>-1"'
```

Временный сертификат (шаг 2.4) — на ноутбуке `curl -k` (PowerShell — `curl.exe -k`), иначе `curl: (60)`.

**Ожидаемый вывод:** на ноутбуке среди заголовков — `x-request-id: p7-<команда>-1` (регистр имени заголовка может быть `X-Request-Id`: через HTTP/1.1 прокси меняет его, это не ошибка); на сервере — строка JSON `request finished` с этим `request_id`, `"method": "GET"`, `"path": "/health"`, `"status": 200`, `"level": "info"`, `timestamp`. Строку целиком скопируйте в комментарий-итог. Строки нет, а в логе `INFO:     ... "GET /health HTTP/1.1" 200` — на сервере старый образ: тег не сменился (шаг 7.1).

#### Шаг 7.3: Перезапуск при падении (3 мин)

Падение процесса приложения изнутри контейнера — как в демо воркшопа №7:

```bash
docker compose exec app sh -c 'kill -TERM 1'
sleep 5
docker inspect -f '{{.State.Status}} restarts={{.RestartCount}}' "$(docker compose ps -q app)"
```

**Ожидаемый вывод:** `running restarts=1`. Через 20–30 секунд `docker compose ps` — `app` снова `(healthy)`, `curl` на `/health` с ноутбука — `200`. `restarts=0` — процесс 1 в контейнере — оболочка (миграции командой `app`: `sh -c "alembic upgrade head && uvicorn ..."`), а оболочка-процесс 1 сигнал игнорирует: `docker compose exec app sh -c 'kill -TERM -1'` — сигнал всем процессам контейнера, кроме первого; проверка та же. `docker compose stop`, `restart` и `docker kill` для этой проверки не годятся: остановленный вручную контейнер политика `restart` не поднимает.

| № | Проверка | Принято, если |
|---|---|---|
| 1 | HTTPS и редирект — команды 1–2 | `301` или `308` с `Location: https://...`; затем `200 0` **в команде без `-k`**: код `200` без `-k` — сертификат прошёл проверку. Вместо этого `curl: (60)` и `000 <число>` — сертификат не прошёл проверку: команда предупредила о временном сертификате (шаг 2.4) — «спорно: временный сертификат» по этому выводу, не предупредила — «не выполнено». | 2 | Закрытые порты и `/docs` — команды 3–5 | `8000` и `5432` — не ответили: таймаут `curl: (28)`, `curl: (7) ... | 3 | `X-Request-ID` — команда 6 | В ответе заголовок `x-request-id: accept-<ваша команда>-1` (или `X-Request-Id`: регистр имени не важен); строку лога с ним команда покажет на шаге 8.2. Заголовка нет, а новой версии на сервере нет — «спорно: старый образ» |

## Если не работает

Сначала найдите сообщение об ошибке: в выводе команды, в `docker compose logs <сервис>` на сервере или в логе джоба (вкладка **Checks**). Ищите его в таблицах.

### SSH и сервер

| Симптом | Причина | Что сделать |

### HTTPS и прокси

| Симптом | Причина | Что сделать |
|---|---|---|
| `curl: (6) Could not resolve host` | Поддомен не указывает на сервер или опечатка | `nslookup <поддомен>` — есть адрес; нет — преподавателю |
| `curl: (35)` и `SEC_E_INTERNAL_ERROR` (Windows) или `tlsv1 alert internal error` | У прокси нет сертификата для этого имени: выпуск ещё идёт или не удался; `DOMAIN` в `.env` не равен поддомену | Подождать 30–60 с; `docker compose logs proxy` — строка ошибки Let's Encrypt; `DOMAIN` — без `https://` и `/` |
| `curl: (60)`, `SEC_E_UNTRUSTED_ROOT` или `unable to get local issuer certificate` | Сертификат не от Let's Encrypt: Traefik отдаёт `TRAEFIK DEFAULT CERT`, пока выпуск не удался; или включён `tls internal` | `docker compose logs proxy` — ошибка ACME; временный сертификат — только по шагу 2.4, `curl` — с `-k` |
| `CRYPT_E_NO_REVOCATION_CHECK` или `CRYPT_E_REVOCATION_OFFLINE` в `curl.exe` (Windows) | Windows не может проверить отзыв сертификата из этой сети | Добавить `--ssl-no-revoke` к команде `curl.exe` (не проверено курсом в сети аудитории) |
| В логе прокси `too many failed authorizations` или `rateLimited` | Лимит Let's Encrypt: 5 неудачных проверок имени в час ([Rate Limits](https://letsencrypt.org/docs/rate-limits/)) | Не перезапускать прокси; найти первую ошибку в логе (DNS, порт 80); временный сертификат по шагу 2.4, Let's Encrypt — через час или в ДЗ 1 |
| Nginx: `cannot load certificate "/etc/letsencrypt/live/.../fullchain.pem"`, `proxy` перезапускается | certbot не запускался, не выдал сертификат или выпустил его на другое имя | certbot не запускался — раздел 2.2 шаблона с тем же поддоменом, что в `DOMAIN`. certbot закончился ошибкой (нет `Successfully received certificate.`) — повторно не запускайте больше одного раза: блок «Временный сертификат» раздела 2.2 шаблона, затем `docker compose up -d` (шаг 2.3) |
| certbot: `live directory exists for <поддомен>` | Временный сертификат Nginx не удалён перед выпуском (ДЗ 1) | Команда удаления блока «Временный сертификат» раздела 2.2 шаблона (удаляет `live/` и `renewal/`), затем выпуск ещё раз — не больше одного повтора: каждый такой выпуск идёт в лимит Let's Encrypt |
| certbot: `Could not bind TCP port 80` | Прокси уже запущен и держит порт 80 | `docker compose stop proxy`, certbot, `docker compose up -d` |
| Traefik: `404 page not found` постоянно | Нет маршрута: меток нет у `app`, нет `traefik.enable=true`, или `Host(...)` не равен адресу запроса | Метки — раздел 2.3 шаблона; `docker compose up -d`. `404` только во время деплоя — так и есть: пока `app` не `healthy`, Traefik снимает маршрут (окно шага 7.1) |
| `502 Bad Gateway` постоянно | `app` не запущен или не слушает 8000 | `docker compose ps`, `docker compose logs app` |
| Порт `8000` отвечает с ноутбука | У `app` остался `ports:` в `deploy/compose.yaml` | Убрать, коммит, на сервере `git pull`, `docker compose up -d` (шаг 2.4) |

### Состав команды и особые случаи

- **Ключ на сервере только у отсутствующего участника.** Входит второй владелец ключа; нет ни одного — преподавателю до занятия: курс добавит ключ присутствующего
- **Владелец пути из `CODEOWNERS` не пришёл.** Удалённый approval (ссылка ему в чат); нет к 105-й минуте — временное снятие `Require review from Code Owners` владельцем репозитория **только с разрешения преподавателя**, merge, правило сразу вернуть; в ДЗ 1 — второй владелец пути в `CODEOWNERS`
- **Команда из 5:** раскладка на 4; пятый — второй автор документов (ADR 006 и ADR 003 параллельно) и второй приёмщик на этапе 8
- **На занятии двое** — таблица «Команда из 2 человек» шага 0.2

Не нашли своего случая — покажите преподавателю **текст ошибки** и команду или шаг, который её вызвал.

## Чек-лист для преподавателя

| Переменные на сервере | `deploy/.env.example`, `.gitignore` в PR | `deploy/.env` не в git; секреты через `${...:?...}` |
| Автодеплой | Комментарий-итог; у B — джоб `deploy`; у A — `deploy.sh` | Новый тег `sha-` на сервере после merge; время «merge → новая версия» |

| Настроены переменные окружения на сервере (не в коде) | `deploy/.env` на сервере, права `600`, вне git |
| Есть скрипт или CI/CD стадия для автоматического деплоя | `deploy/deploy.sh`; способ B — джоб `deploy`, C — `poll.sh` по расписанию |
| Приложение перезапускается автоматически при падении (systemd / docker restart policy) | `restart: unless-stopped`, проверка шага 7.3 |

### 1. Закрыть незавершённое

Довести до merge PR практики и развернуть новую версию на сервере, если не успели (этапы 6–7; GitFlow — второй релиз, затем обратный merge `main` → `develop` по `CONTRIBUTING.md`); комментарий-итог — по шаблону шага 7.4. Ответить на замечания приёмки. **Способ B без секретов на занятии (ситуация E):** владелец задаёт секреты по блоку «Только способ B», затем любой PR с изменением кода → merge → зелёный `deploy`; ссылка на прогон — в комментарий-итог. **Способ B или C перенесены с занятия** — то же: первый деплой без участника, ссылка или строка `poll.log`. **Временный сертификат** — Let's Encrypt по разделу 2 шаблона (Caddy — PR, удаляющий строку `tls internal`, затем на сервере `git pull` и `docker compose up -d --force-recreate proxy`; Nginx — сначала удалить временный, блок «Временный сертификат» раздела 2.2), строку `CURL_INSECURE=1` из `deploy/.env` удалить, `sh deploy.sh <текущий тег>` — код `0`; строка из «Рисков» ADR 006 снимается строкой «Истории изменений». **Ситуация C и ситуация B без ревью другой команды:** полный ADR 006 по [материалам воркшопа №7](../../workshops/workshop7/workshop7-materials.md), разделы 5.1–5.5 (файл уже есть: команду `curl` раздела 5.1 не выполняйте; ситуация B — дописать и ревью), ревью команды, которую назовёт преподаватель, комментарием в PR, перенос в файл коммитом с `--author` рецензента, ответы; «Принято» — отдельным PR после ревью, не позже воркшопа №8: он опирается на п. 1–8 ADR 006. Это исключение из правила «„Принято“ — в одном PR с кодом»: код уже в основной ветке, ADR догоняет его отдельным PR, как в ситуации C практики №6. **Снималось `Require review from Code Owners`:** правило возвращено, второй владелец пути — в `CODEOWNERS`.
