# Материалы для самостоятельного изучения (Воркшоп №4)

**Тема воркшопа:** 12-Factor App и безопасность: конфигурация и секреты
**Время на подготовку:** около 1 часа 25 минут — 75 минут чтения и 10 минут практической проверки

На воркшопе ваша команда проверит свой проект по принципам 12-Factor App, проверит историю репозитория на утёкшие секреты, составит список всех параметров конфигурации и выберет механизм конфигурации в ADR 003. Код на занятии не пишется: класс настроек по этому ADR вы напишете на практике №4. Лекции не будет.

Как читать этот файл: разделы 0–4 — подготовка до занятия. Раздел 5 — рабочие таблицы и команды занятия, заранее его открывать не обязательно. Раздел 6 — домашнее задание.

---

## 0. Что уже должно быть сделано

После практики №3 в вашем репозитории есть `compose.yaml`, `.env.example` с `POSTGRES_PASSWORD` и `APP_PORT`, а `GET /health` читает `DATABASE_URL` через `os.environ`. На ноутбуке, где поднимали стек, лежит `.env` с вашим паролем — **не удаляйте его**: на воркшопе по нему вы будете сверять список параметров.

Если PR со стеком ещё не смержен, это не мешает: на занятии вы будете брать факты из ветки этого PR (раздел 5.1). Если у команды пока нет своего приложения, вы работаете по фрагменту кода, который преподаватель покажет на занятии, и составляете целевой список параметров для FastAPI + PostgreSQL.

Docker нужен для проверки истории хотя бы на одном ноутбуке команды. Без Docker та же проверка делается командами git, только грубее (раздел 5.2).

**Материалы 3 и 4 читайте как сравнение**, а не как руководство к коду: на воркшопе команда сравнит три способа читать конфигурацию — `os.environ`, как сейчас, `pydantic-settings` и третий (python-dotenv или environs) — и запишет выбор в ADR 003.

**Секреты в истории git.** В курсе историю не переписывают: force push запрещён правилами вашего репозитория, а копии репозитория у сокомандников и в форках всё равно останутся. Секрет, однажды попавший в коммит, считается скомпрометированным и заменяется на новый. Поэтому статьи о чистке истории читать не нужно.

## 2. Практическая проверка (10 мин)

**Шаг 1.** Скачать образ сканера секретов. Команда одинакова для PowerShell, Git Bash, macOS и Linux:

```bash
docker pull zricethezav/gitleaks:v8.28.0
```

Скачивается около 23 МБ, на диске образ займёт около 73 МБ. **Ожидаемый вывод:** среди последних строк — `Status: Downloaded newer image for zricethezav/gitleaks:v8.28.0` или, если образ уже был скачан, `Status: Image is up to date for zricethezav/gitleaks:v8.28.0`.

**Как проверить:**

```bash
docker run --rm zricethezav/gitleaks:v8.28.0 version
```

**Ожидаемый вывод:** `v8.28.0`. Если Docker у вас не работает, пропустите шаг 1: на воркшопе проверку выполнит участник с работающим Docker, а без него — команды git из раздела 5.2.

**Шаг 2.** Проверить, был ли `.env` когда-нибудь закоммичен. В корне репозитория команды:

```bash
git switch main            # GitFlow: git switch develop
git pull
git log --all --oneline -- .env
```

**Ожидаемый вывод:** пустой — файл `.env` не попадал ни в один коммит ни в одной ветке, которую вы скачали.

Если появились строки с коммитами — `.env` был в истории, и пароль из того коммита считается скомпрометированным. Ничего не удаляйте и историю не переписывайте. Если после `git rm --cached .env` на практике №3 вы ещё не сменили пароль — задайте в `.env` новый и выполните `docker compose down -v`, как в шаге 5.1 практики №3. Остальное разберёте на воркшопе.

**Шаг 3.** Ответьте себе на вопрос, проверять не нужно — проверим на воркшопе вместе: в вашем `.gitignore` есть строка `.env`. Если бы год назад кто-то закоммитил `.env`, а потом убрал его командой `git rm --cached`, — нашёл бы сканер пароль сегодня? А пароль `admin123`, записанный прямо в `config.py`?

## 3. Вопросы для самопроверки

На воркшопе эти вопросы отдельно не разбираются: на них опирается работа в командах. Если на какой-то вопрос нет ответа, вернитесь к материалу из таблицы.

1. Что из этого — конфигурация в смысле 12-Factor: пароль базы, адрес базы, порт приложения, название команды `TEAM_NAME`, версия приложения? Почему?
2. Пароль закоммитили, а потом убрали командой `git rm --cached`. Защищён ли он теперь? Что с ним нужно сделать?
3. Чем `.env` отличается от `.env.example`? Где по 12-Factor должны жить значения для сервера?
4. Сейчас при локальном запуске без Docker `/health` отвечает `503` с `DATABASE_URL is not set`. В какой момент вы узнаёте об отсутствии переменной? Когда об этом сообщит приложение на `pydantic-settings`?
5. `DB_CONNECT_TIMEOUT=abc` — таймаут подключения к базе, который приложение читает как число. Что сделает `int(os.environ["DB_CONNECT_TIMEOUT"])`, а что — `pydantic-settings`? Что вернёт `bool("false")`?
6. Почему сканер секретов — страховка, а не гарантия? Какой пароль он может не заметить?
7. Что попадает в Docker-образ при сборке, а что приложение должно получать только при запуске контейнера? Как это связано с фактором V?

## 5. Работа на занятии: ADR 003

Итог занятия — один файл в отдельной ветке: `docs/adr/003-configuration.md` со статусом «Предложено». В «Контексте» — аудит по 12-Factor и результат проверки истории, в «Рассмотренных вариантах» — сравнение трёх способов, в «Решении» — выбор. В конце файла — три приложения: А — список параметров конфигурации, Б — ревью другой команды, В — ваши ответы на ревью.

**Чего в файле быть не должно:** ни одного реального значения пароля, ключа или строки подключения с паролем. Вместо значения пишется, где оно хранится: «в `.env` у каждого разработчика», «на сервере, вне git».

### 5.1. Ветка и файл ADR

Ветка — по вашим правилам именования из `CONTRIBUTING.md`, например `docs/adr-003-configuration`. Команды на GitFlow создают её от `develop` и открывают PR в `develop`.

```bash
git switch main            # GitFlow: git switch develop
git pull
git switch -c <ветка-по-вашим-правилам>
```

Скопировать шаблон ADR из корня репозитория:

```bash
# macOS / Linux / Git Bash
curl -fsSL --create-dirs -o docs/adr/003-configuration.md https://raw.githubusercontent.com/andrey-limasov/app-conf/main/workshops/workshop2/adr-template.md
# Windows PowerShell
curl.exe -fsSL --create-dirs -o docs/adr/003-configuration.md https://raw.githubusercontent.com/andrey-limasov/app-conf/main/workshops/workshop2/adr-template.md
```

**Ожидаемый вывод:** пустой; файл `docs/adr/003-configuration.md` начинается строкой `# ADR 001: Выбор стратегии ветвления Git` — заголовок вы замените по таблице ниже.

Если ADR у вас называются иначе (например, `docs/adr/adr-001-....md`), назовите файл по своему правилу, номер оставьте 003. Если номер 003 у вас уже занят другим решением — возьмите следующий свободный и укажите в описании PR, что это ADR о конфигурации.

**Если в команде два ноутбука:** файл ADR правится только на одном — на том, где создана ветка. Со второго выполняйте проверку истории (раздел 5.2) и команды `git grep` (раздел 5.3), результаты пересылайте в чат команды. Две правки одного файла в одной ветке дадут конфликт при push.

**Если compose-файл у вас называется `docker-compose.yml`,** а не `compose.yaml`, — во всех командах и таблицах раздела 5 подставляйте своё имя.

**PR практики №3 не смержен.** Ветку ADR всё равно создавайте от основной ветки разработки, а факты берите из ветки PR, не переключаясь на неё:

```bash
git fetch origin
git show origin/<ветка-PR-практики-3>:compose.yaml
git show origin/<ветка-PR-практики-3>:.env.example
git grep -n -E "environ|getenv" origin/<ветка-PR-практики-3> -- "*.py"
```

### 5.2. Проверка истории на секреты

Сначала скачайте свежие ветки сокомандников, **ветку не переключайте** — вы остаётесь на ветке ADR:

```bash
git fetch origin
```

Сканер проверяет все ветки, которые есть на ноутбуке, включая скачанные `origin/...`. Основную ветку вы уже обновили командой `git pull` в разделе 5.1. Затем из корня репозитория:

```bash
# macOS / Linux
docker run --rm -v "$(pwd):/repo:ro" zricethezav/gitleaks:v8.28.0 git /repo --redact --no-banner -v
# Git Bash на Windows
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd):/repo:ro" zricethezav/gitleaks:v8.28.0 git /repo --redact --no-banner -v
# Windows PowerShell
docker run --rm -v "${PWD}:/repo:ro" zricethezav/gitleaks:v8.28.0 git /repo --redact --no-banner -v
```

Что значат ключи: `:ro` — сканер получает папку только на чтение; `git /repo` — проверить всю историю коммитов, а не текущие файлы; `--redact` — не выводить найденные значения на экран; `-v` — показать по каждой находке файл и коммит.

**Ожидаемый вывод:** среди последних строк — `INF N commits scanned.` и `INF no leaks found` или `WRN leaks found: N`; перед каждой строкой стоит время. По каждой находке — блок со строками `RuleID:`, `File:`, `Line:`, `Commit:`, `Author:`, `Email:`; на месте значения — `REDACTED`. Если репозиторий не на GitHub, в начале может появиться `INF Unknown SCM platform` — на результат это не влияет.

**Если в Git Bash** появилось `stat C:/Program Files/Git/repo: no such file or directory` — вы забыли `MSYS_NO_PATHCONV=1`. **Если в выводе видны символы вида `[90m`** — терминал не поддерживает цвет, добавьте `--no-color`.

**Без Docker** — две команды git. Они не ищут секреты по содержимому, а показывают, где искать:

```bash
git log --all --oneline -- .env
git log --all --oneline --name-only -i -G "password|secret|token|api_key"
```

Первая — коммиты, в которых менялся `.env`. Вторая — коммиты, в которых менялись строки со словами `password`, `secret`, `token`, `api_key`, и файлы этих коммитов. Почти все строки второго вывода — ожидаемые: `compose.yaml`, `.env.example`, схема окружения. Подозрительный коммит откройте у себя, не на проекторе: `git show <коммит> -- <файл>`, и посмотрите, стоит ли там реальное значение или `${...}`, `changeme`, только имя переменной.

**Как классифицировать находку:**

| Что найдено | Вывод | Что делать |
|---|---|---|
| Реальный пароль базы в `.env`, `compose.yaml`, коде — в любом коммите, даже удалённый позже | Скомпрометирован | Новый пароль в `.env` у каждого участника и `docker compose down -v` — база пересоздаётся с новым паролем |
| Реальный ключ внешнего сервиса (API, почта, облако) | Скомпрометирован | Отозвать ключ у провайдера **сразу, на занятии**, получить новый, положить только в `.env` |
| Заглушка (`changeme`, `example`), значение из документации, тестовая строка | Ложное срабатывание | Записать, почему это не секрет |

Историю не переписывайте и файлы ради сканера не удаляйте. Вывод сканера не вставляйте в PR, чаты и ADR и не выводите на проектор: без `--redact` в нём значения секретов, а с `--redact` — email авторов коммитов.

**Что записать в «Контекст» ADR** — значения секретов не пишутся никогда:

```markdown
**Проверка истории на секреты** (ГГГГ-ММ-ДД): gitleaks 8.28.0, `gitleaks git --redact`, все ветки
на ноутбуке. Найдено: N.

| Файл | Коммит | Правило | Вывод |
|---|---|---|---|
| `.env` | `a1b2c3d` | `generic-api-key` | Скомпрометирован: пароль БД, ротирован ГГГГ-ММ-ДД |
```

Таблица идёт в «Контекст» ADR, в раздел «Проблема». По каждому пункту — отметка и **место**: файл и номер строки. ✅ — выполнено, ❌ — не выполнено, ⚠️ — спорно (запишите, в чём сомнение).

| № | Фактор | Что проверить | Где смотреть | Отметка | Место (файл:строка) |
|---|---|---|---|---|---|
| 1 | III | В коде нет значений, которые различаются между окружениями: хосты, порты, адреса внешних сервисов | Команда 1 ниже | | |
| 2 | III | В текущих файлах репозитория нет секретов | Команда 2 ниже | | |
| 3 | III | В истории нет секретов | Раздел 5.2 | | |
| 4 | III | Приложение читает настройки из переменных окружения, и везде одним способом | Команда 3 ниже | | |
| 5 | IV | База и внешние сервисы подключаются по адресу и ключу из окружения: замена базы на серверную не требует правки кода | `compose.yaml` → `environment` у сервиса приложения; `main.py` | | |
| 6 | V | В образ не попадает конфигурация: `.env` в `.dockerignore`, в `Dockerfile` нет `ENV` и `ARG` со значениями паролей и ключей | `.dockerignore`, `Dockerfile` | | |
| 7 | V | Версия приложения задана в одном месте. `version` в `pyproject.toml` — допустимый единственный источник. ❌ — если версия продублирована в коде, например `version="0.2.0"` в `FastAPI(...)` в `main.py` | Команда 4 ниже | | |
| 8 | X | В `dev` те же сторонние службы и версии, что будут в `prod`: PostgreSQL той же версии, а не SQLite или заглушка | `compose.yaml` (или `docker-compose.yml`) → `image` у базы | | |

По пункту 7: практика №3 велела поле `version` в `pyproject.toml` не трогать — на воркшопе и в домашнем задании его не правьте. Если версия записана и в `pyproject.toml`, и в коде, поставьте ❌, укажите оба места; как свести версию к одному источнику, решите на практике №4.

Команды — одинаковые для PowerShell, Git Bash, macOS и Linux. `git grep` ищет только по файлам под git, поэтому `venv/` и `.env` в выдачу не попадут. В команде 1 указаны оба имени compose-файла: отсутствующий файл ошибки не даёт.

```bash
# 1. Хосты, IP-адреса, адреса со схемой (postgresql://, https://), порты
git grep -n -E "localhost|([0-9]{1,3}\.){3}[0-9]{1,3}|[a-z]+://|5432|8000" -- "*.py" Dockerfile compose.yaml docker-compose.yml
# 2. Подозрительные слова в текущих файлах
git grep -n -i -E "password|secret|token|api_key"
# 3. Где код читает окружение
git grep -n -E "environ|getenv" -- "*.py"
# 4. Где задана версия
git grep -n -E "version" -- "*.py" pyproject.toml
```

Пустой вывод команды — это тоже результат: запишите «не найдено». Если вывод длинный и открылся в режиме просмотра — выход клавишей `q`. Имена хостов без точек и схемы (`db`, имя сервера) команда 1 не найдёт — ищите их глазами в выводе команды 3 и в `compose.yaml`.

**Если у команды нет приложения:** пункты 1–8 отметьте по фрагменту кода, который преподаватель показывал на занятии, а в «Месте» укажите строку фрагмента.

### 5.4. Список параметров конфигурации (приложение А)

Скопируйте блок в конец ADR и заполните. В таблицу входят:

- все переменные из `compose.yaml` (ключи `environment` и всё, что стоит в `${...}`) и из `.env.example`;
- всё, что код читает из окружения (команда 3 раздела 5.3);
- все значения, зашитые в код и `Dockerfile`: хосты, порты, имя базы и пользователя, таймауты, `TEAM_NAME`, `version` — если они у вас есть;
- ключи внешних сервисов, если приложение к ним обращается.

Значение, которое одинаково во всех окружениях, — не конфигурация, а часть кода. Его тоже внесите в таблицу: в колонке «Где задаётся сейчас» оставьте место в коде, в `dev` и `prod` — одно и то же значение, в «Назначении» допишите «не конфигурация, остаётся в коде». Так рецензент увидит, что вы это значение рассмотрели, а не пропустили.

```markdown
## Приложение А. Параметры конфигурации

Источники: `compose.yaml`, `.env.example`, `main.py`, `Dockerfile` (ветка: ...).

| Имя | Назначение | Где задаётся сейчас | dev | prod | Секрет | Обязательный / умолчание |
|---|---|---|---|---|---|---|
| `POSTGRES_PASSWORD` | Пароль пользователя `postgres`; Compose передаёт его базе и подставляет в `DATABASE_URL` | `.env` на ноутбуке, подстановка `${...}` в `compose.yaml` | Свой у каждого разработчика, в `.env` | На сервере, вне git; задаёт тот, кто разворачивает | Да | Обязательный, без умолчания (`:?` в `compose.yaml`) |
|  |  |  |  |  |  |  |
```

Правила заполнения:

- В колонках `dev` и `prod` для секретов — **где хранится и кто задаёт**, а не значение. Для несекретных параметров — значение или правило («порт 8000; если занят — свой в `.env`»)
- Колонка `prod` — гипотеза: сервер появится в модуле 4. Пишите, что должно быть на сервере, а не «как в `dev`»
- Строка, в которой хотя бы часть — пароль (например, `DATABASE_URL`), — секрет целиком
- «Обязательный» — приложение или стек не должны запускаться без этого параметра. «Умолчание» — какое значение подставится, если параметр не задан, и где это умолчание записано

**Перед коммитом** вставьте в конец ADR, после приложения А, заготовки приложений Б и В из раздела 5.6 — рецензент заполнит их на месте, не тратя время на поиск бланка.

### 5.5. Варианты и критерии сравнения

Три варианта обязательны: A — `os.environ`, как сейчас; B — `pydantic-settings`; C — python-dotenv + `os.environ` или environs, по выбору команды. Вариант A — честный кандидат: если после сравнения вы оставите его, решение станет обоснованным, а не привычкой.

Таблица сравнения ставится в начало раздела «Рассмотренные варианты»: строки — критерии, колонки — три варианта. Выберите **минимум пять** критериев, важных для вашей команды. Не знаете ответа для какого-то варианта — поставьте в клетку `?` и ссылку из колонки «Где искать»: на занятии такая клетка засчитывается, закрываете её дома.

| Критерий | Где искать |
|---|---|
| Когда приложение сообщает, что обязательной переменной нет: при старте или при первом запросе | pydantic-settings → Usage; environs → Basic usage; для `os.environ` — ваш `/health` |
| Проверка и приведение типов (`int`, `bool`, URL) | pydantic-settings → Parsing environment variable values; environs → Supported types |
| Порядок источников: переменная окружения, `.env`, умолчание — что побеждает | pydantic-settings → Field value priority; python-dotenv → Getting Started (`override`) |
| Чтение `.env` при локальном запуске без Docker | pydantic-settings → Dotenv (.env) support; python-dotenv; environs → Reading .env files |
| Защита секретов от вывода в лог | [Pydantic: SecretStr](https://pydantic.dev/docs/validation/latest/api/pydantic/types/) — что печатается вместо значения |
| Как переключаются `dev` и `prod` | 12-Factor, фактор III; документация инструмента |
| Новые зависимости и стоимость перехода с текущего `os.environ` | `pyproject.toml` после пробного `uv add` / `poetry add` в отдельной ветке; ваш `main.py` |
| Опыт команды, документация | Команда; документация инструмента |

**«Решение» на занятии** — четыре пункта, по одной-две фразы:

1. Механизм: какой вариант выбран и по какому критерию он выиграл
2. Окружения: как приложение узнаёт, что оно в `dev` или в `prod`, и что меняется между ними
3. Где живут значения `prod` и кто их задаёт
4. Чем предотвращается попадание секретов в git: что в `.gitignore`, какой инструмент проверки (gitleaks или detect-secrets — ставится на практике №4) и когда он запускается

`.env.example` на воркшопе и в домашнем задании не меняйте: новые переменные появятся в нём вместе с кодом, который их читает, на практике №4. Исключение — если в нём нашлось реальное значение (раздел 5.2).

Коммит и первый push ветки ADR. Ключ `-u` связывает локальную ветку с веткой на GitHub: без него первый `git push` новой ветки завершится ошибкой `has no upstream branch`.

```bash
git add docs/adr/003-configuration.md
git commit -m "docs: propose ADR 003 configuration and secrets"
# не свой ноутбук: git commit --author="Имя Фамилия <email-из-GitHub>" -m "docs: propose ADR 003 configuration and secrets"
git push -u origin <ваша-ветка>
```

**Как проверить:** `git status` показывает `Your branch is up to date with 'origin/<ваша-ветка>'`; на GitHub ветка видна в списке веток. PR можно открыть сразу, если успеваете; иначе — в домашнем задании 1.

### 5.6. Ревью другой команды (приложения Б и В)

Рецензент заполняет приложение Б **прямо в файле авторов**, на их ноутбуке. Авторы коммитят его отдельным коммитом с `--author` рецензента, затем заполняют приложение В. Вне воркшопа рецензент пишет то же самое комментарием в PR, а авторы переносят его в файл тем же способом.

**Как проверять — 7 минут:**

| Время | Что делать |
|---|---|
| 1 мин | Прочитать ADR целиком, молча. Вопросов пока не задавать |
| 3 мин | Пройти чек-лист сверху вниз. По каждому критерию найти **конкретное место** — колонка «Где смотреть» подсказывает какое. Критерии 3 и 8 проверяются не только по ADR: откройте `compose.yaml`, `.env.example`, выполните команду из колонки |
| 1,5 мин | **Холодная проверка.** Представьте: модуль 4, вы разворачиваете приложение этой команды на сервере, авторов рядом нет. Выпишите в таблицу будущий `.env` для `prod`: имя переменной и откуда взять значение. Значений не пишите. Чего не хватило — запишите |
| 1 мин | Из ❌ и ⚠️ выбрать **до двух главных замечаний** по формуле. Нет ни ❌, ни ⚠️ — не придумывайте замечаний: напишите «Блокирующих замечаний нет» и проверьте, что у каждого ✅ есть комментарий |
| 0,5 мин | Рекомендация или вопрос за пределами чек-листа; имя и логин |

**Замечание строится по формуле:** где → что не так → чем это грозит → что предлагаете.

| Не замечание | Замечание |
|---|---|
| «Всё хорошо» — без указания, где проверяли | «Приложение А, строка `DATABASE_URL`: в колонке «Секрет» — «нет». В строке есть пароль: её вывод в лог или в PR раскроет пароль. Предлагаем отметить как секрет» |
| «Непонятно, где prod» | «Решение, п. 3: значения `prod` — в `.env.prod` в корне репозитория. `git check-ignore -v .env.prod` выводит пустую строку — файл попадёт в коммит. Предлагаем добавить его в `.gitignore` и записать риск» |
| «Мало критериев» | «Таблица сравнения: критерий «удобство» без пояснения, оценки «+» у всех трёх вариантов. Выбор по таблице не следует. Предлагаем заменить на «когда приложение сообщает об отсутствии переменной»» |

**ADR без замечаний — нормальный результат,** если он доказан: у каждого ✅ указано, где вы это увидели. Выдуманное замечание хуже честного «замечаний нет».
