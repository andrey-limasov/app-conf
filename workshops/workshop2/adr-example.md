## Контекст

Наша команда разрабатывает Task Tracker — систему управления задачами для студенческих проектов — в рамках курса "Управление конфигурацией бизнес-приложений".

**Характеристики проекта:**

- Размер команды: 3 человека
- Длительность проекта: 16 недель (1 семестр)
- Частота релизов: промежуточные демо каждые 2 недели + финальный релиз в конце семестра
- Уровень опыта команды с Git: Иван — уверенно, Мария — базово, Алексей — новичок
- Требования к стабильности `main`: высокие, т.к. проект оценивается преподавателем и другими командами

**Проблема:** Нам необходимо выбрать стратегию ветвления Git, которая позволит:

1. Параллельно работать над несколькими фичами без конфликтов
2. Обеспечить стабильность основной ветки
3. Соответствовать требованиям DoD курса (PR с approval, чистая история)
4. Быть посильной для нашей команды по уровню сложности

## Рассмотренные варианты

### Вариант A: GitFlow

**Суть:** Строгая стратегия с отдельными ветками `main`, `develop`, `release`, `hotfix` и `feature`.  
**Плюсы:**

- Чёткое разделение сред (dev, release, prod)
- Предсказуемый процесс релизов
- Подходит для больших команд с релизами по расписанию

**Минусы:**

- Избыточная сложность для маленькой команды
- Ветка `develop` постоянно отстаёт от `main`, что создаёт конфликты
- Требует дисциплины, которую сложно поддерживать в учебном проекте

**Подходит ли нам:** Нет — для команды из 3 человек с релизами раз в 2 недели это overkill.

### Вариант B: GitHub Flow

**Суть:** Простая стратегия: `main` всегда стабилен, фичи разрабатываются в короткоживущих ветках и мержатся через PR.  
**Плюсы:**

- Простота и понятность для новичков
- Быстрая интеграция и обратная связь
- Идеально соответствует DoD курса (PR с approval)

**Минусы:**

- Нет интеграционной ветки — нестабильный код может попасть в `main`
- Требует быстрого code review
- Большие фичи могут создавать конфликты

**Подходит ли нам:** Да — простота и соответствие DoD перевешивают минусы, которые можно митигировать.

### Вариант C: Trunk-Based Development

**Суть:** Все разработчики коммитят в `main` как можно чаще (минимум раз в день), используя feature flags для скрытия незавершённых фич.  
**Плюсы:**

- Минимум конфликтов при merge
- Быстрая обратная связь
- Подходит для практик непрерывного деплоя

**Минусы:**

- Требует высокого уровня CI/CD и автотестов
- Нужна культура feature flags, которой у нас пока нет
- Сложно для новичков в команде

**Подходит ли нам:** Нет — у нас нет мощного CI/CD и опыта с feature flags.

## Решение

Мы выбрали стратегию **GitHub Flow**.

**Схема ветвления:**

```
main:    ●─────────●─────────●─────────●─────────●
          \         \         \         \
feature/   ●───●     \         \         \
auth:             \   \         \         \
feature/           ●───●         \         \
tasks:                     \       \         \
feature/                    ●───●   \         \
dashboard:                          ●───●       \
```

**Правила работы с ветками:**

1. Ветка `main` всегда стабильна и готова к деплою
2. Каждая фича разрабатывается в отдельной ветке `feature/[название-фичи]`
3. Перед merge в `main` обязателен PR с минимум 1 approval от сокомандника
4. Имена веток: `feature/...`, `bugfix/...`, `hotfix/...`
5. Сообщения коммитов следуют Conventional Commits
6. Ветки удаляются после merge

## Обоснование решения

**Почему мы выбрали именно эту стратегию?**

1. **Соответствие размеру команды:** Для команды из 3 человек GitHub Flow достаточно прост, чтобы его мог освоить даже Алексей (новичок). GitFlow создал бы лишнюю бюрократию.

2. **Частота релизов:** Наши демо каждые 2 недели требуют частой интеграции. GitHub Flow позволяет мержить фичи по мере готовности, а не ждать релизного окна.

3. **Уровень опыта команды:** У нас 2 человека с базовым/начальным уровнем Git. GitHub Flow проще для понимания — всего 2 ветки (`main` и feature), без `develop` и `release`.

4. **Требования DoD курса:** DoD требует PR с approval для всех изменений в `main`. GitHub Flow построен вокруг этой практики, поэтому идеально вписывается в требования.

## Последствия

### Положительные (+)

- Простота: вся команда быстро освоит процесс
- Быстрая интеграция: фичи мержатся каждые 2-3 дня
- Полное соответствие DoD курса
- Легко настроить branch protection rules

### Отрицательные (-)

- Нет интеграционной ветки — нужно полагаться на CI/CD для проверки стабильности
- Требует быстрого code review (иначе PR накапливаются)
- Большие фичи могут создавать конфликты

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Конфликты при merge больших фич | Средняя | Среднее | Разбиваем большие фичи на мелкие PR, мержим каждые 2-3 дня. Регулярно синхронизируем feature-ветку с `main` через `git pull --rebase` |
| Нестабильный код попадёт в `main` | Низкая | Высокое | Настраиваем CI/CD с автотестами. Branch protection rules запрещают merge без approval и зелёного CI |
| PR накапливаются из-за медленного review | Средняя | Среднее | Договорились: ревью в течение 24 часов. Если ревьюер занят — просим другого сокомандника |
