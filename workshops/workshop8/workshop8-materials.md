# Материалы для самостоятельного изучения (Воркшоп №8)

**Тема воркшопа:** Документация как артефакт: README, ADR, OpenAPI. Как написать, чтобы развернули за 5 минут
**Время на подготовку:** около 1 часа — 42 минуты чтения и 15 минут практической проверки

На воркшопе ваша команда сверит README с разделом 7 Definition of Done, перепишет запуск так, чтобы человек вне команды поднял стек за 5 минут без вопросов, напишет инструкцию развёртывания на сервере по пунктам 1–7 ADR 006 и папке `deploy/`, дополнит описание OpenAPI по пункту 8 ADR 006 и соберёт в README индекс ADR. Итог занятия — один Pull Request с документацией; на занятии он не мержится. Другая команда проверит его холодным запуском: свежий клон вашей ветки, только README, таймер. Нового ADR на занятии нет. Лекции не будет. Нужен ноутбук с Docker хотя бы у одного участника.

Как читать этот файл: разделы 0–4 — подготовка до занятия. Раздел 5 — рабочие таблицы, каркасы и команды занятия, заранее его открывать не обязательно. Раздел 6 — домашнее задание.

## 0. Что уже должно быть сделано

После практики №7 и её домашнего задания 1 в вашем репозитории: папка `deploy/` (`compose.yaml`, конфигурация прокси, `deploy.sh`; у способа C — `poll.sh`), приложение отвечает по `https://<поддомен>`, ADR 006 «Принято» в основной ветке. Это вход инструкции развёртывания: она описывает то, что уже работает.

Если что-то из этого не готово, воркшоп всё равно проходит — по строке своей ситуации:

| Ситуация | Что делать на воркшопе |
|---|---|
| ADR 006 пока «Предложено» (ситуации C, I и B без ревью практики №7) | Инструкция развёртывания — по тексту ADR 006 «Предложено»; в описании PR — строка «ADR 006 — Предложено». «Принято» — отдельным PR, срок прежний: не позже воркшопа №8 (домашнее задание 1 практики №7) |
| VPS нет (ситуация I практики №7) | Инструкция развёртывания — в файле `DEPLOY.md` в корне репозитория, в README — ссылка на него ([Definition of Done](../../definition-of-done.md), примечание 2: «если нет доступа к серверу — можно предоставить подробный `DEPLOY.md`»). Проверено у вас пока только на ноутбуке — так и напишите в `DEPLOY.md`. `DEPLOY.md` — место для инструкции, пока VPS нет, а не замена сервера: аренда VPS, Let's Encrypt и приёмка по URL — домашнее задание 1 практики №7, срок прежний. Исключение DoD по примечанию 2 — только если сервера не будет до защиты; согласуйте его заранее |
| Бизнес-эндпоинтов (CRUD основной сущности) нет — только `/`, `/health`, `/version` | Документируете то, что есть: пример ответа у `/version`, `503` у `/health`; в «Предметной области» README — какие эндпоинты будут |
| GitFlow: `develop` отстаёт от `main` (обратный merge после релиза практики №7 не сделан) | Обратный merge `main` → `develop` — до занятия, по `CONTRIBUTING.md`: это домашнее задание 1 практики №7, не новое. Иначе README в `develop` вы будете сверять не с тем кодом, что работает на сервере |
| Вариант (б) пункта 8 ADR 006 (basic auth) ещё не сделан | В README — что проверяющий увидит на публичном адресе сейчас: `/docs` → `404`. Basic auth — домашнее задание 4 практики №7, срок прежний |
| Вариант (а): файла `docs/openapi.json` в репозитории нет | Выгрузка — на занятии (раздел 5.5) |
| Вариант (а) в п. 8 записан как «артефактом CI», а джоба, который выгружает схему, в `ci.yml` нет | На занятии — файл `docs/openapi.json` скриптом раздела 5.5, как у всех: `ci.yml` на занятии не меняется. Расхождение с п. 8 — строка в «Историю изменений» ADR 006 (правило раздела 5.4) |
| Вариант (а) «артефактом CI», и джоб уже выкладывает схему артефактом | Скрипт и файл не нужны: в README «API» — где взять артефакт (прогон `CI` основной ветки, имя артефакта) и `/docs` при локальном запуске с `APP_ENV=dev` |

**Не добавляйте в README, в описание API в коде и в список ADR ничего до занятия:** аудит на занятии идёт по состоянию «как есть», правки — в одном PR.

## 2. Практическая проверка (15 мин)

Записи этого раздела — вход таблицы аудита на занятии (раздел 5.2). Ничего не коммитьте. Нужен Docker; без Docker — запасной вариант в шаге 2.

**Шаг 1. Разделы README.** В корне репозитория, на основной ветке разработки (`main`, GitFlow — `develop`), выведите заголовки README:

```bash
# macOS / Linux / Git Bash
grep -n '^#' README.md
```

```powershell
# Windows PowerShell
Select-String -Path README.md -Pattern '^#'
```

**Ожидаемый вывод** — номера строк и заголовки, например `5:## Команда`, `23:## Запуск через Docker Compose`. Строки внутри блоков кода, начинающиеся с `#`, — комментарии команд, их пропустите. Запишите для каждого из шести пунктов README в разделе 7 [Definition of Done](../../definition-of-done.md) — название и описание, стек, запуск локально через Docker Compose, развёртывание на сервере, примеры API запросов со ссылками на OpenAPI, участники — какой заголовок его закрывает или «нет».

**Шаг 2. Что FastAPI знает о вашем API.** Поднимите стек по своему README в режиме `dev` (в `.env` — `APP_ENV=dev`), затем запросите схему. Порт — ваш `APP_PORT`, по умолчанию 8000:

```bash
# macOS / Linux / Git Bash
curl -s http://localhost:8000/openapi.json | grep -o '"title":"[^"]*"' | head -1
curl -s http://localhost:8000/openapi.json | grep -oE '"examples?"' | wc -l
curl -s http://localhost:8000/openapi.json | grep -o '"503"' | wc -l
```

```powershell
# Windows PowerShell
$j = curl.exe -s http://localhost:8000/openapi.json
[regex]::Match($j, '"title":"[^"]*"').Value
[regex]::Matches($j, '"examples?"').Count
[regex]::Matches($j, '"503"').Count
```

**Ожидаемый вывод** у типичного проекта после практики №7:

| Что увидите | Что это значит |
|---|---|
| `"title":"Project Name"` | Заголовок схемы — заглушка каркаса практики №1 |
| `0` (вторая команда) | Ни одного примера запроса или ответа в схеме: команда считает и ключи `"examples"` у полей моделей, и ключи `"example"` у описанных ответов |
| `0` (третья команда) | Ответ `503` не описан нигде, хотя `/health` его возвращает |
| Первая команда ничего не вывела | Схема не отдаётся: `curl -s -o /dev/null -w '%{http_code}' http://localhost:8000/openapi.json` (PowerShell — `curl.exe -s -o NUL -w "%{http_code}" http://localhost:8000/openapi.json`) — `404` значит стек в `prod`: `APP_ENV=dev` в `.env`, `docker compose up -d`, повторите |

**Без Docker:** те же сведения — из кода. Путь к `main.py` подставьте свой, если он лежит в пакете (`app/main.py`):

```bash
# macOS / Linux / Git Bash
grep -nE 'title=|description=|version=|examples|responses=' main.py
```

```powershell
# Windows PowerShell
Select-String -Path main.py -Pattern 'title=|description=|version=|examples|responses='
```

Нет строк с `examples` и `responses=` — примеров и описанных кодов ошибок нет.

**Шаг 3. README совпадает с кодом?** Сравните то, что README обещает, с тем, что отвечает код:

```bash
# macOS / Linux / Git Bash
curl -s http://localhost:8000/version
grep -n '/version' README.md
grep -nE '@(app|router)\.(get|post|put|patch|delete)' main.py
```

```powershell
# Windows PowerShell
curl.exe -s http://localhost:8000/version
Select-String -Path README.md -Pattern '/version'
Select-String -Path main.py -Pattern '@(app|router)\.(get|post|put|patch|delete)'
```

Запишите: совпадает ли версия в ответе с версией в README; есть ли в README каждый эндпоинт из `main.py` (маршруты в других файлах — найдите тем же шаблоном в них); что README говорит про `/docs` в `prod` и совпадает ли это с п. 8 ADR 006. Каждое расхождение — строка «устарело» в таблице аудита.

**Шаг 4. Остановить стек:** `docker compose down`. На занятии холодный запуск пойдёт на свободных портах.

**Как проверить:** `git status --short` выводит то же, что до проверки: команды только читают файлы.

## 3. Вопросы для самопроверки

На воркшопе эти вопросы отдельно не разбираются: на них опирается работа в командах. Если на какой-то вопрос нет ответа, вернитесь к материалу из таблицы.

1. Ваш README: «`git clone`, `docker compose up --build`, откройте `/health`». Человек вне команды выполнил это в свежем клоне. Что у него есть, чего нет, и где он остановится? Что материал 5 говорит о читателе инструкции?
2. `/health` в вашем коде возвращает `503` через `JSONResponse`. Будет ли `503` в схеме OpenAPI? Что нужно написать, чтобы был (материал 3)?
3. В `prod` `openapi_url=None`. Можно ли всё равно получить схему из того же кода, не поднимая сервер? Прямого ответа в материалах 1–3 нет — запишите своё предположение, на занятии его проверим. Что понадобится, чтобы `main.py` вообще импортировался при вашем модуле настроек (fail fast, практика №4)?
4. Схема лежит в репозитории файлом `docs/openapi.json`. Через неделю добавили эндпоинт и забыли выгрузить схему. Что станет с файлом? Как это заметить до merge?
5. В README скопированы команды из `deploy.sh`. Через месяц скрипт поменяли. Что стало с README? Что надёжнее — копия команды или ссылка на файл и пункт ADR (материал 4)?
6. Вы меняете в PR только README и мержите его в `main`. Что запустит ваш `ci.yml`? Появится ли новый образ? Окажется ли он на сервере при вашем способе автодеплоя из п. 4 ADR 006?
7. Решение ADR 003 о `/docs` в `prod` отменено вариантом (в) п. 8 ADR 006. Удалять ли ADR 003 или его раздел? Что говорит материал 6?

## 5. Работа на занятии: PR с документацией

Итог занятия — один PR из отдельной ветки в основную ветку разработки (GitFlow — в `develop`). В нём: README — запуск, развёртывание на сервере (или ссылка на `DEPLOY.md`), раздел «API», индекс ADR; описание API в коде (`main.py`); при варианте (а) п. 8 — `scripts/export_openapi.py` и `docs/openapi.json`. Таблица аудита README — в описании PR. Минимум на занятии: запуск, развёртывание, один эндпоинт в OpenAPI полностью, индекс ADR. Остальное — домашнее задание 1.

**PR на занятии не мержится.** Merge в `main` собирает новый образ, а у способов B и C автодеплоя сразу ставит его на сервер, который нужен до защиты. GitFlow: PR занятия идёт в `develop`, в `main` и на сервер документация попадёт релизом (задание 2). Merge — домашнее задание 1, после ревью и approval, с проверкой, что деплой прошёл.

**Чего на занятии не делаете:** не пишете новый ADR; не переписываете ADR 001–006 (если инструкция развёртывания разошлась с ADR 006 — одна строка в его «Историю изменений», раздел 5.4); не меняете `ci.yml`, папку `deploy/` и `compose.yaml`; не мержите PR.

### 5.1. Роли и ветка

**Роли** — сразу, их вы запишете в описание PR:

| Роль | Что делает на занятии |
|---|---|
| Ведущий PR | Создаёт ветку, ведёт таблицу аудита (раздел 5.2) и индекс ADR (5.6), сводит текст ролей в файлы, делает коммиты и PR |
| «Запуск» | README: запуск локально через Docker Compose (раздел 5.3) |
| «Деплой» | README: развёртывание на сервере или `DEPLOY.md` (раздел 5.4) |
| «API» | Описание API в `main.py`, раздел «API» README; вариант (а) — выгрузка схемы (раздел 5.5) |
| Рецензент | Работает в одной из ролей выше, на этапе проверки уходит делать холодный запуск README другой команды (раздел 5.8) |

Втроём: «Деплой» совмещается с ведущим PR. Вдвоём: «Запуск + Деплой» и «API + ведущий PR», рецензент — первый.

**Ветка** — по вашим правилам именования из `CONTRIBUTING.md`, например `docs/readme-deploy-openapi`. Команды на GitFlow создают её от `develop` и открывают PR в `develop`.

```bash
git switch main            # GitFlow: git switch develop
git pull
git switch -c <ветка-по-вашим-правилам>
```

**Один ноутбук на команду:** роли пишут свой текст параллельно — в заметке или в чате команды, — а в файлы его вносит тот, кто за ноутбуком, по очереди; README и ADR остальные читают на GitHub с телефона. **Два ноутбука:** файлы правятся только на том, где создана ветка; со второго читайте ADR 006 и `deploy/`, пересылайте текст в чат команды. Две правки одного файла в одной ветке дадут конфликт при push.

### 5.5. OpenAPI (роль «API»)

Схему строит FastAPI, но только из того, что объявлено в коде (материалы 1–3). Минимум на занятии — три правки в `main.py`, остальные эндпоинты — домашнее задание 1.

**1. Описание API** — в `FastAPI(...)`: `title` и `description` вместо заглушки каркаса. `version` не трогайте: её меняет релиз (по ADR 003 или `CONTRIBUTING.md`), а README приводится к коду — пример `/version` в README такой, какой ответ вы получили на шаге 3 раздела 2:

```python
app = FastAPI(
    title="<Название сервиса>",
    description="<Что делает сервис, одна-две фразы. Где схема: /docs при APP_ENV=dev; в prod — по п. 8 ADR 006>",
    # version, docs_url, redoc_url, openapi_url — как сейчас (п. 8 ADR 006)
)
```

**2. Один бизнес-эндпоинт полностью** — примеры полей запроса и описанные ответы с ошибками. Пример для создания и чтения заявки; модели и пути подставьте свои. У своего эндпоинта меняете только модели (`Field`) и аргументы декоратора (`summary`, `responses`); тело функции и хранилище — ваши, их не трогайте. Импорты объедините со своими: `HTTPException` добавьте в существующую строку `from fastapi import …`, строку `from pydantic import …` — к импортам в начале файла; порядок поправит `uv run ruff check --fix .` (Poetry — `poetry run ruff check --fix .`). Иначе `ruff check` и `lint` в PR остановятся на `I001 Import block is un-sorted or un-formatted`:

```python
from fastapi import HTTPException
from pydantic import BaseModel, Field


class TicketIn(BaseModel):
    title: str = Field(description="Что сломалось", examples=["Не включается проектор"])
    room: str = Field(description="Где", examples=["А-214"])


class Ticket(TicketIn):
    id: int = Field(examples=[1])
    status: str = Field(examples=["new"])


class Problem(BaseModel):
    detail: str


tickets: dict[int, Ticket] = {}  # хранилище примера; у вас — своё


@app.get(
    "/tickets/{ticket_id}",
    summary="Одна заявка",
    responses={
        404: {
            "model": Problem,
            "description": "Заявки с таким номером нет",
            "content": {
                "application/json": {"example": {"detail": "Ticket not found"}}
            },
        }
    },
)
def get_ticket(ticket_id: int) -> Ticket:
    if ticket_id not in tickets:
        raise HTTPException(status_code=404, detail="Ticket not found")
    return tickets[ticket_id]
```

Код ошибки описывается в `responses` у каждого эндпоинта, который его возвращает: сам по себе `raise HTTPException(status_code=404)` в схему не попадает. `422` FastAPI добавляет сам у эндпоинтов с телом или параметрами. **CRUD нет:** пример ответа у `/version` — ключ `200` в `responses` с `content` и `example`, как у `503` ниже.

**3. `503` у `/health`.** Ответ, который код отдаёт через `JSONResponse`, нужно описать (материал 3):

```python
@app.get(
    "/health",
    # остальные аргументы декоратора — как сейчас
    summary="Приложение и база отвечают",
    responses={
        503: {
            "description": "База данных недоступна",
            "content": {
                "application/json": {
                    "example": {"status": "unhealthy", "database": "unavailable"}
                }
            },
        }
    },
)
```

Тело примера — то, что ваш `/health` действительно возвращает при недоступной базе.

**Как проверить:** код приложения входит в образ, поэтому после правки `main.py` уже запущенный стек отдаёт старую схему. Пересоберите приложение: `docker compose up -d --build` (стек в `dev`), дождитесь ответа `/health` — шаг 4 вашего README. Затем команды шага 2 раздела 2 — `"title"` ваш, число примеров (вторая команда) больше нуля, `"503"` — не меньше одного; в браузере `http://localhost:8000/docs` — ваш заголовок, у эндпоинта видны пример запроса и коды ответов. Затем линтеры и тесты локально — команды из вашего `CONTRIBUTING.md`: это те же проверки, что запустятся в PR.

**4. Ссылка на схему в README — по варианту п. 8 ADR 006.** Раздел «API» README: таблица эндпоинтов (метод и путь, что делает, коды ответов, пример ответа), пример запроса к бизнес-эндпоинту и абзац «Схема OpenAPI» — по своему варианту:

| Вариант п. 8 | Что написать в абзаце «Схема OpenAPI» |
|---|---|
| (а) файл | Ссылка на файл `[docs/openapi.json](docs/openapi.json)`; `/docs` — только при локальном запуске с `APP_ENV=dev`; команда выгрузки и проверка, что файл совпадает с кодом (ниже). «Артефактом CI» с готовым джобом — вместо файла: где взять артефакт (раздел 0) |
| (б) basic auth | Что увидит проверяющий на публичном адресе без пароля: `https://<поддомен>/docs` → `401` (пока basic auth не сделан — `404`); пароль в README не пишется — кто и как его выдаёт; схема без пароля — локально, `/docs` при `APP_ENV=dev` |

Пример запроса в README — для bash `curl` и для Windows PowerShell `Invoke-RestMethod`: в Windows PowerShell 5.1 `curl.exe` с JSON в одинарных кавычках теряет двойные кавычки при передаче внешней программе, и сервер отвечает `422` `JSON decode error` (проверено при подготовке материалов):

```bash

```

```powershell

```

В Windows PowerShell 5.1 кириллица в ответе `Invoke-RestMethod` отображается искажённой; заявка при этом сохранена верно — проверьте `curl.exe -s http://localhost:8000/tickets/1`.

**Вариант (а): выгрузка схемы файлом.** Схему можно получить из кода и при выключенных в `prod` `/docs`: `app.openapi()` работает при `openapi_url=None`. Создайте `scripts/export_openapi.py`:

```python
"""Выгрузка схемы OpenAPI в docs/openapi.json — работает и при APP_ENV=prod.

Запуск из корня репозитория: uv run python scripts/export_openapi.py
Нужна переменная DATABASE_URL (любое непустое значение: к базе скрипт не подключается).
"""

import json
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(ROOT))

from main import app  # если main.py в пакете: from app.main import app

target = ROOT / "docs" / "openapi.json"
target.parent.mkdir(exist_ok=True)
text = json.dumps(app.openapi(), ensure_ascii=False, indent=2) + "\n"
target.write_text(text, encoding="utf-8", newline="\n")
print(f"{target.relative_to(ROOT).as_posix()}: {len(text.encode())} bytes")
```

Файл пишет сам скрипт, в UTF-8 и с переводами строк LF: перенаправление `> docs/openapi.json` в Windows PowerShell 5.1 записывает файл в UTF-16 (проверено при подготовке материалов), и тот же файл из bash получится другим.

Выгрузить и проверить. Модуль настроек при импорте `main.py` требует `DATABASE_URL` (fail fast): без неё скрипт остановится: `database_url` над строкой `Field required`; у вариантов A и C1 модуля настроек практики №4 — `Не заданы обязательные переменные окружения: DATABASE_URL`, у C2 — `EnvNotSetError`. Если в вашем `.env` есть строка `DATABASE_URL` для запуска без Docker — переменная не нужна:

```bash
# macOS / Linux / Git Bash
DATABASE_URL=postgresql://unused uv run python scripts/export_openapi.py
git diff --exit-code docs/openapi.json
```

```powershell
# Windows PowerShell
$env:DATABASE_URL = "postgresql://unused"
uv run python scripts/export_openapi.py
Remove-Item Env:DATABASE_URL
git diff --exit-code docs/openapi.json
```

Poetry — `poetry run python scripts/export_openapi.py`. **Ожидаемый вывод:** `docs/openapi.json: <число> bytes`. Первая выгрузка — файл новый, `git diff` его не показывает (`git status` — `?? docs/openapi.json`): пустой `git diff` у файла, которого нет в git, ничего не доказывает. Добавьте его в коммит (раздел 5.7); после коммита `git ls-files docs/openapi.json` выводит путь — файл в ветке. Повторная без изменений в коде — `git diff` без вывода, код выхода `0`. Вывод `git diff` есть — схема в файле не совпадает с кодом: закоммитьте новый файл. В README «API» — эти две команды и что значит пустой вывод. `warning: ... LF will be replaced by CRLF` — предупреждение git, не ошибка; при пустом `git diff` строка ` M docs/openapi.json` в `git status` исчезает после `git add`, в коммит ничего не попадает.

```bash
git commit -m "docs: add server deployment guide"

git add main.py            # вариант (а): git add main.py scripts/export_openapi.py docs/openapi.json
git commit -m "docs: describe API examples and errors in OpenAPI"

git add README.md
git commit -m "docs: add API section and ADR index to README"

git push -u origin <ваша-ветка>
```

Пути — свои: `main.py` в пакете — `app/main.py`. GitHub Flow и Trunk-Based: PR в `main`; GitFlow — в `develop`. PR: **Pull requests → New pull request**, ваша ветка, заголовок `docs: README, deployment guide and OpenAPI`, в описание — таблица аудита (раздел 5.2) и строка «Не мержить до ответа на ревью холодного запуска». Trunk-Based со squash: коммиты ролей при merge сольются в один — роли и авторы остаются в описании PR.

**Как проверить:** PR открыт, во вкладке **Checks** идут обязательные проверки вашего `ci.yml`. Красная проверка (линтер, тест на `/docs` или схему) — исправление в той же ветке, новым коммитом. `publish` на PR не запускается.

**Перед холодным запуском** авторы останавливают свой стек — порты должны быть свободны: в своей папке `docker compose down` (без `-v`, данные базы останутся).

### 5.8. Холодный запуск другой командой (рецензент)

Рецензент проверяет документацию другой команды **на её ноутбуке**, в новой папке, только по её README: так ваш README будут читать другие команды перед защитой, когда ставят баллы «Воспроизводимость» и «Документация» ([система оценивания](../../assessment.md), раздел 2). Авторы молчат и записывают каждый вопрос рецензента: каждое действие, которого в README нет, и каждый вопрос авторам — замечание. Вне воркшопа рецензент делает то же на своём ноутбуке.

**Бланк — заранее.** Как только преподаватель назовёт команду, которую вы проверяете, — до перехода к её ноутбуку: на телефоне откройте её PR (вкладка **Pull requests** её репозитория), вставьте бланк (ниже) в поле комментария и не отправляйте; PR ещё не открыт — вставьте бланк в заметку телефона. Клетки таблиц заполняйте по ходу запуска и трассировки.

**Как проверять — 13 минут:**

| Время | Что делать |
|---|---|
| 6 мин | Переход к ноутбуку авторов, свежий клон ветки PR в новую папку (команды ниже) и запуск **только по README авторов**. Таймер 5 минут — от `git clone` до ответа `200` на `/health`. Записывайте каждую команду, которой нет в README, и место, где остановились. 5 минут вышли — запишите, на каком шаге README вы были |
| 4 мин | Трассировка инструкции развёртывания — три вопроса Т1–Т3 по тексту README (или `DEPLOY.md`) и ADR 006, без вопросов авторам; три проверки OpenAPI О1–О3 |
| 3 мин | Главные замечания в бланке, отправить комментарий в PR авторов; убрать за собой стек и папку |

Клон ветки PR (имя ветки — в шапке PR авторов). Команду `git clone` из README выполните с `-b <ветка-PR>` и в папку `cold-check` — это не замечание:

```bash
cd ..
git clone -b <ветка-PR> https://github.com/<владелец>/<репозиторий>.git cold-check
cd cold-check
```

Нет Docker на ноутбуке авторов — проходите README по шагам без выполнения: что нужно до шага, откуда каждое значение, что должно получиться. Бланк тот же, вместо времени — «без запуска».

После комментария — убрать за собой:

```bash
docker compose down -v
cd ..
rm -rf cold-check
# Windows PowerShell: Remove-Item -Recurse -Force cold-check
```

**Трассировка инструкции развёртывания.** Сервер и деплой считайте сделанными так, как написано в инструкции. Инструкцию не выполняете — у вас нет ключей к серверу авторов.

| № | Вопрос |
|---|---|
| Т1 | Чистый сервер, вы — новый участник с ключом SSH. Какие команды по порядку до `200` на `https://<поддомен>/health`? Откуда берётся каждое значение `deploy/.env`? |
| Т2 | В основную ветку смержен новый коммит. Как он попадёт на сервер, кто или что это запускает? Как понять, что получилось? |
| Т3 | Новая версия отвечает `503`. Как вернуть прошлую, по какому тегу и где этот тег взять? Где посмотреть логи и как найти строки одного запроса? |

**Три проверки OpenAPI:**

| № | Что проверить | Где смотреть |
|---|---|---|
| О1 | `title` и `description` — не заглушка `Project Name` / `Project description` | `main.py` или `/docs` стека холодного запуска |
| О2 | У одного бизнес-эндпоинта (CRUD нет — у `/version`) пример запроса или ответа и описанные коды ошибок; у `/health` — `503` | `/docs` или `main.py` |
| О3 | README «API» по варианту п. 8: (а) `git ls-files docs/openapi.json` выводит путь — файл есть в ветке, затем выгрузка командой из README и `git diff --exit-code docs/openapi.json` без вывода; «артефактом CI» — ссылка из README открывает прогон с артефактом схемы; (б) сказано, что увидит проверяющий на публичном адресе и где схема без пароля; (в) ссылка на публичный `/docs` открывается | README, раздел «API» |

**Замечание строится по формуле:** где → что не так → чем это грозит → что предлагаете.

| Не замечание | Замечание |
|---|---|
| «README непонятный» | «README, „Запуск“, шаг 2: `cp .env.example .env` есть, а что поменять в `.env` — нет. На 2-й минуте я спросил авторов, нужно ли менять `changeme`. На защите это вопрос — минус „Воспроизводимости“. Предлагаем строку „замените `changeme` на свой пароль“ и проверку шага» |
| «Деплой описан плохо» | «„Развёртывание“, шаг 2: переменные `deploy/.env` перечислены, но откуда взять `APP_TAG` для первого запуска — нет. В Т1 новый участник не запустит стек. Предлагаем колонку „откуда значение“: последний тег `sha-` из Packages» |
| «В Swagger мало примеров» | «`GET /tickets/{ticket_id}`: код возвращает `404`, в схеме его нет, примеров у полей нет. Проверяющий не увидит, как выглядят запрос и ошибка (DoD 7, „Есть примеры запросов/ответов“). Предлагаем `Field(examples=...)` и `responses={404: ...}` (раздел 5.5)» |

**Документация без замечаний — нормальный результат,** если он доказан: стек поднялся по README без вопросов, Т1–Т3 протрассированы без пробелов, у О1–О3 указано место. Выдуманное замечание хуже честного «замечаний нет». Проверяется документация, а не люди. Не исправляйте файлы за авторов.

**Бланк комментария** — в PR авторов, вкладка **Conversation**, с вашего аккаунта GitHub:

```markdown

| Т1 |  |  |
```

**Нет устройства с GitHub у рецензента:** авторы публикуют комментарий со своего аккаунта, первой строкой — «Ревью: [имя], @[логин рецензента]»; рецензент до конца дня отвечает под ним со своего аккаунта «подтверждаю».

**Ответы авторов** — в том же PR, ответом на комментарий: по каждому замечанию и каждому пробелу трассировки — что изменили (ссылка на коммит) или почему не согласны; не успели — «ДЗ 1».
