# Техническое задание для итогового проекта

**Курс:** Управление конфигурацией бизнес-приложений  
**Формат:** Командный проект (3-4 человека)  
**Стек:** Python 3.11+, FastAPI, PostgreSQL, Docker, CI/CD  
**Статус:** Базовые требования (могут быть расширены командой)

---

## Цели проекта

1. **Образовательная:** Применить на практике все инструменты и практики, изученные в курсе (Git, Docker, CI/CD, конфигурация, деплой).
2. **Инженерная:** Создать работающее клиент-серверное бизнес-приложение с полной инфраструктурой разработки и поставки.
3. **Командная:** Отработать навыки командной разработки, code review и управления проектом.
4. **Прикладная:** Получить готовый шаблон (boilerplate) для использования в выпускной квалификационной работе (ВКР).

---

## Минимальный функциональный продукт (MVP)

Каждая команда должна реализовать **минимум** следующий функционал:

### 1. Основная бизнес-сущность (CRUD)

**Требования:**

- Минимум 1 основная сущность (например, "Задача", "Заявка", "Бронирование")
- Полная реализация CRUD-операций:
  - `POST /resource` — создать
  - `GET /resource` — получить список (с пагинацией)
  - `GET /resource/{id}` — получить详情
  - `PUT /resource/{id}` — обновить
  - `DELETE /resource/{id}` — удалить

**Примеры сущностей:**

- Задачи (Task)
- Заявки (Request/Ticket)
- Бронирования (Booking)
- Пользователи (User)
- Товары (Product)
- События (Event)

### 2. Аутентификация и авторизация

**Требования:**

- Регистрация пользователей (`POST /auth/register`)
- Вход в систему (`POST /auth/login`)
- JWT-токены или сессионная аутентификация
- Защита эндпоинтов (только авторизованные пользователи могут создавать/изменять/удалять)
- Разграничение прав (опционально, но желательно):
  - Администратор может удалять любые записи
  - Пользователь может управлять только своими записями

### 3. Валидация данных

**Требования:**

- Все входные данные валидируются через Pydantic-модели
- Осмысленные сообщения об ошибках валидации
- Проверка уникальности (например, email не должен дублироваться)
- Проверка ссылочной целостности (нельзя удалить пользователя, у которого есть связанные записи)

### 4. Работа с базой данных

**Требования:**

- PostgreSQL в качестве СУБД
- ORM: SQLAlchemy или Tortoise ORM
- Миграции через Alembic
- Минимум 2 связанные таблицы (например, User и Task)
- Индексы для часто запрашиваемых полей

### 5. Обработка ошибок

**Требования:**

- Глобальный обработчик ошибок
- Осмысленные HTTP-коды и сообщения:
  - `400 Bad Request` — ошибка валидации
  - `401 Unauthorized` — не авторизован
  - `403 Forbidden` — нет прав
  - `404 Not Found` — ресурс не найден
  - `500 Internal Server Error` — внутренняя ошибка
- Логирование всех ошибок

## Нефункциональные требования

### 1. Производительность

- Время ответа API: не более 500 мс для 95% запросов
- Поддержка минимум 100 одновременных подключений
- Пагинация для списков (по умолчанию 20 записей на страницу)

### 2. Безопасность

- Пароли хэшируются (bcrypt или аналог)
- JWT-токены имеют срок действия (например, 24 часа)
- Секреты не хранятся в коде (используются переменные окружения)
- Защита от SQL-инъекций (через ORM)
- CORS настроен правильно (только разрешенные домены)

### 3. Тестируемость

- Минимум 60% покрытия кода тестами
- Тесты делятся на:
  - Unit-тесты (для сервисов)
  - Integration-тесты (для API)
- Тесты запускаются в изолированном окружении (тестовая БД)

### 4. Масштабируемость

- Код не зависит от конкретного окружения (12-Factor App)
- Конфигурация через переменные окружения
- Состояние хранится в БД, а не в памяти приложения

## Примеры тем проектов

### 1. Система управления задачами (Task Tracker)

**Описание:** Аналог Trello/Jira для управления задачами в команде.

**Основная сущность:** Задача (Task)

**Дополнительные сущности:**

- Проект (Project) — группа задач
- Пользователь (User) — участник проекта
- Комментарий (Comment) — к задаче

**Примеры эндпоинтов:**

- `POST /tasks` — создать задачу
- `GET /tasks?project_id=1&status=open` — получить задачи проекта
- `PUT /tasks/{id}/status` — изменить статус задачи
- `POST /tasks/{id}/comments` — добавить комментарий

**Сложность:** Средняя

---

### 2. Система бронирования переговорных комнат

**Описание:** Сервис для бронирования переговорных комнат в офисе.

**Основная сущность:** Бронирование (Booking)

**Дополнительные сущности:**

- Комната (Room) — переговорная с характеристиками
- Пользователь (User) — сотрудник
- Оборудование (Equipment) — проектор, доска и т.д.

**Примеры эндпоинтов:**

- `POST /bookings` — забронировать комнату
- `GET /bookings?room_id=1&date=2024-01-15` — получить бронирования
- `GET /rooms?available_at=2024-01-15T10:00:00` — найти свободные комнаты
- `DELETE /bookings/{id}` — отменить бронирование

**Сложность:** Средняя

---

### 3. Система учета заявок (Help Desk)

**Описание:** Сервис для подачи и обработки заявок в техподдержку.

**Основная сущность:** Заявка (Ticket)

**Дополнительные сущности:**

- Пользователь (User) — клиент
- Специалист (SupportAgent) — обработчик
- Категория (Category) — тип заявки

**Примеры эндпоинтов:**

- `POST /tickets` — создать заявку
- `GET /tickets?status=open&assignee_id=1` — получить заявки специалиста
- `PUT /tickets/{id}/assign` — назначить исполнителя
- `POST /tickets/{id}/comments` — добавить комментарий

**Сложность:** Высокая

### 4. Система управления библиотекой

**Описание:** Сервис для учета книг и выдачи их читателям.

**Основная сущность:** Книга (Book)

**Дополнительные сущности:**

- Читатель (Reader) — пользователь
- Выдача (Loan) — запись о выдаче книги
- Автор (Author) — автор книги

**Примеры эндпоинтов:**

- `POST /books` — добавить книгу

- `POST /loans` — выдать книгу
- `PUT /loans/{id}/return` — вернуть книгу

**Сложность:** Средняя

**Описание:** Бэкенд для сервиса заказа еды с доставкой.

**Основная сущность:** Заказ (Order)

## Ограничения и допущения

### Ограничения:

1. **Время:** Проект должен быть реализован за 16 недель (один семестр).
2. **Команда:** 3-4 человека, все должны внести вклад.
3. **Стек:** Только Python/FastAPI + PostgreSQL (не допускается использование других языков или СУБД).
4. **Инфраструктура:** Только бесплатные инструменты (GitHub/GitLab, Docker Hub, учебный VPS).

### Допущения:

1. **Клиентская часть:** Не требуется (только API). Если хотите сделать фронтенд — это бонус, но не обязательно.
2. **Масштаб:** Проект рассчитан на 100-1000 пользователей, не нужно проектировать под миллионы.
3. **High Load:** Не требуется реализовывать сложные оптимизации (кеширование, шардирование и т.д.).
4. **Мобильная версия:** Не требуется, но API должен быть удобным для использования с мобильных устройств.

## Бонусные задачи (по желанию)

Если команда выполнила MVP и хочет получить дополнительную оценку, можно реализовать:

1. **Фронтенд:** Простой интерфейс на React/Vue/Flutter.
2. **WebSocket:** Уведомления в реальном времени (например, обновление статуса задачи).
3. **Файловое хранилище:** Загрузка аватарок, документов.
4. **Интеграции:** Отправка email/SMS уведомлений.
5. **Админ-панель:** Интерфейс для управления пользователями и данными.
6. **Микросервисы:** Разделение на 2-3 сервиса (но это усложнит деплой).
7. **Мониторинг:** Интеграция с Prometheus/Grafana.

**Важно:** Бонусные задачи не компенсируют невыполненный MVP. Сначала — обязательные требования, потом — дополнительные.

## Этапы реализации

### Этап 1: Инициация (Недели 1-2)

- Выбор темы проекта
- Создание репозитория
- Настройка базовой структуры FastAPI
- Написание CONTRIBUTING.md

### Этап 2: Базовый функционал (Недели 3-6)

- Реализация CRUD для основной сущности
- Подключение PostgreSQL
- Настройка миграций Alembic
- Базовая аутентификация

### Этап 3: Контейнеризация и конфигурация (Недели 7-8)

- Написание Dockerfile
- Настройка docker-compose
- Вынос конфигурации в переменные окружения
- Удаление секретов из истории Git

### Этап 4: CI/CD и автоматизация (Недели 9-12)

- Настройка пайплайна (линтинг, тесты, сборка)
- Публикация Docker-образа в реестр
- Автоматический деплой на сервер

### Этап 5: Деплой и наблюдаемость (Недели 13-14)

- Развертывание на VPS
- Настройка reverse-proxy и HTTPS
- Структурированные логи
- Health-check эндпоинты

### Этап 6: Документация и защита (Недели 15-16)

- Написание README, ADR
- Подготовка презентации
- Репетиция live-demo
- Защита проекта
