## Назначение репозитория

Этот репозиторий содержит **полный методический комплект** курса "Управление конфигурацией бизнес-приложений". Он используется:

1. **Студентами** — как основной источник требований, инструкций и критериев оценки
2. **Преподавателями** — как сценарии занятий, карточки ролей, чек-листы
3. **ИИ-агентами** — как контекст для генерации материалов, ответов на вопросы, проверки соответствия DoD

**Ключевой принцип:** Все материалы курса согласуются со студентами на воркшопе №1 и могут быть изменены только по общему согласию.

## Модель веток и worktree

Репозиторий живёт в двух ветках, подключённых через `git worktree`:

| Ветка | Рабочая папка | Что содержит | Кому видна |
|---|---|---|---|
| `main` | `app-conf-all/app-conf/` | Материалы для студентов | Публично (remote `student`) |
| `teacher` | `app-conf-all/app-conf-teacher/` | Всё из `main` + преподавательские материалы | Только преподаватель |

**Как это работает:**

- В ветке `main` файл `.gitignore` содержит правила `*-teacher*` и `*-teacher/` — любые преподавательские файлы физически невидимы для git в этой ветке.
- В ветке `teacher` эти правила удалены (коммит `b15e013`), поэтому папки `workshops-teacher/`, `additional-files-teacher/` и файлы `*-guide-teacher.md` отслеживаются.
- `teacher` — **надмножество** `main`: все общие документы (`syllabus.md`, `definition-of-done.md`, `assessment.md`, `project-requirements.md`, `home-work-*.md`, `practices/`) должны быть идентичны в обеих ветках.

### Правило синхронизации (обязательное)

Общие документы редактируются **только в `main`**. После каждого изменения общих документов:

```bash
cd app-conf            # ветка main
git add -A && git commit -m "docs: ..."
git push student main

cd ../app-conf-teacher # ветка teacher
git merge main         # .gitignore ветки teacher сохранится автоматически
```

Преподавательские материалы создаются **только в `app-conf-teacher/`** и в `main` не попадают никогда.

**Типовая ошибка:** создать файл `*-teacher*` в папке `app-conf/` (ветка `main`). Git молча его проигнорирует, файл не попадёт ни в одну ветку и потеряется при смене машины. Так уже терялся `practice-1-guide-teacher.md` (восстановлен 2026-09-20).

### Восстановление worktree после переноса папки

Если репозиторий перемещали, ссылка worktree ломается (`git worktree list` показывает `prunable`, git в `app-conf-teacher/` падает с `fatal: not a git repository`). Лечится из папки `app-conf/`:

```bash
git worktree repair ../app-conf-teacher
```

`.git`-файл в `app-conf-teacher/` и `app-conf/.git/worktrees/app-conf-teacher/gitdir` должны содержать **абсолютные пути той ОС, где ведётся работа** (для этой машины — `C:/Users/Samsung/qwen/projects/app-conf-all/...`).

### Remote

| Remote | URL | Назначение |
|---|---|---|
| `student` | https://github.com/andrey-limasov/app-conf | Ветка `main`, публичный репозиторий для студентов |
| `teacher` | **не настроен** | Планируется приватный репозиторий для ветки `teacher` |

Пока remote `teacher` не создан, ветка `teacher` существует только локально — единственная копия преподавательских материалов находится на рабочей машине. Это основной риск проекта.

## Методологические принципы курса

### 1. Перевёрнутый класс (Flipped Classroom)

**Студенты изучают теорию ДО занятия** по списку материалов. На занятии — только практика, обсуждение, применение.

**Следствие для ИИ-агента:** При генерации материалов для воркшопа НЕ включать лекционный контент. Только задания, обсуждения, практику.

### 2. Peer Teaching (студенты учат студентов)

На воркшопе №2 каждая команда готовит презентацию по одной из стратегий ветвления и преподаёт остальным.

**Следствие для ИИ-агента:** Задания должны быть структурированы так, чтобы студенты могли самостоятельно изучить тему и объяснить её другим.

### 3. Проектное обучение (Project-Based Learning)

Весь курс — это один командный проект (16 недель), разбитый на модули. Каждый модуль добавляет слой инфраструктуры.

**Следствие для ИИ-агента:** Новые материалы должны вписываться в логику развития проекта, а не быть изолированными темами.

### 4. Оценка 360°

Оценка складывается из:
- Оценки преподавателя (по DoD)
- Peer review (оценка других команд)
- Peer assessment (оценка сокомандников, коэффициент вклада)

**Следствие для ИИ-агента:** Все артефакты должны быть пригодны для оценки по трём направлениям.

### 5. ADR как обязательный артефакт

Минимум 2 ADR (Architecture Decision Record) по ключевым решениям. ADR — это не формальность, а инструмент фиксации решений.

**Следствие для ИИ-агента:** При генерации ADR соблюдать структуру: Контекст → Рассмотренные варианты → Решение → Обоснование → Последствия → Риски и митигация.

## Глоссарий курса

| Термин | Определение |
|---|---|
| **DoD (Definition of Done)** | Критерии готовности проекта. 7 групп требований, все обязательны |
| **ADR (Architecture Decision Record)** | Документ фиксации архитектурного решения. Структура: Контекст → Решение → Обоснование → Последствия |
| **Peer Teaching** | Формат занятия, где студенты готовят и проводят презентации для других команд |
| **Peer Review** | Межкомандное ревью артефактов (ADR, код, документация) |
| **Peer Assessment** | Оценка вклада сокомандников (анонимная, влияет на коэффициент вклада) |
| **Workshop** | Лекция-воркшоп (нечётные недели). 90 минут, интерактивный формат |
| **Practice** | Практическое занятие (чётные недели). 180 минут, самостоятельная работа по инструкции |
| **Conventional Commits** | Стандарт написания сообщений коммитов: `feat:`, `fix:`, `docs:`, `refactor:` и т.д. |
| **12-Factor App** | Методология построения современных приложений. Код отделён от конфигурации |
| **Branch Protection** | Правила защиты ветки на GitHub/GitLab (запрет прямого push, требование PR) |
| **Health-check** | Эндпоинт `GET /health`, возвращает 200 OK если приложение работает |
| **Multi-stage build** | Оптимизация Dockerfile: сборка в одном образе, запуск в другом (меньший размер) |
| **Feature flag** | Переключатель функциональности в коде. Используется в Trunk-Based Development |

## Правила работы с файлами

### Именование файлов

- **kebab-case** для всех файлов (`practice-1-guide.md`, `adr-template.md`)
- **Суффиксы:**
  - `-guide.md` — инструкция для студентов

  - `-template.md` — шаблон документа
  - `-example.md` — заполненный пример
- **Нумерация:** `workshop-1-scenario.md`, `practice-1-guide.md`, `adr-001-branching-strategy.md`
- **Папки:** `workshop{N}/`, `practice{N}/` — без дефиса

### Структура документов

**Для инструкций (practice-N-guide.md):**
1. Цели (по таксономии Блума)

3. Пошаговая инструкция с таймингом
4. Сводка полезных ссылок
5. Чек-лист самопроверки
6. Чек-лист для преподавателя
7. Домашнее задание

**Для сценариев (workshop-N-scenario.md):**
1. Цели воркшопа
2. Подготовка (за 3-4 дня)
3. Поминутный сценарий (тайминг, реплики преподавателя, действия студентов)

**Для ADR:**
1. Статус (Предложено / Принято / Устарело)

## Инструкции для ИИ-агента

### Перед любой работой с репозиторием

1. Проверить, в какой рабочей папке идёт работа: `app-conf/` — ветка `main` (студенты), `app-conf-teacher/` — ветка `teacher` (преподаватель)
2. Преподавательский файл создавать **только** в `app-conf-teacher/`, иначе `.gitignore` его проглотит
3. После правки общих документов в `main` — смерджить `main` в `teacher` (см. "Правило синхронизации")
4. После завершения документа — обновить `ROADMAP.md`

### Что делать, если...

**...просят сгенерировать новый документ для курса:**
1. Определить тип документа (инструкция практики / сценарий воркшопа / ADR / лист оценки)
2. Определить ветку: студенческий документ → `main`, преподавательский → `teacher`
3. Использовать соответствующий шаблон из раздела "Шаблоны документов"
4. Убедиться, что документ соответствует DoD (`definition-of-done.md`)
5. Добавить связи с другими документами (граф связей)
6. Использовать правильный формат именования

**...просят проверить соответствие DoD:**
1. Открыть `definition-of-done.md`
2. Пройтись по всем 7 группам критериев
3. Для каждого пункта проверить: выполнено / не выполнено / частично
4. Вернуть чек-лист с пометками

**...просят сгенерировать ADR:**
1. Использовать шаблон `workshops/workshop2/adr-template.md` и пример `workshops/workshop2/adr-example.md` (обе ветки)
2. Заполнить все разделы: Контекст → Варианты → Решение → Обоснование → Последствия → Риски
3. Убедиться, что решение соответствует DoD
4. Добавить схему ветвлений (если ADR про стратегии)
5. Указать источники

**...просят сгенерировать инструкцию для практики:**
1. Использовать шаблон из раздела "Шаблоны документов"
2. Определить цели по таксономии Блума (создать, применить, проанализировать)
3. Разбить на этапы с таймингом (всего 180 минут)
4. Добавить чек-листы для самопроверки и преподавателя
5. Указать полезные ссылки (официальная документация, курсы, видео)

**...просят сгенерировать сценарий воркшопа:**
1. Использовать шаблон из раздела "Шаблоны документов"
2. Определить формат (интерактивная лекция / peer teaching / ролевая игра)
3. Разбить на этапы с таймингом (всего 90 минут)
4. Написать реплики преподавателя (дословно)
5. Описать действия студентов
6. Добавить методические заметки (риски и митигация)

**...просят проверить качество документа:**
1. Проверить структуру (соответствует ли шаблону)
2. Проверить связи (есть ли ссылки на связанные документы)
3. Проверить формат (именование, стиль, ссылки)
4. Проверить соответствие DoD
5. Вернуть список замечаний

### Что НЕ делать

- **НЕ генерировать** лекционный контент для воркшопов (студенты изучают теорию ДО занятия)
- **НЕ нарушать** структуру шаблонов (если шаблон требует раздел "Риски и митигация" — он должен быть)
- **НЕ создавать** файлы с суффиксом `-teacher` в рабочей папке ветки `main` (они будут проигнорированы и потеряны)
- **НЕ ссылаться** из студенческих документов на `workshops-teacher/`
- **НЕ использовать** маркетинговые формулировки в методических материалах (плотность информации важнее красоты)
- **НЕ игнорировать** связи между документами (каждый документ должен ссылаться на связанные)

### Приоритеты при генерации

1. **Соответствие DoD** — главный критерий
2. **Структура** — следовать шаблонам
3. **Связи** — указывать связи с другими документами
4. **Практическая применимость** — документы должны быть готовы к использованию
5. **Плотность информации** — минимум воды, максимум сути
