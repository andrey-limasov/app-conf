# Definition of Done (DoD)

**Курс:** Управление конфигурацией бизнес-приложений  
**Формат:** Командный проект 

---

## Критерии завершенности проекта

Проект считается завершенным и готовым к защите, если выполнены **ВСЕ** следующие требования:

---

### 1. Репозиторий и контроль версий

- [ ] Публичный репозиторий на GitHub/GitLab
- [ ] Чистая история коммитов:
  - Осмысленные сообщения коммитов (Conventional Commits)
  - Нет мусорных коммитов ("fix", "wip", "test")
  - Нет закоммиченных секретов, `.env` файлов, `__pycache__`, `.venv`
- [ ] Применена стратегия ветвления (GitFlow / GitHub Flow / Trunk-Based)
- [ ] Все изменения в `main`/`master` только через Pull Request
- [ ] Каждый PR имеет минимум 1 approval от другого участника команды
- [ ] Есть файл `.gitignore` с правильными правилами
- [ ] Есть файл `CONTRIBUTING.md` с правилами работы в команде

---

### 2. Конфигурация и секреты

- [ ] Код отделен от конфигурации (принцип 12-Factor App)
- [ ] Все настройки окружения читаются из переменных окружения
- [ ] Используется `pydantic-settings` или аналог для управления конфигурацией
- [ ] Секреты НЕ коммитятся в Git
- [ ] Есть файл `.env.example` с примером необходимых переменных (без реальных значений)
- [ ] Поддержка минимум 2 окружений: `dev` и `prod`
- [ ] Настроены pre-commit hooks для проверки секретов (например, `detect-secrets` или `gitleaks`)

---

### 3. Контейнеризация

- [ ] Есть рабочий `Dockerfile`
- [ ] Dockerfile оптимизирован:
  - Использует multi-stage build (если применимо)
  - Кэширует слои зависимостей
  - Использует non-root пользователя
- [ ] Есть `docker-compose.yml` для локальной разработки
- [ ] `docker-compose.yml` включает:
  - FastAPI приложение
  - PostgreSQL базу данных
  - (Опционально) Redis или другие сервисы
- [ ] Команда `docker-compose up --build` поднимает весь стек с первого раза
- [ ] Приложение доступно на `localhost:8000` (или другом порту) после запуска
- [ ] База данных инициализируется с миграциями при первом запуске

---

### 4. CI/CD пайплайн

- [ ] Настроен пайплайн в GitHub Actions или GitLab CI
- [ ] Пайплайн запускается автоматически на каждый PR в `main`
- [ ] Пайплайн включает следующие стадии:

**Линтинг и форматирование:**
- [ ] `ruff` / `flake8` или аналог для проверки стиля кода
- [ ] `black` или аналог для форматирования
- [ ] `mypy` или аналог для статической проверки типов

**Тестирование:**
- [ ] Автоматический запуск `pytest` или аналога
- [ ] Тесты запускаются в изолированном окружении
- [ ] Используется сервис-контейнер PostgreSQL для тестов
- [ ] Минимум 60% покрытия кода тестами

**Сборка артефактов:**
- [ ] Автоматическая сборка Docker-образа
- [ ] Публикация образа в реестр (Docker Hub / GitHub Container Registry)
- [ ] Образ тегируется версией или SHA коммита

- [ ] Все стадии пайплайна проходят успешно (зеленый статус)
- [ ] Merge в `main` заблокирован, если пайплайн красный

---

### 5. Деплой

- [ ] Приложение развернуто на сервере (VPS или облако)
- [ ] Приложение доступно по публичному URL
- [ ] Настроен reverse-proxy (Nginx / Traefik / Caddy)
- [ ] Настроен HTTPS (Let's Encrypt или аналог)
- [ ] Настроены переменные окружения на сервере (не в коде)
- [ ] Есть скрипт или CI/CD стадия для автоматического деплоя
- [ ] Приложение перезапускается автоматически при падении (systemd / docker restart policy)

---

### 6. Наблюдаемость

- [ ] Настроено структурированное логирование (`structlog` / `loguru`)
- [ ] Логи включают:
  - Timestamp
  - Level (INFO, WARNING, ERROR)
  - Request ID (для отслеживания запросов)
  - Контекст (какой эндпоинт, какой пользователь)
- [ ] Есть health-check эндпоинт: `GET /health`
  - Возвращает `200 OK` если приложение работает
  - Проверяет подключение к базе данных
- [ ] Логи пишутся в файл или отправляются в систему сбора логов
- [ ] Есть базовый мониторинг (хотя бы просмотр логов на сервере)

---

### 7. Документация

**README.md:**
- [ ] Название проекта и краткое описание
- [ ] Стек технологий
- [ ] Инструкция по запуску локально (через Docker Compose)
- [ ] Инструкция по развертыванию на сервере
- [ ] Примеры API запросов (ссылки на OpenAPI)
- [ ] Список участников команды

**CONTRIBUTING.md:**
- [ ] Правила работы с Git (стратегия ветвления)
- [ ] Правила написания коммитов
- [ ] Правила code review
- [ ] Как запустить тесты локально
- [ ] Контакты команды

**OpenAPI документация:**
- [ ] Автоматически генерируется FastAPI (`/docs` или `/redoc`)
- [ ] Все эндпоинты описаны с параметрами и примерами
- [ ] Есть примеры запросов/ответов

**Architecture Decision Records (ADR):**
- [ ] Минимум 2 ADR по ключевым архитектурным решениям
- [ ] Каждый ADR содержит:
  - Контекст (какая была проблема)
  - Решение (что выбрали)
  - Обоснование (почему именно это)
  - Последствия (плюсы и минусы)

---

## Система оценивания

Детальная система оценивания 360° (преподаватель, другие команды, сокомандники), включая формулы расчета коэффициента вклада и шаблоны форм, вынесена в отдельный документ **[assessment.md](assessment.md)**

---

## Чек-лист для самопроверки перед защитой

Перед защитой проекта команда должна убедиться, что:

- [ ] `docker-compose up --build` работает с первого раза
- [ ] Все тесты проходят
- [ ] Пайплайн CI/CD зеленый
- [ ] Приложение доступно по публичному URL
- [ ] `/health` возвращает `200 OK`
- [ ] README содержит все необходимые разделы
- [ ] Есть минимум 2 ADR
- [ ] Подготовлена презентация (7 минут)
- [ ] Подготовлен сценарий live-demo (5 минут)
- [ ] Все участники команды готовы отвечать на вопросы

---

## Примечания

1. **Все пункты обязательны.** Если хотя бы один пункт не выполнен, проект не считается завершенным.

2. **Исключения возможны** только по согласованию с преподавателем заранее (например, если нет доступа к серверу — можно предоставить подробный `DEPLOY.md`).

3. **Качество важнее количества.** Лучше сделать 5 эндпоинтов, но качественно, чем 20, но с багами.

4. **Документация — это часть продукта.** Если ваш проект невозможно развернуть по README, он не готов.
